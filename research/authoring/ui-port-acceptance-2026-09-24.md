The diagnostic `/port-smoke.html?verify=1` is a second browser entry built from `createTrustedAuthoringCore`, `createTrustedStudioBootstrap` and injected browser devices. Its view receives only `StudioPresentationPort`; it does not import `main.ts` or rely on the production control IDs. Without `?verify=1`, it refuses to initialize. It is a boundary probe, not a proposed UI design. Checks used an isolated local server, verification browser storage and a disposable `XFAS_DATA_DIR`, never Nathan's active draft or library.

No application console errors were observed after the local ignored preview assets were made available to the isolated server. Browser automation could not supply a local saved-V file to the native picker, so the actual click-to-import flow was not retested here. File acquisition/cancellation, saved-V decoding/action restoration and workspace persistence have focused tests and earlier evidence; this remains an explicit browser-automation limit, not runtime game proof.

One presentation issue surfaced: the file port retains the **last** successful package result after later draft edits and library refresh until another Check/Build begins. The subsequent application change now adds `package.freshness: current | stale` by comparing the exact authored collection captured for the request with the live draft. It handles edits made while a request is in flight as well as later changes, and retains the historical result for review. A redesigned UI must show that distinction; it must not present a stale result as a current package check. Package bytes, eligibility and SQLite revisions were not changed.
