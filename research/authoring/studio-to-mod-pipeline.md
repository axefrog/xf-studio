# From XF Studio collection to a Cyberpunk mod candidate

28 September 2026. This is a map of the **current local pipeline**, for a reviewer who knows the idea of a mod but not the file formats. Build produces an offline-verified, private **candidate**. “Loadable” here means the expected archive and declaration files have been built and independently unpacked and checked. On its own it proves nothing in game; the in-game findings below come from three sessions.

**What has been seen in game.** Diagnostic builds in the test MO2 profile were observed in three sessions: the [finish board](../../experiments/016-finish-board/README.md#runtime-results) on 25 September, [experiment 020](../../experiments/020-session-2/README.md#results-26-september-2026-run-through-the-runtime-bridge-partial) on 26 September and [experiment 028](../../experiments/028-session-3/README.md#5-results-28-september-2026) on 28 September. All were with a feminine V on game 2.31. They showed:
- The XF selector registers and switches in the creator, gameplay and photo mode, and saves keep it.
- The window's placement holds, and its sharper lines are visible.
- The 0.4 mm plate lift holds at extreme close range and in motion.
- The closed lids are clean on four eye shapes.
- Colour-shifting behaves as designed.

Still open in game: the flat finishes' separation (inconclusive under creator light), Shimmer (sessions 3 and 4 saw a static grid of oversized dots, and session 6 saw the sparse grain that replaced it as glossy vinyl; rebuilt as dense specks over a satin base, not yet in game), the diagnostic Glitter route (board 1 looked printed in session 6; board 2 not yet in game), the `hx_` component under a head-hiding item, and everything about the masculine V's selector. No build made with the current code has been in game: its feminine resources differ from the tested ones only in values the golden tests pin and in the component name.

**Which V a mod is for.** A mod is for **both a feminine and a masculine V** when Build can prepare the masculine eye plate from the male head the launch route loads; the two creators then each get their own XF selector with the same looks and one shared set of textures ([Masculine V](#the-masculine-vs-selector)). When his plate can't be prepared (his head is missing, not an audited version, changed by an unsupported head mod, or the developer plate override is set), the mod is **for a feminine V only**: Build still makes it. Each feature's result carries whom its mod is for as a plain phrase (`FeatureCheck.audience`, generic: the result card ends the product line with it, "Eye makeup in the “XF” selector, for a feminine and a masculine V" or "…, for a feminine V only") and what it falls short of as warnings (`FeatureCheck.warnings`: one sentence, the reason then the step, with the control that takes the step, e.g. Open Settings). The card shows each warning in the warning tone directly under its product; the manifest records both. Before any Build prepared the plates for the route, Check's one note says what Build still decides ("Build checks which looks reach the eye area and whether the mod can also fit a masculine V.").

The short version: the Studio saves editable makeup as data. Check and Build make a package-only copy that omits active layers with unsupported finishes, presets left without active exportable layers, presets whose makeup never reaches the eye plate (judged on the plate's own UVs), looks with no eye makeup, and other features' parts of a look (no other feature has a mod exporter yet). They report every omission while leaving the authored collection untouched. Build then merges each retained preset's visible layers into one decal draw: a small set of texture maps chosen by the preset's finish route (three for flat finishes), attached to that route's eye-plate material pattern. Flat and faceted maps are 2048 × 512 and cover only the plate's own UV rectangle, which the material maps back with a UV transform ([plate-local UV window](#the-plate-local-uv-window)); colour-shift maps stay on the 1024 head atlas. A prepared **diagnostic** collection can also send a flat-pigment preset through the [diagnostic Glitter route](#the-diagnostic-glitter-route) (4096 × 1024 flake maps with nested mips, optionally an emissive accent on a second plate chunk); the Glitter finish itself still has no route. Build then writes a character-creator selector with an Off choice for each body the mod is for, packs the resources, independently checks the package, and places only a verified copy in a host-owned private candidate directory. Since platform step 8 each exportable feature has an **exporter**, and a collection builds one or more **mods** (products): one merged mod by default, split when the person chooses ([Mods and the package plan](#mods-and-the-package-plan)). A look collection's only exporting feature is eye makeup, so every collection build is one mod, **XF Eye Artistry** unless renamed, byte for byte what the one-product pipeline built. Expressions export through **expression sets** instead: a set of saved expressions builds its own photo-mode expression mod through the same host, builder, verifiers and manifest ([Expression sets](#expression-sets-photo-mode-expression-mods)). A separate developer command builds **XF Finish Showroom**, an in-game test mod of mannequin heads wearing the presets, around the same verified eye-makeup output ([XF Finish Showroom](#xf-finish-showroom-a-test-mod-of-mannequin-heads)). Localhost uses the project's ignored `dist/`; desktop uses private Electrobun user data. Build does not install files: after Build, **Add to my mod manager** installs a mod only once the person has read and accepted its plan ([below](#adding-a-built-mod-to-the-mod-manager)), and the separately invoked diagnostic transfer copied one **localhost** candidate pair into a new MO2 profile and mod. [Product decision](../../projects/xf-studio/data/product-direction.md), [local build boundary](local-package-build.md), [runtime test card](../../docs/validation.md#prepared-single-session-test-card).

The diagram has entries into the same TypeScript filter from a localhost Studio request, an authenticated desktop request and an exported collection JSON file explicitly passed to the CLI (a prepared test candidate's diagnostic knobs only with `--diagnostics`, which neither host passes). All use the same filter and 32-pixel compiler preflight; the arrows show this shared policy, not one shared running process. **Check mod export** stops after eligibility and needs no WolvenKit, game file or 3D preview. Both hosts run Check and Build through one package host service (`runProductBuild`, [`platform/export/product-host.ts`](../../projects/xf-studio/authoring/src/platform/export/product-host.ts)): Check in a fresh Bun worker with a 15-second deadline (localhost used to run it through the CLI with 2 minutes); timeout or cancellation publishes no result. **Build mod files** uses the same partial-export filter and the same TypeScript resource builder and independent verifier in either host; **Python is not involved**. Each host runs that builder as one bounded Bun child process: localhost runs `tools/build_collection_package.ts` from the source tree, desktop runs its single bundled `build.js`. Before the builder starts, each host prepares the [built-in eye plate](#where-the-eye-plate-comes-from) from the head the game is expected to load for the saved launch route (direct or the selected MO2 profile), including a head supplied or patched by a mod; a missing or unsupported head resource, or a head mod whose shape data does not fit the plate recipe, stops Build with a plain explanation. The direct CLI does not derive a plate; it takes an explicit `--plate` directory. Desktop checks readiness before starting that work: its asset-free packaged builder bundle, WolvenKit and game inputs must pass. A bounded probe also executes a small script through the selected Bun path (or Electrobun's main executable when unset); file presence alone cannot enable Build. The browser sends the action and collection snapshot, with no tool or output paths. Desktop keeps its writable work, staging and candidate roots under Electrobun user data, disjoint from the configured game, MO2 and all input paths. The read-only packaged tools legitimately share the Electrobun channel root, so the gate checks each writable package subtree rather than rejecting that common parent. Build stops a timed-out or cancelled process tree (the builder and any WolvenKit child it started) and removes per-build intermediates. It requires the builder's answer to equal its own plan of the same snapshot (every mod, feature, look, omission, hash and the plate's provenance) and each candidate folder to hold exactly its manifest and the archive/XL pair it names, with their lengths and SHA-256 values, before moving the staged candidates into the private candidate store and checking them there again. A disposable installed canary, built while Build still ran the Python programs, completed the authenticated host Build route with four presets and 16 independently verified resources. Its archive payloads match the earlier localhost candidate after independent unbundling, but archive-file hashes differ because the index records build times. The TypeScript desktop Build route has been run from source with the real bundled builder, WolvenKit 9.0.1 and a fresh private data root (see [Build pipeline port](#build-pipeline-port)); it has not yet been repeated in an installed canary. Localhost retains its server overrides and project dist root. ## Mods and the package plan

A collection's exportable features are grouped into **mods** (products) by its **package plan**, which is stored with the collection only when it differs from the default ([feature-module platform §6](feature-module-platform.md#6-export-mod-products-and-the-package-plan-pipe-12), [step 8 status](feature-module-platform.md#step-8-status)):

| Choice | Default | The person may |
|---|---|---|
| Which features ship together | one mod holding every exportable feature | move a feature into a mod of its own, or merge mods (`package.split`, `package.assign`, `package.merge`) |
| Archive name | `xfs_c<collection>` for the default mod (the name every eye-makeup build has had); `xfs_m<product>` for another | never shown or edited; ID-based, so renaming never changes load order |
| Mod name (mod-manager folder) | one feature: its brand (**XF Eye Artistry**); several: **XF Looks** | rename it (`package.rename`; the "XF " prefix is a default, not a rule) |
| Selector and resources | per feature, the same whichever mod carries them | — |

The **Mod package** panel lists the mods with a menu that offers only what applies: Rename, "Use the default name" once renamed, and moving or merging features once the collection holds more than one exportable feature. Renaming a mod to another mod's name of the same collection is refused ("Another mod of this collection is already called …"); when two derived names clash, the later mod gets the collection's name added, or a number when that would not be a valid folder name. "Save as copy" gives every mod of the copy a fresh ID (the default mod the copy's collection ID, every split-off mod a new UUID), so no archive of the copy shares a name with, and hides, one of the original's. A feature may be in only one mod: a plan that puts it into two is refused (named by the feature's label), two features claiming one namespace or depot path are refused at Check in plain words (the namespace or path goes to the host log only), and the diagnostic transfer refuses to place a build any installed mod already holds part of.

A package plan this version can't use is kept exactly as it was stored: a later `xfs/package-plan-N` schema, or a `xfs/package-plan-1` plan with a field this version doesn't know (such as the planned per-feature selector labels), counts as made with a newer version; anything else unreadable counts as damaged. The collection still opens, edits and saves with the plan written back unchanged; the panel shows why in plain words, and the `package.*` actions, Check and Build refuse it (actions and requests with reason code `unavailable`; the export host with `package_plan_newer` or `package_plan_damaged`).

Check and Build plan every mod, run each feature's exporter (its eligibility, plan and, for Check, preflight), then the mod's checks: no shared depot path or namespace, `.xl` entries that merge, and the highest version per framework requirement. Omissions are decided once, by the export host: a **whole look** is left out only when no feature of any mod packages anything of it (with the reason of the feature that left it out, or "Nothing in it can be made into mod files yet." when it holds no part an exporter packages or the features' reasons differ); a part of a feature that has no exporter is reported once for the whole collection; a feature with nothing left to package is reported and left out while the others still build. Each feature's own list keeps what it leaves out of looks that are packaged: its layers (labelled with the feature in the result's wording when several features export), and its part of a look another feature packages. Each verified mod gets its own candidate folder and `xfs/local-package-2` manifest, which records only that mod's omissions (see [promotion](#what-check-build-and-verify-each-prove)).

## Expression sets: photo-mode expression mods

An **expression set** is a named, ordered list of saved expressions in the local library (`part_preset_sets`, beside `part_presets`; [expression editor design §6](../animation/expression-editor-design.md#6-export-route)). The Expression sets panel creates, renames and deletes sets, adds, removes and reorders their expressions, names the set's mod (**XF Expressions - <set name>** by default; a colon can't be in a folder name) and chooses which expression table it carries. Check and Build of a set send a **package-only collection** built from it to the same package route a look collection uses: the set's ID and name, one look per saved expression still in the library (in the set's order), a package plan naming the mod, and a `presetSet` mark with the table choice. Only the expressions exporter reads that mark, so a look collection's expression parts never join its mods.

## What each kind of data means

| Thing | What it contains | What it is **not** |
|---|---|---|
| Recipe | A versioned, editable ordered layer stack: contours, warp fields, pigment/softness, colour, opacity, finish and optional layer effects (mottle). In the Studio it is eye makeup's part (`xfs/eye-makeup-part-2`), with no recipe schema of its own: each layer's Glitter, game-matched optics and mottle models are versioned by their own IDs. Recipe files (`eye-artistry/recipe-1`, `xfs/recipe-2` through `xfs/recipe-12`) migrate on read; writers, including collection-1 files, use the oldest `xfs/recipe-N` that holds every layer, and a collection-1 file read by Check or Build keeps its recipes' own schemas. | A texture, mod or saved V. The browser preview resolution is independent of the recipe. |
| Collection | A collection of looks with a stable collection UUID and named preset UUIDs/revisions. Export collection writes `xfas/collection-1` JSON (each preset carrying a recipe) whenever that format holds the looks exactly, and `xfs/collection-2` (each preset carrying parts by feature) otherwise; Check, Build and the CLI read both and package each look's eye-makeup part. The eye-makeup view of a collection-2 collection lists what it leaves out (`omitted`: a look without eye makeup, another feature's part); the Studio sends that view, and Check, Build and the manifest report each entry as an omission. The `xfas` schema name is retained for compatibility after the XF Studio rename. An exported file prepared as an in-game test candidate may also carry diagnostic-only `diagnostics` (`xfs/export-diagnostics-1`: a per-preset plate lift, flat-surface override, head-UV layout or glitter flake field, see [Plate lift](#plate-lift-at-build) and [the diagnostic Glitter route](#the-diagnostic-glitter-route)); the Studio never writes, shows or keeps them. Both hosts' own collection parsers drop them before Check or Build, and the CLI honours them only with an explicit `--diagnostics` (without it such a file is refused with that reason), so only a deliberately built test candidate carries them. | A game selector by itself. It can travel between Studio installations. |
| Workspace draft | Unsaved collection edits plus editor selections and preview context, in origin-bound browser storage on localhost or a host-owned private workspace file on desktop. | A new SQLite revision or packaged mod. |
| SQLite revision | Explicit, immutable local library snapshot with conflict protection. | The latest browser draft unless the user saved it. |

## Where layers become one look

**The merge happens in the Studio compiler, before WolvenKit and before ArchiveXL.** One preset is evaluated on its route's texture grid (2048 × 512 texels over the [plate-local UV window](#the-plate-local-uv-window) for flat and faceted presets, 1024 × 1024 over the head atlas for colour shift) and becomes **one decal draw** on the plate. Only enabled layers with opacity above zero participate. Their masks use the same recipe evaluator as the browser/PNG path. The [route policy](../../projects/xf-studio/authoring/src/engines/layered-makeup/finish-export.ts) first picks one route for the whole preset, because one draw has one material template and one set of material constants. Its per-finish table (game-matched model, route, surface values and user notes) is the single source for the finish catalogue, recipe validation, the preview's surface values and the compiler:

|---|---|---|---|---|---|

| Faceted | `mesh-decal-faceted-v1` | Any game-matched Shimmer layer (flat finishes may share the preset) | diffuse, roughness, metalness, **normal** | 2048 × 512 plate window | shared `@faceted` (`mesh_decal.mt`, `NormalsBlendingMode` 1, UV transform) |
| Fresnel | `mesh-decal-fresnel-v1` | Every active layer the game can draw is one game-matched Colour-shifting pigment (Glitter and earlier-model layers are left out first) | **mask**, **gradient** (16 × 16) | 1024 × 1024 head atlas (the template has no UV transform) | per preset `@fresnel_<preset>` (`mesh_decal_gradientmap_recolor_blendable.mt`) with its shift constants |

**A layer's coverage includes its mottle.** A mottled layer (`effects.mottle`, `mottle-1`; [vector engine extensions §7](vector-engine-extensions.md#7-mottle-skin-like-breakup-for-eye-makeup)) has its coverage modulated inside the shared evaluator, at each texel's authored UV in skin millimetres (the region's `skin` scale) and at the route grid's own texel spacing. So the window maps, the Fresnel head mask, the diagnostic route's pigment coverage and the verifier's 4096 head-UV reference all carry it, and nothing else in the pipeline changes: Check and Build treat mottle as a layer property (no eligibility rule, no new map or material constant), and the game draws the alpha it always draws. The plate-reach test judges a mottled layer on its mottled coverage, as the verifier's reference has it (step 4 of [the plate-local UV window](#the-plate-local-uv-window)), because mottle can break a soft edge up to nothing. Unmottled layers compile byte-identically to before.

For flat and faceted presets the compiler walks the layers bottom-to-top, applies each layer's colour and coverage, and accumulates colour, roughness, metalness, coverage and (faceted) the grain normal in destination-channel space. Diffuse alpha stores the square root of coverage for the inspected `mesh_decal.mt` path. A Fresnel preset writes linear coverage (that template does not square it) and a uniform base-colour texture; its `FresnelColor` constant is stored sRGB-encoded, because the engine sRGB-decodes every `Color` parameter before the program reads it ([materials open question 11](../../knowledge/materials-and-shaders.md#7-open-questions)). There is no separate game selector for each layer. Each flat finish writes one constant surface from the route policy's table: Matte roughness 1.0, Satin 0.38 and game-matched Glossy 0.12 at metalness 0, Metallic 0.27 at metalness 0.65; a Fresnel preset writes roughness 0.32 and metalness 0.08 as material biases, below the 0.1 at which skin leaves subsurface scattering ([decal reference §10](../materials/shader-decal.md#10-recommended-changes-ranked)). The browser preview reads the same table. Matte/Satin/Metallic values are provisional; Glossy, Shimmer and Colour-shifting are **experimental** and listed as such by Check, Build and the manifest. Game-matched Shimmer writes one uniform surface (roughness 0.32, metalness 0.3) and a grain normal: about a quarter of the texels (0.4 × the layer's density) tilt 12° or more at random azimuths, so every tilted grain clears the mode-1 fade, and the rest stay flat so the skin's normal shows. The grain is white noise at one grain per window texel (about 0.13 × 0.12 mm; on the built-in plate's window that is 4376 × 3420 grains per unit of head UV, which the manifest records); a window compile that would put more than one grain in a texel is refused rather than exported faint. A map coarser than that, such as a head-UV diagnostic, holds its grains' mean with roughness widened by what the texel hides, and from 16 grains per texel a flat normal. BC5 compression lowers about 2 % of the tilted grains below the fade's full weight (WolvenKit 9.0.1, measured offline in [experiment 030](../../experiments/030-shimmer-grain/README.md#through-wolvenkits-bc5-offline)), and the manifest says so ([Shimmer design](../materials/finish-designs/shimmer.md), [grain](../../projects/xf-studio/authoring/src/engines/layered-makeup/shimmer-grain.ts)). [Finish designs](../materials/finish-designs/README.md), [compiler](../../projects/xf-studio/authoring/src/engines/layered-makeup/preset-compiler.ts), [raster evaluator](../../projects/xf-studio/authoring/src/engines/layered-makeup/recipe.ts).

Active **Glitter** layers, and Glossy, Shimmer or Colour-shifting layers still in their earlier browser-study model, have no route (the diagnostic Glitter route below draws flakes from a test candidate's knob over flat pigment layers; it never carries a Glitter layer). So do Colour-shifting layers that share a preset with other exportable finishes or with a different shift. Layers no route can carry are left out first, so a Colour-shifting layer beside a Glitter layer still exports on the Fresnel route with only the Glitter layer omitted. The package filter omits those active layers with the reason, then omits any preset left without active exportable layers. Check and Build both report each excluded layer and whole preset; they refuse the collection only when no exportable preset remains. A look nothing is packaged of is reported once as an omitted whole preset by the export host (a look with no part any exporter packages: "Nothing in it can be made into mod files yet."; eye makeup no longer reports a look without eye makeup as its own omission, since another feature may package it), and another feature's part of a look as an omitted `part`; the original preset count includes looks without eye makeup, and the packaged copy and its hash never carry the list. The Studio offers Check, Build and Export build plan only while at least one look this version can edit has eye makeup: a look made with a newer version of XF Studio is left out as an omitted whole preset ("It was made with a newer version of XF Studio.") and never counts, and a collection with nothing else is refused with that reason. An exported build plan (`xfas/export-plan-1`) carries the view's `omitted` list whenever the view leaves something out; the field is optional, so readers that don't know it are unaffected, and the package pipeline plans its packaged copy, which never carries it. A disabled or zero-opacity layer does not contribute and is not reported as an omission. The compiler itself still strictly rejects unsupported active layers if called without the package filter; it never silently flattens them. The individual **Export mask** command is a different output: a 2048 × 2048 white-RGB/coverage-alpha PNG for one layer, independent of its enabled state and not the preset package. Preview quality at 512/1K/2K/4K changes generated browser textures only. [Package filter](../../projects/xf-studio/authoring/src/package-filter.ts), [compiler gate](../../projects/xf-studio/authoring/src/engines/layered-makeup/preset-compiler.ts).

**Route mip chains.** Flat maps keep the coverage-space chain below. A faceted normal's lower levels are plain means of the decoded speck vectors, so unresolved specks shorten and the shader's mode-1 alpha fades them out; its roughness levels add the lost speck variance to the mean roughness (α′² = ᾱ² + v). Shimmer's *shimmer-grain-2* writes glossy specks (roughness 0.26, metalness 0.35) on about 86 % of texels and a satin base (0.5, 0.05) on the rest, so its level 0 varies per texel and its lower levels average ([Shimmer design](../materials/finish-designs/shimmer.md)). A Fresnel mask's levels are plain coverage means; its gradient is uniform. Window maps are non-square: 2048 × 512 halves to 4 × 1 and then along its length alone (two-texel means) to 1 × 1, 12 levels. A diagnostic glitter preset's chains are **drawn per level** (nested flake mips, [below](#the-diagnostic-glitter-route)), 13 levels at 4096 × 1024, and only its diffuse alpha follows the flat coverage chain. The independent verifier restates each rule. [Route chains](../../projects/xf-studio/authoring/src/engines/layered-makeup/route-mip-chains.ts).

## The plate-local UV window

The plate keeps the head's UV0, so a head-atlas texture spends only the plate's rectangle (0.453 × 0.145 of the atlas) on it: about 0.56 × 0.40 mm per texel on the lids at 1024. `mesh_decal` transforms the UV of every texture it samples, t = `UVScale`·(uv − 0.5) + 0.5 + `UVOffset`, from the UV as stored in the mesh (decompiled programs; [experiment 019](../../experiments/019-uv-window/README.md)). Build therefore spends every texel on the plate:

1. **Derive the window from the plate being packaged.** The builder serializes the plate first and reads its stored UV0 bounds (U 0.2732–0.7266, V 0.6763–0.8213 for the built-in plate). Each axis is widened by 1/64 of the window's span on each side and clamped to the atlas, so 62/64 of each axis's texels land on the plate and the finer levels' filter taps never wrap across an edge. [`plate-uv-window.ts`](../../projects/xf-studio/authoring/src/engines/layered-makeup/plate-uv-window.ts).
2. **Rasterise into it.** The compiler evaluates each layer with the recipe's own evaluator at each window texel's authored UV (`rasterWindow`), so the recipe and the UV editor are unchanged; Shimmer's grain is drawn per window texel. Each window preset also writes a head-UV coverage reference over the window (4096 texels across the atlas, about 0.14 × 0.10 mm) for the verifier; it is not packaged. The reference is a crop of the **head-atlas raster** (`raster`, the editor's and preview's path), deliberately not `rasterWindow`: a fault in the window code (a mirror, offset or scale) then moves the maps but not their reference, and the verifier's mapping gate fails. A test bakes with `rasterWindow` mirrored in its own process and requires that failure.
3. **Map it back in the material.** `@preset` and `@faceted` carry `UVScaleX`, `UVOffsetX`, `UVScaleY` and `UVOffsetY` (for the built-in plate 2.136780, 0.000261, 6.680135, −1.661879). V is signed for two facts checked offline: the Studio authors in glTF UV, 1 − the stored V, and WolvenKit's XBM import stores image rows bottom to top (its export flips them back). So the window's stored-V rectangle maps to t ∈ [0, 1] with the compiler's rows in natural order, and `UVOffsetY` is negative.
4. **Plan on where the plate is.** The plate's **UV footprint** (its stored UV0 bounds, the window, every vertex UV and triangle; [`plate-uv-window.ts`](../../projects/xf-studio/authoring/src/engines/layered-makeup/plate-uv-window.ts)) decides which presets can show at all. A preset whose exportable layers reach at least 2/255 coverage at none of the plate's sample points (every vertex and six points inside every triangle, the verifier's own set) is drawn off the plate's rectangle or in one of its holes, so it would be invisible and its window map would fail the verifier. Check and Build omit it as a reported omission ("Its makeup doesn't reach the eye plate, so it wouldn't show in game"; [`plate-reach.ts`](../../projects/xf-studio/authoring/src/plate-reach.ts)); if no preset reaches the plate, nothing is built and the message says to move the shapes onto the eyelids. An unmottled layer is judged on its coverage at each sample point (smooth, so the step above the verifier's 1/255 covers interpolation between reference texels). A **mottled** layer is judged as the verifier will read it: its bytes at the 4096 reference raster's texel centres (mottle sampled at that raster's spacing), interpolated bilinearly at each sample. Otherwise a preset whose only contact is a soft edge that mottle breaks up would pass Check and then fail Build's verifier ("no content at the plate's UVs") instead of being reported; now Check and Build both omit it, and for a one-layer preset the test is exactly the verifier's own `authored` count.
5. **Keep what cannot move on head UV.** The Fresnel route's template has no UV transform, so colour-shift presets keep 1024 head-atlas maps. A diagnostic collection may keep a flat or faceted preset on head UV (`uvSpace: "head"`, entry suffix `_head`, no UV constants) to compare densities side by side.

At 2048 × 512 a texel is about 0.13 × 0.12 mm on the lids: today's texel count and GPU memory (2.67 MiB per flat preset, 4.0 MiB faceted, with full chains), about 4.3 times the linear density across the lids and 3.3 times down them. `build.json` records the bounds, the window, its constants and the footprint's SHA-256 (`plateUv`); each compiled record names its `uvSpace`, grid and window. Check, the build result and `manifest.json` record the plate they planned on (`plateUv`: window, bounds and footprint SHA-256; null in a Check made before any plate was prepared). Whether the game samples the window exactly as the decompiled programs say is the first question of experiment 019's test card; nothing here has been seen in game.

## The diagnostic Glitter route

The [Glitter game route](../../knowledge/glitter-in-game.md#3-primary-route-resolved-glint-flakes-mesh_decal-plate-local-window) is built as a **diagnostic** route for in-game tests ([experiment 021](../../experiments/021-glitter-board/README.md)). The Glitter finish itself keeps no route: Glitter layers in any collection, this one included, are still omitted with a reason. Only a prepared collection's `glitter` knob (`xfs/export-diagnostics-1`, [`export-diagnostics.ts`](../../projects/xf-studio/authoring/src/export-diagnostics.ts)) selects the route, for a preset whose active layers are all flat finishes. Its `base` surface (roughness, metalness) replaces the pigment layers' own; each `region` names one pigment layer and gives flake statistics (width, spread, cover, tilt, roughness, metalness, colour, seed), a mip rule (`nested` or `box`), or mirrors another region's flakes across u = ½; an optional `accent` takes the lowest-key share of one region's flakes. The knob cannot be combined with a surface override or head UV. Only the CLI's `--diagnostics` honours it; both hosts drop it.

**Glitter flakes 2** (after session 6; [experiment 033](../../experiments/033-finishes-rework/README.md)). A region's flakes may also set:
- `tiltMinDeg`: every flake tilts at least this much, then |N(0, σ)| up to the maximum;
- `roughnessMax` and `metalnessMin`: each flake draws its own roughness and metalness in those ranges;
- `largeShare` with `largeSizeMm`: a share of larger flakes;
- `clusterMm` with `clusterFloor`: a value-noise density envelope.

Each field is optional; pairs go together. A region without them draws exactly the first recipe's catalogue: same draw order, same bytes. The extra draws follow the first recipe's per flake, and a clustered flake redraws its centre until it is accepted, at most 64 times. The sheen's roughness and metalness use the middle of the per-flake ranges, and its variance the floored tilt distribution. [`glitter-studio-flakes.ts`](../../projects/xf-studio/authoring/src/glitter-studio-flakes.ts) derives these fields from a Studio glint layer's settings, and the board uses it. The verifier restates the fields' rules, the draw order and the envelope flake for flake, and checks that no fully covered flake texel tilts less than its floor.

**Regions** ([`glitter-region.ts`](../../projects/xf-studio/authoring/src/glitter-region.ts)). A region's rectangle is its layer's **outline bounds**: everywhere the layer's coverage can be non-zero. The drawn curve lies in the convex hull of its control polygon (each knot and both tangent endpoints on a Bézier outline, or each Catmull–Rom knot with the segment's equivalent Bézier controls, which covers overshoot); coverage reaches half the widest softness width (layer or knot feather) beyond the curve; warp fields move it by at most their summed displacement. Build clips the rectangle to the plate window before sizing the flake catalogue (cover × area over the mean flake area), and a region may hold at most **200,000** flakes. Planning applies the same rules over the head's UV square, whose count bounds the window's from above, so Check refuses what Build would: a region layer mirrored by symmetry, one outside the UV square, or one over the flake budget, each with a plain reason.

1. **Maps** ([`glitter-route.ts`](../../projects/xf-studio/authoring/src/glitter-route.ts)): 4096 × 1024 over the plate window (about 0.065 × 0.059 mm per texel). Diffuse RGB is the pigment mixed toward the flake colour; diffuse alpha is √coverage of the pigment layers with the flat coverage chain, so the decal covers exactly what they cover. Roughness and metalness composite the base surface toward each flake's. The normal holds each flake's tangent X, Y, dilated two texels beyond its box. `flakes` is the flake mask (`NormalAlphaTex`), clipped by the region layer's coverage and never outside the pigment's.
2. **Nested mips:** each level re-draws a region's flakes at width max(w, 2 texels), keeping the key-ordered prefix that covers cover × 0.7^(L − L*) and none wider than 1.2 mm; the rest becomes sheen (roughness toward ((r_f²)² + E[sin²θ])^¼, metalness and colour toward the flake's). A `box` region keeps its level 0 and takes each lower level from the plain 2 × 2 BOX chain of the level-0 bytes. The bake records every channel's whole chain (`levels`), and the builder writes it as the DDS input unchanged.
3. **Material:** one shared `@glitter` `mesh_decal` entry with `NormalAlpha` 1, `UseNormalAlphaTex` 1, `NormalsBlendingMode` 1, the surface alphas and scales at 1, and the window's UV transform.
4. **Accent chunk:** a preset with an accent gets a 2048² head-UV mask (the emissive template has no UV transform) with the accent flakes at least 2 texels wide and nested the same way, and its own `@accent_<preset>` entry on `mesh_decal_emissive_subsurface.mt` (`EmissiveMask`, `EmissiveMaskChannel` (1, 0, 0, 0), `EmissiveColor` the flake colour's sRGB bytes, the knob's `EmissiveEV`, `AlphaThreshold` 0). The template multiplies the colour by `EmissiveEV` directly, so the knob parser and the verifier both refuse an accent at 0 or below (it would draw black); the board uses 1, the flake colour itself. The plate gains one last render chunk at the accent presets' lift (`plan.plate.accentChunk`, so `liftsMm` is `[0.4, 0.4]` for the board): the accent preset binds it to its accent entry, every other preset to `xfs_hidden`.
5. **Verification:** the verifier restates the route from the recipe and knob (including the region, catalogue-size and flake-budget rules above), the material and accent constants, the chunk bindings and texture sizes, and checks the chains' published properties and the flakes' contents rather than re-drawing them ([What Check, Build and Verify each prove](#what-check-build-and-verify-each-prove), item 4).

A normal collection never reaches any of this: its plan, materials and chunks are unchanged. A golden test pins every committed ordinary collection's plan, plate materials, appearances, `.archive.xl` and (for the finish board and session 2) every baked map to the results from before the route's cleanup, updated deliberately only for the finish defaults (Matte's roughness maps, the Colour-shifting materials and plans) ([`ordinary-package-golden.test.ts`](../../projects/xf-studio/authoring/tests/ordinary-package-golden.test.ts)), and a rebuild of the session-2 candidate gave the same 41 archive members, byte for byte ([experiment 021](../../experiments/021-glitter-board/README.md#consistency)).

## XF Finish Showroom: a test mod of mannequin heads

## Where the eye plate comes from

Every preset is drawn on one **expanded eye plate** per body. The feminine plate is a 3,010-triangle, 1,620-vertex cut of the female player head the game loads (`h0_000_pwa_c__basehead.mesh` and `h0_000_pwa__morphs.morphtarget`, as supplied or patched on the user's launch route), skinned and morphed exactly like the head underneath. The plate is part of XF Studio, but its geometry is CDPR's, so the product ships only an asset-free **recipe** ([`eye-plate-recipe.json`](../../projects/xf-studio/authoring/src/eye-plate-recipe.json)): the selected triangle IDs as 105 inclusive ranges, their face/vertex ID hashes and expected topology, the SHA-256 of each audited source resource revision (currently game 2.31), and the output layout. Build derives the plate from the user's own installed game; nobody configures a plate folder. The masculine plate is the same kind of cut of the male head, from its own recipe; [below](#the-masculine-plate).

```text
Saved launch route (direct, or the selected MO2 profile)
   generic resolver: mounted archives + .xl patches -> winning head .mesh and .morphtarget, patches of plate data
   a mod folder, or an archive index searched before the head, unreadable -> "couldn't read" explanation, Build stops
   missing anywhere -> "missing" explanation, Build stops
   same chosen archives (path, size, time), recipe and head choice as a published plate? yes -> reuse it, no extraction
WolvenKit unbundle each winning archive (and patch sources)  -->  private work dir; hash every resource
   base game, no plate-data patch:   supported recipe revision?   no -> "unsupported" explanation, Build stops
   mod supplies or patches the head: unpatched base-game parts must still be a supported revision
   cache hit (recipe + source hashes + head provenance + deriver version)?   yes -> reuse after re-hashing the cached files
   WolvenKit serialize (mesh and morph in one launch) -> apply .xl patches as ArchiveXL does -> TypeScript byte cut
      -> WolvenKit deserialize -> serialize again (one launch)
   independent verifier (decodes plate and head separately)   fail -> no plate, Build stops
      (from a mod's head, a failed cut or check -> "your head mod ... isn't supported yet" + escape hatch)
   publish atomically: <cache>/xfs-expanded-eye-plate-r1-<key>/{resources/, plate-manifest.json, json-<WolvenKit id>/}
      (json-<id>/: that serialize-again readback, kept so every Build reads the plate without starting WolvenKit)
```

**Which head.** The plate must match the head the game draws, so it is cut from the resources the game is expected to load for the saved launch route, not always from `archive/pc/content`. The host adapter ([`eye-plate-head-resolver.ts`](../../projects/xf-studio/authoring/src/eye-plate-head-resolver.ts)) opens the route with the generic [resolver](../../knowledge/mod-loading.md) (source discovery, mount order, RDAR indexes and `.xl` files) through the host's shared installation registry: an installation the preview already opened is reused only while every folder and file it read is unchanged, and the route is opened again otherwise (index caches go under the plate cache's `resolver/` folder when Build opens it first). The pure planner ([`eye-plate-head-source.ts`](../../projects/xf-studio/authoring/src/eye-plate-head-source.ts)) then applies the same rules the character resolver uses: the first mounted provider of each depot path wins, ArchiveXL copies and links apply only when no archive has the path, and `.xl` patches of the two resources are applied as ArchiveXL 1.27.3 applies them at load time, limited to properties that reach the plate. A mesh patch changes plate data only when it names `renderResourceBlob` (ArchiveXL then also copies the bones, LOD and bounds fields); a morph patch can change `blob` (named explicitly), `boundingBox`, `targets` (merged by name) and `baseTextureParamName`. Patches that change only properties the plate replaces (mesh appearances, morph `baseMesh`, `baseMeshAppearance`, `baseTexture`) are recorded as ignored. Nothing here knows about any particular mod. The [application service](../../projects/xf-studio/authoring/src/eye-plate-service.ts) applies the policy:

- **Base game wins, no plate-data patch:** as before, the head must match a supported recipe revision.
- **A mod supplies or patches the head:** the plate is cut from those resources when the recipe's gates hold: the selected triangles, their order and the vertex mapping must be the audited ones (the recipe's vertex-ID hash), the morph target count must match, the mesh and morph base must agree, and the independent verifier must pass against the effective head. Base-game resources used unpatched must still be a supported revision. Skin bytes are preserved exactly relative to the head actually used.
- **A mod changes the head's topology** (or the gates otherwise fail): Build stops with `plate_source_modded` and names the mod: "Your installed head mod … changes the head's shape data in a way XF Eye Artistry doesn't support yet". The message gives the way round: set "Head used for the eye plate" to "The unmodified game head" under Game & tools in the Mod package panel (or disable that mod in the selected profile). That choice is the typed Local setup field `eyePlateHead` (`installed` by default, or `base-game`); both hosts read it for every Build, and `XFS_EYE_PLATE_HEAD=base-game` remains a developer override. It cuts the plate from the base-game head, records `kind: "base-game-override"` and adds a limit that the makeup may not sit exactly on the modded head.
- **The route could not be read completely enough** to trust which head it loads: Build stops with `plate_source_incomplete` and one next step. That happens when source discovery could not read a mod folder, profile or entry that may hold an archive or `.xl` file (a skipped link to a plain text file does not count), or when an archive's index is unreadable and the game searches that archive before the head's winning archive (or a head resource or plate-relevant patch source was found nowhere). An unreadable archive searched after the winner cannot change the head and is only noted.

The plate manifest's `head` record lists, without physical paths, each resource's depot path, winning archive, group, provider (MO2 mod name or installed game) and SHA-256, the SHA-256 of any winning mod archive, each applied patch with the properties it changed, and each ignored patch with the reason. `source.revisionId` is the audited revision for a base-game head and `installed-mods` otherwise. The package manifest's `plate` record carries the same `head` record, and both hosts compare it exactly. The cache key includes that provenance, so a plate cut from one source is never reused for another.

**The reference installation.** Read-only, on 25 September 2026 with WolvenKit 9.0.1, the resolver found for the MO2 profile `XF Studio diagnostic 2026-09-25` (and for `2025 (again)`): the head **mesh** comes from the base game (`basegame_4_appearance.archive`, SHA-256 `e877b91a…`, the audited 2.31 revision), and the `-KS- UV Texture Framework` `.xl` (`!!!_UV4.xl`) patches it from `ks_uv_donor\ks_donor_head_f.mesh` with no `props`. Under ArchiveXL's rules such a patch replaces appearances but not the existing render blob, so it cannot change the plate and is recorded as ignored. The **morph target** comes from the Facial Customisation Rig Fix (`zz_FacialCustomizationFix_xBaebsae.archive`, resource `16ec1fae…`) over the base copy. Its geometry, base buffer, diffs, mapping and target names equal the base game's; it renames six per-target bone names (`l_/r_J_jaw_ear_0..2_JNT` to `…_unused`) in all 105 targets. The topology gates pass. The derived plate mesh is unchanged (`58081caf…`); the morph (`b681d6a9…`) differs from the base-game-derived one (`b8b7c055…`) only in carrying the fix's target metadata, which the plate verifier now requires. With all mods disabled, both resources come from the base game. Real localhost Builds of the four-preset fixture and the private five-look Satin collection through the package handler on this route passed the independent verifier with 16 and 19 members; against base-game-plate builds, only the plate morph target member differs. Resolving the route takes about 2–3 s per Build with warm index caches. This is a tool-source expectation of what the game loads, not runtime evidence; the candidate promoted into the diagnostic profile on 25 September predates it and carries the base-game morph.

The cut ([`eye-plate-cut.ts`](../../projects/xf-studio/authoring/src/eye-plate-cut.ts)) works on WolvenKit's JSON form of both resources and **copies bytes; it never decodes and re-quantizes**. It keeps the selected vertices in ascending head order and the selected triangles in native order and winding, and keeps the head's position quantization. Each retained vertex element is copied from the head rows: position, both skin index/weight pairs, both UV sets, normal, tangent and vertex colour. The mesh render buffer and the morph's embedded base buffer are cut independently, so native skin bytes are preserved in **both**, as the plate rule requires. For every morph target it keeps the head's own 12-byte diff rows and per-target quantization for selected vertices and remaps only their 16-bit vertex indices. The output layout matches what the historical plate used: head-only `PS_ExtraData` and light-blocker streams, garment-support parameters and skin-normal texture deltas are dropped, vertex factory 4, one `xfs_eye_plate` appearance and one local `mesh_decal.mt` material (the builder replaces material and appearances per collection anyway). The [independent verifier](../../projects/xf-studio/authoring/src/eye-plate-verify.ts) re-serializes the finished CR2W resources and, with its own decoder, requires every retained element, triangle, morph-diff row, target name/order and quantization to equal the head, and the topology to match the recipe. The [application service](../../projects/xf-studio/authoring/src/eye-plate-service.ts) owns the source gate, cache policy and cancellation; [WolvenKit execution](../../projects/xf-studio/authoring/src/eye-plate-wolvenkit.ts) and [cache files](../../projects/xf-studio/authoring/src/eye-plate-cache.ts) are adapters. No Python or .NET is involved.

The cache is host-owned private storage: ignored `authoring/data/eye-plate-cache/` on localhost (`XFS_PACKAGE_PLATE_CACHE` relocates it) and `userData/plate-cache/` on desktop. Every Build still resolves the route: it checks the shared opened installation against the mod setup (its mod lists and folders, the MO2 ones where the instance's `ModOrganizer.ini` puts them, PIPE-05; about 50 ms on the reference route) and opens it again (source discovery, index caches and `.xl` files, synchronously in the host) only when something changed. When the chosen archives (path, size, modification time and entry paths), patches, recipe and head choice equal those of a published plate, that plate is reused without extracting, serializing or hashing the head: on 25 September on the reference MO2 route, a first derivation took 32.6 s and the next run 2.2 s in total (previously about 7 s for a cache hit). Otherwise the head is read again and the full cache key decides. Mod archive hashes for provenance are remembered by path, size and time for the host session. Cache entries written before head-source resolution have no `head` record and are derived again once. Each entry also holds the plate's UV footprint, `plate-uv.json`, computed from the finished mesh resource and recorded in the manifest's `uv` record (file, SHA-256, bounds and window); entries without it, with a footprint that no longer matches its record, or with a window that the current window rule (recomputed from the recorded bounds) would not give, are derived again once (on the reference installation the rederived mesh and morph are byte-identical, `58081caf…` and `b8b7c055…`). A change to how the footprint itself is read from the mesh changes the footprint schema, which has the same effect. Should the resource builder still find that the plate's own UVs give another footprint than the recorded one, it stops with `package_prerequisite_stale` naming the plate; the shared host service then discards that cache entry and build once more on a freshly derived plate (once only), so the user never has to delete the cache or build again. The cache records its last outcome for the game folder, content archives, and launch route and head choice (`routeKey`); readiness reports `plate_source_missing` or `plate_source_unsupported` with that explanation while the game's content archives are unchanged, so updating or repairing the game (or XF Studio) lets the next Build try again. **The plate's JSON is kept with it (PIPE-130).** Each entry also keeps WolvenKit's JSON of its two resources in `json-<id>/`, one folder per WolvenKit identity (`wolvenKitIdentityKey`), with a record binding each document to the SHA-256 of the resource bytes it was serialized from and to its own SHA-256 and length (kept conversions in [`derived-cache.ts`](../../projects/xf-studio/authoring/src/derived-cache.ts)). A new plate keeps the readback that verified it; an entry published before, or for another WolvenKit, gets it once (both files in one launch) when a Build reuses it. It is published by renaming a finished folder into place and is advisory: when it can't be written, the Build serializes the plate as before. The host checks only the record and the documents' lengths (so it never hashes 30 MB on its event loop); the resource builder reads it only when the record names exactly the plate's resources by name and SHA-256 and this Build's WolvenKit, and every document still has its SHA-256, and otherwise serializes the plate itself. A changed head (a game patch, a head mod, another head choice) gives another cache entry through the archive stamps above, so its JSON is never read for another plate. The independent verifier never reads it. Localhost keeps a hidden developer override, `XFS_PACKAGE_PLATE`, for an explicit plate directory; the desktop host has none. The wrapper records which plate was packaged in the manifest (`plate`: recipe, source revision, cache key, resource hashes and head provenance, or `source: "override"`), and both hosts reject a result that names a different plate than the one they prepared.

**How it compares with the historical plate.** The previous production input was experiment 004's private conversion of a Blender cut. On the same 2.31 head it covers the same 3,010 triangles in native order and winding, with no baked edits or offsets, but it differs in ways the derived plate fixes. It has 1,635 vertices (15 split duplicates of 13 head vertices). Its skin weights were re-normalized on import and are not the head's bytes in either buffer. Its vertex colour is uniformly white, where the head has 21 distinct values. Its positions, normals, tangents and morph deltas were re-quantized (up to 2.6 µm in positions and 9.4 µm in morph deltas, with 1-LSB normal/tangent differences). Experiment 012's neutral cut already had native triangles, skin, UVs and colour but still re-quantized geometry. The derived plate has **zero** differences from the head in every retained element and morph row. The decal pixel shader reads no vertex-colour input, so the colour difference probably has no visible effect [hypothesis]. Full comparison: [Experiment 012](../../experiments/012-native-plate-bootstrap/README.md#built-in-production-plate).

The derived resources are byte-identical across repeated runs and between WolvenKit CLI 8.17.4 and 9.0.1 (mesh `58081caf…`, morph `b8b7c055…`). A real localhost Build of the four-preset fixture with the derived plate and one with the old private plate each passed the independent verifier with 16 unpacked resources. Fourteen members, including every texture, the `.app`, the customization resource and the `.archive.xl`, were byte-identical; only the plate mesh and morph target differ. The cached plate still passes the plate verifier. A surface exactly coincident with the head relied on the decal pass's depth bias alone, and in game (25 September) it broke into skin-coloured patches close up; packaging therefore lifts it (next section).

### The masculine plate

The masculine V's plate ([`eye-plate-recipe-pma.json`](../../projects/xf-studio/authoring/src/eye-plate-recipe-pma.json), `xfs_eye_plate_pma`) is cut from `h0_000_pma_c__basehead.mesh` and `h0_000_pma__morphs.morphtarget` by the same code, service, cache, route resolution and verifier as the feminine plate. Its selection is the male head's triangles whose three corner UVs are all feminine-plate UVs ([male V plan §4.1](../character-customization/male-v-plan.md#41-a-masculine-plate-is-required)): 3,010 triangles and 1,627 vertices, all 100 morph targets, audited against the 2.31 male head. Its raw topology has 11 boundary loops and one pinched vertex where the feminine plate has 6 and none. Every extra loop is a **native seam of the male head**: 23 vertices that the head stores twice at one position, with byte-identical normal, skin indices and weights and every morph row, so the two copies never part under skinning, any morph target or the lift. The head's own triangles leave a zero-width slit between them. The recipe declares them (`selection.seams`), and the verifier finds them from the plate's own bytes and requires the welded surface to be closed and unpinched: two eye rings of 802 vertices, 198 boundary edges in 4 loops, the feminine plate's shape (its own 16 seam pairs, where its corner strips meet the rings, leave its raw topology closed, so its recipe declares none). Welding is only a topology check; the plate keeps the head's triangles and bytes. On the reference installation (28 September 2026) the plate derived in 24 s and passed with exact native bytes in the mesh and the morph's base buffer (69,920 morph rows); WolvenKit CLI 8.17.4 and 9.0.1 give identical files (mesh `7e8975c2…`, morph `4397f3aa…`). Its stored UV bounds and so its texture window are exactly the feminine plate's. Evidence and method: [male V plan §4.1](../character-customization/male-v-plan.md#41-a-masculine-plate-is-required).

The masculine plate is an **optional** Build prerequisite (`eye-makeup/plate-masculine`, `optionalPrerequisites` in the exporter): the host prepares it after the feminine plate when it offers it (both hosts do) and never stops a Build over it; only cancellation stops. Its outcome is recorded in its own status file in the plate cache (`status-xfs-expanded-eye-plate-pma.json`; the feminine plate keeps `status.json`), which Check reads for the same route: a ready plate, or a missing, unsupported or modded masculine head with its reason and step. The head-mod step names “The unmodified game head”, which is one setting for both heads, so the sentence says it covers both V's. An isolated test server can stand the masculine plate in with a fixed outcome (`XFS_TEST_MASCULINE_PLATE=<plate code>`, for UI checks of a feminine-only Build). The developer plate override (`XFS_PACKAGE_PLATE`) has no masculine plate, so such a build is for a feminine V only. The CLI takes `--plate-masculine` and `--plate-masculine-manifest` beside `--plate`.

### Plate lift at Build

Every vanilla face decal measured (2.31 female eye makeup, lips, freckles, pimples) is the head's vertices pushed **0.40 mm** out along the head's normals, with morph targets that keep the offset along each target's normal; the legacy eye-makeup build and a community eyeshadow mod reuse that geometry ([experiment 017](../../experiments/017-plate-depth/README.md)). Build does the same to the packaged copy of the built-in plate ([`plate-lift.ts`](../../projects/xf-studio/authoring/src/plate-lift.ts)): base positions become p + 0.4 mm × n with the head's stored shading normal n, and each morph row's position delta gains 0.4 mm × (normalize(n + Δn) − n). Skin indices and weights, normals, tangents, UVs, colour, triangles, morph mappings and every morph normal/tangent delta stay the head's bytes, and the mesh and the morph's base buffer receive identical bytes, so the skin-byte rule holds. The head's position quantization still covers the lifted plate, and must: a lift that would leave it is refused rather than re-quantizing every position. 24 of the 105 targets need a slightly wider delta range and are re-encoded to exactly the range of their lifted deltas (largest error 7.5 µm). The masculine plate is lifted the same way; 22 of its 100 targets are re-encoded (largest position error 3.0 µm, largest morph delta error 6.6 µm, reference installation). The cache keeps the exact cut, so the preview and the cached plate's head correspondence are unchanged. `build.json` records the lift (`plateLift`, and `masculine.plateLift`). The lift follows the vanilla construction, and like vanilla eye makeup it lets the lids overlap where eye shapes close them. In game it holds: the 0 mm plate broke up at extreme close range while 0.1 mm and 0.4 mm held (26 September). In motion, blinking and turning showed no edge, no lifted look and no skin at the inner corners (28 September). At full closure on eye shapes 01, 02, 10 and 12, no eye showed between the lids, the lashes sat on the lid line, no bare skin showed between crease and lashes, and nothing poked through. That closes the eyelid-contact gates of experiments [006](../../experiments/006-plate-clearance/README.md) and [012](../../experiments/012-native-plate-bootstrap/README.md) for the shipping plate at normal viewing, as "not visible in game". The offline dense-idle, subframe and finite-contact gates were not rerun on the lifted plate. The creator's eye crop can't resolve sub-millimetre contact either, so contact below that scale is neither excluded nor visible. A clearance correction is not needed, and the work stays paused; any later candidate must still be morph-aware and finite-contact-aware and keep the skin-byte rule.

A diagnostic collection can ask for other lifts per preset, and a diagnostic glitter accent adds one more chunk at its presets' lift ([above](#the-diagnostic-glitter-route)). Distinct lifts become one plate render chunk each, laid out like vanilla multi-chunk decals; each preset's mesh appearance binds its own chunk and binds the others to `xfs_hidden`, a `mesh_decal` instance whose colour, normal and surface alphas are all 0, so hidden chunks write nothing. A diagnostic flat-surface override gets its own material entry (`@flat_<hash>`). A normal collection builds one chunk and the unchanged materials. So that a diagnostic package is never mistaken for a production one, Check, `manifest.json` and the build result record the plate's lifts (`plateLiftsMm`, `[0.4]` for a normal collection), and each packaged preset that carries knobs lists them in its identity (`presets[].diagnostics`); the host's result gate requires both to equal its own plan.

## How those maps become game resources

The resource builder first reads the host-prepared plate mesh/morph as WolvenKit JSON (the copy [kept with the cached plate](#where-the-eye-plate-comes-from) when it still matches, else its own `convert serialize`) and derives the [plate-local UV window](#the-plate-local-uv-window) from the plate's UVs; the plate's whole UV footprint must equal the one the preflight planned on, or Build stops with `package_prerequisite_stale` naming the plate (the host service then discards that cached plate and builds once more; see [the cache](#where-the-eye-plate-comes-from)). Its bake step then validates the collection, plans its names, compiles each preset through its route on that route's grid, and writes the hashed raw maps (plus each window preset's coverage reference), `plan.json` and `compiled.json`. The resource builder then computes a complete mip chain from those maps, writes DDS inputs, and asks WolvenKit to import colour as gamma-aware XBM, scalar maps as linear XBM and facet normals as normal maps (one launch per group: a group's import settings are process-wide environment values). The imports start at once and run while it **lifts the plate positions** as described in [Plate lift](#plate-lift-at-build) and changes **resource references and appearance/material metadata** (window entries gain the UV transform); then one `convert deserialize` over the model, `.app` and customization folders converts every new resource (its output is flat; each file then moves to its depot folder). At most two WolvenKit processes run at once (`DEFAULT_WOLVENKIT_CONCURRENCY`: each takes about 1.2 GB whatever its input), and the build waits for every one it started before it reports a failure. It never reskins the plate. With the masculine V it serializes his plate beside hers and checks that its UVs give her footprint's texture window, lifts it with the same lifts, gives it the same appearances and materials and binds his morph target to his mesh. The independent verifier serializes the unbundled plate members and the plate input files itself and, with its own decoder, requires every non-position byte to equal the input, each chunk's positions to be the input lifted along its normals within half a quantization step, each morph row to be the lifted input delta, and mesh and morph base to be identical; bone data and morph targets must equal the input, and the target count must equal the plate recipe's (105 for the current recipe). Eyelid contact was checked in game ([Plate lift](#plate-lift-at-build)). [Bake](../../projects/xf-studio/authoring/src/package-bake.ts), [resource builder](../../projects/xf-studio/authoring/src/package-resource-builder.ts), [resource definitions](../../projects/xf-studio/authoring/src/package-resources.ts), [WolvenKit adapter](../../projects/xf-studio/authoring/src/package-build-wolvenkit.ts), [verifier](../../projects/xf-studio/authoring/src/features/eye-makeup/verify/verify-build.ts).

The resource graph is deliberately small:

- **One** `xfs_collection.inkcharcustomization` supplies one female head customization option (the masculine V's twin is [below](#the-masculine-vs-selector)). Its label (`localizedName`) is just **XF** (see [Mod name and MO2 folder](#mod-name-and-mo2-folder)): the creator row shows the label and the chosen preset name on one line, and in game (25 September) a long label such as "XF Eye Artistry" let preset names of about 28 characters or more overlap it. Its definitions list index `0` as `xfs_off`, followed by one entry per authored preset, with display names from the collection. The option joins two head groups, as vanilla eye makeup's appearance options do: `character_customization` (the creator screen) and `face` (the player entities' face controller in gameplay and photo mode). In game, a build listed only in `character_customization` rendered in the creator but not in photo mode; the verifier now requires both groups. Current tags name New Game, HairDresser and Ripperdoc contexts in the resource; the creator showed the label and every preset name as plain text [runtime, 25 September].
- **One** `xfs_collection.app` holds an Off definition with no components and a shared template definition with one `entMorphTargetSkinnedMeshComponent`. The preset selector names carry a suffix that the inspected ArchiveXL rules are expected to expand through the template. The independent verifier checks this **source-derived expansion model**; it does not run ArchiveXL.
- **The component is `hx_xfs_c<collection>_makeup`** (`MAKEUP_COMPONENT_PREFIX` in [the planner](../../projects/xf-studio/authoring/src/preset-collection.ts)). It is the one generated name that doesn't start with `xfs_`, so that a head-hiding item hides the makeup with the head.
  - **How ArchiveXL matches it.** A component's ArchiveXL prefix is the text up to and including the first `_`, when that `_` is at index 2–5 [source: ArchiveXL 1.27.3 `Garment/Prefix.cpp`]. Chunk-mask overrides apply to a component by exact name and by that prefix (`States.cpp` `ApplyChunkMaskOverride`).
  - **What `hide_Head` hides.** ArchiveXL's bundled `hide_Head` hides the prefixes `h0_`, `he_`, `heb_`, `ht_`, `hx_` and `i1_`, plus beards and four head morph components (`bundle/source/resources/VisualTags.xl`). It is registered from the `visualTags` of an equipped item's `.app` definition (`Garment/Extension.cpp` `RegisterComponentOverrides`).
  - **Why `hx_`.** Vanilla eye makeup's component is `hx_000_pwa__basehead_makeup_eyes_01` (`pma` for masculine V) [resource: `hx_000__basehead_makeup_eyes_01.app`]. `hx_` is the prefix of every creator head decal ([CC file chain](../../knowledge/cc-file-chain.md#naming-conventions-resource)). The old name, `xfs_c<collection>_makeup`, had the prefix `xfs_`, which no rule hides, so the makeup would have floated where the head was.
  - **Nothing else catches `hx_`.** No other bundled ArchiveXL tag names `hx_`. The garment layer order doesn't list it, and the component isn't a garment. A mod's own `.xl` tag that hides `hx_` now hides the XF makeup exactly as it hides vanilla makeup.
  - **What the base game carries.** No vanilla item carries `hide_Head`: the 2.31 TweakDB holds no `hide_Head`, `hide_H1` or `hide_F1` string [resource: byte search of `tweakdb_ep1.bin`], and the cooked visual-tag preset (`ep1\entities\appearancename_visualtags.json`) has none either. Its head tags are `hide_H1`, `hide_F1`, `hide_Hair`, `hide_Beard` and, on the eight `outfit_01__q307__*` quest looks only, `hide_FacialCustomization` [resource]. Vanilla helmets therefore cover the makeup rather than hide the head.
  - **Evidence status.** The Modding Docs head diagram lists `hide_Head` as an ArchiveXL tag, apart from the base-game `hide_H1`, `hide_F1` and `hide_Hair` [wiki, image: [LadyLea's head guide](https://github.com/CDPR-Modding-Documentation/Cyberpunk-Modding-Docs/blob/be2f44eed8419342ec13f72ed9cab008e9f7b289/.gitbook/assets/VisualGuide%20-%20AXL%20Tags%20%26%20Base%20Tags%20-%20Head%20-%20By%20LadyLea.png) on the [tags page](https://github.com/CDPR-Modding-Documentation/Cyberpunk-Modding-Docs/blob/be2f44eed8419342ec13f72ed9cab008e9f7b289/for-mod-creators-theory/core-mods-explained/archivexl/archivexl-tags.md)]. The behaviour is source-derived and untested in game ([next-sessions plan](../runtime/next-sessions-plan.md#n2-finish-close-out-headgear-kill-switch) 2.6).
  - **What the verifier checks.** It requires the component to be exactly `hx_<namespace>_makeup`, and it restates ArchiveXL's prefix rule to confirm the prefix is `hx_`. Every other generated name must still start with `xfs_`.
  - **Effect on identity.** The rename changes the component's name and its derived ID. Appearance, selector, resource and archive names are unchanged, so a saved selection should still resolve [hypothesis: the save records the option and appearance, not the component].
- **One** copied/referenced `xfs_eye_plate.mesh` and **one** `xfs_eye_plate.morphtarget` serve the collection. The morph resource points to the new mesh path and seed appearance. The model is the [built-in eye plate](#where-the-eye-plate-comes-from) derived from the user's game: 105 morphs, the head's exact vertex and skin bytes and one material entry. Local material instances use soft texture paths with `{material}` substitution: one shared `@preset` (`base/materials/mesh_decal.mt`) for flat presets, one shared `@faceted` for faceted presets, and one `@fresnel_<preset>` (`base/materials/mesh_decal_gradientmap_recolor_blendable.mt`) per colour-shift preset, carrying its shift colour and a distance fade pushed out to 1000 m. A diagnostic glitter preset uses a shared `@glitter`, and one with an accent adds its `@accent_<preset>` (`base/materials/mesh_decal_emissive_subsurface.mt`). Presets on the seed's shared entry stay empty mesh-appearance stubs that ArchiveXL expands from the seed; any other preset names `<appearance>@<entry>` explicitly, which ArchiveXL resolves to the same template entry by the same `@` rule (`Extension.cpp`). Each preset adds a mesh appearance identity and its own route textures, not a separate plate copy.
- **One** `.archive.xl` text declaration tells ArchiveXL about each body's customization resource (`female:`, and `male:` with the masculine V) and each body's `.app` in the `player_customization.app` scope. The `.archive` holds the binary resources. The declaration is beside the archive in `archive/pc/mod/`, not inside it.

### Mod name and MO2 folder

XF Studio is the app; the eye-makeup mod it builds is **XF Eye Artistry**. That name is the MO2 mod entry and folder and the name the Studio shows for the package; the in-game selector label is the short brand **XF** so preset names fit beside it. It is display text only: the `xfs_` resource names, UUID-derived namespace, schema IDs and `axefrog/appearance_studio` depot root do not change with it.

One constant, `EYE_MAKEUP_MOD` in [`src/mod-branding.ts`](../../projects/xf-studio/authoring/src/mod-branding.ts), defines it. The planner copies it into the export plan as `modName` and `selectorLabel`. Check reports both. The resource builder writes `selectorLabel` into the customization option and refuses a plan without an XF-branded label. The independent verifier checks the converted option's label against the plan. The mod name a product carries comes from the package plan: a name the person gave, else the brand of its one feature (`FeatureModule.exports.brand`, which eye makeup takes from `EYE_MAKEUP_MOD`), else "XF Looks". The builder records it in the manifest (`modName`, with `nameSource` saying whether the person chose it), and the host result gate rejects a manifest or result whose names differ from its own plan. The feature's plan (`plan.json`) keeps the brand, so moving a feature between mods changes no resource. The MO2 install transport, diagnostic stage and promotion tools use the candidate manifest's `modName` as the dedicated folder and modlist entry, so a renamed mod stages and promotes under its own name (the stage plan and the promotion record carry it; older ones without it mean XF Eye Artistry). The name is checked as a folder name first. The transport never writes into an MO2 folder of that name that XF Studio didn't create (no live install of its own and files in it): it refuses in plain words and suggests renaming one of the two. Staging and promotion refuse a build that any installed mod already holds part of: every MO2 mod folder (enabled or not) and the game's `archive/pc/mod` are read for `.archive.xl` files declaring one of the resources the candidate's declaration declares, which finds a copy whichever stage or install put it there (each stage's own install receipts can't). Add to my mod manager reads only what the game would load ([below](#adding-a-built-mod-to-the-mod-manager)). Experiment 011 derives its diagnostic label ("XF Eye Artistry Shimmer diagnostic") from the same plan. A test fails if another TypeScript module or the Experiment 005 Python oracle spells the name itself.

The 25 September diagnostic promotion predates this name. It created the MO2 folder `XF Studio`, and its candidate's selector still reads `XF Studio · Eye makeup`. The tools treat `XF Studio` as a **legacy folder of the same mod**:

- Install and promotion refuse while an `XF Studio` folder exists (case-insensitive), so a second copy is never created beside it. Roll back that promotion, or remove the folder in MO2, first.
- A source profile that enables `XF Studio` is refused as already enabling XF Eye Artistry. The stage planner reports a legacy folder or modlist entry and adds a caution.
- Recovery and rollback still accept a promotion record naming the legacy folder, so the 25 September promotion remains reversible. Any other folder name in a record is refused.
- A scratch stage prepared under the legacy folder name must be staged again before promotion.

The legacy development mod `XF Eye Artistry CCXL - Dev` is a different, older mod; it is not treated as an earlier install. The diagnostic clone disables it in the copied profile only and places the XF Eye Artistry row directly below it in MO2's left pane. Without it, the row goes where MO2 puts a new mod, never inside a framework section; an existing row keeps its position ([placement rule](framework-version-check.md#mo2-placement-rule)). Frameworks are only reported, never installed or toggled.

## What Check, Build and Verify each prove

1. **Check mod export** validates the complete collection, filters a package-only copy, and runs a small 32-pixel compile for each retained preset. It reports the original preset count, packaged identities (with any diagnostic knobs), every omitted layer, preset and part, the plate lifts and the filtered snapshot SHA-256. When the host's plate cache holds a plate prepared for the same game folder, unchanged game content archives, the same recipe, and the same launch route and head choice, Check also plans on that plate's UV footprint (both hosts read it through the cache status; the CLI takes `--check --plate-manifest <file>`), omits presets that do not reach it and records it (`plateUv`). The route identity (`eyePlateRouteKey`) covers the route settings, the head choice, and the size and time of the game's mod folder and `modlist.txt`, the MO2 profile's `modlist.txt`, MO2's overwrite folder and the manual mod folder, so installing, enabling, disabling or reordering mods, switching profile or changing the head choice all count; editing files inside an existing MO2 mod folder does not (the next Build resolves the head anyway). The footprint must also follow the current window rule. Without such a plate (a fresh install, or any of those changes since the last Build) Check cannot judge plate reach: it records `plateUv: null` and says so plainly in its `notes` ("Whether each look reaches the eye area is checked when you Build."), and Build then reports any such omission. Shipping the vanilla head's plate footprint with XF Studio, so Check could always plan on it, was considered and not done: the footprint is every plate vertex's UV and every triangle of the CDPR head's eye area, a verbatim extract of game mesh data rather than asset-free metadata, and it would still not describe a modded head. Check makes no archive or SQLite save. It does not need the game or WolvenKit. An invalid or empty collection, one above 16 MB, or one with no exportable preset fails. Desktop Check has a 15-second worker deadline and returns no result on timeout, cancellation or worker failure. This is an eligibility check, not a visual promise.
2. **Build mod files** captures the current Studio draft, even when it has unsaved edits, without creating a SQLite revision. The server accepts only a same-origin request on `127.0.0.1`, computes its own filtered plan and both original/filtered hashes, and writes a temporary original snapshot. The CLI checks that source has not changed, uses the **same filter**, then requires separate private build/dist roots outside the declared game, plate-cache, source and tool directories before writing an immutable filtered build snapshot. Symlinks and Windows junctions in writable root paths are refused, including an `--output-root` link that would escape dist. Its WolvenKit and game paths come from private local settings or higher-priority server environment overrides, never browser package input. The eye plate has no setting: the host derives it from that game before the builder starts. Build then filters again on **that** plate's UV footprint: the host from the plate manifest's `uv` record (localhost reads a developer-override plate's mesh with its own WolvenKit serialize), the CLI from the same record or, for an override or an older manifest, by serializing the plate mesh once; both must agree, as the result gate checks. Unset build paths stay unset; there is no developer-specific fallback. Direct CLI use takes an exported collection file instead.
3. **Build conversion and pre-pack gate** produce each preset's route texture maps, full mip chains and mesh/morph/app/customization resources. No PNG copies are written. Before calling WolvenKit's packer, the builder requires the physical generated tree to equal the planned resource paths exactly. Paths must already be lowercase, relative, slash-separated and made from archive-safe characters; no traversal, separator aliases, unsupported extension, symlink or path-hash collision is accepted. This avoids WolvenKit silently normalizing a name or skipping a file. Each feature writes into its mod's one staging tree and checks its own files against its plan; the host then requires the whole tree to be exactly the union of every feature's files before it packs once, renames the archive to the mod's archive name and writes the `.archive.xl` merged from each feature's entries. Eye makeup's build record (`features/eye-makeup/build.json`) includes per-recipe and map hashes, plate input stem and path/hash entries, each archive member's canonical path, WolvenKit-compatible 64-bit path hash and SHA-256; the mod's `build.json` records the packed archive and `.archive.xl` hashes and each feature's files. Localhost build output stays under ignored project `build/`; desktop uses private user-data work and staging roots that are removed after Build. The fixture's checked-in `latest-build.json` belongs to the Experiment 005 oracle and is never changed by Build.
4. **Independent verification** is a separate TypeScript module that imports nothing from the compiler or builder (see [Build pipeline port](#build-pipeline-port)). It sources its own evidence: it copies the packed archive and the plate input files into an empty work directory, unbundles that archive copy with its own WolvenKit call, and requires the exact set and SHA-256 of the unpacked members to equal the build record. Only then does it run its own `convert serialize` on those members and the plate inputs (one launch; its copies of the plate inputs are named `plate-input.<name>` apart from the packaged plate members of the same stem) and its own texture `export`, so every check reads data derived from hash-checked members; none of the builder's conversions are read. **It does not take routes on trust:** it re-derives each preset's route from its packaged recipe with its own restated finish rules (any colour shift means the Fresnel route with one pigment and nothing else, otherwise any Shimmer means faceted, otherwise flat; Glitter and earlier-model layers have none), and the plan's route and material entry and the compiled record must match; a missing route fails instead of counting as flat. Since platform step 8 the archive-level part runs once per mod in the **product verifier** (`platform/export/product-verifier.ts`): it copies the archive into an empty folder, hashes and unbundles it, and requires the members to be exactly the features' generated files and the `.archive.xl` exactly the merged declaration; each feature's verifier (eye makeup's in `features/eye-makeup/verify/`) then checks its own members, converting a copy of its subset when the mod holds other features. The builder also passes the packaged collection it prepared, and every recipe in `build.json` must equal it. It rechecks the physical resource inventory against the plan and build record, then checks resource structure and names; the plate against its input and the recipe's morph target count. Every top-level plate field the build does not own must be the input's (only appearances and materials of the mesh, and the base mesh reference and seed appearance of the morph, are the build's). The mesh render blob, the morph base blob and the morph blob are compared with the input **as whole objects**: the only fields allowed to differ are those the lift changes, and each is re-derived rather than read from the package: the chunk list (byte offsets, index offsets), topology, buffer sizes and offsets, zero padding, morph counts, starts, totals and the mapping buffer (the input's, once per chunk). The head's position quantization must be the input's, and a morph target's delta quantization either the input's or exactly the range of its lifted deltas. Positions must be the input lifted along its normals (the restated 0.4 mm default or each preset's diagnostic lift, one chunk per lift, hidden chunks writing nothing) within half a quantization step and 0.01 mm, and every morph delta the lifted input delta within half a step and 0.02 mm; any diagnostic surface override, which must equal the packaged collection's; the Off/template/preset links; each route's material template, entry name and every material constant (the Fresnel shift constants restated from the preset's recipe; the stored `FresnelColor` is not restated but decoded with the verifier's own sRGB decoder, each channel within one byte of the normalised linear shift colour, so an encoding in the wrong direction, or none, fails; and each window entry's UV transform re-derived from the packaged plate's own UVs with the restated window rule, compared at float32 precision); each preset's texture space (window unless its route cannot transform UVs or a diagnostic keeps it on head UV) and every texture's dimensions; that a BC4 level decoded by the verifier itself from each preset's stored XBM is the exported level with its rows reversed (the import flip every UV mapping relies on); that each window map, sampled at 19,680 points of the packaged plate through the restated shader transform and row flip, matches the authored head-UV coverage reference (mean error below 0.03, under 1 % of points off by more than 0.5, and a signed offset estimate within one window texel on each axis: a joint search over shifts of the map lookup up to ±8 texels, refined to 1/16 texel, for the least total difference, made only with at least 24 samples of authored content and an edge strength of 8 (below that, as for makeup that barely reaches the plate or is very faint, the estimate would be noise and is not made); a map with no content at the plate, a map empty at the plate wherever the authored makeup reaches it at 2/255 or more however faint, or a decoded check with nothing to compare, is a plain verification error); explicit and stub chunk-material bindings; source-derived `{material}` texture paths; imported XBM metadata per channel (`TCM_Normalmap` for facet normals); each supplied mip chain byte for byte against its own restated reference (coverage space, variance-widened roughness, facet normals, linear mask, uniform gradient); decoded base-map colour/coverage/scalar/normal tolerances; and the entire decoded mip chain against those references. It parses the `.archive.xl` as YAML from the same bytes it hashes and requires exactly each planned body's customization registration (`female`, and `male` with the masculine V) and each body's app in the `player_customization.app` scope with the planned paths, and nothing else. It restates per body the template's visual tag (`Female` or `Male`) and the option's index (311 or 541). For the masculine V it also requires his four files to be the feminine ones' `_pma` twins, checks his customization, `.app` and plate exactly as hers against **his own** plate input (hashed at the start and the end, lifted along his normals, his recipe's 100 targets), requires his plate's UV window to be hers and every look to resolve to the same textures through his selector; the pixel and mip checks run once, on her plate's UVs, since the textures are shared. The plate input hashes must equal the build record and the host's prepared plate at the start and again at the end. It reports the archive, `.archive.xl` and plate input hashes, each preset's re-derived route, and `installed: false`, `gameRenderingVerified: false` and explicit limits. For a diagnostic glitter preset ([Glitter route](#the-diagnostic-glitter-route); [`glitter-checks.ts`](../../projects/xf-studio/authoring/src/features/eye-makeup/verify/glitter-checks.ts)) it re-derives the route from the recipe and the restated knob, checks `@glitter` and the accent entry's template and constants, the accent chunk's lift and bindings, and 4096 × 1024 and 2048² texture sizes, and requires every supplied chain to be the baked chain byte for byte. It restates the knob's rules too: the planning rules for regions (outline bounds clipped to the window, no symmetry, at most 200,000 flakes), `tiltMaxDeg` at least a quarter of the tilt spread, and no surface override or head UV beside the knob. Since nested levels are drawn, not reduced, it checks their published properties instead of recomputing them: the diffuse alpha is the flat coverage chain of level 0 exactly; flakes lie only inside the pigment's coverage and near their regions; no normal tilts beyond the knob's maximum, and no fully covered flake texel less than its region's tilt floor (glitter flakes 2); each nested region's level-0 mask mean is between 0.5 and 1.6 times its cover; every fully covered flake component in a nested region holds at least 2.3 texels² of mask (a 2-texel flake holds 2.6); at least half of each coarser level's component centroids fall on a finer-level flake (an independently drawn level would score near its cover); `box` regions equal the BOX chain of level 0 byte for byte; and flake-free levels carry the restated sheen within one byte. It also reads the **flakes' contents**. On every texel whose flake mask is 255 inside exactly one region (every level of a nested region, level 0 of a `box` one), roughness and metalness must be within one byte of that region's flake values and the diffuse must be the flake colour. Most such texels must be tilted (when the spread is at least 1°), and at least 99 % must carry the tangent (X, Y) of one of the region's catalogue flakes near the texel, within one byte. That catalogue is the verifier's own restatement of the seeded generator (xoshiro128**, draw order, mirror), which pins the tangent frame's signs and the flakes' places. At level 0, fully covered texels without flakes must carry a pigment within the active layers' colours and the knob's base surface, moved by the region's restated sheen share. So all-flat normals, flake material reset to the base, a negated normal Y, flipped rows and a grey pigment each fail. For the accent, at least three quarters of its level-0 components away from the feathered edge must sit within one window texel of a flake. A BC4 level the verifier decodes itself from the accent's stored XBM must be the exported level with its rows reversed. Sampled at the packaged plate's own UVs on a dense barycentric grid (91 points per triangle), the accent mask must fall on its own layer's authored head-UV coverage (Build records that layer's reference beside the preset's): at most 2 % of its drawn mass may lie where the layer has none. Against the decoded XBMs it bounds every level's error, the flake normals' angle error (BC5) and the flake-edge mask error (BC4), and requires the decoded levels 1–3 to be closer to the supplied nested chain than to a BOX chain (WolvenKit kept the supplied mips). It cannot establish actual game shader filtering or executed ArchiveXL expansion.
5. **Promotion** happens only after every mod's verifiers succeed. The exporter compares its verifier's report with its plan (the re-derived routes, the plate input hashes and the plate lifts must equal Check's); the builder copies just each mod's `.archive` and `.archive.xl` to a staging folder under the host's private dist root, writes `manifest.json`, checks that the promoted files hash to exactly what the verifiers checked, and renames every staging folder to its unique final directory only once all mods verified; if one rename fails, the ones already renamed are removed, so a Build promotes all of its mods or none. The host then calls the shared result gate with its own root: it checks containment and requires the builder's answer to equal its own `checkProducts` plan of the same snapshot (the collection hash, original count, omissions, and per mod its name, archive, own omissions and features with their looks, routes, diagnostic knobs, omissions, experimental finishes, packaged hash, plate lifts, the plate footprint it planned on and the plate's provenance), and each manifest to say the same, each feature's plan hash included, before returning the paths. Moving the candidates into the store is all or nothing too: every destination is checked before the first move, and a failure (or a failed gate in the store) removes the ones already moved. Containment holds on canonical paths (so a root named by a Windows 8.3 short form, as on CI runners, matches its long form) and lexically: the result must be written below the root, as given or in canonical form (the folders the path and root share, such as an 8.3 temporary folder, are compared in canonical form, but links in the path's own segments are not followed), so a path outside the root that reaches in through a junction is refused, and a package folder inside that is a junction leading out is refused too. A missing result, manifest or payload gives the same plain containment error. Every containment check on the way (the builder's private roots, the result gate, the install transport's store, receipts and target, the diagnostic staging, the desktop's writable build folders, zip extraction and the cache removals) uses one helper, [`src/platform/api/path-containment.ts`](../../projects/xf-studio/authoring/src/platform/api/path-containment.ts) (PIPE-08): absolute paths only, `..` folded, Windows case, slashes, drive letters, UNC shares and device prefixes compared as Windows compares them, and the real checks through links. `--output-root` cannot direct a build outside the chosen private `--dist-root`. Desktop supplies a temporary staging root, then moves a passing candidate into `package-candidates/` and rechecks it there; it removes snapshot, work and staging roots on completion or failure. A failed preflight/verifier does not promote a candidate, and a host identity-gate failure returns no accepted result.

The `xfs/local-package-2` manifest (one per mod; [`platform/export/manifest.ts`](../../projects/xf-studio/authoring/src/platform/export/manifest.ts), whose reader also accepts the one-feature `xfs/local-package-1` every earlier build wrote) identifies the mod (`productId`, `modName` and `nameSource`, `archive`), the original collection SHA-256 and original preset count, **this mod's own omissions** (the whole looks, parts and features of the collection's omissions that belong to its features and looks; one no built mod owns, such as a look holding no exportable part, goes to the first mod, the default one when it builds, so every omission is in some manifest), the highest framework requirements, and per feature: its exporter and version, namespace, brand, selector label and placement (its own selector or vanilla option sets), packaged preset IDs/revisions/appearance names with each preset's export `route` (as the verifier re-derived it), each excluded layer and its part of any look another feature packages, each included layer whose finish adapter is **experimental**, the packaged snapshot's SHA-256, the plan's SHA-256, eye makeup's `details` (the plate lifts, the plate footprint the omissions were judged on, which eye plate was packaged: the recipe, source revision, cache key, resource hashes and `head` provenance of the built-in plate, or `source: "override"` with resource hashes; `bodies`, whose creators get the selector; and `masculinePlate`, his plate's record, when he is included) and its verification (looks, files, limits). It also records hashes and sizes of the archive and `.archive.xl`, the verified file count, and explicit `installed: false` / `gameRenderingVerified: false`. It currently does **not** record an explicit compiler version or complete toolchain/version/provenance lock; those are release-traceability gaps. WolvenKit may place timestamps in the archive index, so two builds from identical resource artifact paths/hashes can have different packed archive hashes. Compare source/resource hashes as well as the packed hash: `tools/compare-package-candidates.ts` is the re-runnable byte-identity gate (it unbundles two candidates with WolvenKit and compares their members, `.archive.xl` bytes and manifests, and any intermediate folder pairs with `--tree`, JSON without WolvenKit's export-time `Header`). [Builder](../../projects/xf-studio/authoring/src/platform/export/product-builder.ts), [recorded checkpoint](local-package-build.md#offline-checkpoint--24-september-2026).

### Adding a built mod to the mod manager

After Build, each mod in the result offers **Add to my mod manager** and **Show in folder**: the Mod package panel's mods and each expression set's mod (the set panel composes the same button and review sheet through its view context, `ctx.modInstall`; the part preset service offers each set's latest verified Build, `PartPresetService.builtMods`). The page names a build only by its candidate ID; the host decides every path from the settings (Settings › Game). Adding is two steps, served by [`src/mod-install-host.ts`](../../projects/xf-studio/authoring/src/mod-install-host.ts) at `/api/mod-install` on both hosts (UI-82).

- **Plan.** The host says in plain words exactly what would change: on the MO2 route, the mod's files in its own `mods/<mod name>` folder (the instance's configured folders, not assumed defaults) and one row added, switched on, to the chosen profile's `modlist.txt` by the [MO2 placement rule](../../projects/xf-studio/authoring/src/mo2-placement.ts) (the file is the reverse of MO2's left pane; the row goes to the bottom of the lowest section without frameworks, beside an earlier name of the mod if one is listed; an existing row keeps its place and is only switched on); on the direct route, the files in the game folder. A mod's files keep their paths below that folder: the archive and `.archive.xl` in `archive/pc/mod`, and a product's [extras](#expression-sets-photo-mode-expression-mods) from its manifest (overlay archives beside the main one, TweakXL files in `r6/tweaks/<archive>/`). A plain archive and `.xl` are one line; a mod with extras names every file, the folder it goes into and what it is, and an update names any file of the earlier install the new build no longer has, which it removes. A build with a file of any other kind (a newer XF Studio's) is refused in plain words, naming the file, before the manifest reader would call it unreadable (the host reads the manifest as written; the transport's `extraFileKind` knows these two kinds only), with Show in folder, which still opens it, as the way on: its plan's `next` is `reveal`, and the sheet makes Show in folder its primary button, focused, in place of Add. A mod with extras names its folder (or the game folder) once in the plan's first line and every other folder relative to it. The success message says where to see the mod: the character creator for eye makeup, photo mode for expressions. A blocked plan says why and carries its one next step as data (`next`: open Game & tools, rename the mod in Mod package, or check again), which the sheet shows as the button (UI-99). A plan changes nothing, with one exception: an earlier install that was interrupted is finished or undone first, and the plan says which (below).
- **Consent.** `install` carries the plan's token, which covers everything the plan showed: the files and target, the settings revision, the mod list's exact bytes, where the row goes and why (its placement, which depends on the frameworks found) and the earlier install. Anything different since, and the install is refused with nothing changed (INSTALL-07).
- **Ownership.** The trusted transport ([`mod-install-transport.ts`](../../projects/xf-studio/authoring/src/mod-install-transport.ts)) refuses an MO2 folder of that name XF Studio didn't create (files in it and no live install of its own; MO2's own `meta.ini` doesn't count), a file it didn't put there (checked by hash, extras included: a TweakXL file another tool placed at the same path refuses), and a feature another XF mod already holds. Every candidate file is checked against the manifest's hash before copying, and every copy again after staging and after it is moved into place. It keeps a receipt naming every file (the extras too), a journal and a backup of every earlier file, so an update replaces, and uninstall or rollback removes, exactly its own files; the product's own `r6/tweaks/<archive>` folder is removed once empty, never `r6/tweaks` or another mod's file. The receipts are **per user on this computer**, shared by localhost and the desktop app ([`src/host-state.ts`](../../projects/xf-studio/authoring/src/host-state.ts): `%LOCALAPPDATA%\XF Studio\install-receipts`), so each recognises the other's install and they share one lock; a record in a host's earlier own folder (`<data>/install-receipts`) is taken over once and set aside there (INSTALL-04). A recorded install whose files are gone (the mod removed in MO2, or its files deleted) counts as uninstalled: the plan offers a fresh install and says so, and a file of it still present is replaced only while it is exactly the one recorded (INSTALL-03).
- **Interrupted installs.** The journal holds the receipt the install was about to write. On the next plan the host finishes an install whose new files are all in place (removing any earlier file the new build no longer has), undoes one that is partly done (the earlier files come back from their verified backup), or forgets one whose files are all gone; a file that is neither the new nor the earlier one is named and left alone (INSTALL-02).
- **Mod Organizer 2 and the game.** One `tasklist` run, off the server thread and bounded by a timeout, says whether Mod Organizer 2 and Cyberpunk 2077 are running. MO2 open blocks an MO2 install (it rewrites its mod list when it closes); the game running blocks replacing an `.archive` and finishing an interrupted install (it holds the file open). Where the process list can't be read, the install waits too (INSTALL-10).
- **The mod list, byte for byte.** `modlist.txt` is read as bytes and decoded as UTF-8 (with or without a BOM) or, failing that, the system's single-byte ANSI code page; the decode is used only if encoding it again gives back the same bytes, and every row keeps its own line ending and trailing spaces ([`mo2-modlist-text.ts`](../../projects/xf-studio/authoring/src/mo2-modlist-text.ts), INSTALL-05). A list that can't be read back exactly, is read-only, is linked to another file or is missing is refused in the plan with the step that fixes it (MO2 rewrites its list when a mod is switched off and on). At install the new list is written and flushed beside the old one **before** any mod file is copied, then moved into place; the previous list is kept in the private receipts folder (INSTALL-08). Every reader of the list (the install plan, the placement, the framework check, source discovery and the runtime diagnostics) reads its rows through one reader, `mo2ModlistRows` in [`mo2-instance.ts`](../../projects/xf-studio/authoring/src/mo2-instance.ts), as MO2 does: spaces around a row ignored, `+` or no prefix enabled, `-` disabled, `*` foreign, `_separator` rows carry no files (PIPE-10).
- **Duplicates.** Part of the build already loaded from somewhere else blocks the install: the profile's switched-on mods, MO2's Overwrite folder and the game's `archive/pc/mod` are read for `.archive.xl` files declaring one of the candidate's resources (at most 64 per folder, 1 MB each). A switched-off or unlisted MO2 mod is not loaded, so it never blocks. The advice fits the place: switch the MO2 mod off, move the file out of Overwrite, remove a hand-copied file, or disable a Vortex mod and deploy; a file Vortex deployed (by its `vortex.deployment.json`) is never to be renamed, since that breaks Vortex's record of it (INSTALL-06, UI-100). The legacy `XF Studio` diagnostic folder is refused with its one action (remove that mod in MO2).
- **Failures.** A first install that fails before any file is in place removes the empty folders it created, so MO2 never lists an empty mod (INSTALL-09). A mod name ending in `_separator` is a rename step on the MO2 route (INSTALL-11).
- **Test copies never write.** A verification workspace (`?verify`) uses `/api/verification/local-settings`, a settings store of its own that starts from the host's settings and keeps every change to itself, and `/api/verification/mod-install`, which plans read-only and refuses every change. A localhost server with its own data folder (`XFAS_DATA_DIR`, as every test and acceptance server has) or settings folder (`XFS_SETTINGS_DIR`) keeps its settings and receipts there, never reads or writes the person's real ones, and doesn't add mods unless `XFS_MOD_INSTALL=on` (for install tests against temporary fixtures). Neither recovers an interrupted install (INSTALL-01, UI-98).

Frameworks and every other mod are never installed, replaced, switched off or moved; an older eye-makeup mod still switched on is named in the plan for the person to decide. A successful add says where the mod is and to start the game from Mod Organizer 2; it proves nothing about game behavior. **Show in folder** opens the build's `archive` folder (beside its `r6` folder when it has one) for installing by hand. Report a problem recognises XF Studio's own installs by these receipts, extras included: each file is matched in the folder the receipt placed it in, so an expression mod's table overlay is known as XF Studio's.

The separate first-game diagnostic path copies the candidate pair and selected profile metadata into an ignored scratch root. A transfer planner reads that stage and shows exact destination paths, bytes, hashes, profile changes and collision gates without writing to MO2. After the fixture tests and live dry-run, its explicit action created the new `XF Studio diagnostic 2026-09-25` profile and dedicated `XF Studio` mod in the reference MO2 instance. That run predates the XF Eye Artistry name; the folder is now treated as a legacy install of the same mod (see [Mod name and MO2 folder](#mod-name-and-mo2-folder)). The original `2025 (again)` modlist SHA-256 stayed unchanged, the promoted pair matched the candidate manifest, and a private completion receipt was written without a pending journal. MO2's selected profile was not changed. The transfer checks the source candidate against its manifest, the staged transport receipt and staged file hashes, source profile metadata, and current archive filename collisions. Its journal/receipt support conflict-aware recovery and rollback of only unchanged created paths. It writes its journal and receipt with the install transport's durable writer and checks links with its link walk (`writeJsonDurably`, `assertNoLinkedPath`), and its clone's list switches the predecessor off with the placement's row rewrite (`disableMo2Mods`), whatever the file's line endings. Neither stage nor transfer reruns the independent archive verifier; neither proves an archive winner or game behavior. [Transfer tool](../../projects/xf-studio/authoring/tools/runtime-diagnostic-promotion.ts), [prepared session card](../../docs/validation.md#prepared-single-session-test-card).

## Build speed and stage progress

A Build of the two-preset reference collection with both bodies' plates reaches its last step, **Checking the mod files**, 2.8–2.9 s after **Build now** when the plates are cached, and the verified result arrives **14.0–16.0 s** after it, the verifier's WolvenKit steps running side by side; measured through the host service on the development PC with WolvenKit 9.0.1, 30 September 2026 (`tools/build-bench.ts --alternate-verifier`, six warm runs interleaved run by run with five in the earlier one-at-a-time order, which took 18.1–19.7 s; the CPU at 19–79 % when sampled, 27 GB free; the [performance backlog](../backlog/performance.md) has every run). Written wholly by WolvenKit, the same collection reached step 5 at 13.4–13.8 s and its result at 28.5–29.8 s (pass 2's interleaved runs). The six-preset finish board (25 resources) reaches step 5 at 7.1 s warm (4.5 s of it compiling its six looks) and its result at 23.8 s. The first Build, which cuts both plates with WolvenKit, reached step 5 at 47 s and its result at 62 s (WolvenKit-only: 57 s and 72 s); cutting the plates is 44 s of that. What each stage does now:

| Stage (`PackageBuildStage`) | Work | WolvenKit launches (warm) |
|---|---|---|
| `prepare` (host) | resolve the route's head; reuse the cached plates and their [kept JSON](#where-the-eye-plate-comes-from); settled `.xl` additions are kept per opened installation; start the builder | none |
| `compose` (builder) | read each plate's kept JSON, compile the looks' maps | none |
| `convert` (builder) | mip chains and DDS; every texture imported and every resource written [natively](#native-resource-writer) | none (one per kind the native writer refuses) |
| `pack` (builder) | pack the staging tree into one archive natively | none |
| `verify` (builder) | product verifier's unbundle (each overlay archive's beside it); then the features' verifiers side by side: eye makeup's one serialize of members and plate inputs beside its texture export | 3, at most 2 at once |

Everything before `verify` now takes about 2.8 s; the verifier's launches are almost all of the rest (11–13 s: the unbundle alone, then serialize and texture export together). Each WolvenKit launch still costs about 2.3 s before it does any work, and about 1.2 GB of memory.

**Stage progress (PIPE-131).** The builder prints `XFS_PACKAGE_PROGRESS={"stage": …}` as each stage starts (the platform: `compose`, `pack`, `verify`; a feature may report `convert`), and the host's service (`PackageHostService.buildProgress`) keeps the running Build's stage, its step among the five and how many looks it builds; it reports `prepare` itself. `GET /api/package/progress` answers it on both hosts (codes and counts only). The page asks every 400 ms while its Build runs and shows "Step 3 of 5: Converting 2 looks…" in the Mod package panel's one progress line, with the bar filled to the middle of that step. Stages only move forward, and the Build's own answer is the last word. Step 5, "Checking the mod files…", starts once the archive is written: the mod is built, and not yet offered until the check passes.

**Compression.** Buffers are compressed at Oodle Kraken Optimal2 and resource bodies at Normal, as WolvenKit does ([archive formats §2](../../knowledge/archive-format.md#2-compression-kark-and-oodle)); in a native Build that is about 0.9 s of the convert and pack stages, mostly the two morph targets' buffers and the BC7 textures.

## Native resource writer

**Build writes the mod's resources itself (PIPE-130), and WolvenKit only checks them.** The builder's conversions go through the native writer's tools ([`native-resource-tools.ts`](../../projects/xf-studio/authoring/src/native-resource-tools.ts)) in place of WolvenKit's:

| Step | Written natively by | What WolvenKit did before |
|---|---|---|
| Eye makeup's CR2W resources (plate meshes and morph targets, `.app`, `.inkcharcustomization`) from the builder's JSON | [`cr2w-writer.ts`](../../projects/xf-studio/authoring/src/native/write/cr2w-writer.ts) with [`package-writer.ts`](../../projects/xf-studio/authoring/src/native/write/package-writer.ts) for each appearance's compiled components | `convert deserialize` |
| Every texture (`.xbm`) from its DDS mip chain | [`xbm-writer.ts`](../../projects/xf-studio/authoring/src/native/write/xbm-writer.ts) with XF Studio's texture compressor | `import`, one launch per texture group |
| The archive from the staging tree | [`rdar-writer.ts`](../../projects/xf-studio/authoring/src/native/write/rdar-writer.ts) | `pack` |
| The expressions exporter's resources (two animation sets, the face-rig `.app` patch, the expression table) | Not written natively: WolvenKit, until an oracle proves them | `convert deserialize`, as before |

The bytes are WolvenKit's, not an approximation of them ([archive formats §14](../../knowledge/archive-format.md#14-writing-resources-and-archives-as-wolvenkit-does)): a property is left out exactly when WolvenKit leaves it out (its generated classes' defaults, read into [`writer-classes.json`](../../projects/xf-studio/authoring/src/native/write/writer-classes.json) by `tools/native-writer-classes.ps1`); buffers and archive segments are compressed by the player's own copy of the game's Oodle at the levels WolvenKit uses (Optimal2 for buffers, Normal for bodies); textures are flipped as WolvenKit's import flips them and compressed by the same DirectXTex encoders it runs (BC4 and BC5 on the CPU, BC7 by DirectXTex's DirectCompute encoder on the GPU). That compressor is `xfs_bcn.dll` ([`native/bcn`](../../projects/xf-studio/authoring/native/bcn/xfs_bcn.cpp), built from the official DirectXTex source by `tools/build-native-bcn.ts`; it needs nothing but Windows and Direct3D 11).

**Byte for byte.** Two real Builds were written both ways on the development PC on 30 September 2026 and compared ([`tools/native-writer-oracle.ts`](../../projects/xf-studio/authoring/tools/native-writer-oracle.ts), `tests/native-writer.test.ts`): the two-preset reference collection for both bodies (14 resources: four plate meshes and morph targets, two `.app`, two `.inkcharcustomization`, four BC4 and two BC7 textures) and the six-preset finish board (flat, faceted and colour-shift routes, 25 resources including a BC5 normal map). Every resource is identical to WolvenKit 9.0.1's, and so is each archive except the file time each index entry records (and the index CRC over them), which differs between two WolvenKit runs too. Every Build written natively passed the independent verifier.

**Only what an oracle proves (NATIVE-72, PIPE-135).** The writer can encode any class in its table, but its bytes have been compared with WolvenKit's only on eye makeup's resources. So a `deserialize` is written natively only when the exporter names an oracle (eye makeup's `deserialize` passes `{ oracle: "eye-makeup" }`) and each document's root class is one that oracle covers (`NATIVE_WRITER_ORACLES` in [`native-resource-tools.ts`](../../projects/xf-studio/authoring/src/native-resource-tools.ts): `CMesh`, `MorphTargetMesh`, `appearanceAppearanceResource`, `gameuiCharacterCustomizationInfoResource`; with the `CMaterialInstance` files inside the mesh and the `CBitmapTexture` textures, the six classes the oracles cover). An exporter that names no oracle (expressions, whose face-rig `.app` has the same root class as eye makeup's) has every document converted by WolvenKit as given, in one launch, and each is recorded with the reason. The writer also reads only WolvenKit 9.0.1's JSON (`WKitJsonVersion` 0.0.9), and with any other WolvenKit (8.17.4 is still accepted for Builds) the whole Build is WolvenKit's, since the class table and the oracles come from 9.0.1. A new exporter's resources move to the native writer only once an oracle of its own is captured, compared and listed.

**WolvenKit per file.** The native writer refuses what it can't write exactly: a class or property its table doesn't know, a reference stored as a hash, a texture setting or format it hasn't matched to WolvenKit, a staging tree with a link, or a missing prerequisite (the game's Oodle library, or the compressor or a Direct3D 11 device for BC7). Each refused file is made by WolvenKit, all of a kind in one launch, and the rest stay native. The build record and the manifest's `resourceWriters` list the files written natively (and `archive` for the pack) and each file WolvenKit made, with the reason; with nothing refused, a Build starts no WolvenKit process until verification. `XFS_NATIVE_WRITER=off` (a developer switch) sends everything to WolvenKit, which is how the oracles are captured.

**The verifiers stay independent.** The product verifier unbundles the archive with WolvenKit, and eye makeup's verifier serializes the members and exports the textures with WolvenKit, as before; neither imports anything from `src/native/write/` or the tools adapter (`tests/native-boundary.test.ts`, `tests/mod-verifier.test.ts`). The verifier tools are asynchronous and cancellable (`VerifierTools`, [`verifier-wolvenkit.ts`](../../projects/xf-studio/authoring/src/verifier-wolvenkit.ts)): steps that don't depend on each other run side by side through `sideBySide` ([`platform/api/export.ts`](../../projects/xf-studio/authoring/src/platform/api/export.ts)), at most two WolvenKit processes at once (the Build's own limit, about 1.2 GB each; the Build's tree peaked at 3.1 GB). The product archive's unbundle runs beside each overlay archive's; then the features' verifiers run side by side, and eye makeup's serialize runs beside its texture exports. Every step follows the Build's `AbortSignal`; the first step to fail aborts its siblings and is the failure reported (never a sibling's cancellation), and a Build cancelled during verification answers `package_build_cancelled`. A mod is promoted only after every step has passed, so nothing is offered for **Add to my mod manager** before it is verified: the Build's answer still comes after verification. The progress line's step 5 ("Checking the mod files…") starts as soon as the archive is written. `XFS_VERIFIER_CONCURRENCY=1` (a developer switch; it can only lower the limit) runs the steps one at a time in the order they were queued, which is how the before-and-after was measured.

**In the desktop app.** The compressor ships in the app's build tools at `app/native/xfs_bcn.dll`, listed with its SHA-256 in their manifest (`desktop/prepare-build-tools.ts`, which builds it with the same `tools/build-native-bcn.ts` localhost uses). CI's Windows runner builds it from the pinned DirectXTex release (`native/bcn/directxtex.json`: release, URL and SHA-256; the script refuses any other bytes) with its Visual Studio C++ tools, CMake and the Windows SDK's `fxc`, deterministic (`/Brepro`: two clean local builds gave the same bytes) and with a static C runtime; `verify-canary.ts` requires it in the update archive, loads the packaged bytes and compresses a block with them, and scans its strings for user paths. Which compressor a Build may load is [`packaged-build-tools.ts`](../../projects/xf-studio/authoring/src/packaged-build-tools.ts)'s decision: in the desktop app only the packaged copy, and only when its bytes match the manifest (the developer's `XFS_BCN_LIBRARY` is ignored there); in the source tree `XFS_BCN_LIBRARY` as given, then the one built into the ignored `data/tools/xfs-bcn`, only when its bytes match the SHA-256 its `xfs_bcn.json` records (NATIVE-75; with no record it isn't loaded). The host's readiness check treats it as optional: a manifest-listed compressor that is missing leaves Build ready, and one whose bytes changed makes the install need repairing. Missing, changed or failing to load, the Build imports its textures with WolvenKit (one launch per texture group, a few seconds) and the manifest's `resourceWriters` says why; the person sees no difference but the time. The packaged builder from a canary archive built all eleven resources of a feminine two-preset Build natively, textures included, and with the compressor's bytes altered fell back to WolvenKit for the textures with that reason (30 September 2026).

**Cancellation (NATIVE-74).** The native tools take the Build's signal: they check it between files and before packing, and stop with the Build's cancellation. One texture's compression or one document's conversion runs to its end.

**Not yet done.** The expressions exporter's resources have no oracle yet, so WolvenKit converts them. The plate cut is still WolvenKit's (44 s of a first Build); the verifier's unbundle must finish before its conversions start.

## Build pipeline port

**Build no longer needs Python.** Both hosts run the TypeScript modules below; end users need only the game, WolvenKit CLI and the Bun runtime the app already has. WolvenKit resolves as a developer override (`XFS_PACKAGE_WOLVENKIT`, localhost only), then the path in Build setup, then XF Studio's own copy of the pinned official 9.0.1 release, downloaded once with the user's consent and verified by SHA-256 ([WolvenKit on first use](../../projects/xf-studio/authoring/desktop/README.md#wolvenkit-on-first-use)). Readiness checks the CLI's version, commands and .NET runtime before Build starts. Experiment 005's Python programs (`build.py`, `verify.py`, `mip_maps.py`, `archive_inventory.py`) are kept unchanged as a **research oracle** for comparisons; the product never calls them. The port had two phases: phase 1 ported the arithmetic, the path gate and the verifier; phase 2 ported the orchestration and switched the hosts.

| Python (Experiment 005 and the retired wrapper) | TypeScript | Notes |
|---|---|---|
| `mip_maps.py` mip arithmetic and DDS writer | [`src/engines/layered-makeup/flat-mip-chain.ts`](../../projects/xf-studio/authoring/src/engines/layered-makeup/flat-mip-chain.ts) | Pure, with no file access. Follows NumPy's float64 order: each 2×2 average is `((a + b) + c) + d` divided by 4, squares are `x * x`, and only the 2.4 and 1/2.4 powers call `Math.pow`. |
| `archive_inventory.py` pre-pack gate | [`src/archive-inventory.ts`](../../projects/xf-studio/authoring/src/archive-inventory.ts) (pure) and [`src/archive-inventory-fs.ts`](../../projects/xf-studio/authoring/src/archive-inventory-fs.ts) (directory walk) | Same canonical-path rules, FNV-1a 64 depot hashes, collision and exact-plan checks. **How the hosts run it.** Both hosts hand requests to the one package host service (`runProductBuild`, PIPE-03): Check in a fresh Bun worker (`tools/package_check_worker.ts`, bundled into the desktop view as `check-worker.js`) with a 15-second deadline, Build as one bounded child process with a 40-minute deadline, so compiling and verifying never block the host. Localhost runs the CLI from the source tree with Bun; the desktop installer ships one asset-free Bun bundle of the same CLI (`build-tools/app/tools/build.js`, manifest schema `xfs/desktop-build-tools-2`) and runs it with XF Studio's own Bun. The host passes the prepared plate in a `--prerequisites` file; the builder checks its provenance before it creates any build folder. Both stop the whole process tree, WolvenKit included. Each WolvenKit step also has its own 4-minute limit, as in `build.py`. Every WolvenKit command in Build, the independent verifier, the eye-plate derivation and the 3D preview runs through one [WolvenKit runner](../../projects/xf-studio/authoring/src/wolvenkit-cli.ts) over the shared [process-tree runner](../../projects/xf-studio/authoring/src/process-tree.ts): one success policy (exit code, time limit, cancellation, `Unhandled exception`), a typed missing-.NET-runtime failure with one shared plain message, and the version probe; each consumer maps its errors to its own codes. The verifier is synchronous, so it uses the runner's blocking form through an injected adapter ([`verifier-wolvenkit.ts`](../../projects/xf-studio/authoring/src/verifier-wolvenkit.ts)) and still judges each result with its own checks; the character resolver's fetcher is the one WolvenKit caller left outside the runner. A `pythonExecutable` value saved by an earlier version is dropped when settings load, and Python is no longer part of readiness.

**One deliberate byte detail.** `build.py` wrote the `.archive.xl` declaration in Windows text mode, so every candidate so far has CRLF line endings. The TypeScript builder writes the same CRLF bytes, so the declaration stays byte-identical. YAML accepts either form.

**Verifier independence.** `verify.py` imported `mip_levels`, `destination_contributions` and `read_dds_levels` from the compiler's `mip_maps.py`, and `inventory` from the builder's gate. So a compiler regression could also change the values it was checked against. The TypeScript verifier reimplements the coverage-space arithmetic, the DDS reader and the resource inventory inside its own directory. The [boundary test](../../projects/xf-studio/authoring/tests/mod-verifier.test.ts) allows only `node:` built-ins, imports between the verifier's own files, the platform's export types and eye makeup's export info (its exporter ID), so WolvenKit reaches it only as injected tools; the architecture boundary test also forbids it to reach its exporter, any engine or the pipeline modules the exporter wraps, even through other modules. Its finish rules are a deliberate restatement of the builder's table, and a [test](../../projects/xf-studio/authoring/tests/mod-verifier-routes.test.ts) fails if the two disagree. The supplied mip chain is still compared **byte for byte** with the verifier's reference chain. The float order above is part of that published contract, so this is a comparison between two separate implementations of one specification, not a tolerance check.

**Verifier inputs.** `verify.py`, and the first TypeScript port, read the builder's own round trip, texture export and plate serialization, so a fault in one of the builder's conversions could be checked against itself. The verifier now sources its own evidence. In an empty work directory (`<build>/verify`, the product verifier's) the archive copy is unbundled and every member checked against the features' build records; in its own (`<build>/features/eye-makeup/verify`) eye makeup's verifier copies the plate inputs, checks its members, and runs its own WolvenKit `convert serialize` (members and plate inputs) and `export` (textures; the game folder is passed only because WolvenKit's `export` requires `--gamepath`). The builder therefore no longer round-trips its resources or exports textures. The verifier still reads three kinds of builder file, each bound by hash or recomputation: the baked raw base maps (checked against the SHA-256 in `build.json`; `verify.py` read PNG copies of them), the supplied DDS mip chains, which it compares byte for byte with its own reference chain, and each window preset's head-UV coverage reference (checked against its SHA-256 and crop in `build.json`). The reference is the one input that states what was authored rather than what was built, so the builder produces it through the head-atlas raster, never the window rasterizer that made the maps (see [the plate-local UV window](#the-plate-local-uv-window)); the verifier cannot import either, so that separation, and the test that mirrors `rasterWindow`, are what keep the mapping gate independent. It takes decoded base levels from its own DDS export (level 0) instead of a PNG export; `verify.py` already asserted on every build it passed that the exported PNG equals DDS level 0, so the PNG round trip added no evidence. The expected morph target count comes from the plate recipe through the plate manifest; a developer override plate has no recipe, so its own non-zero count is accepted. On 25 September 2026, with WolvenKit 9.0.1, real Builds of the four-preset fixture (16 members, about 18 s of verification) and the private five-look collection (19 members) passed; the four-preset members were byte-identical to the previous TypeScript build's. Private copies of the four-preset build were then rejected in each of four deliberate corruptions: one texture member changed and repacked with the new archive hash re-recorded ("differs from its generated payload"), a declaration with an extra `resource.patch` and one registering `male` instead of `female` (both passed the earlier substring check), and a plate input changed after the build.

**Since the plate-local UV window**, production flat and faceted maps are 2048 × 512 window maps, which the Python oracle does not model. `tools/bake_collection.ts`, which the oracle calls, keeps the historical head-UV layout, and the plan it writes says so (every preset `uvSpace: "head"`, under its route's historical entry name, which the oracle writes without UV constants), so the parity results below describe that layout and the head-UV code paths the window left unchanged (the flat, faceted and mask chain arithmetic on square maps, the inventory and the resources other than the plate mesh's material values).

**Measured parity, phase 1.** The comparison was run on 25 September 2026 with WolvenKit 8.17.4 and a fresh private build of the four-preset [editor fixture](../../experiments/005-preset-collection/editor-collection.json):

- **Mip chains:** all 12 DDS files byte-identical to Python, both freshly compiled and against the build's Python-written import chains. Three random 1024² stress maps gave 0 differing bytes and 0 differing float64 values across every level. `Math.pow` and NumPy's power do differ by at most 1 ulp on about 0.03% of 2 million sampled inputs (including 1 of the 256 byte values for the 2.4 power), but none of these crossed a `floor(x·255 + .5)` rounding boundary in any test. If one ever does, the verifier's byte comparison refuses the build rather than accepting it silently.
- **Inventory:** all 16 records identical to Python, and path acceptance and hashes agree on the oracle cases.
- **Verifier:** both verifiers pass the same build. The reports have identical structure and values, except four `premultipliedDestination.mean` statistics that differ by at most 2.7 × 10⁻¹⁶ relative. NumPy sums that strided 5-channel view in a different order; 1-D means and the 95th percentile match NumPy exactly. A tampered supplied mip byte fails both verifiers. On this machine the TypeScript verifier took about 5.2 s against Python's 9.4 s.

**Measured parity, phase 2.** On 25 September 2026, with WolvenKit CLI 9.0.1 and the installed game 2.31, both fixtures were built twice: once by the retired Python wrapper and Experiment 005 (with the verified built-in plate), and once through the **real localhost package handler** running the TypeScript builder, which derived its own plate into a fresh private cache. The fixtures were the four-preset [editor fixture](../../experiments/005-preset-collection/editor-collection.json) and a private five-look Satin collection. For each pair:

- **Every unpacked archive member is byte-identical:** 16 of 16 for the four presets and 19 of 19 for the five looks. So are the generated resource trees before packing, the baked raw maps, `plan.json` and `compiled.json`, every DDS mip-chain input and every WolvenKit DDS export. The `build.json` inventories (paths, sizes, SHA-256 and 64-bit path hashes) are equal, and so are the plate stem and plate input hashes. Both builds used the same plate bytes (mesh `58081caf…`, morph `b8b7c055…`).
- **The `.archive.xl` declarations are byte-identical.**
- **The generated resource JSON is equal** once WolvenKit's export header is set aside (its timestamp and source path).
- **The two verifiers' reports agree**, except for the same `premultipliedDestination.mean` statistics as in phase 1 (four or five values, at most 2.7 × 10⁻¹⁶ relative).
- **Packed `.archive` hashes differ,** as expected, because WolvenKit writes build times into the archive index.

The desktop Build host was also run from source with the real bundled `build.js`, a fresh private data root and the four-preset fixture. It derived the plate, built, verified and promoted a candidate, and left its snapshot, work and staging roots empty. Unbundling that candidate's archive gave the same 16 member hashes as the Python build, and its `.archive.xl` was byte-identical. TypeScript localhost Builds took about 43 s with a cached plate and about 64 s including a first plate derivation. These are offline equality results, not a game test.

Rerun the comparisons from the authoring directory with `bun tools/compare-build-port.ts mips | supplied <build> | inventory <build> | verify <build> | builds <python-build> <typescript-build>`. It is a development tool that needs Python, and it writes only to ignored build directories. `builds` only reads two finished, verified intermediates of the same collection and plate. `verify` needs the PNG copies that only the Python oracle writes. The unit tests stand alone; their Python oracle cases are skipped with a message when NumPy is unavailable. Public CI runs without them; before a release, `XFS_REQUIRE_ORACLES=1 bun test` turns those skips into failures ([authoring checks](../../projects/xf-studio/authoring/README.md#checks)).
