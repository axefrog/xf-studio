# Local collection-to-package boundary

The archive builder now checks generated resources immediately before packing: the physical tree must equal the collection plan's mesh, morph, app, customization and three texture paths per retained preset. Every depot path must already be canonical and have an allowed extension; symlinks, unexpected/missing files and path-hash collisions fail the build. The independent verifier rechecks the tree against the recorded canonical path, 64-bit depot hash and SHA-256 inventory, then requires the exact same unpacked archive member set. This is independent of how a future approved installer transports the verified package.

For a detailed diagram and plain-language walkthrough of this path, see [From XF Studio collection to a Cyberpunk mod candidate](studio-to-mod-pipeline.md).

The Studio's **Export collection** action downloads an editable snapshot with stable collection/preset UUIDs: `xfas/collection-1` whenever every look is eye makeup that format holds, otherwise `xfs/collection-2`. The builder reads both; from a collection-2 file it takes each look's eye-makeup part. The Studio's TypeScript package builder (a port of Experiment 005, which first did this) compiles this format into one ArchiveXL character-creator selector, using the Studio's built-in eye plate and the flat `mesh_decal.mt` adapter. The authoring [package CLI](../../projects/xf-studio/authoring/tools/build_collection_package.ts) is a separate, local build action around that compiler. Direct CLI use does not save a collection revision, install a mod, or launch the game.

The Studio also has **Check mod export** and **Build mod files** beside the collection export actions. These actions capture the current draft as the `xfas/collection-1` eye-makeup view of its looks (`eyeMakeupCollection`), including edits unsaved at click time. They do not save a SQLite revision or alter the draft; edits made during the build do not change its input. Export collection retains its existing explicit save-before-download behavior. The server accepts only same-origin requests on `127.0.0.1`, enforces the 16 MB collection limit, parses the collection contract, and accepts no browser-supplied executable, source-resource or output paths. The typed request adapter is `authoring/src/package-action.ts`; `package-server.ts` owns the HTTP/tool boundary. It runs the CLI asynchronously with one build at a time, checks the result manifest against the exact original snapshot hash, filtered snapshot hash, retained preset identities and omission list, and shows the resulting ignored `dist` path or the compiler/tool failure in the Studio status area. The browser action never installs, deploys or launches the game. Closing the page does not cancel an already started server build.

The localhost server reads WolvenKit and game paths from private Local setup, with `XFS_PACKAGE_WOLVENKIT` and `XFS_PACKAGE_GAMEPATH` server environment overrides taking precedence. It has no developer-specific build-input fallback. Bun is the running server executable (`XFS_PACKAGE_BUN` points elsewhere for development; there is no Bun setting). These values are never accepted from the browser. Before starting the CLI, Build derives the [built-in eye plate](studio-to-mod-pipeline.md#where-the-eye-plate-comes-from) from that game into the ignored `authoring/data/eye-plate-cache/` (relocatable with `XFS_PACKAGE_PLATE_CACHE`) and passes it with `--plate` and `--plate-manifest`. `XFS_PACKAGE_PLATE` is a hidden developer override that supplies a plate directory instead. Check mod export needs no WolvenKit/game input; Build reports a missing local input, or a missing or unsupported game head, clearly. The candidate remains private and requires the runtime checks below.

Run from HQ (use your own local game/tool paths). The direct CLI does not derive the plate; pass a plate directory, for example one prepared with `bun projects/xf-studio/authoring/tools/derive_eye_plate.ts --game PATH_TO_GAME --wolvenkit PATH_TO_WolvenKit.CLI.exe --cache ABSOLUTE_PRIVATE_DIR` (it prints the `resources` directory):

```powershell
bun projects/xf-studio/authoring/tools/build_collection_package.ts `
  --collection C:/path/to/xfs.collection.json `
  --plate PATH_TO_PLATE_CACHE/xfs-expanded-eye-plate-r1-KEY/resources `
  --wolvenkit PATH_TO_WolvenKit.CLI.exe `
  --gamepath PATH_TO_GAME --check
```

Remove `--check` to build; a standalone preflight needs only `--collection`. The CLI is TypeScript run by Bun; **no Python is needed** (the Python wrapper it replaced was removed, and Experiment 005's Python programs remain only as a research oracle). Preflight parses the entire collection, omits unsupported **active** layers in a package-only copy, drops presets with no active exportable layers, reports each omission, and invokes the same flat compiler at 32px on the retained presets. It rejects collections with no exportable content, malformed IDs/recipes and files over 16 MB. The original file is hash-checked; an immutable filtered snapshot with its own hash becomes the build input, so editing the source during the longer build cannot change the package behind its manifest. The [resource builder](../../projects/xf-studio/authoring/src/package-resource-builder.ts) then runs the 1024px compiler, full authored mip chains and WolvenKit conversion in an intermediate directory under ignored `projects/xf-studio/build/`. The independent TypeScript verifier checks binary resources, decoded maps/mips and unpacked archive payloads. **Only after it passes**, the [package service](../../projects/xf-studio/authoring/src/package-build-service.ts) copies the verified `.archive` and `.archive.xl` into a unique ignored `projects/xf-studio/dist/<namespace>-<timestamp>/archive/pc/mod/` directory, alongside a hash/identity/omission manifest. `--output-root` can select only within the configured private `--dist-root`, never outside it. For a portable host, the CLI accepts `--app-root` (the read-only code root), `--build-root` and `--dist-root`; omitted values use the localhost checkout defaults. Before Build writes an intermediate, it requires disjoint build/dist roots and refuses either root overlapping the declared game, plate, app, WolvenKit or Bun directories. An optional `--plate-manifest` names the host-verified built-in plate; the service checks its resource hashes and records the plate's identity in the package manifest; writable root paths containing symlinks or Windows junctions are also refused. The host must choose and protect the private roots, including keeping them outside any separately configured MO2 installation, which the CLI has no path for. With `--machine-result`, the CLI prints one `XFS_PACKAGE_RESULT=` line, or an `XFS_PACKAGE_ERROR=` line with a code on failure. The final result gate accepts the host's dist root and checks the returned manifest against the original and filtered snapshots before the host accepts the package path.

The output is an installable **candidate**, not a game-tested release. The flat adapter supports active Matte, Satin (`regular`) and Metallic layers with provisional shader parameters; game-matched Glossy, Shimmer and Colour-shifting layers use experimental routes ([finish designs](../materials/finish-designs/README.md)). Glitter layers, earlier-model layers of those three finishes, and colour-shift layers that share a preset with other finishes are excluded with named warnings; disabled/transparent experimental layers are not reported as omissions. A preset with no remaining active supported layers is excluded with a separate whole-preset warning. The authored collection and SQLite library remain unchanged; no optical look is silently flattened. One package produces one selector for the retained presets. Stable UUID-derived resource identities survive preset display-name changes, though indices change when reordered or partially excluded and game save behavior is unproven. The plate can still intersect sampled idle poses. ArchiveXL registration, A→B→Off clearing, pose clearance, compatibility and rendering must be checked in a later batched game session.

The package embeds plate geometry cut locally from the user's own CDPR head. Therefore the plate cache, build intermediates and `dist` remain ignored and private; none is suitable for Git or automatic public distribution. A clone needs an installed game whose head matches a supported recipe revision (currently 2.31) and WolvenKit, but no private plate files. Fixture reproduction with the Python oracle still works with the original `build.py`/`verify.py` defaults. The product CLI never touches `latest-build.json` or checked-in experiment results.
