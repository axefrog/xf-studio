## 1. Host: first-frame demand uses the shared lanes

**Cause [source]:** creator presentation waited only for person jobs; poses and facial control analysis used fair slices without the shared lane policy. A whole facial preparation is not a suitable single-slot job: it later waits indefinitely for an Expressions request, and other reads depend on its rig. Holding that slot while waiting for another job would deadlock dependencies.

**CPU policy (`22bb619b`, retained):** cooperative read turns use person > shown > ahead, with 1 ms ahead slices and fixed, non-renewable 50 ms eligibility deadlines while shown reads are in flight. These clock deadlines cannot wait on another operation completing. Preparation jobs alone retain slot/tail/hold/quiet barriers. **Native policy (current fix):** all request kinds share person > shown/default > background queue order. A host adapter stamps the current lane on requests at the shared installation port (ahead maps to background), unless the caller explicitly chose a priority. It covers document fetches and direct animation/texture/mask/geometry calls. The active request finishes, then the highest queued lane runs, FIFO within that lane. No scheduler completion permit, timer or second worker is added.

| Lane | Work |
|---|---|
| `person` | Existing V requests, installation checks and Clear; unchanged preparation/commit policy |
| `shown` | Facial rig/setup, blink bake, idle catalogue/body reads; explicitly requested expression listing retains shown priority |
| `ahead` | Creator presentation, pose catalogue, inert/control-relation analysis, existing background V resolve and upkeep; expression prefetch stays ahead |

Both host roots pass the same scheduler into the facial, idle and pose hosts; the creator already receives it. Creator/pose scans, idle catalogue reads and the in-app control probe take cooperative turns. Setup/blink/idle work now retains CPU preference across short I/O gaps without requiring its completion to release dependencies. Person requests retain their immediate start and pre-emption route; single preparation-slot, commit, tail, exclusive-Clear and job quiet-period policies remain.

**What “solver ready” means [source + CPU regression]:** blink waits for `rigReady`, which is resolved **before** `startSolver()` and the editor's control probe. The matching measured log was correlation under contention, not a direct promise dependency. ## Scheduler: bounded protection for shown I/O

**Cause:** `ef601ead` could make a lookup tail wait for exclusive Clear while Clear awaited that tail. Removing async-scope barriers solved those cycles, but also allowed much more ahead native work to be submitted during shown I/O. The decoder already had a special background queue for explicitly marked text/prefetch requests; ordinary creator CCO reads carried no lane and entered its normal FIFO. CPU grace alone cannot reprioritise an already-submitted native backlog. The second coordinator trace establishes that this is the remaining large delay.

**Design:** keep the cycle-free pump and add bounded grace for ahead reads while any wanted shown read is in flight. Every ahead CPU ticket records `notAfter = queuedAt + 50 ms` once. The pump admits it earlier if no shown read remains; new shown reads never move that ticket's deadline. At its deadline it competes normally by lane/FIFO, regardless of running jobs, tails, holds, dependencies or exclusivity. Ahead readers yield at 1 ms while shown reads are active, otherwise at the ordinary 8 ms. Slices remain cooperative: one indivisible scan/solve unit can overrun them. Only cooperative shown reads trigger grace, never a queued/running exclusive person job. Abort immediately withdraws a shown read's influence even if its callback has not returned; success/failure also release it in `finally`.

**Why no dependency wait-cycle can form:** a read's eligibility depends on its fixed monotonic deadline, not another operation completing. Even a shown → shared ahead lookup → stopped parent's tail → Clear chain cannot keep the lookup ineligible past that deadline. A grant holds no permit across I/O. Thus the scheduler adds no reverse completion edge to an operation waiting on the read. Finite ready work drains after bounded grace; continuously ready higher CPU work can still starve lower priority work, but a caller awaiting that dependency is not itself ready. As before, external I/O needs its owner's deadline/cancellation.

**Grace and trade-off:** retain the measured 50 ms CPU grace. The reverted 2000 ms experiment did not restore the short blink response; extending a CPU eligibility delay cannot fix requests already queued to the decoder. The native queue fix adds no worker heap, data copies, cache schema or completion dependency. Its trade-off is deliberate: queued ahead work finishes later while person/shown requests are waiting. One already-running request (and a cold worker's startup) remains non-preemptive and bounded by existing worker budgets. Installing a new worker for catalogue CPU remains a separate option if contention survives remeasurement.

**Regressions:** eight 5 ms shown I/O gaps finish at 40 ms with no ahead CPU admitted; ahead starts immediately when shown ends. A long shown read allows ahead at its original 50 ms deadline despite new shown activity, then enforces the 1 ms slice; ordinary slices return after shown ends. A shared ahead lookup joined by shown work and retained through a stopped parent's `afterwards()` drains before exclusive Clear and a later person job. Failure and abort on either side leave zero wake timers, including an abandoned shown callback. Prior occupied-slot/tail cycles, dependency reads in every parent lane, person holds, immediate person response and priority tests remain green. Admission-order tests now assert bounded grace as well as order; no browser/performance timing gate was changed.

### Early recovery and exclusive requester streams (merged in `1ddc24de`)

**Finding [source + real-host regression]:** a head's style update remains alive while another head prepares. Sharing a page-wide requester made B cancel A's host want; A's unknown-state poll then reissued A and cancelled B. Identity-equality tests did not exercise these concurrent lifetimes. `2f9b41fe`'s transaction recovery remains correct; its page-wide identity assumption was wrong.

**Ownership and invariant: at most one live want per requester ID.** `browser-scene-heads.ts` owns an exclusive incoming requester stream. Priming, no destination and cancelled construction do not replace this stream, so a later POST can supersede the obsolete host want. `startHeadDetails` acquires its lease: acquisition synchronously aborts the old lease, disposes its detail service and aborts its preload work before another service can send. A released old lease cannot revoke a newer one. When a newly constructed head becomes resident, it retains its stream and construction gets a fresh one before show exposes callbacks. Warm reuse retains the head's original stream. Concurrent resident/shown/incoming heads therefore have distinct IDs. Inside one service, `CharacterDetailActions` already aborts the previous transaction before starting another; the lease adds exclusivity across service replacements. Preloads retain a separate `-ahead` ID and one controller per device, tied to the head lease; their polling timer is now abort-owned too.

**Why no cancellation loop or wait cycle can form:** a shared ID can only move to a new service after its previous service is disposed, so the previous service cannot poll `unknown` and reissue a want. A shown A updating while B prepares holds a different requester, so neither replaces the other's host want. Lease transfer is synchronous revocation, not an asynchronous completion wait; it adds no scheduler dependency. Transaction-owned setup recovery is unchanged: it cannot publish the old failure, spend twice or outlive its signal. No new timer/fence is introduced.

**1. Warm core verification [source + real-host tests].** Every new host lacked the in-memory verification memo and asynchronously hashed about 20 MB in 256 KiB chunks. A completed full check writes a small atomic `preview-verified.json` receipt beside the cache manifest. It records manifest/asset generations (device, inode, size, nanosecond modification/change/birth times) and the mandatory record digest. Sync and async readiness validate the manifest identity, exact expected filenames, every lowercase 64-hex SHA-256 and positive safe-integer byte count before considering a receipt. They reconstruct generations from this manifest and never follow receipt paths. The current `xfs/preview-core-verified-2` receipt must exactly match that reconstruction; old-version, missing-binding, missing/damaged receipts and changed generations fall back to complete verification and are rewritten after success. An unreadable receipt write is advisory and only loses reuse. Eligible unchanged generations skip bulk hashing; the small `preview-core.json` record (about 4.6 KB) is always checked against its required manifest digest on readiness, memo and final HTTP validity checks. Record checks use a separate function with a required digest; missing record bindings also make in-memory generation validation fail. The first upgraded start pays one full verification for a v1 receipt; subsequent warm starts retain the fast path.

**Trust model (maintainer decision):** the core receipt accelerates a readiness claim; it does not establish rendering integrity. The trusted root is the host-produced derivation manifest under the existing source/status/recipe checks. The host always checks the record against that manifest, captures one response buffer, hashes it against the manifest-derived ETag and sends that exact buffer. The browser requires that strong content ETag, hashes the received record ArrayBuffer, and only then parses it; this also refuses unchecked cached record bytes left by an older host. It checks every received geometry/texture ArrayBuffer against the verified record before parsing or decoding. A lazy resource response or optimistic 304 therefore cannot make corrupted resource bytes render; the page checks the actual bytes it uses. Eligibility (positive device/inode, valid timestamps and finer-than-millisecond write/change precision) is only a first filter: a provider can synthesize ctime from mtime and pass it. Containment and final settings/generation checks remain. The post-frame full audit below withdraws stale bulk-readiness claims. This covers accidental changes to host-owned derived files, not malicious replacement of the trusted manifest and all matching content together.

**First filter [source + real-host regression, `843db594`]:** coarse/aligned, zero or missing generation fields still force hashing at receipt, memo and final HTTP checks, with no persistent reuse. Ordinary fine-grained NTFS metadata retains the cheap path. These checks detect ordinary metadata-changing edits, but the reviewer supplied a positive-ID/sub-millisecond provider whose ctime mirrors mtime. The new regression models that tuple, changes bytes without changing size, restores mtime, and deliberately demonstrates the initial fast readiness/304 before the second layer detects the mismatch. No further filesystem or provider detection is added.

**Second layer: one post-frame full verification [source + CPU/real-host regressions].** Readiness records internally whether it consumed a receipt or performed full hashes. Accepting a receipt also records an audit obligation per body/installation independently of the evictable five-second readiness memo. Another body's preparation can clear all memos without erasing this obligation; its completion before the frame notification therefore cannot suppress the audit. A full check fulfills the obligation; that body's own replacement/rebuild or core-service disposal retires it. The viewport sends `verify` through the existing preparation transport only after a head is shown and crosses two animation-frame callbacks; hidden preparation sends nothing. Hide, runtime/viewport release or application abort cancels pending callbacks, and an epoch guard refuses late callbacks. Page request cancellation belongs to `PreviewPreparationActions` and both bodies are notified at most once per page. The host independently admits at most one verification per body/session from the retained obligation; a full initial hash needs none. It uses the shared scheduler's cooperative **ahead** lane outside the preparation slot, hashes through existing 256 KiB async reads and takes cooperative turns between chunks. Success changes neither state nor receipt and does not repeat later. A disconnected page does not own or cancel the host's scan; core-service disposal, rebuild or replacement work does. Desktop shutdown passes its AbortSignal; localhost process cleanup disposes the same owner. No new timer or fence is introduced; the two pending frame callbacks are explicitly withdrawn on release.

**Mismatch and publication:** the service removes the receipt and writes a non-ready status only if the captured status still belongs to this generation. A newer published status is preserved. The host forgets readiness/check memos and enters its existing `prepare()` path when setup is usable and the preparation owner is free, returning ordinary `preparing` state and using the existing page poller. Missing setup returns the ordinary setup state; another body already preparing leaves the normal busy state, without suppressing this body's verification. The verification does not throw a bare background error. If receipt/status invalidation cannot be persisted, the session retains a force-hash flag until a successful ordinary preparation, so it cannot re-adopt the bad receipt in memory. Cancelled scans do not invalidate anything, close opened files in finally and leave no late publication. `settled()` also waits for preparation started by verification.

**Why this adds no wait cycle:** the scan holds no preparation slot, job tail, exclusive permit or page lease. Its cooperative read admission follows the existing fixed eligibility deadlines, not another job's completion. Filesystem reads and finite chunk hashing finish independently of the scheduler's preparation slot; repair begins only after the scan has returned from its cooperative scope. No reverse completion dependency is introduced. Ahead priority can delay background completion under demand; this is one deferred recheck, not a hard wall-clock deadline or periodic monitoring of edits made later in the session.

### Direct BCn evaluation (no implementation)

Native parsing already identifies cooked format, selected mip, placements and data bounds ([archive textures](../../knowledge/archive-format.md#10-textures-xbm)). A future port could return original validated blocks plus typed layout/colour/mip metadata rather than a PNG. Keep it behind native/game public ports, negotiate per renderer, version the resource record/cache identity and hash every transferred block resource. Do not bypass PNG fallback, page integrity or G2 admission.

| Cooked format | WebGL extension / format family | Windows ANGLE/D3D11 and layout implications |
|---|---|---|
| BC1 / DXT1, BC3 / DXT5 (BC2/DXT3 if encountered) | `WEBGL_compressed_texture_s3tc`; gamma variants require `WEBGL_compressed_texture_s3tc_srgb` | DXGI BC1/2/3 UNORM or SRGB families. Distinguish opaque versus one-bit-alpha BC1 semantics; the sRGB RGB format can be emulated by RGBA with non-opaque alpha. Do not infer alpha use just from a filename. |
| BC4 / BC5, including signed variants if present | `EXT_texture_compression_rgtc` | DXGI BC4/5 UNORM/SNORM. BC4 samples red, not the grey RGB PNG currently served: replicate explicitly for material consumers. Existing BC5 PNG is RG with B=0/A=255 and no Z reconstruction; retain the shader's XY/Z and green-channel convention. Use linear sampling for normals/data. |
| BC7; BC6H if later needed | `EXT_texture_compression_bptc` | DXGI BC7 UNORM/SRGB; BC6H signed/unsigned float. Choose the sRGB BC7 variant only from the record's colour semantics. BC6H is absent from the observed default V and needs an HDR policy rather than an RGBA8 assumption. |

The exact extension names and block/subimage restrictions are in [S3TC](https://registry.khronos.org/webgl/extensions/WEBGL_compressed_texture_s3tc/), [sRGB S3TC](https://registry.khronos.org/webgl/extensions/WEBGL_compressed_texture_s3tc_srgb/), [RGTC](https://registry.khronos.org/webgl/extensions/EXT_texture_compression_rgtc/) and [BPTC](https://registry.khronos.org/webgl/extensions/EXT_texture_compression_bptc/). [ANGLE's D3D11 format implementation](https://github.com/google/angle/blob/main/src/libANGLE/renderer/d3d/d3d11/formatutils11.cpp) represents these BC families. This is implementation capability, not a promise that a particular driver, feature level or Chrome policy advertises every extension: require `getExtension` and supported compressed formats; retain PNG/RGBA when unsupported or a resource/layout cannot be represented.

- **Channels/normal maps:** the observed native mappings are DXTNoAlpha -> BC1, DXTAlpha/Linear -> BC3, Normalmap/QualityRG -> BC5, QualityR -> BC4, QualityColor -> BC7. Preserve typed semantics for converted core maps, multilayer bakes, masks and CPU skin/decal reads. Generated/converted maps remain RGBA unless separately proven. CPU-read companions still need pixels; do not remove their decode just because GPU-only maps use blocks.
- **Orientation:** PNG rows are flipped relative to cooked XBM rows. Compressed block upload cannot use ordinary pixel-unpack row flipping. A sample-coordinate adaptation must preserve every material's UV, tangent/normal and decal/bake convention. Reordering blocks alone is not a general flip, especially for BC7/partial blocks; avoid recompression and prove parity before selecting an approach.
- **sRGB:** `isGamma` currently controls interpretation, not converted file bytes. Choose compressed sRGB formats exactly for those consumers; data/normal/roughness stay linear. BC4/5 have no sRGB flavour. A packed texture used with different semantics may need different views/resources; do not apply a global gamma conversion.
- **Mips:** first keep today's selected mip (largest at or below 4096) and sampling policy as the comparison baseline. Compressed textures require explicit validated mip levels with legal block-aligned subupdates, including tiny tail levels; no compressed `generateMipmap` substitute is assumed. Using original game mips may improve game fidelity but changes today's browser-generated chain, especially normals/alpha. Treat that as a separate visual decision, with byte/range bounds for each mip and a complete PNG fallback.
- **Cost/fidelity:** a 4096-square base level is 64 MiB RGBA8, 8 MiB BC1/4 or 16 MiB BC3/5/7; a full power-of-two chain is roughly 4/3 of that. Original blocks avoid PNG decode, CPU RGBA expansion and 4x/8x upload bytes without new compression loss. Hardware interpolation/rounding, sRGB filtering, alpha semantics, rows, channels and mip choice can differ from today's CPU-decoded preview. Closer to original game storage does not prove identical pixels or game shaders. This is a larger, separately reviewed native/protocol/material/upload track; proceed only after cropped-band measurement and capability/fidelity proofs.
