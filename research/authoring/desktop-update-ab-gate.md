# XF Studio private desktop A→B update gate — 25 September 2026

## Decision

Do not run Electrobun's native updater against the current installed canary or enable the Studio update capability. The installed 0.1.0 canaries have no `release.baseUrl`; their packaged `version.json` has an empty `baseUrl`, and the Windows setup/update artifacts are unsigned. Electrobun 2.0.1 does not add Windows signing during packaging. This machine exposes zero code-signing certificates in `Cert:\CurrentUser\My` and `Cert:\LocalMachine\My` (certificate **count** only was inspected). A private HTTPS host and a code-signing identity with a trusted verification path have not been established. No feed, installer, game/MO2 target or existing Studio identity was changed for this gate.

The [2.0 updater API](https://framework.blackboard.sh/electrobun/apis/updater/) supports separate `checkForUpdate()`, `downloadUpdate()` and `applyUpdate()` calls on this Bun main runtime. It says `applyUpdate()` consults `before-quit`, uses a post-exit helper for transactional replacement and restores the prior app after failed replacement. The [hosting guide](https://framework.blackboard.sh/electrobun/guides/updates/) requires a base URL embedded in version A, describes canary update metadata and full-archive fallback after a missing/broken delta, and expressly calls the bundle hash a routing identifier rather than a content-authentication mechanism. The [signing guide](https://framework.blackboard.sh/electrobun/guides/code-signing/) says Hutch does not currently sign Windows releases. Those are framework claims, not observations of Studio's A→B path. Our fake-port tests prove only the host's three consent transitions and fail-closed unavailable state.

Signing the setup executable alone would leave the downloaded tar containing Bun code, views and build tools unauthenticated. The signed trial must bind the **exact update archive bytes** to an independently verified publisher identity, with a signed manifest or equivalent authenticated release envelope, and verify that binding before native apply. HTTPS and the Electrobun hash alone do not meet that gate. The present native adapter supplies no such pre-apply verification hook, and the update service's `signedRelease` flag is caller-provided evidence, not verification. Do not set it true because a test double passes. Establish and test a way to inspect the native updater's prepared archive and reject an untrusted candidate before wiring the adapter into the real main process. If 2.0.1 cannot expose that safely, use an independently verified replacement mechanism or keep automatic updates disabled.

## Isolated signed trial, once the prerequisites exist

1. Reserve a new disposable app name and identifier, separate from `dev.axefrog.xf-studio`, every prior UI/Build trial identifier and all regular channel roots. Keep **the same** trial identifier, `canary` channel and private HTTPS base URL in A and B. Version A and B must have distinct semantic versions and bundle hashes. The feed must hold only this trial's artifacts, be access-restricted, and keep the A full archive plus any A-hash patch. Never repoint an existing installed identity at the feed.
2. Build A and B from reviewed source with the pinned Electrobun 2.0.1/Hutch toolchain. Run the existing asset-free allowlist gate on both setup ZIPs and update archives; record exact SHA-256 values, packaged `version.json` and `update.json` identity/channel/version/hash/base URL agreement. Keep installer, archive, feed staging, signed manifest, logs and any test certificate material in ignored private locations. Do not include preview assets, SQLite, settings, credentials, game resources or MO2 data.
3. Apply Windows Authenticode signing to the relevant setup and executable payloads, verify their publisher chain and timestamp under the selected release policy, and sign an envelope containing the exact B archive digest, length, version, channel and trial identifier. Verify the envelope and archive against a pinned publisher key before `applyUpdate()`. A wrong publisher, changed archive, changed metadata or unexpected redirect must stop before restart. Record the signer thumbprint and digest, never a private key. Prove the verification step also covers delta-chain output or require a verified full archive. Use an actual trusted release signing process for release evidence; a disposable test certificate can exercise mechanics but cannot establish public publisher trust.
4. Install A as an ordinary Windows user without elevation. Inspect the actual program, update workspace and `Utils.paths.userData` roots. In its isolated data root, create a synthetic SQLite collection revision, distinct normal and `?verify=1` workspace selections, a settings change and a synthetic resumable transaction journal. Hash/copy those records for comparison. Never borrow Nathan's real library or source bindings.
5. With network blocked, show A's installed version/build identity from packaged metadata, no update, usable data and no implicit check. Restore the private feed. Trigger **Check** in the view and confirm only a check request; trigger **Download** separately and confirm archive verification and `ready`; trigger **Apply and restart** separately. Before native apply, block on active edit flush and build/install transactions. The current close-flush handler covers native window close, not an accepted updater restart; the current `before-quit` callback stops the host and is not evidence of a saved update restart. Implement and exercise a dedicated synchronous veto plus acknowledged save/drain path first.
6. After relaunch, inspect the installed **B** identity, executable signature, unchanged isolated user-data root, SQLite revision and settings/workspaces, and a recoverable journal. Compare exact bytes or logical database contents as appropriate. Confirm the old app did not run after a successful B launch. App-only uninstall must preserve those data; explicit app-plus-data removal must remove only this disposable identity.
7. On a fresh A install/snapshot for each fault, repeat with an unavailable feed, interrupted download, deliberately missing patch (expect full-archive fallback), corrupted archive/signature (expect pre-apply refusal), forced replace failure (expect Electrobun's prior-app restoration), denied `before-quit`, failed workspace save and offline restart after B. Record version on disk, version actually relaunched, update status history, feed requests, user-data hashes, error shown in the view and any orphaned staging. A test that merely throws from the fake port does **not** prove rollback.

Only after this matrix passes on a standard-user account and the actual Studio host exposes busy-transaction and save vetoes should the production composition root instantiate the native adapter and mark trust gates accepted. The capability and consent controls remain off in all ordinary builds until then. No public release or game runtime claim follows from this trial.

## Evidence and limits for this checkpoint

The existing focused Bun update tests passed: two tests, 13 assertions. Source inspection confirmed `main.ts` never imports `update-electrobun.ts`; `createDesktopServer()` receives no trial port, `host.ts` reports `updater: false`, and the canary artifact verifier rejects any nonempty packaged `baseUrl`. No native update request, archive download, replacement, rollback, installed A→B or standard-user test occurred here. The framework pages are current documentation consulted on 25 September; the application dependency is pinned to 2.0.1, and the source-level test of its Windows helper remains part of the signed trial.
