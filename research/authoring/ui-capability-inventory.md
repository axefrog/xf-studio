## Status vocabulary and data boundaries

- **Working:** available in the local editor and checked offline or in the isolated browser. It does not imply accurate REDengine output.
- **Preview study:** a usable browser experiment with visible limits; the game compiler may reject it.
- **Local package candidate:** archive and ArchiveXL declaration passed independent structural verification but have not been installed, rendered or tested for selector switching in game.
- **Queued:** known need or expansion area, not a control the redesign should pretend works. Later authoring categories require discussion with the maintainer before implementation.

Four separate kinds of state must stay intelligible. A **portable recipe** contains makeup layers only. A **portable collection** contains named presets and stable identities. **SQLite** stores explicit immutable collection revisions with conflict protection. The **browser workspace** autosaves the unsaved draft, selections, Undo, viewing state and decoded V locally. Preview quality and camera are workspace preferences, not recipe history or export quality. Exported build plans are compiler inputs, not installable mods. The current `?verify=1` URL has isolated draft and library storage for tests; do not use the active working draft as a design fixture.

## Work a user can do now

### Collection and library — working

Create a collection; name it; add, copy, select, rename, reorder and remove presets. A preset can hold an empty layer stack. Switching preserves each preset's unsaved recipe, active layer, selected point/field and up to 80 recipe Undo states. A removed preset can be restored from the last 20 retained removals, including after reload. Opening or importing another collection can be reversed to the preceding draft; this is a different recovery action from recipe Undo. An empty collection can be edited but cannot be exported or built. Preset IDs remain stable across rename and reorder, and SQLite tracks per-preset versions separately from collection order changes. [Collection session](../../projects/xf-studio/authoring/src/collection-session.ts), [operations](../../projects/xf-studio/authoring/src/collection-workspace.ts), [storage](../../projects/xf-studio/authoring/src/collection-store.ts).

Save an atomic collection revision to the local SQLite library, or save a copy under a new collection identity. Browse/refresh saved collections and open one deliberately; opening must not silently discard a draft. Concurrent windows cannot silently overwrite a newer revision. During a save, edits can continue and remain in the draft even though the saved snapshot is immutable. SQLite history is retained internally, but a revision browser/restore and a backup/restore UI are **queued**. Browser draft autosave is separate from explicit SQLite save. Legacy look revisions survive the database migration unchanged. Collection files can be imported within a 16 MB budget; a recipe JSON within 1 MB can be imported as a **new preset** without replacing the rest. Export a single editable recipe; export a collection or build plan after saving an immutable snapshot. Import and export validation must explain invalid/future schemas and keep the existing draft. [Collection service](../../projects/xf-studio/authoring/src/collection-service.ts), [portable format](../../projects/xf-studio/authoring/src/preset-collection.ts).

### Layers and composition — working

Add, duplicate, rename, select, enable/disable, reorder, reset and remove layers. Zero layers are legal; 32 is the present preview/import budget, not a product limit on presets. Layer IDs survive rename and reorder. Recipe order is bottom-to-top; frontmost rendering is the last enabled layer. Undo restores structural edits, including removal of the last layer. A disabled layer remains authored and may intentionally be exported as an individual mask, but it does not contribute to a package. Do not turn the historical four-layer prototype into a fixed product count. The original Eye Artistry designs and IDs are references, not a compatibility target. [Layer operations](../../projects/xf-studio/authoring/src/layer-stack.ts), [recipe validation](../../projects/xf-studio/authoring/src/recipe.ts).

Each layer owns its name, visibility, base colour, opacity, finish, mirror setting, one closed contour, point pigment, edge softness and zero to eight displacement fields. The mask is a coverage result independent of colour. Shape guides describe the contour **before** warp; the rendered makeup reflects warp. There is currently one contour per layer with 3–24 points. Multiple contours, holes, group-level composition, layer isolation and layer blending controls are plausible future growth, so shape and layer concepts must scale rather than be hard-coded to the present count.

### Shape, pigment and warp authoring — working

Select, move and remove contour points, with a minimum of three; insert near the closest curve section, including the closing section and mirrored instance. Newly added and reset layers start with four Bézier contour points in a compact upper-lid wash; duplicate retains the source shape. Imported older recipes retain Catmull–Rom geometry until an explicit, undoable Bézier conversion. In Bézier mode each point can have incoming/outgoing tangent arms and Smooth (aligned, independent lengths), Symmetric (opposite equal lengths) or Corner (independent) behavior. Splitting a Bézier section retains its analytic curve, although raster tessellation can produce small edge-pixel differences. A tangent arm can cross an eye opening: it is a vector guide attached to its parent point, **not** a surface anchor. It appears on the head only when that parent is visible/front-facing; actual contour points remain surface-constrained. Extreme valid handles may cause long jobs or expensive guide rebuilding and need honest busy/cancel/error feedback. [Bézier contract](../../research/authoring/projected-tangent-controls.md).

Set a point's pigment strength independently of edge softness. New layers use continuous boundary blending, with an adjustable point-blend distance; historical layers retain legacy nearest-section strength until explicitly upgraded. A zero-strength point is not a guarantee of zero pigment at that exact location, because neighboring strengths mix. Set one uniform edge-softness width or enable per-point widths that interpolate along the boundary. Switching back to uniform retains authored per-point widths for later re-enabling. Point weights, handles and softness interpolate on insertion and transform with a shape. Separate addable softness-field anchors are explicitly **on hold**. [Pigment](../../projects/xf-studio/authoring/src/pigment-edit.ts), [softness](../../projects/xf-studio/authoring/src/softness-edit.ts), [directional-softness contract](directional-softness-contract.md).

Add, select, edit and remove up to eight warp fields per layer. A field has a stable ID, origin, displacement vector and Gaussian reach. Its influence fades beyond the indicated reach; it is not a hard cutoff. Fields add their displacement at the original sample coordinate, so overlap is smooth and a zero-vector new field changes nothing. Reset a selected field's vector without removing its origin/reach. Fields may strongly fold the mask; they do not deform the head geometry. Field selection is editor memory, while field values are in the portable recipe. [Recipe actions](../../projects/xf-studio/authoring/src/recipe-actions.ts), [multiple-warp contract](../backlog/path-and-falloff-controls.md#multiple-warp-field-controls--requested-23-september).

Translate, rotate and scale the entire active shape in UV space. Rotation/scale pivot at the selected contour point. Spatial softness and pigment-blend widths, warp origins/vectors/reaches and Bézier handles transform coherently; invalid whole-shape proposals are rejected atomically rather than clamping and deforming individual points. Mirrored editing maps back to the canonical authored side. Continuous drags and short scale-wheel bursts create one Undo step; Escape, pointer cancellation and focus loss roll back an active gesture. The pure transform operation exists, but gesture start/stop and stale-context protection still live in view adapters. [Gesture contract](shape-gesture-contract.md), [pure transform](../../projects/xf-studio/authoring/src/shape-transform.ts).

### Editing spaces and inspection — working

The same contour, tangent and warp data can be edited in UV or directly on the deforming head. UV can show both eyes, one eye, switch sides, fit the authored shape/fields/handles, pan and zoom; its crop and side persist without entering recipe Undo. Face guides follow morphs, full skin weights and idle/blink. Surface picking rejects far-side/occluded controls and missing UV coverage; moving back into a valid region resumes an interrupted drag. Actual points/fields retain plate constraints. Transparent brow/lash cards do not hide guides, but opaque head/eye depth does. The 3D view orbits, pans, zooms, resets to a front framing and can show/hide surface controls or plate wireframe. Camera operations are workspace state. Surface-distance falloff, overlapping UV islands on arbitrary future meshes, layer isolation and pen-specific interaction are **queued**. [UV](../../projects/xf-studio/authoring/src/uv-editor.ts), [surface](../../projects/xf-studio/authoring/src/surface-editor.ts), [surface constraints](projected-tangent-controls.md).

### Colour and optical behavior — working selection, mixed preview maturity

Seven distinct finish families can be chosen: Matte, Satin (`regular` internally), Shimmer/pearl, Metallic/foil, Glitter, Glossy/wet look and Colour-shifting. Metallic must remain its own semantic class rather than an alias for Shimmer. Colour, opacity and shape are independently editable. These finish names describe intended cosmetic appearance; browser shaders have not been proven equivalent to the game's materials. Shimmer, Glitter, Glossy and Colour-shifting are **preview studies** and have no production game adapter. The local package filter omits active unsupported layers and names each omission; the compiler itself still rejects those finishes if passed directly. Matte, Satin and Metallic have a provisional flat game adapter and are allowed in local package candidates. Finish taxonomy and engine mapping may grow, so present it as extensible data with fidelity/export status, not a closed set of special-purpose switches. [Taxonomy](../materials/makeup-finish-taxonomy.md), [package filter](local-package-build.md).

Shimmer and Classic Glitter expose seeded flake fineness/density/orientation controls. Glitter additionally has versioned browser models: Classic reflective map; irregular raster facets with count, size, variation, orientation and independent facet colour; direct-light glints; clustered fine glints; and denser fine speckles with density, fine-facet share, strength and independent colour. Model changes are undoable. The selected model and its settings are portable; settings remembered while comparing **other** models are browser-workspace memory and do not travel with the recipe. Historical model versions retain their original look. Generated candidate counts are **not** visible sparkle counts. Dense raster facets are restricted to known eye UV regions and may be rejected outside them; 4K irregular output exceeds the current resource budget. Direct-light variants use the mask worker but calculate glints in the browser shader. None is a validated match to the supplied reference photographs or an exportable REDengine Glitter. [Browser studies](../materials/fine-speckle-browser-study.md), [direct study](../materials/direct-glint-browser-checkpoint.md).

### Preview character and motion — working context with fidelity limits

Read a local `sav.dat` in the browser, apply supported female facial morphs and eye shape to the head/plate/details, and report which references matched local assets versus remaining unresolved. No raw save bytes are retained or uploaded; decoded appearance choices persist in the browser workspace and can be exported as appearance data. A later eye-shape override persists without changing the original imported data. One specifically researched saved Kala eye diffuse can load from an ignored, hash-verified local manifest; unmatched selections fall back to the reference eye instead of leaving a stale texture. An opt-in source eye-roughness study exists for the matched eye. Normal/roughness interpretation, refraction and full effective archive-winner resolution remain open. [Save reader](../../projects/xf-studio/authoring/src/save-reader.ts), [eye evidence](../../research/eye-artistry/eye-preview-adapter-plan.md).

Independent visibility controls exist for brows, lashes, matching saved-V hair and piercing context. Brows/lashes are saved-reference preview assemblies, with more faithful brow alpha/gradient and approximate lash colour; they are **not** authoring tools. Saved-V hair is available only for an exact locally resolved hash and definition, with approximate browser shading and no physics. Piercing preview includes vanilla female choices and a private PRC slice/combined bank; the selected style/colour is **viewport-only** and never changes the imported V. Optional local assets can be missing, mismatched or unavailable individually without blocking eye-makeup work. Resource origin, approximate material status and missing dependencies need visible diagnostics. A full saved-V assembly and provider-neutral MO2/Vortex/manual resolution are queued. [Hair](../../research/eye-artistry/saved-v-hair-preview.md), [piercings](../../research/jewellery/prc-preview-slice.md), [roadmap](../backlog/jewellery-and-customization.md).

Control vertical field of view (10–90°), camera orbit/target/distance, exposure and key-light angle; use normal-map and eye-optics study toggles for diagnosis. FOV adjustment attempts to preserve the viewed face area's scale within camera bounds; when it cannot, report the limitation and offer a known framing reset. The game's FOV convention is not calibrated to this viewer. Preview-quality preferences choose 512, 1K, 2K or 4K for **generated masks and optical maps**, independent of recipe, history and 2048² mask export. Show aggregate memory estimates, capacity/hardware limits, per-layer progress/readiness and retry after failure. Keep last **complete** preview visible while new work computes; do not claim stale or partially published layers are ready. Disabled slots use tiny placeholders. [Preview-quality contract](preview-quality-contract.md), [camera behavior](camera-zoom-design.md).

An extracted female character-creator close-up body clip and offline-solved facial motion can play as a preview. Enable/disable idle; pause/resume at the current phase; independently include head movement and facial movement. Muting both holds the editing pose while preserving phase; turning idle off resets its pose/time/pause but remembers the two contribution preferences. A separate synthesized eyelid-closure slider/Blink study applies while idle is off. Do not present the separate stronger `ui_closeup_shot_eyes` clip as proven default game idle. Exact live graph timing, wrinkles and game material motion remain open. [Idle guide](../../docs/idle-animation-guide.md), [brow motion gap](../animation/brow-idle-gap.md).

## Programmatic application contract required before the redesign handoff

The [source-audited action catalogue](ui-action-catalogue.md) now distinguishes exact implemented command IDs, read-only state and capability queries from missing wrappers. Collection/library, recipe/layer, gesture transactions, preview, quality, motion and saved-V services have been extracted, but there is still no single broad application registry. At the time `main.ts` still coordinated renderer jobs, file/download adapters and some view/persistence details; that shell has since been retired and the one composition root is `studio-startup.ts`. The redesign should consume a completed contract; it must not silently implement domain behavior in its controls. [Architecture checkpoint](ui-architecture-boundary.md), [handoff gate](../backlog/claude-ui-overhaul.md).

Capability queries must use **target identity and context**, not only a global selection: for example, a context menu over an inactive layer should be able to offer Duplicate or Move without first mutating the active layer.

Current gaps after the extractions are listed precisely in the [action catalogue](ui-action-catalogue.md#remaining-contract-work-and-expansion): a unified registry, complete target-aware capability queries, high-level point/field/shape and view commands, file/download and job-state ports, consistent transaction/error contracts, and persistent dock/theme services. The core must remain responsible for recipe migration, exact raster evaluation, SQLite revision rules, save parsing, asset resolution and compiler eligibility.

## Context-menu and scenario acceptance

Context menus must support target-aware actions for collection, preset, layer, point, tangent, warp, shape interior, empty UV space and viewport background. Native text editing menus remain available in inputs and editable text; ordinary browser menus are suppressed on non-text studio surfaces without breaking right-drag pan. Menus should use the same action catalogue and disabled reasons as any other affordance. Keyboard and screen-reader equivalents must exist for operations that otherwise require a pointer. Opus decides the visual and workflow treatment.

1. Start with an empty collection, create two presets with different layer counts, rename/reorder them, switch repeatedly, edit each and reload. Names, IDs, draft contents, selection and each preset's Undo must remain coherent; saving makes a SQLite revision without swallowing edits made during an in-flight save.
2. Import a legacy Catmull–Rom recipe as a new preset. It retains its old mask; explicitly convert one layer to Bézier, split a curve and Undo. The rest of the collection and old SQLite revisions stay unchanged.
3. Edit a point, tangent, per-point pigment and softness, then add overlapping warp fields on one eye and manipulate the mirrored copy. UV and head show the same authored result; Escape cancels a gesture and a completed gesture uses one Undo. A tangent may cross the eye hole while its parent remains the real anchor.
4. Move/rotate/scale a whole shape with a selected pivot, then pan/zoom the UV and change camera FOV. Whole-shape edits affect the recipe and Undo; navigation does not. Crossing a shape bound rejects the whole proposal. Reload restores the viewing frame.
5. Compare all five Glitter models, change facet colour independently from base pigment and switch away/back. Only the active model/settings travel in a recipe; other remembered choices remain local. Inspect clear preview-study language. A package preflight names the active unsupported Glitter layer and omits it from the package-only copy; a flat candidate remains possible if exportable content remains elsewhere. The authored recipe is unchanged.
6. Load a local V, inspect matched versus unresolved eye/brow/lash/hair/piercing resources, set a viewport-only piercing choice, pause the idle, move the camera and reload. Decoded V and view context restore; the original save and makeup recipe do not acquire the temporary piercing choice. Missing local assets degrade transparently.
7. Choose 4K preview quality and trigger a hardware/budget failure or cancelled replacement. The last complete layers remain identifiable, stale layers never claim readiness, and retry is available. Mask export remains 2048² and collection revisions remain unchanged.
8. Save and export a collection, inspect the build-plan distinction, then build a package from an unsaved rename. The manifest identifies the captured snapshot; SQLite retains its prior revision and the result is labelled uninstalled/unverified. Closing the page is not shown as successful cancellation of a server build.
9. Open a different collection, use Undo collection open, remove/restore a preset, and recover from malformed future workspace data. No path silently overwrites the original draft. Conflict on concurrent SQLite save gives a specific recovery path.
10. Dock, float, magnetize and tab panels, save/reload layout, and perform the equivalent moves by keyboard. During dragging, only cursor location selects a docking target, even when a large panel overlaps other panels.
