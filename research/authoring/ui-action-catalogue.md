# XF Studio action and capability catalogue for the UI handoff

**Desktop update gate, 25 September.** `GET /api/desktop/update` returns a detached `xfs/desktop-update-1` snapshot with installed version/channel/hash, optional checked update, phase, disabled reason and separate `canCheck`, `canDownload`, `canApplyAndRestart` capabilities. `POST /api/desktop/update` accepts only `{schema:"xfs/desktop-update-action-1", action:"check"|"download"|"applyAndRestart"}` after the existing session and same-origin write checks. Each dispatch is explicit user consent for that one stage; `applyAndRestart` additionally asks in the desktop About view. The trusted host owns the feed, signing and trial gates; the browser cannot supply an update URL, path or hash. No action changes a recipe, Undo or SQLite revision. Production is disabled pending the recorded acceptance gates; the host test exercises refusal and the pure two-version harness exercises the transition policy. [Service](../../projects/xf-studio/authoring/desktop/update-service.ts), [host tests](../../projects/xf-studio/authoring/desktop/tests/update-service.test.ts).

**Desktop shell extension, 25 September.** The private Electrobun host exposes `GET /api/desktop/capabilities` only behind its loopback session cookie. Its detached read-only snapshot reports packaged `version`, `channel` and `buildHash` from `Resources/version.json`, the shell's `userDataPath`, preview-asset presence, package Check support and explicit `false` for package Build, installation and updater. The desktop-only About control and missing-assets first-run state consume that snapshot; they have no recipe/Undo effect and no writable path action. The endpoint rechecks preview-asset presence on each read. An unavailable host or invalid packaged metadata fails visibly rather than borrowing a source `package.json` version. The localhost entry has no desktop About/update action. Desktop `package.check` snapshots unsaved work through the existing file workflow; its host validates and compiles in a fresh Bun worker with a 15-second deadline, one active Check at a time, and a complete result or typed error. It never changes the recipe, history or SQLite revision. [Host contract](../../projects/xf-studio/authoring/desktop/host.ts), [transport test](../../projects/xf-studio/authoring/desktop/tests/server.test.ts), [packaging gate](../../projects/xf-studio/authoring/desktop/verify-canary.ts).

24 September 2026. This is a source audit of the **current in-process API**, not a promise that every capability is already one public command. It complements the [functional inventory](ui-capability-inventory.md) and [Opus handoff brief](../backlog/claude-ui-overhaul.md). The command strings below are exact implemented `kind` values unless a section explicitly says **missing/proposed**. They are TypeScript application boundaries, not an HTTP scripting endpoint. A new UI should preserve validation, Undo, persistence and results through these boundaries; it should not mutate a snapshot, invoke a hidden DOM button or write SQLite directly. `StudioApplication` now aggregates `snapshot/subscribe`, exact action/request/gesture descriptors, `actionsFor` and `descriptorsFor(target)`, `capability/dispatch`, `contextCapability(target,action)` for concrete target/payload checks, `choicesFor(target,kind,field,base?)` for enumerated choices with current capability, `requestCapability/execute`, and explicit control/gesture transactions. The registry covers all 60 implemented public top-level action IDs, nine async request IDs and four low-level gesture proposals at compile time. A descriptor identifies payload types, required fields, target versus input sources, nested variants, static limits, scope and Undo/async policy; it does **not** predict every final parser constraint. Renderer-supplied piercing labels/definitions are now a detached application snapshot; other dynamic asset choices still need similar ports. The service-specific contracts below remain authoritative.

**Guidance actions, 25 September.** Tours are presentation state, not document state. `GuidanceService` ([engine](../../projects/xf-studio/authoring/src/studio-ui/guidance/engine.ts)) publishes a detached snapshot and takes five actions (`GUIDANCE_DESCRIPTORS`: scope `guidance`, effect `view`, Undo `none`):

- The snapshot holds `active` (tour, step index and count, content, a target of `anchor`, `panel`, `offer` or `none`, and buttons with capabilities), the `last` outcome and a `revision`.
- `guidance.startTour {tourId}`, `guidance.next`, `guidance.back`, `guidance.skip` and `guidance.finish`. `back` is refused on the first showable step and `finish` before the last.
- Tour buttons carry ordinary commands from this catalogue (actions, file workflows, `previewSetup.*` and the dock's panel reveal) and go through the same validated paths, so they never bypass validation or Undo.
- `tours.record {tourId, outcome: completed|skipped|declined}` is a UI preference action; it never touches a recipe, Undo or SQLite.
- `port.links.open(link)` opens a named public page (`project-knowledge`, `project-issues`, `project-releases`); the host maps the name to its URL.

See [feature-module platform §6a](feature-module-platform.md#6a-guidance-tours-spotlights-and-help-v1-built).

**Feature facades, live documents and look transactions (step 5, 26 September).** See [step 5 status](feature-module-platform.md#step-5-status).

- `port.features()` lists the registered feature modules (`{id, label, stage}`, catalogue order). `port.feature(id)` returns that feature's facade: `kinds()`, `capability`, `dispatch`, `limitsFor` and `choicesFor` over **its own** kinds (another owner's kind is refused with `invalid_value`), and `editable()`, which refuses with `unavailable` and a plain reason while the selected look holds a newer build's data. Eye makeup's facade adds `view()` (the cached editor view that was `port.editor`), `controlBegin/Edit/Commit/Cancel`, `layerExport`, `finishCatalogue` and `glitterModelCatalogue`; any other feature's `view()` is a detached `{part, editor}` of its live document.
- Every registered feature beside eye makeup has a live document for the selected look; a feature without a bespoke handler runs its registered `capability`/`apply` over it and records one `part` step by its Undo policy. The trusted `app.transaction(label, features, fn)` records one `look` step for everything `fn` dispatches to the named features; it leaves no step when nothing changed, reverts without Redo when `fn` throws or returns a failure, and refuses (`busy`) inside a gesture, a form control or another transaction. Inside it, Undo and any other owner's action are refused with `busy`. No presentation action uses it yet; tests compose a synthetic second feature (`tests/look-transaction.test.ts`).
- **Locked looks.** A look holding a newer build's data is kept verbatim and locked. Every feature action, gesture, form control, look transaction and `recipe.export`/`mask.export` on it is refused with `unavailable` and the reason; collection edits on it still work. `library.summary()` marks it `locked: true`; `save`/`saveCopy` are refused while the draft holds one; `package` omits it with "It was made with a newer version of XF Studio."

**Action registry and owners, 26 September.** Every action above is registered by exactly one owner in `STUDIO_REGISTRY` ([composition list](../../projects/xf-studio/authoring/src/compose/studio-registry.ts), [registry](../../projects/xf-studio/authoring/src/platform/core/registry.ts)). This is step 1 of the [feature-module platform](feature-module-platform.md#step-1-status).

- **Owners.** Six system families (`history`: `history.undo`, `history.redo`, `history.jumpTo`; `collection`; `preview`: `camera.*` and `preview.*`; `motion`; `quality`; `savedV`) and one feature module, `eye-makeup` (every recipe action plus `layer.edit` and `layer.setEnabled`).
- **IDs.** Kinds stay flat. A kind's qualified ID is `<owner>/<kind>`, e.g. `eye-makeup/layer.setColor`. Step 5 renamed the Undo port: `recipe.undo`/`recipe.redo` are `history.undo`/`history.redo`, and the Undo policy of a feature action's look-history step is `part` (was `recipe`). No stored data names an action kind or an Undo policy.
- **Derived.** `actionKinds()`, `actionDescriptors()`, `registry()`, `descriptorsFor()` and every Undo policy come from the registry, in registration order (`tests/golden/studio-registry.json`, which differs from the step-1 capture by exactly the step-5 rename).
- **Spec fields (step 5).** A spec carries its inputs' `units` (system families and features) and a feature spec its state-dependent `limits` and its `consequence` override, so `limitsFor` and `consequences` read the registry instead of the retired `action-limits.ts` tables (`tests/spec-fields.test.ts`, golden captured before the move).
- **Unknown kinds.** A kind no owner registers is refused with `invalid_value` ("Unknown command.") by `capability`, `contextCapability` and `dispatch`; it is never routed to another service.
- **Reason codes** are chosen by the check that refuses. A validation issue implies its code (`range` → `limit`, `mode` → `incompatible_mode`, `required` → `needs_input`, otherwise `invalid_value`). No code is read from message text.

## How to read and query the current API

For a replacement presentation, obtain `StudioPresentationPort` from the trusted composition root. Its grouped `authoring`, `library`, `files`, `viewport`, `preferences`, `localSetup`, `installDetection`, `previewSetup` and read-only `previewReadiness` surfaces are the current callable contract; `snapshot()` combines detached state and `subscribe()` covers all six sources. Readiness reports `ready`, `updating` or `blocked` from current worker/resource state, not merely the selected resolution. The port forwards actions to the existing validators and does not expose the authoring document, renderer, worker or storage transport. The one composition root, `studio-startup.ts` (started by the localhost entry `studio-main.ts` and by the desktop bootstrap), constructs it and passes it to `studio-ui/`; `tests/trusted-studio-bootstrap.test.ts` also mounts it with no page controls. [Composite port](../../projects/xf-studio/authoring/src/studio-presentation.ts), [independent browser acceptance](ui-port-acceptance-2026-09-24.md).

A menu can pass the actual hit layer ID to `choicesFor({kind:"layer",id}, "layer.setFinish", "finish")`; each finish value carries a candidate action and current structured capability. For a form or keyboard command with a concrete value, call `contextCapability(hitTarget, action)` before showing/enabling it, then call `dispatch(action)` when invoked. The latter validates again in case the document changed. A missing required value returns `needs_input`; a mismatched hit target returns `missing_target`; a value outside a declared range returns `limit`. `capability(action)` itself applies the same payload types and ranges, so `dispatch` and `controlEdit` refuse out-of-range values too. An exception after that gate is classified by its owner: a collection service code, the family's declared code (`unavailable` for the preview, motion and quality devices), `internal` for a programming fault, otherwise `invalid_value`. These checks do not turn the static schema into a complete parser or discover whether a coordinate hits the shape.

**Cheap read-only views (added 24 September for the redesigned presentation).** `port.feature("eye-makeup").view().recipe()/layer()/active()/selected()/selectedField()/revision()/canUndo()` (the port's `editor` until step 5) read the cached detached editor view; `library.summary()` returns a primitive projection (collection id/name/revision, presets with live layer counts, removal stack, previous draft) without cloning histories; `authoring.previewState()` returns preview/motion/quality/saved-V/gesture/control state without the document or collection; `authoring.finishCatalogue()` and `glitterModelCatalogue()` return labels, descriptions and export status mirroring the compiler gate; `port.status.snapshot()` reports browser autosave, preview asset diagnostics, Glitter measurements and the latest adapter message. Use these for painting; `snapshot()` clones every Undo history and is for diagnostics. The custom target-aware context menus, command palette, dock/float/magnetic/tab panel system and theme preference are now implemented in `src/studio-ui/` ([delivery record](ui-overhaul-2026-09-24.md)).

For current context-menu hits, `ViewportAttachment.contextAt(source,clientX,clientY)` uses the existing UV or on-head editor picker and calls `StudioApplication.contextQuery(hit)`. It returns the source, mirrored instance and visual affordance, plus a bound context for `uv-empty`, `head`, `shape`, `point`, `tangent` or `field`, relevant **existing** command candidates and each candidate's current capability. Layer, preset and collection rows can call `contextQuery` directly with their stable IDs. Input candidates carry `requiresInput:true` and a command/variant ID; after collecting a value, call `boundActionCapability(context, action)`, then `dispatchContext(context, action)`. Dispatch rechecks the target, collection/preset identity, geometry revision for layer/shape/point/tangent/field hits, payload, domain capability and final parser. An unrelated command or a stale bound context is refused. Empty UV space has no standalone edit command yet; pan/zoom and coordinate-based insertion remain adapter gestures, so the query returns no invented action. Pickers classify most specific first: a visible control of the selected layer (on-head only while surface controls are on), then painted makeup (the selected layer, then the frontmost other visible layer, so a right-click on another layer's makeup offers *Select this layer*), then bare character geometry (`head`: skin, eyes, plate or another visible detail, never makeup hidden behind them) or `uv-empty`. Only a position with no geometry at all (or outside the canvas) is no hit, the true background. This is read-only hit discovery, not a menu UI or a second geometry evaluator. [Viewport attachment](../../projects/xf-studio/authoring/src/viewport-attachment.ts), [hit context builder](../../projects/xf-studio/authoring/src/studio-context-targets.ts), [facade](../../projects/xf-studio/authoring/src/studio-application.ts).

## Exact commands: collection, preset and library

`CollectionAction` targets the **current draft**. `preset.edit.command` is a nested discriminated union; its inner `kind` is not a top-level command ID. IDs are UUIDs. Collection edits do not create a recipe Undo entry; preset removal has its own last-20 recovery stack, and opening/importing a collection has a separate four-draft browser recovery queue. Switching presets stashes the recipe, selected layer/point/field and up to 80 recipe Undo entries for the outgoing preset. [Collection session](../../projects/xf-studio/authoring/src/collection-session.ts), [workspace operations](../../projects/xf-studio/authoring/src/collection-workspace.ts).

| Exact action/payload | Target, result and capability/validation |
|---|---|
| `preset.edit` `{command:{kind:"add"}}` | Collection; add empty preset with fresh stable ID, select it. No explicit fixed preset cap. |
| `preset.edit` `{command:{kind:"copy"|"remove",id}}` | Named preset ID. Copy gets a new ID; remove can be restored. Missing ID disables. |
| `preset.edit` `{command:{kind:"rename",id,name}}` | Named preset ID; trimmed, nonempty name up to 120 characters is validated at dispatch. |
| `preset.edit` `{command:{kind:"move",id,to}}` | Named preset ID and zero-based destination in current order. Invalid index or stale ID disables. Stable ID survives reorder. |
| `preset.edit` `{command:{kind:"restore"}}` | Restore most recently removed preset at its old position with editor memory. Disabled if removal stack is empty. |
| `preset.select` `{id}` | Draft selection; preserves the outgoing preset's editor state. Unknown preset disables. Workspace state, not recipe Undo. |
| `collection.rename` `{name}` | Current collection name. Invalid collection name fails validation. |
| `collection.open` `{collection,revision?}`; `collection.undoOpen` | Open a validated collection object; add the current draft to the bounded recovery queue. Recover walks the queue, keeping the draft left behind reachable. `collection.undoOpen` capability reports availability; the summary projects the next draft, queue count/limit and oldest draft for a capacity warning. In normal UI, use async `CollectionRequest.open` to fetch by ID first. |
| `package.rename` `{productId,modName}` | One XF mod the draft builds (the package plan, [feature-module platform §6](feature-module-platform.md#6-export-mod-products-and-the-package-plan-pipe-12)). Names it as it appears in a mod manager; an empty `modName` goes back to the name that follows its features ("XF Eye Artistry" for eye makeup alone, "XF Looks" for several). Refused with a plain reason for a name Windows cannot use as a folder (`< > : " / \ | ? *`, a trailing full stop, reserved names, over 80 characters), and (`invalid_value`) for another mod's name of the same collection, case-insensitively, instead of silently adding a suffix. A collection change (unsaved until Save), no Undo step. |
| `package.assign` `{feature,productId}`; `package.split` `{feature,newId?}`; `package.merge` `{productId,intoId}` | Move a feature into an existing mod, into a new mod of its own (`newId` from the host's ID source), or everything of one mod into another. Offered only when the draft holds more than one exportable feature; with eye makeup alone `package.split` is refused ("Eye makeup is already a mod of its own."). A feature is in exactly one mod; a plan putting it into two is refused. The plan is stored with the collection only when it differs from the default. Every `package.*` action is refused (`unavailable`, with the plain "made with a newer version" or "damaged" wording) while the collection's stored plan is one this version can't use; that plan is kept and saved back unchanged, and `package.check`/`package.build` are refused with the same reason. |
| `collection.importRecipe` `{recipe,name}` | Add an imported recipe as a **new preset**; preserves existing presets. File reading/1 MB budget is outside this command. |
| `collection.saved` `{result,sourceId}` | **Internal reconciliation**, not a user command: update saved identity/revisions after transport returns, retaining in-flight draft edits and rejecting a different current collection. |

`CollectionRequest` is the async/library and file-data layer. `execute` serializes requests through `busy`; save/export requests snapshot the draft before transport. `StudioFileOperations` now wraps local file selection/download and mask baking through a typed device port, then delegates collection validation, package outcomes and recovery to the existing service. [Collection service](../../projects/xf-studio/authoring/src/collection-service.ts), [file workflow service](../../projects/xf-studio/authoring/src/studio-file-operations.ts).

| Exact request/payload | Effect, side effect and recovery |
|---|---|
| `initialize`; `refresh` | List SQLite collection summaries; initialize merges a legacy draft if no restored collection, or creates an unsaved one-preset draft from the current workspace when the library is empty. No SQLite write until Save. |
| `open` `{id}` | Fetch saved collection by ID, then open as a recoverable prior-draft switch. ID must still be in the current list; otherwise refresh. |
| `save`; `saveCopy` | SQLite immutable revision; copy creates a new collection ID. Transport enforces revision conflicts. Edits made during the request remain in the live draft; a stale result for another draft is rejected. |
| `exportCollection`; `exportPlan` | **Save first** when the library takes the collection, then return portable collection JSON or a compiler build-plan JSON and filename for a download adapter; a collection the library refuses (it needs `xfs/collection-2`) is exported from the draft without a save, and the message says so. A build plan is not a mod. These operations can cause a SQLite write or conflict. |
| `import` `{text,bytes}` | Parse a portable collection (current 16 MB budget) and open it as a recoverable draft switch. Invalid JSON/schema leaves current draft. File acquisition is outside the service. |
| `package` `{action:"check"|"build"}` | Snapshot the **unsaved** draft without saving SQLite. Check reports eligible retained presets and every omitted active unsupported layer/whole preset; Build creates an offline-verified private candidate if content remains. Both use the same package filter. Build uses a localhost server, one build at a time, and cannot be cancelled by closing the page. Neither installs or game-tests a mod. Errors include no exportable content, invalid input, missing local resources and verifier failure. [Package contract](studio-to-mod-pipeline.md). |

## Exact commands: layer structure and recipe editing

`LayerAction` is `{kind:"layer.edit",command:LayerCommand}` or `{kind:"layer.setEnabled",id,enabled}`. Its nested commands are `add`, `duplicate(id)`, `remove(id)`, `reset(id)`, `rename(id,name)` and `move(id,to)`; `add` and `duplicate` also carry the new layer's `newId`, which the host fills in before the registered apply runs (presentations omit it). The layer array is **bottom-to-top**; `to` is zero-based. Add creates a mirrored four-point Bezier upper-lid wash without a warp field. Reset applies that starting shape while preserving ID/name; duplicate gets a new ID and keeps its source geometry. Removing the last layer is legal. The eye-makeup port checkpoints, and the preview coordinator replaces/render-reschedules the stack for structural edits and redraws the affected slot for visibility. `layer.setEnabled` is a recipe edit, not a view-only hide. [Layer stack](../../projects/xf-studio/authoring/src/engines/layered-makeup/layer-stack.ts), [layer actions](../../projects/xf-studio/authoring/src/authoring-eye-makeup.ts).

`RecipeAction` uses stable `layerId` for every variant. A selected point still uses an **index**, not a stable point ID. The wrapper has `dispatch(action, record=false)`: discrete callers explicitly request one Undo checkpoint, while slider controls use separate start hooks to avoid one history entry per intermediate value. Selection effects do not record Undo; content edits validate the complete proposed recipe before publication. Render effects are `selection`, `scheduled` or `immediate`, with affected layer index. [Recipe actions](../../projects/xf-studio/authoring/src/engines/layered-makeup/recipe-actions.ts), [render scheduler](../../projects/xf-studio/authoring/src/authoring-render-scheduler.ts).

| Exact action/payload | Target and effect; current capability or final validation |
|---|---|
| `layer.select` `{layerId}`; `point.select` `{layerId,index}` | Workspace editor selection; missing layer/point disables. No recipe Undo. |
| `point.remove` `{layerId,index}` | Remove contour point, minimum three. Missing point or minimum count disables; discrete UI records one Undo. |
| `path.edit` `{layerId,command:{kind:"enable-bezier"}}` or `{kind:"point-mode",index,mode:"aligned"|"symmetric"|"corner"}` | Explicit legacy-curve conversion or point tangent constraint. `recipeActionCapability` only checks layer existence here; invalid point/path mode fails in the path helper/parser. One discrete Undo. |
| `field.select` / `field.add` / `field.remove` / `field.clear` `{layerId,fieldId?}` | Selected warp field, new zero-vector field, removal or vector reset. Select/remove/clear require an existing field ID; add disables at eight fields, and its `fieldId` is the new field's ID, which the host fills in before the registered apply runs. Select is workspace-only; others edit recipe. |
| `field.setReach` `{layerId,fieldId,radius}` | Warp radius clamped to 0.005–0.2 UV; existing field required. Reach is a Gaussian influence scale, not a hard boundary. |
| `pigment.edit` `{layerId,command:{kind:"point-strength",index,value}}` | Per-point pigment `0..1`. Invalid index/range fails in pure helper. |
| `pigment.edit` `{...,command:{kind:"smooth-strength",enabled}}` or `{kind:"strength-blend",value}` | Toggle continuous point gradients or set its blend distance; blend requires smooth mode and must be `0.000125..0.02`. Old recipes are upgraded only by explicit edit. |
| `softness.edit` `{layerId,command:{kind:"variable-softness",enabled}}` | Toggle interpolated point widths; disabling retains the widths for later reuse. |
| `softness.edit` `{...,command:{kind:"point-softness",index,value}}` or `{kind:"uniform-softness",value}` | Edge widths `0.0005..0.06` UV; point edit requires boundary mode and a valid point. |
| `layer.setColor` `{layerId,color}`; `layer.setOpacity` `{layerId,opacity}` | Authored pigment colour (`#rrggbb`) and opacity (`0..1`). Parser validates; continuous controls use `controlBegin/Edit/Commit/Cancel` for one Undo. `controlEdit` runs the same capability gate as `dispatch` and returns `{ok}` or `{ok:false,code,message}`. Direct facade dispatch records a discrete one-step Undo. |
| `layer.setSymmetry` `{layerId,symmetry}`; `layer.setFinish` `{layerId,finish}` | Mirroring and one of the current finish families. Immediate recipe/render effects; UI records a discrete Undo. Finish selection does not imply game-export support. |
| `glitter.selectModel` `{layerId,model:"classic"|"irregular"|"direct"|"clustered"|"fine"}` | Select versioned Glitter preview model; wrong finish or unknown model disables. Selected settings enter recipe; alternate comparison settings live in workspace memory. Discrete Undo. |
| `glitter.setClassic` `{layerId,key:"cells"|"density"|"tilt",value}` | Classic flake controls, also used for Shimmer. Incompatible current model disables. Numeric limits are finally validated by recipe parser. |
| `glitter.setIrregular` `{layerId,key:"count"|"radius"|"spread"|"tilt"|"color",value}`; `glitter.setDirect` `{layerId,key:"density"|"fineShare"|"strength"|"color",value}` | Model-specific preview settings. Wrong mode disables; parser enforces actual limits and colour type. These are browser studies, not game-export adapters. |

The recipe remains portable and per-preset; `AuthoringDocument` holds current recipe, selection and up to 80 deduplicated Undo snapshots. `RecipeActions.snapshot()` and `AuthoringDocument.snapshot()` are detached copies. `AuthoringPresentation` supplies compile-time read-only detached recipe/layer/field reads and selection to today's layer/property controls; `AuthoringGeometry` supplies cached detached reads to UV and on-head coordinate adapters, preserving captured target identity through an in-place gesture and invalidating it on replacement. Collection switching uses `AuthoringDocument.restore()` to publish recipe, selection, field selection and history atomically. `AuthoringDocument` still exposes trusted in-process setters and live recipe references to application/renderer wiring in the composition root (`studio-startup.ts`): **do not present these as a safe general script surface**. The complete recipe parser/gesture validation and `AuthoringGestures` are the mutation gates. #### The character namespace

**One owner: the character context** (CORE-58). `CHARACTER_CONTEXT_FAMILY` (family `characterContext`, registered in `STUDIO_OWNERS`; [character context](../../projects/xf-studio/authoring/src/character-context.ts)) holds which V the makeup is shown on and every creator choice set on it. The browser's `CharacterContextActions` ([service](../../projects/xf-studio/authoring/src/character-context-actions.ts)) owns the state, its own Undo history and the actions below; the host interprets the state with the installation's creator catalogue ([catalogue service](../../projects/xf-studio/authoring/src/cc-catalogue-service.ts)). The family needs no scene. Before the 3D preview is ready there is no context, and every action is refused as `not_ready` (CORE-64); after that, every action that changes choices (set, hide makeup, reset, reset all, keep changes) is refused as `not_ready` until the catalogue of the shown V's body has loaded, while a V change (default V, a save, a preset) and Undo/Redo never wait for it (CORE-73). Names follow one shared rule from preset to request to host ([creator names](../../projects/xf-studio/authoring/src/creator-names.ts): at most 255 characters, no control characters or backslash; 2,048 choices per V; PIPE-79). None records a step in a look's history (policy `none`) or touches a recipe, collection, save or package; the context keeps its own history instead (CORE-59). The earlier `character.tryChoice` (family `characterDetails`) is retired: a piercing style is the Piercings row's `character.setOption`, and `CharacterDetailActions` only shows the V the context describes.

**Reads.** `previewState().character` is the context's small snapshot: catalogue phase and message, origin (default, save or preset and its name), body gender, how many choices are set, the Undo and Redo labels, `keepable`, whether a view is on its way (`viewing`, `viewError`), `notes` (a loaded preset's entries that couldn't be carried) and `retry` (whether `character.retry` would try something). Every page and search names its catalogue; an answer from another catalogue starts the panel again (PIPE-81). `status.assets.characterDetails` carries `updating`, `updateError` (a change that couldn't be prepared keeps the V as shown and says so; CORE-63) and `drawn` (the head options the shown record draws, which settles a `conditional` coverage).

**Files.** `characterPreset.import` reads a `.json` file (1 MB of UTF-8 at most, JSON parsed once) and dispatches `character.loadPreset`; `characterPreset.export` asks the host for the preset of the choices set (each named as this installation offers it, with its mod) and downloads it as `<name>.xfs-character.json`, saying how many entries were left out (unwritable, or naming a personal folder or address).

**Persistence.** The workspace's preview state stores `character` (`{origin, name?, bodyGender?, choices, kept?}`) only once something was set, so a workspace that never used these controls keeps its stored bytes; the retired `piercingStyle`/`piercingDefinition` fields are written back as read, and an untouched context turns them into the matching Piercings choices once the catalogue is ready (CORE-74). The Undo history isn't stored.

### Host actions

`PreviewPreparationActions` (`src/preview-preparation.ts`) and `WolvenKitSetupActions` (`src/wolvenkit-setup.ts`) are renderer-side host request ports used by the preview setup service (`src/preview-setup.ts`); their IDs have descriptors in `PREVIEW_PREPARATION_DESCRIPTORS` and `WOLVENKIT_DESCRIPTORS`. `preview.refresh` (read), `preview.prepare` and `preview.rebuild` (effect `derive`, cancellable; rebuild sets a ready preview aside and prepares it afresh, for a damaged preview) and `preview.cancel` take no payload. `wolvenkit.refresh` and `wolvenkit.recheck` (read; recheck forgets cached runtime and tool detection) take none; `wolvenkit.install` (effect `install-tool`, cancellable) takes only `{version}`, the person's consent to download exactly the pinned release the consent dialog showed, and `capability` refuses any other version or a state that cannot install; `wolvenkit.cancel` stops a running download. The host supplies the URL, hash, folder and every path; none has Undo. Both ports share one polled host-state port (`src/host-state-poller.ts`): they poll while work runs, keep polling with backoff when a poll fails while work was last known to be running, publish `connection()` (consecutive failures, whether a retry is scheduled), apply replies in request order (a reply older than one already applied only answers its caller), share one in-flight refresh while nothing newer was sent, apply nothing after `dispose()`, and publish detached `xfs/preview-core-state-1` / `xfs/wolvenkit-setup-1` snapshots, which pure view functions (`previewView`, `wolvenKitCard`, `wolvenKitConsent`) turn into plain card and dialog text. The desktop host's `/api/desktop/open-link` opens only named official pages (`wolvenkit-licence`, `wolvenkit-release`, `runtime-installer`, `runtime-page`) resolved from the host's own state; on localhost the same state-resolved URL opens in a new tab. When the host's setup changes outside the setup views (game folder chosen, WolvenKit ready, preview prepared), the setup service calls `LocalSetupActions.requestRefresh()` so Build availability follows (no window event).

### Diagnostics and problem reports

`port.diagnostics` ([`src/diagnostics/actions.ts`](../../projects/xf-studio/authoring/src/diagnostics/actions.ts); [how it works](../../docs/diagnostics.md)) has `snapshot()`, `capability(action)`, `dispatch(action)` and `descriptors()` (`DIAGNOSTICS_DESCRIPTORS`: scope `host`, no Undo; none touches a recipe, Undo or the library, and none sends anything by itself), plus `notice({source, message, code?})` and `fullText(item)`, a read of one part's whole text for the review's full view (the page's own parts, or the host's through `POST /api/diagnostics/item`; null when the report expired). The shell's `Feedback` calls `notice` for an error notice about to be shown: it returns null for an expected refusal (`isExpectedFailure`: the platform reason codes plus `cancelled`, `conflict`, `stale_result`, `invalid_json`, `invalid_collection`, `no_exportable_content`), and otherwise logs the failure and returns its reference (the host's, when a failed host request answered with `X-XFS-Error-Ref` moments before). The notice shows the reference and **Report this problem**. `snapshot().notice` is the newest failure an app service asked to show (`pageFailure(…, {notify: true})`); the shell shows each once, with its reference.

| Action | Payload | Effect |
|---|---|---|
| `diagnostics.prepareReport` | `{ref?, activity?}`: an `XF-XXXXXX` reference (older `XF-XXXX` ones still read); the recent notices the person saw | Asks the host to prepare a report (`POST /api/diagnostics/report`) and publishes `snapshot().report`: the groups, their items (label, detail, size, ticked, preview), the running total against the 20 MB limit, and `files`, the `README.md` and `report.json` as they would be saved from the ticked parts. `opens` increments. Refused while preparing |
| `diagnostics.setIncluded` | `{item, included}` | Ticks or unticks one part. Refused before a report is ready, for an unknown part, over the limit (`limit`), and for a mod's own files until the sharing confirmation (`needs_input`) |
| `diagnostics.confirmSharing` | `{confirmed}` | The person's confirmation that they may share the offered mods' files. Unconfirming unticks them |
| `diagnostics.setDescription` | `{text}` (at most 4,000 characters) | The person's own description, placed first in the report |
| `diagnostics.saveReport` | none | The host makes one ZIP of the ticked parts (`POST /api/diagnostics/bundle`, carrying the sharing confirmation, which the host checks for mod files); the page saves it through the file device. When the host no longer holds the report, the report turns `failed` with `expired` set, and the review offers **Prepare again** |
| `diagnostics.copySummary` | none | Copies the readable summary |
| `diagnostics.openIssue` | none | Opens a pre-filled GitHub issue: the title and a short summary only. The host builds the link, redacted with the configured folders; the desktop host opens it in the person's browser, and on the dev server the page opens the host's link in a new tab (never one of its own) |
| `diagnostics.setMode` | `{mode: "normal" \| "deep"}` | Diagnostic mode: a wider rolling window with every resource read, for 24 hours |
| `diagnostics.closeReport` | none | Forgets the prepared report on the page |

The report window (`studio-ui/diagnostics/report-dialog.ts`), Help's **Report a problem…** and the palette's **Report a problem…** and **Turn diagnostic mode on/off** use only these. App services report a failure a person may see with `pageFailure(area, code, message, error, options)` on the page and `hostFailure(area, code, message, error)` on a host: one line at the catch site, with no logger to hold.

## Persistence, async boundaries and truthful state

| Kind of state | Current owner and safe read | Persistence/Undo rule |
|---|---|---|
| Editable makeup | `AuthoringDocument.snapshot()`; `RecipeActions.snapshot()`; collection session stashes per-preset state. | Recipe in portable preset; current editor/history in browser workspace. Explicit SQLite save makes an immutable revision. Content edits use recipe Undo; selection does not. |
| Draft/library | `CollectionService.view()` includes detached draft, saved summaries, `busy` and progress. | Draft autosaves locally; SQLite only on explicit Save/Save copy or collection/plan export. Preset restore and undo-open differ from recipe Undo. |
| Preview/UV/camera/motion | Service snapshots; `uvEditor.snapshot()` is adapter-owned; renderer port supplies camera/idle phase. | Browser workspace only, including decoded V and Glitter comparison choices. No recipe Undo. Workspace composition uses service snapshots; the current layout adapter still reads panel/scroll state from DOM. |
| Preview calculation | Quality `blocked/error`; mask-client diagnostics and renderer readiness in main orchestration. | Worker jobs are cancellable/cooperative internally; partial results must not be shown as ready. No unified immutable `layerReady/stale/failed` selector yet. |
| Package operation | `CollectionService.view().progress` and `StudioFileOperations.snapshot()` publish status, last detached Check/Build result (`xfs/package-check-2`/`-build-2`: every product the draft builds, each feature's looks, omissions and experimental finishes), errors and collection-open recovery capability; each verified product has an `xfs/local-package-2` manifest (readers accept `-1`). `CollectionService.summary().products` lists the mods the draft would build, and `packagePlanIssue` says in plain words why a stored plan can't be used. Omissions are decided once by the export host: the result's `omissions` (whole looks no feature packages anything of, parts without an exporter, features left out) and each product's own subset, beside each feature's own (its layers, and its part of a look another feature packages). | Unsaved-draft snapshot in its stored form, package plan included. Check creates no files; Build produces ignored private candidates only after independent verification, one per product. Manifest identifies the collection's SHA-256, each feature's packaged SHA-256, retained looks and omissions; `installed:false`, `gameRenderingVerified:false`. No server-build cancellation contract. |
| Workspace save | `WorkspacePersistence.snapshot()` and subscription (published only on change): `idle/saved/nearly-full/full/repaired/protected/unavailable`. | 180 ms debounce after activation, page-hide/visibility flush, separate `?verify=1` key. Unchanged content is not rewritten. Stored size is bounded ([editor invariants](editor-invariants.md#browser-workspace-persistence)); trimming beyond the standard policy reports `nearly-full`, a refused write `full`. A failed restore protects original storage from overwrite; damaged recovery entries are dropped with `repaired`. |

## Contextual menus: useful commands and honest gaps

These are **candidate menu contents**, not a prescribed menu design. The redesigned presentation now implements them in `src/studio-ui/target-menus.ts`, opened from the row panels and `panels/viewports.ts` (bound through `contextQuery`/`contextAt`, dispatched through `dispatchContext`); `allowsNativeTextMenu` keeps native text editing menus, and right-drag still pans. Every offered command should query its typed capability against the **hit target ID**, then revalidate at dispatch. A contextual action must not first change the active selection merely to reach another target. [Current native-menu policy](../../projects/xf-studio/authoring/src/context-menu.ts).

For example, an already constructed service can query and invoke a nonselected preset without changing selection first:

```ts
const action = { kind: "preset.edit", command: { kind: "copy", id: hitPresetId } } as const;
const capability = service.actionCapability(action);
if (capability.available) service.dispatch(action);
else renderDisabledReason(capability.reason); // Presentation callback, not a Studio API.
```

**Menu rules (implemented).** Context menus are actionable, not informational. Every menu (head view, UV map, layer, preset and collection rows) is composed from sections through `menuFromSections`, which drops any section without an action or submenu; a disabled entry counts only because it states why in words, and only where the command is genuinely relevant to the target. No section merely reports that nothing is available (the old "Background · No editable control under the cursor", "View changes are not edits", "No shape here" and "Target changed" captions are gone). Target-specific actions come first, labelled by what is under the cursor (with the owning layer and "mirrored copy" where it applies), then the viewport's view actions under a short "Head view" or "UV view" heading. Bare skin, empty UV space and background therefore show the view section alone. `tests/context-menu-sections.test.ts` checks every section of every target kind's menu (a `Record` over hit kinds makes a new kind fail to compile until it is covered), and `tests/context-hit-classification.test.ts` checks the head/background/makeup/handle classification with real rays in both views. [Target menus](../../projects/xf-studio/authoring/src/studio-ui/target-menus.ts), [menu sections](../../projects/xf-studio/authoring/src/studio-ui/menu.ts).

A point-menu command similarly uses the hit layer/index; the caller decides the discrete Undo checkpoint by passing `true`. A long drag instead enters `AuthoringGestures` once and commits/cancels that transaction. These two paths must not each add their own checkpoint for one interaction.

| Hit target | Immediately reusable commands | Missing typed/queryable bridge before a reliable menu |
|---|---|---|
| Collection or saved-list row | Rename draft; Save/Save copy; Refresh; Open by saved ID; Undo open; Export collection/plan; Check/Build. | Collection create, dirty/conflict selector, structured package eligibility per preset, package cancellation. |
| Preset row | Select, copy, rename, move, remove; restore last removal at collection scope. | Multi-select/bulk commands, revision browsing/restore, structured disabled reasons for all data validation. |
| Layer row | Select, enable, duplicate, rename, move, reset, remove; colour/opacity/finish/symmetry editing. | Unified top-level layer dispatcher and target-aware confirmation/transaction for destructive edits; layer isolation and blend modes are future work. |
| Point or tangent | Select/remove point; set strength/softness; enable Bézier and choose aligned/symmetric/corner mode. | High-level insert/move/tangent command and capability for hit geometry. Existing gestures use an index and an opaque application-held live identity; presentation reads detached geometry. |
| Warp origin/vector/reach | Select, add, remove, clear vector, set reach. | Typed origin/vector commands and position-aware capability outside pointer proposals. |
| Shape interior/empty UV/bare skin | A bound shape hit (any visible layer) offers layer selection, add warp and Bézier conversion where applicable. Empty UV and bare skin offer no standalone command, so their menus show only view actions. Existing gesture adapters translate/rotate/scale and insert near a curve; UV can fit, pan, zoom or switch eye view. | Tool-mode and UV navigation action IDs, high-level shape transform/insert command with one Undo and coordinate-aware capability. Empty-canvas menus must not imply a contour exists. |
| Viewport/background | Front, FOV, visibility, preview tier/rebuild, lighting, motion, eye/piercing context. | Orbit/pan/zoom commands, asset/job readiness selector, custom contextual menu and keyboard equivalence. |

## Coordinate, history and query additions

Added 25 September; contracts and tests are summarised in the [boundary assessment](ui-architecture-boundary.md#application-api-additions-25-september). Coordinates are canonical (unmirrored) UV.

| Exact action/query | Payload and behaviour |
|---|---|
| `point.move` | `{layerId,index,u,v}`; one Undo. |
| `point.insert` | `{layerId,u,v}`; nearest contour section in UV (exact Bézier split); selects the new point; refused at 24 points. |
| `point.setTangent` | `{layerId,index,side:"in"|"out",du,dv}`; relative arm, respecting aligned/symmetric/corner; needs Bézier handles. |
| `shape.transform` | `{layerId,command:{kind:"translate",du,dv}|{kind:"rotate",radians}|{kind:"scale",factor},pivotIndex?}`; pivot defaults to the selected point; scales widths, blends and warps like the gesture; rejected atomically. |
| `field.setOrigin` / `field.setVector` | `{layerId,fieldId,u,v}` / `{layerId,fieldId,du,dv}` (pull within ±0.1 UV). |
| `history.redo` | Workspace action; session-only Redo, discarded by any other edit, preset switch or restore. `authoring.history()` gives the Undo/Redo labels and depths. |
| `history.jumpTo` | `{entryId}` from `historyTimeline()` (a step ID or its `startId`). Goes to the look right after that step as **one** change: the application applies the Undo or Redo steps between atomically, publishes the recipe once and resets preview resources once. It creates no entry of its own and keeps every step (done steps become redo-able; redo-able ones become done). Refused with `busy` while a gesture or form transaction is open, `missing_target` for an ID that is no longer in the history (another preset, a restored history, or undone steps that a new edit discarded) and `invalid_value` for the current step. `consequences()` reports `recoverableBy: history.redo` for a jump back and `history.undo` for a jump forward. |
| `authoring.historyTimeline()` | Detached `HistorySnapshot` of the current preset: `steps` oldest first (`id`, `label`, `actionKind`, optional `layerId`, optional `at` epoch ms, `state: "done"|"undone"`), `current` (index of the step the look follows, −1 at the oldest kept state), `redoCount`, `trimmed` ("Older steps were not kept") and `startId`. IDs are opaque, session-unique and stable across Undo, Redo and jumps; labels and times are session-only (restored steps read "Earlier change" without a time). It carries no recipes, so the planned look-wide history ([feature-module platform §3](feature-module-platform.md#3-undo-history-and-persistence-budgets-core-02)) can publish the same shape. |
| `camera.navigate` | `{command:{kind:"orbit",yaw,pitch}|{kind:"dolly",factor}|{kind:"pan",dx,dy}}`; view state only. |
| `viewport.uvNavigate` | `{kind:"pan",du,dv}` or `{kind:"zoom",factor,at?}`; view state only, persisted like wheel/right-drag. |
| `authoring.limitsFor(target,kind,variant?)` | Current input limits and units, including state-dependent Glitter bounds and mode requirements: the spec's `units` and static `inputLimits`, then the owning feature's `limits` (step 5). |
| `authoring.consequences({action}|{file}|{request})` | Replaced content, durable writes, recoverable state that would be lost, recovery path, whether to confirm. |
| `library.persistence()` | Draft versus library revision: `baseline`, `dirty`, `dirtyPresets`, `structureDirty`. |
| `files.activity()` / `files.cancel(id)` | In-flight file and collection work with request IDs; cancel refuses honestly. |
| `previewReadiness.snapshot().layers`, `viewport.snapshot().uv.selection` | Per-layer preview state; whether the selected point/warp is inside the UV view. |

Capability refusals may carry `issue: {code, field, message}` for structured validation.

## Remaining contract work and expansion

The following are **missing API work**, even when a current control or pointer gesture already performs the behavior: non-piercing renderer asset options and complete parameterized capabilities for shape/empty-canvas hits; authoritative immutable asset state (per-layer preview readiness now exists); and presentation of the new coordinate, history and query contracts (arrow-key nudging, consequence-driven confirmation beyond collection replacement). The new hit-context query covers existing commands and stale identity, but cannot claim unavailable coordinate-based operations. File acquisition and download now have a typed device port; UV/head coordinate adapters use detached copies that cannot mutate the document, though their local types remain mutable for gesture identity. A versioned dock/theme preference contract is present, while the custom context menu, dockable/floating/magnetic/tabbed panels and theme UI do not exist yet. Dock snap decisions must use cursor position, with keyboard alternatives. These requirements are from the [handoff brief](../backlog/claude-ui-overhaul.md); they do not dictate visual composition. The facade and composite port are exercised without any page controls by `tests/studio-application.test.ts`, `tests/studio-presentation.test.ts` and `tests/trusted-studio-bootstrap.test.ts`; the former standalone boundary fixture page and `/port-smoke.html` were retired with the sidebar shell.

Design the action *categories* to grow: more cosmetic finish adapters and material combinations; brows, jewellery/piercings, cheek makeup, hair, expression/animation and later tattoos; provider-neutral source assets; release/installation and runtime package evidence; and longer-term quest design. Current brow/lash/hair/piercing controls are preview context, **not** authoring actions for those categories. Each later authoring feature requires discussion with the maintainer before implementation. Do not hard-code one special control per present category, finish, model or package stage. [Product direction](../../projects/xf-studio/data/product-direction.md), [future feature backlog](../backlog/jewellery-and-customization.md), [functional inventory](ui-capability-inventory.md).

Examples for acceptance: ask capability for Duplicate on a nonselected layer ID and dispatch that same ID; change a point's strength and softness, then Undo the intended transaction; begin a UV shape drag, change preset, and confirm stale proposals cannot commit; Save while continuing draft edits and inspect both the stored revision and current draft; Check a collection with one Glitter-only preset and one Matte preset, then Build the same draft and compare omissions/retained identities against the manifest; recover from unavailable optional hair without blocking makeup editing; reload with camera, UV, imported V, preview quality and per-preset history intact. After the missing layout/theme services exist, also reload dock state and system/light/dark override without touching recipe data. Use `?verify=1` and keep game rendering claims separate from offline package verification.
