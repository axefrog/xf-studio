# XF Studio presentation boundary — incremental extractions

24 September 2026. This is an incremental implementation checkpoint, **not** the completed gate for the Opus 5.5 UI overhaul. See [the delegation brief](../backlog/claude-ui-overhaul.md) for that gate.

## What is now independent of controls

`authoring/src/collection-actions.ts` exposes typed in-process commands for preset add/copy/rename/move/remove/restore/select/expand; collection rename, open, undo-open and recipe import; and save-result reconciliation. The adapter returns a detached read-only-by-copy view, provides `capability(action)` with a disabled reason for known invalid targets, and can notify subscribers after successful commands. It calls the existing `CollectionSession`, so draft switching, per-preset editor memory, stable identities, recovery and in-flight save reconciliation still follow the same validated rules. `collection-ui.ts` now reaches these operations through `CollectionApplication`'s narrow view port.

`authoring/src/editor-actions.ts` provides typed `layer.edit` and `layer.setEnabled` operations over recipes, plus target-aware capability checks. The returned recipe is validated; its source is not mutated. `main.ts` routes layer-list actions, including visibility, through that path. `RecipeHistory` now owns the existing deduplicated, bounded 80-entry history and returns detached snapshots. Structural layer changes still trigger the original full slot replacement; visibility still redraws only its affected slot.

The second extraction adds `authoring/src/recipe-actions.ts`. It exposes target-aware typed actions and capability reasons for layer selection, point selection/removal, Bézier conversion/mode, warp selection/add/remove/clear/reach, pigment strength and edge softness, colour/opacity/symmetry/finish, and all current Glitter preview-model settings. It validates a proposed recipe before publishing and keeps untouched layer object identities so deferred per-layer renders are not lost if another layer changes before the next frame. The controller returns detached read-only snapshots and notifies subscribers after successful actions. The present UI adapters now dispatch these actions; a discrete action records one recipe Undo entry, while slider gestures still use their existing begin hooks so a continuous interaction produces one entry. Glitter model comparison memory remains workspace-only; only the selected model/settings enter the portable recipe.

The third extraction puts UV and on-head gesture proposals through `RecipeActions.applyGesture`. The adapters still perform input capture, picking, coordinate conversion, mirrored mapping and gesture bookkeeping, but they no longer write live recipe points, fields or whole shapes. Each proposed edit carries its layer identity (and point/field identity where relevant), is parsed against the current recipe schema before publication, and schedules only its affected layer. Existing gesture start/cancel hooks retain the one-step Undo and Escape behaviour. `ViewportAdapter` gives the two editors explicit attach/detach/resize/cancel/capture lifecycle; detach removes their listeners and render resources. `PreviewActions` provides DOM/Three-independent commands, detached camera/preference snapshots and capability reasons for FOV, front view, exposure, key light, surface guides, wireframe, normals, eye optics and brow/lash/hair visibility. Orbit/pan camera state is read through its injected port when snapshotted, including changes made by the renderer controls.

The fourth extraction adds `CollectionService` and an injected `CollectionTransport`. List/load/save/copy/export/import/package sequences, legacy-draft merge, immutable request snapshots, busy/progress/success/error state and capability reasons now live outside `collection-ui.ts`. The service preserves editor changes made while a save is in flight and refuses to reconcile a save response onto a different collection identity. Package checks/builds use the unsaved draft snapshot without writing SQLite. Current partial export keeps eligible Matte/Satin/Metallic content, reports omitted preview-only content with warnings, and returns `no_exportable_content` only when nothing eligible remains. The current view still reads a selected local file and initiates a download, but it no longer chooses request order, draft reconciliation or package result text. The HTTP adapter retains the current local endpoints and SQLite rules.

The fifth extraction adds `MotionActions`, `PreviewQualityActions` and `SavedAppearanceActions`. Motion restore, pause, head/facial contribution switches, blink commands and readable state are independent of the controls; the renderer's phase and animation implementation remain injected. Quality tier validation, selection and recoverable error state are similarly separate, while `main.ts` still owns worker cancellation, texture disposal and render ordering through an injected replacement callback. Saved-V parsing, validation, application and suggested eye selector value form one command; the view only selects a local file and paints the result. `PreviewActions` now also covers eye-shape and piercing visibility/style/colour, with available choices supplied by the renderer port. These services publish detached snapshots, subscriptions and capability reasons. No portable recipe or SQLite format changed.

The sixth extraction adds `AuthoringDocument` and `WorkspacePersistence`. The former is the live in-process owner of recipe, active layer/point, selected warp and Undo history; `main.ts` reads and publishes these through it instead of retaining parallel top-level variables. It provides change subscriptions, detached snapshots, validated atomic restore and the original bounded/deduplicated history. Gesture proposals still preserve live layer identity and explicitly publish their in-place change. The latter owns the 180 ms autosave, explicit activation after startup, page-hide/visibility flush, isolated verification key, and the protected-storage policy when restore failed. It receives an injected workspace capture and storage port. Workspace and recipe schemas remain unchanged.

The seventh extraction adds `AuthoringGestures` and `AuthoringRenderScheduler`. UV and on-head editors now hand begin/apply/commit/cancel events to one DOM-free gesture transaction service; it checkpoints once, validates the source and stable target before each proposal, and restores Undo only for an accepted edit in the still-current layer. The editors retain pointer capture, coordinate conversion, wheel-burst timing, and stale-context checks, and call commit on release or burst completion. `AuthoringDocument` publishes typed action/gesture rendering effects. The scheduler subscribes to those effects, coalesces active-layer and gesture renders by live layer identity, renders inactive/immediate changes directly, and provides explicit stack-order and active-first full rebuilds for structural changes and quality recovery. Its port still calls the unchanged renderer/raster work in `main.ts`; neither raster arithmetic nor worker cancellation changed.

The eighth extraction adds `AuthoringControlEdits`, `WorkspaceComposer` and a high-level preview policy. Colour, opacity, pigment, softness, warp reach and Glitter form controls now pass through typed begin/edit/commit/cancel transactions with one Undo per continuous gesture, empty-edit cleanup and stale-layer guards. `control-edit-ui.ts` translates pointer, key, change and blur events; the application service owns history. `WorkspaceComposer` builds a detached saved state from document, preview, motion, quality, collection and layout ports. Before preview assets finish loading, it preserves prior camera and scroll state while accepting current authoring edits; afterward it uses the typed preview/motion snapshots. Only the layout adapter reads panel DOM state. `planLayerPreview` exposes missing/recover/unavailable/request outcomes with active priority, optical-map need, disabled-placeholder release and capacity reason; `main.ts` still owns canvases, workers, cancellation and complete texture publication. No recipe, SQLite, compiler or raster arithmetic changed.

The ninth extraction adds `StudioApplication`, a single in-process, DOM-free facade over the existing document, recipe/layer, gesture/form, collection, preview, motion, quality and saved-appearance services. It publishes detached aggregate snapshots and subscriptions, exact action/request IDs, target-specific candidate actions with current capability reasons, typed dispatch outcomes, collection async outcomes, and an opaque gesture entry point that resolves live layer/point/field identity internally. Direct recipe dispatch records one Undo for content edits, while form controls use explicit begin/edit/commit/cancel; collection removal/open retain their separate recovery policies. Existing collection async operations and preset edit, layer finish/symmetry, point removal, Glitter model, quality and lighting controls now exercise the facade. Core validation and renderer ownership did not move. This is an incremental seam: other controls and both gesture adapters still call their older services directly.

The tenth extraction routes both UV and on-head editors' mutation proposals through `StudioApplication.beginGesture/applyGesture/endGesture`. The proposals contain values and target IDs, never the live `Layer`, point or field objects; the facade owns those identities in an opaque session, checks target continuity and exposes a queryable gesture capability. The adapters retain geometry reads, coordinate mapping, pointer capture, wheel timing and their existing stale-context guards. A compile-time complete registry now describes all 53 public top-level action IDs, nine collection request IDs and four gesture proposal IDs, with scope, payload fields, nested variants, Undo/recovery policy and async effect. The facade supplies structured reason codes for known target, busy, limit, mode, asset and readiness failures while preserving the underlying message. `application-boundary-fixture.html` is a minimal replacement presentation over the facade without the current sidebar, Three renderer, worker or browser storage. Build it with `bun build src/application-boundary-fixture.ts --outdir public/build --target browser`, then open `/application-boundary-fixture.html?verify=1` on the local authoring server. It is a contract fixture, not a proposed visual design.

The eleventh extraction adds `AuthoringGeometry`, a versioned detached view for both UV and on-head drawing, picking and stale-pointer checks. Repeated animation-frame reads return the cached view without cloning the live recipe. A validated in-place gesture refreshes only its affected layer and retains captured point/field/array identity; a recipe replacement or path-point array replacement invalidates the corresponding gesture context. The application facade still owns the live gesture references. `AuthoringLayerActions` now owns layer capability checks, the single Undo checkpoint and structural versus single-layer publication; `main.ts` supplies only a renderer-resource reset callback. `StudioApplication.contextCapability(target, action)` validates scope, hit-target match and descriptor payload before calling the domain capability, while `choicesFor` reports live capability for enumerated choices such as finishes, Glitter models and preview quality. The production Add/Duplicate layer and Remove point disabled states now query application capabilities instead of duplicating limits in `main.ts`. These queries remain advisory; dispatch and parser validation are authoritative.

These are internal commands, not a network or plugin execution interface. The collection/layer action IDs are `preset.edit`, `preset.select`, `preset.expand`, `collection.rename`, `collection.filesOpen`, `collection.open`, `collection.undoOpen`, `collection.importRecipe`, `collection.saved`, `layer.edit`, and `layer.setEnabled`. Recipe action IDs are `layer.select`, `point.select`, `point.remove`, `path.edit`, `field.select`, `field.add`, `field.remove`, `field.clear`, `field.setReach`, `pigment.edit`, `softness.edit`, `layer.setColor`, `layer.setOpacity`, `layer.setSymmetry`, `layer.setFinish`, `glitter.selectModel`, `glitter.setClassic`, `glitter.setIrregular`, and `glitter.setDirect`. Collection, layer and recipe capability checks are synchronous; validation remains authoritative at dispatch. A future menu may query capabilities, then dispatch the same command. A stale target after the query is still rejected at dispatch.

`AuthoringDocument.replaceRecipe` also atomically validates a structural or Undo replacement and clamps its selected layer and point. This fixed an orphan selection in the replacement-presentation fixture after Add layer → Undo; the fixture now returns to four layers, six active points and 0.85 opacity.

The twelfth extraction adds `AuthoringPresentation`, a narrow read-only TypeScript port over cached detached geometry and primitive selection state. The production layer list, property controls, warp selectors, recipe download and verification diagnostics now read that port; those UI paths no longer receive a mutable live recipe. UV/head coordinate adapters keep their detached identity-stable geometry view for pointer capture. Switching collections now calls the document's atomic `restore` and resets renderer resources, instead of individually assigning history, field selection, recipe and selected point in `main.ts`. The render/worker and application services still use the trusted live document internally. Type-level readonly protects new UI code at compilation, while the detached cache is intentionally updated in place during gestures and therefore is not runtime-frozen. This closes the live-recipe read path for current production control adapters, not the whole shell boundary.

The thirteenth extraction adds `AuthoringPreviewCoordinator` with a typed `PreviewRenderPort`. Quality assessment and tier ownership, active-layer request priority, disabled-slot release, capacity failure, recovery rebuild, stack reset, stale-size/slot publication gating and Ready/Updating/error status decisions now live in a DOM-free application service. `AuthoringRenderScheduler` calls this coordinator, and quality controls read its assessment/status. `main.ts` still constructs the worker and Three scene, owns canvas/optical texture publication and implements the concrete port. A quality switch cancels pending raster work and disposes old canvases before an active-first rebuild; a structural stack reset uses stack order. `RasterClient` still validates the complete result bundle against the request/version and never publishes cancelled or partial work. The coordinator adds a tier/slot check before the device adapter sees a result. Raster arithmetic, fairness, compiler and recipe formats did not change.

The fourteenth extraction adds `StudioFileOperations`, a DOM-free file and package workflow service with a typed `StudioFilePort`. It exposes import/export capabilities and outcomes for recipe, collection and saved-V data, delegates mask baking to a renderer port, and retains detached package check/build results, operation progress, error codes and collection-open recovery capability. The browser adapter still owns hidden file inputs, blob download and the one-off mask worker/canvas. The service delegates collection validation, partial-package eligibility, SQLite revision handling and recovery to the existing `CollectionService` and application callbacks; it does not duplicate those domain rules. Production controls now call the file service instead of reading files or downloading JSON themselves. The state snapshot stores only outcome metadata for exports, avoiding an extra retained copy of large JSON. Portable formats and export quality remain unchanged.

An independently integrated context-target slice adds `StudioApplication.contextQuery`, `boundActionCapability` and `dispatchContext`. A device/DOM adapter supplies a hit for empty UV, shape, point, tangent, warp field, layer, preset or collection; the application binds it to collection/preset and geometry revision, offers only current actions with live capability reasons, and rechecks the binding and final domain parser at dispatch. This is action discovery **after** a hit, not geometric picking or a menu UI. Empty UV honestly offers no standalone edit command. The combined main branch has 310 passing authoring tests, type check and build.

The fifteenth extraction adds `CollectionApplication`, a DOM-free composition service that constructs and owns `CollectionService`, injects transport, and bridges the trusted `AuthoringDocument` export/restore operations. The replaceable `collection-ui.ts` view receives a narrow `CollectionViewPort` with detached collection state, subscriptions, typed commands and capabilities, and file-operation results; it no longer constructs the service or receives editor read/show callbacks. The composition root initializes the service and refreshes the view once the restored collection is ready. Conflict reconciliation, draft recovery, preset switching, unsaved-draft package snapshots and SQLite rules stay in their existing services.

The sixteenth extraction adds `ViewportAttachment`, a typed layout-facing port for the existing head and UV hosts. A replacement layout can attach or rehost either same DOM host, request a resize, cancel input, subscribe to phase changes, and read detached readiness/error, dimensions, capture and camera/UV view state without importing Three, workers or the authoring document. Rehost cancels the relevant gesture before moving; it never invokes `ViewportAdapter.detach()`, which remains a destructive editor-disposal path. A layout must call `resize` after any further sizing/reordering following rehost. `createScene` now skips zero-size device resizes and retains a finite camera aspect while hidden; a deferred initial/front framing request is applied when the host first becomes visible unless a saved camera has been restored. The current shell still provides the browser host-move and renderer/editor device callbacks. This is an attachment contract, not a dock UI or new geometry policy.

The seventeenth extraction adds read-only `ViewportAttachment.contextAt(kind,x,y)`. The UV adapter reuses its existing handle priority and painted-shape test, returning canonical point/field IDs, tangent side, mirrored instance and an honest empty-UV hit. The on-head adapter reuses its existing anchored/projected handle checks and plate/head/eye occlusion before returning the same stable identities; background or occluded surfaces return no hit. The attachment sends the hit to `StudioApplication.contextQuery`, which binds it to the current collection, preset and geometry revision and supplies existing actions/capabilities. Hit queries never select a point, checkpoint Undo or initiate a gesture. Right-click remains a pan input on UV, and native text editing menus remain available. No second geometry evaluator or menu UI was introduced.

The eighteenth extraction closes four current presentation gaps. `recipe.undo` has live application capability and dispatch, with the existing atomic recipe replacement/resource reset retained behind the composition callback; the current shortcut/button and replacement fixture now use that action. `ViewportAttachment.uvCommand` exposes Both, Single, Other and Fit through the retained UV editor, preserving its view persistence, wheel zoom and right-pan. Saved-V import passes the already-applied eye-shape suggestion through `StudioApplication.recordAppliedSavedAppearance`, updating selection without applying geometry a second time. Piercing style/material labels are detached through `StudioApplication.snapshot().previewOptions`, using the same renderer-provided choices for dispatch validation; choices remain preview-only. No portable recipe, package or scene material semantics changed.

## Remaining coupling and next phases

1. `AuthoringDocument` owns live recipe, selection and history; gesture and form services own Undo transactions. Layer/property UI adapters now use the `AuthoringPresentation` read-only port; UV/surface adapters read detached `AuthoringGeometry` and send opaque facade proposals. The geometry adapter interface is still mutable at TypeScript/runtime level for existing transform helpers, though its objects cannot change authored data. Staleness checks depend on version publication and identity checks; arbitrary unannounced writes through trusted document access remain outside the safe presentation contract. `RecipeActions`, renderer scheduling and collection coordination still access `AuthoringDocument` through trusted `main.ts` wiring. Pointer capture, UV view memory and wheel timing remain in presentation adapters. Give a replacement UI shell only facade and narrow renderer ports, and make the UV/head geometry adapter signatures read-only where helpers permit, before unrestricted Opus edits.
2. `CollectionService` owns the async sequences and local draft merge; `StudioFileOperations` brokers local file acquisition/download through an injected device port and publishes package result/recovery state. `CollectionApplication` owns the trusted editor read/show bridge, and `collection-ui.ts` paints detached state through `CollectionViewPort`. The service serializes requests and returns error codes, including conflict and no exportable content. The editor-change subscription is still coordinated through application/bootstrap wiring; a future shell should make that propagation authoritative and add explicit retry/cancellation policy for long-running package builds. Keep SQLite revision rules in the existing store.
3. `main.ts` still creates the Three scene, mask worker, canvases and editors. `ViewportAttachment` gives a replacement layout safe same-host reparenting, zero-size guarding, resize/cancel, detached view/status and read-only actual hit queries; `AuthoringPreviewCoordinator` owns request/recovery/status policy through a typed resource port. `ViewportAdapter.detach()` still disposes editors and is only for final teardown or replacement, never a dock move. The scene binds canvas, resize observer and animation to its original host; a future layout must reparent that stable host and should avoid unbounded rendering work while hidden. `main.ts` still publishes canvas/optical bundles, paints status text and wires scheduler callbacks to DOM refresh/persistence. Picking mechanics and camera orbit/pan remain concrete adapter concerns. Preserve surface constraints, cached occlusion, worker cancellation and complete-bundle publication.
4. `WorkspaceComposer` and `WorkspacePersistence` own snapshot composition and write timing. `browser-workspace-device.ts` now supplies browser storage and event transport with injected capture ports and elements; the old sidebar/details/scroll controls still provide the current layout state and document-wide input/change/click events remain coarse save triggers. The versioned preference action contract is live and persisted, but today's UI does not yet render light/dark variants or a dock layout. The dock redesign must replace the current layout port with its own restore/certification adapter and preserve off-screen recovery. `browser-file-device.ts` now implements the existing local picker/download/mask-worker port using injected picker elements; a new shell can supply its own controls.
5. `ui-action-catalogue.md` and the facade registry enumerate implemented top-level action/request/gesture payloads and their static scopes, nested variants and Undo policies. `StudioFileOperations` adds a separate typed in-process file workflow contract; its IDs are not yet part of the `StudioApplication` static descriptor registry. `ViewportAttachment.contextAt` now supplies actual adapter hits to `contextQuery`, which returns existing ready/input commands with live capability; `dispatchContext` rechecks stale identity and final domain validation. The application does **not** perform geometry picking or expose coordinate-based shape transforms as standalone menu actions. UV view buttons have a typed attachment command, while wheel pan/zoom and camera orbit remain adapter gestures. `actionsFor` remains representative; piercing style/material choices are now detached, while other renderer assets still need option ports. Structured reason codes still translate some domain error text. Async package cancellation is not supported by the server; show truthful busy/result/failure and retry after completion rather than promising cancellation.

The existing sidebar/accordion markup is an implementation of today's UI, not a design constraint. This extraction makes no aesthetic or layout decision. The current branch has no dockable-panel implementation, and the handoff gate remains unmet.

The nineteenth extraction adds `StudioPresentationPort` and `createStudioPresentation` as a narrow composite entry point for a replacement shell. It wraps only public methods from the application, collection, file, viewport and UI preference services; the shell receives no `AuthoringDocument`, live recipe reference, Three object, worker, transport or SQLite handle. Its aggregate snapshot and individual read methods are detached and typed read-only. Current action/context/gesture transactions, library requests, file/package outcomes, safe same-host viewport rehosting, UV view commands and system/light/dark preference actions remain independently callable. `main.ts` constructs the port after trusted services are wired; in `?verify=1` it exposes the port for isolated acceptance without changing the current controls. `UIPreferenceActions` is now constructed from the restored workspace, included in `WorkspaceComposer` capture and subscribed to persistence, so a future theme/layout action survives reload. A focused fixture uses only the composite port after setup to exercise layer and preset edits, Undo, UV commands and stale context, preview quality, recipe download, package Check result and theme preference. The dock engine must implement theme styling, layout semantics and on-screen recovery using the existing versioned preference contract; this port intentionally supplies no dock-tree policy.

The twentieth extraction moves authoring construction into `createTrustedAuthoringCore` and collection/file/presentation assembly into `createTrustedStudioBootstrap`. The latter accepts device ports and a presentation mount callback; it does not read legacy control IDs or import `main.ts`. Production `main.ts` uses both factories, while a separate test constructs and mounts the complete presentation port with no DOM controls and exercises add/Undo, recipe export and theme choice. Trusted service handles remain inside the bootstrap return object for the composition root; only the narrow `StudioPresentationPort` is passed to the mount callback. This is a real boot path for a replacement UI with its own device adapters, not a copied legacy UI entry point. The complete authoring suite passed 323 tests, type check and bundle build after providing the same three ignored local GLB fixtures.

The browser file/workspace extraction moves picker, download and one-off mask-worker mechanics into `browser-file-device.ts`, and workspace restoration, panel capture, autosave event wiring and write transport into `browser-workspace-device.ts`. Both receive their elements and state ports from the shell and contain no legacy control IDs. The existing `main.ts` still supplies its current input/detail/panel elements, so current behavior and storage keys remain stable. Contract tests exercise selection/cancel, verification-key isolation, activation/ready capture and ID-free panel geometry; the full authoring suite passed 326 tests, type check and bundle build after supplying the three ignored local GLB fixtures. Browser file-picker automation remains unverified in this stage.

**Remaining gate:** the current production entry still creates the Three scene, UV/head editors and their renderer/worker resource ports, and supplies old sidebar/control IDs when constructing file and workspace adapters. A replacement production entry must supply those device adapters and layout capture to the factories, attach preview/motion/saved-V services after scene readiness, and repeat browser acceptance through the replacement shell. The factory and browser-adapter tests prove separate construction and contracts but do not prove a complete alternate browser entry with live head rendering, persisted dock layout or actual file selection. Existing coordinate drags remain owned by mounted editors; they are not standalone commands for arbitrary UV coordinates. Do not hand the current legacy `main.ts` to Opus as a freely replaceable module yet.

## Strict boundary for a replaceable presentation

- Application/core: recipe and collection state, validation, Undo transactions, async collection coordination, workspace composition and preview request policy. It should publish immutable snapshots and typed actions with target-aware capabilities. It must not import DOM nodes, browser events, Three scene objects, raw worker messages or HTTP implementation details.
- Rendering and device adapters: Three scene, texture/canvas/worker resource ownership, picking and coordinate mapping, file picker/download and HTTP transport. These may use browser APIs but must present narrow typed ports to application policy. Keep mask-worker cancellation, complete-bundle publication and fairness exactly as currently tested.
- Replaceable UI: component tree, controls, menus, docking, theme, focus and layout. It may query snapshots/capabilities, dispatch actions and attach viewport ports. It must not mutate `Layer`/`Recipe`, call SQLite/store methods, infer package eligibility from finish labels or steer workers directly. `collection-ui.ts` now uses the narrow view port; `main.ts`, `uv-editor.ts` and `surface-editor.ts` still cross parts of this line and need a stable shell/facade before Opus edits them freely.

For handoff, the remaining critical seams are a replacement shell that receives detached application/collection/file state without constructing or dispatching trusted services itself; a documented combined action/file contract for current workflows; and a versioned workspace preference boundary for Opus-owned dock/theme state. Higher-level coordinate actions and renderer asset choices are useful extensions. Do not make game rendering, hypothetical future menu choices or unsupported package cancellation a prerequisite. Then repeat a compact task-oriented pass through the actual replacement boundary before dispatching the redesign.
