# Saved lash profile collision and brow template cross-check

25 September 2026. This is an offline, read-only follow-up for the reference save's Arkhe Fuller style-18 brow and icxrus Soft Natural `05_brown_liquorice` lashes. The selected MO2 profile was `2025 (again)`; its `modlist.txt` SHA-256 remained `64edf00004f8a283a173671d70390d7b16d22cd64da92af7d05e66682537ab4b`. No game or mod-manager state, Studio draft, preview code or distributed asset changed.

## Source-derived candidates

The existing [selected-hash resolver](../character-customization/catalog-prototype.md) scanned 1,161 physical archive indexes from the selected MO2/manual view plus installed `content`, `ep1` and `hot` game roots. It reported zero index errors, ambiguous active virtual archives or visible archive `modlist.txt` entries. In this explicitly selected MO2 route, Arkhe's Fuller archive was the **unique visible indexed provider** for the saved brow app, morph, mesh, material, primary/secondary/normal textures; icxrus's archive was the unique provider for the saved lash app. These source-derived results strengthen the [earlier mod-only brow census](brow-texture-audit.md), but do not observe a game launch or apply ArchiveXL's runtime assembly.

The lash material dynamically requests `base\\characters\\common\\hair\\textures\\hair_profiles\\brown_liquorice.hp` (uint64 resource hash `13919918321801903732`). **Two visible indexed candidates** exist in the same scan:

The current archive resolver deliberately reports **no source-derived winner** when a base-game archive and a mod archive share the hash: that precedence is not modeled in its acceptance-tested rule. It also reports no runtime winner. MO2's `+` state and this hash collision alone do not prove which payload the photographed session rendered. The current Studio intake (`tools/intake_lash_profile.py`, retired 25 September 2026 in favour of the resolver's R1 archive precedence) pins the **vanilla** SHA-256, so it would omit a materially different installed profile *if* Alliekat wins for this lash. The existing [preview approximation](brow-lash-fidelity.md#lash-colour-source-based-approximation-unresolved-hair-shader) should remain labelled as such.

## Saved choice and assembly boundary

Fresh serialization of icxrus's female customization resource identifies `05_brown_liquorice` as an indexed appearance definition with saved selector swatch `(50,44,40)`. The saved app hash `6047185506343464350` resolves to icxrus's female app, whose source package contains only a `01_blonde_platinum` compiled appearance. The source female lash mesh likewise serializes one `black_carbon@lashes` appearance. Its local `@lashes` material points at icxrus's `.mi`; that instance overrides `Strand_Alpha` and inherits the vanilla eyelash material. The mesh's embedded material binding has `HairProfile = *base\\characters\\common\\hair\\textures\\hair_profiles\\{material}.hp`. The selected `05_brown_liquorice` therefore depends on dynamic appearance/material expansion, not a literal colour texture embedded in the source app.

A historical ArchiveXL 1.26.3 log from **13 September 2026**, SHA-256 `bc717180fdc02718151568dba711f04d45b0cb1f0456329644fdc4ffacf6eaa2`, records loading `CCXL_icxrus_SoftNaturalEyelashes.xl` (line 132) and adding `brown_liquorice` from `archive_xl\\characters\\common\\hair\\h1_base_color_patch.mesh` to icxrus's female lash mesh (line 8506). This is dated evidence that the colour appearance was assembled in that run; it does **not** name a `.hp` payload or establish the source of the photographed game's lash pixels. The source `.xl` scopes the female mesh/morph/app and registers the customization. The currently selected MO2 profile has `enforce_archive_load_order=false` and `reverse_archive_load_order=false`; the resolver saw no visible `archive/pc/mod/modlist.txt`. Those facts constrain mod-archive ordering but do not resolve a mod/base archive collision. Neither an enabled `+` nor a historical mesh-patch line should be promoted to an effective profile-resource winner.

## The payloads are materially different

WolvenKit Console 9.0.1 independently unbundled and serialized the two 1,079-byte CHairProfile resources. Both declare four ID-gradient and four root-to-tip stops and `sampleCount=127`. The profiles differ in colour, not merely file metadata. At the Studio's measured constant placeholder samples—`Strand_ID.r=107/255` and `Strand_Gradient.r=255/255`—the same stop interpolation as `lash-profile.ts` gives:

| Source | ID lookup RGB | Root-to-tip lookup RGB | Channel product RGB | Swatch-fitted browser *study* RGB |
|---|---|---|---|---|
| Vanilla | (106.370, 108.247, 109.911) | (214, 197, 174) | (89.268, 83.626, 74.998) | (48, 45, 41), `#302d29` |
| Alliekat | (123.146, 125.447, 124.563) | (102, 51, 0) | (49.258, 25.089, 0) | (57, 29, 0), `#391d00` |

The Alliekat root-to-tip endpoint differs strongly from vanilla. The rightmost column is **only what the current browser approximation would calculate** after independently fitting each profile to the saved selector swatch `(50,44,40)`. The supplied game/studio comparison shows a darker, slimmer game brow, but its Studio frame predates the corrected double-diffuse brow adapter and does not hold pose, camera, makeup or light constant. This newly found **lash** profile difference does not explain that brow silhouette. It is neither a predicted game colour nor a justification to change the material: the compiled game hair passes do not yield a proven final colour formula or binding table ([earlier program audit](lash-material-followup.md)). The swatch itself may not match a rendered hair card. This profile collision is a concrete candidate for the colour disparity, not a confirmed cause.

A separate brow-template check found resource hash `10501783642502886761` in both `memoryresident_1_general.archive` and `ep1_1_nightcity.archive`. Fresh extraction from each gave **byte-identical** `mesh_decal_double_diffuse.mt` resources, SHA-256 `8546e26140c0a2af78495e20c50c077d686de35435608a253fb3e55ac876bfb7`. Therefore this particular duplicate template cannot explain a material-default difference, regardless of which installed copy is chosen. This does not resolve the brow's normal/post-G-buffer shading or effective Arkhe assembly.

Include all three installed base archive roots (`content`, `ep1`, `hot`); inspect the returned candidates, gaps, container digests and coverage rather than flattening them into a claimed runtime winner. The resolver's source rule is documented in the [catalog study](../character-customization/catalog-prototype.md). The 25 September invocation had 999 profile rows and the hashes/counts above.

Extract each profile separately using `WolvenKit.CLI.exe unbundle <one archive> --hash 13919918321801903732 -o <separate private output>`, then `convert serialize <extracted .hp> -o <existing private JSON directory>`. Keep those resources and JSON under ignored `research/consumers/*/raw` and `*/json`. Read `Data.RootChunk.gradientEntriesID` and `gradientEntriesRootToTip`; sort each by `value`, interpolate at `107/255` and `1`, respectively. `lash-profile.ts` specifies the browser's product and swatch fit. For the brow template, unbundle hash `10501783642502886761` independently from the two named game archives and compare full extracted SHA-256.

The [loader-source trace above](#loader-source-boundary-25-september-2026) establishes only a tool-side mod-first rule and a suggestive depot group layout.
