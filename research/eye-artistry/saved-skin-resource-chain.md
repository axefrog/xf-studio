# Saved skin and mouth resource chain: offline source trace

24 September 2026. This follows the **captured** 2.31 save's `skin_type_05` and `teeth` references through local resource files. It does not identify what the running game loaded. Extraction and decoded images remain ignored under `research/consumers/saved-skin/raw/`; no game/mod pixels or binaries are committed.

## Route and evidence boundary

The save copy has SHA-256 `9e10c26476cb9e6d7a72164f7a2090ee3204c3fe4f23ea85c5353686da5c0748` and records skin resource hash `17283332679908531951`, definition `h0_000_pwa__basehead__01_ca_pale_00_warm_ivory`, in the customization and TPP groups. Its separate teeth entry is hash `4335264894338256315`, definition `female_ht_000__basehead`. The installed vanilla `female_cco.inkcharcustomization` maps these to `base\characters\head\player_base_heads\appearances\head\h0_000__basehead_d05.app` and `...\ht_000__basehead.app`, respectively. FNV-1a path hashes match the saved 64-bit IDs.

The index-only scan used the selected MO2 profile `2025 (again)` (1,161 indexed archives, zero index errors) and, separately, a direct-game/manual-mod route (58 archives, zero errors). These are **source candidates**, not confirmed runtime winners. In particular, the resolver does not yet prove base-game versus mod-archive precedence, effective virtual deployment, REDmod priority, or what was loaded when the save was captured. An unambiguous single candidate is labelled *source-derived* below. The direct route is a different hypothetical installation route, not evidence of the selected MO2 session. Reproduce the scan with the ignored `research/consumers/saved-skin/raw/probe.py` and decimal hashes; WolvenKit Console 8.17.4 `unbundle --hash` and `convert s` supplied the CR2W inspection.

The selected MO2 route has a base copy (SHA-256 `007e5f6afa1b8382e9c4b8f01a5354b69e392279a29d6f8afbb5da258ace4c44`) and Arkhe Smooth candidate (SHA-256 `3dd6d5be85849106004b41c7b39c61bc3d4e2e933bd1794457d711fe7f8d73f9`). The template's `SkinProfile` is `engine\materials\defaults\default.sp` (hash `345814798400471601`): base SHA-256 `b35756e8e610d7304f318ae8e8f7d08fc1507f26b1eb9f6ff7cc56cfd145607b`, Arkhe Warm n Smooth candidate SHA-256 `1c1e3065fdabaf4256112dd707bc4474d255341ca3b42ae8eebd247970fd955b`. Their serialized values differ: blur size 1.4 vs 2.5; lobe mix 1 vs 0.6; falloff `(255,178,165)` vs `(255,155,119)` in RGB. These are source alternatives, not measured SSS behavior or a reason to copy either into the browser blindly.

The selected D05 albedo has a base-game candidate SHA-256 `cc210b3f6b35c4081c7e75ff6db8a616722f58ecfc358137bb153e8e23b04e8f` and Arkhe `Realistic Complexion III – HEAD FAIR III` candidate SHA-256 `659de17df2e47bdec2ea6617276d5b38a79e7d441e0dd52e001db9aaa2b94518`. The normal has base SHA-256 `8629f2213ad22c9ac33531377f3a12afa13aeca6cdb7d3b46bec59abe6b27415` and Arkhe `Face Details – Realistic 01` candidate SHA-256 `03e47ce89b10196166b9e130747b835887edda4c339e003af7a87e282f69cd9d`. The locally decoded mod candidates are 4096² versus 1024² base candidates. The decoded normal has R/G variation and blue fixed at zero; it is a packed input, not a conventional Three RGB normal map. Arkhe's page describes face detail as modifying normal/gloss appearance, but this source scan found no mod override of the inherited `Roughness` path itself. That description does not prove how the shader combines the channels.

The inherited roughness decoded by WolvenKit is 1024² RGBA with R range 41–255 (median 165), G identically **zero**, and B range 115–255. The XBM metadata marks it non-gamma. This establishes that directly feeding this PNG to Three's green-channel `roughnessMap` is invalid; it would read zero at every texel. The numeric distribution alone did not prove the engine channel; the [follow-up compiled variant trace](saved-skin-shader-and-winner.md) now shows R as its base roughness and B as a detail factor, with additional composition before G-buffer output. It still does not prove a final runtime roughness value.

## Mouth assembly is separate

The saved `h053_mouth` is a facial **morph target** on the primary head; it is not a separate saved material. The same save separately selects `teeth` / `female_ht_000__basehead`, via `ht_000__basehead.app` (hash `4335264894338256315`). Two base archive copies of that `.app` are byte-identical (SHA-256 `764c4167bf0063be2559172abf1948dbd9fb1c3847bccdac208fb61d35cb86ac`); an MO2 `Morphtarget and AnimRig Additions` candidate differs (SHA-256 `ebab1c5ce79795a5dcac0d25ca106a01cb419632dfad62e61910eb0039fb2e99`). Both selected definitions reference `ht_000_pwa__basehead.ent` (hash `1487408233268495565`, unique base-game candidate, SHA-256 `52332357fcb398cafd109aa275a86c43aae018166a13ec77e9a576c3acbfd6cc`). Its morph resource `ht_000_pwa__morphs.morphtarget` (hash `4981068608655808581`, SHA-256 `fe1a9f91909d62a42faaf294c7cbc2c41c6acd5a99b56ac38e62f6591a370963`) refers to `ht_000_pwa_c__basehead.mesh` (hash `1542277068820920572`, SHA-256 `076cb660a2e72b1c3e4a43eee53ea12d865ca45389b465ead445111f4fae2e48`). These entity/morph/mesh resources each have one source candidate in both routes.

The teeth mesh's default material inherits `base\characters\common\teeth\teeth_base.mi` (hash `8172030460762459993`, SHA-256 `828dd0d342e978b93fc07239032cf8a2e9231cb921e03ec8da749e273e60594c`). It supplies separate teeth Albedo/Normal/Roughness textures and inherits the same `skin.mt`, but the mesh overrides `SkinProfile` with `customisation_teeth.sp` (hash `17881922866521434132`, SHA-256 `5a43b4550e9a9861151ef397041c229170ecedac9512979b9fa8d46bfe65de00`). That profile has blur size 1, zero falloff RGB, lobe mix 1. This trace establishes a distinct material source for the visible teeth. It does **not** prove which parts are visible at Nathan's closed-lip camera pose or resolve every tongue/inner-mouth component.

## What this says about the white lip seam

The isolated [A/B comparison](../../projects/xf-appearance-studio/authoring/evidence/render-fidelity-study-2026-09-24.md) observed that uniform browser roughness removes the bright line at one fixed neutral camera/light, while flat normals do not. This is **browser evidence** for the old roughness/light response, not proof of the game's cause. The current browser head uses old Blender-master colour/normal/roughness tiles (SHA-256 values in [the optics audit](eye-lip-optics-audit.md)), whereas the saved choice points to a D05 head material with a different roughness XBM and several profile-enabled mod candidates. The maps are different in source, resolution, packing and material logic. Thus the browser's current input chain is demonstrably mismatched to the saved selection; the exact channel and whether the game's own lip line exists are unresolved. Copying the native XBM's G into Three's roughness slot, or applying generic SSS, would not be a valid correction.

The [follow-up source-order and compiled-shader trace](saved-skin-shader-and-winner.md) narrows the current MO2 expectations and identifies this 2.31 `skin` variant's R/B roughness and RG normal arithmetic. It does not establish historical or live winners. Next gate: verify the launch route and effective resource providers, then validate UV/geometry correspondence before an explicit local map adapter compares matched pose, FOV and lights. A batched matched game capture can then test likeness and the real lip seam; no new game launch was needed for this offline work.
