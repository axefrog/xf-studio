# PRC catalog boundary: active slots, shared colours, and source winners

24 September 2026. This is a read-only audit of Nathan's installed MO2 profile and private, previously extracted resources. It extends the [PRC inventory](prc-inventory.md) and [three-slot preview](prc-preview-slice.md); it does not establish a running game's archive winner, grant rights to ship eagul's resources, or implement jewellery authoring.

## Active resource set

`F:/Games/MO2/profiles/2025 (again)/modlist.txt` (SHA-256 `64edf00004f8a283a173671d70390d7b16d22cd64da92af7d05e66682537ab4b`) marks exactly three PRC-named folders enabled: **PRC - Fully Modular Jewellery Framework**, **PRC - Nose ring on both sides (front)** and **PRC - Nose stud**. The other 15 PRC-named folders and **Stretched Septum 2 For PRC** in the [inventory](prc-inventory.md#installed-candidates-and-slot-collisions) are disabled in this profile. This scan covers those named folders, not every archive in the MO2 installation. Their enabled candidate item archives provide `fpm50`, `fpm72` and `fpm74`; the framework contains the `fpm1`–`fpm128` placeholders and the replacement `i0_000__earring_14.app`. The stud folder also contains `nim_piercings_recolor_silver.archive` with `base\eagul\mat_1.mi`. No other active PRC item slot was identified by this bounded scan.

MO2's selected profile and `enforce_archive_load_order=false` support an **offline candidate**: the `PRC_f_*` item archive names precede `PRC_z_999_Framework_128.archive` under the maintained game's alphabetical-first default. The framework and items compete on identical `fpmN.morphtarget` depot paths; item bytes must win for the intended shapes to appear. A profile `+`, installed bytes and an inferred filename order are distinct from a measured launch winner. Direct launch without MO2, an existing generated `modlist.txt`, later deployment, or another archive targeting the same hash could change that outcome. The [provider-neutral resolver contract](../character-customization/mod-source-resolution.md) describes the file-winner, archive-hash-winner and framework stages that a general catalog must keep separate.

## The game's selector is a bank, not three style choices

The previously pinned framework `.app` (SHA-256 `01d4cf980d5531a76fd7424555356103979f48a4d4a60e297ba67074529abe13`) contains **16 female colour definitions** and 16 male definitions. Every female definition contains the complete, ordered `fpm1`–`fpm128` component list, including the same `fpm50`, `fpm72` and `fpm74` morph-resource hashes in every colour. For each definition, all 128 female components use one shared `meshAppearance`: `silver`, `gold`, `plastic_black`, `cooper`, `plastic_red`, `plastic_pink`, `pearl`, `blue`, `mixed`, `mixed2`, `neon_teal`, `pink_metalic`, `rainbow`, `rose_gold`, `steel`, or `wood`. The `i0_000_pwa__earring__NN_*` definition chooses the colour for the **whole bank**, not an independent colour for each installed item. The same-path morph replacement changes a slot's geometry, not this appearance structure.

This means the current studio's separate `prc_fpm50`, `prc_fpm72`, and `prc_fpm74` selectors are useful **single-slot diagnostic previews**, not a representation of the game's option-12 behaviour. If all three item resources win and their geometry is nonempty, the framework `.app` includes all three components in the one selected appearance. A faithful aggregate preview should show the resolved active slots together, with one shared colour choice; independent per-slot visibility can remain an expressly labelled inspection control. The installed resources do not establish that a PRC item is its own new character-creator selector.

The mesh appearance names also exist in all three inspected base meshes: the stud's item-local `fpm50_linked.mesh`, the framework's `wa_linked.mesh` used by `fpm74`, and the game's `i1_000_pwa_c__basehead_earring_03.mesh` used by `fpm72`. This is a source-supported route to **cataloguing** all 16 variants, but not a claim that the present browser shader reproduces their materials. The stud base mesh has two submeshes. In each named colour appearance its first chunk uses the colour-specific `*__01` material, while the second uses `default__02`. In that mesh's local material table, `silver__01` refers to the game's `i1_000_base_03__silver.mi`, but `default__02` refers to `base\eagul\mat_1.mi`. The latter path is supplied by the stud folder's separate recolour archive. Its actual selected shader, stone appearance and conflict winner need their own material resolution. The current private preview shades both stud chunks approximately silver, so it cannot validate the diamond/stone yet.

## Safe incremental catalog route

1. Capture a provider snapshot with explicit profile, enabled flags, file-priority/overwrite evidence, effective archive-order evidence and each archive's resource-hash candidates. A scanner should include inactive candidates for diagnostics but never render them as active. A collision such as the disabled alternatives for `fpm74`, `fpm75` and `fpm17` must retain all providers and an unknown winner until order is supported.
2. Parse the effective framework `.app` as a **sparse bank**: one option resource/definition family, 128 slot component descriptors, 16 sex-specific appearances, their chunk masks and shared mesh-appearance names. Only slots with an active, resolved non-placeholder resource and verified private geometry need a preview asset. Placeholder presence alone is not an installed jewellery style. Preserve the exact provider, depot path, app hash, morph hash and asset digest for each resolved slot.
3. Resolve each morph's `baseMesh` from the active source set plus the game archives before conversion. Slot 50 needs its item-local linked mesh; slot 74 needs the framework linked mesh; slot 72 uses a game mesh. A game-only export silently loses skin for 50/74, as the [three-slot verification](prc-preview-slice.md#linked-mesh-resolution-for-slots-50-and-74) showed. Validate morph/skin structure and hash-pin ignored local GLBs. The current preview manifest's eight-asset cap and silver-only hard-coded intake are appropriate for this bounded trial, not a generic 128-slot importer.
4. For colour preview, follow `meshAppearance → mesh appearance chunkMaterials → materialEntries → local/external .mi` separately per submesh. Preserve unresolved material, texture and `.mlsetup` edges. The current vanilla 8–16 tint correction is only an approximation for these PRC materials. An aggregate view can initially use labelled approximation while exact material inputs are resolved.
5. Keep PRC's pre-CCXL replacement-bank model separate from a future owned-asset export route. The [CCXL file chain](../character-customization/file-chain-map.md) and [PRC inventory](prc-inventory.md#preview-and-future-implementation-routes) identify `piercings`/`piercings_color` as candidate creator slots, while an EquipmentEx item is another route for earrings. Neither demonstrates that third-party PRC assets can simply migrate to CCXL, that independent per-piece colours persist, or that face morphs and saves will behave correctly. Build and test owned geometry only after Nathan reviews jewellery authoring.

No prototype code is proposed here: this audit found a semantic mismatch between the current diagnostic selector and the game's one-bank model, plus material/winner gaps that a generated UI alone cannot close. A data-driven **offline catalog** is feasible; an exact active-game preview still requires source-winner resolution, per-submesh material work and a batched runtime comparison.
