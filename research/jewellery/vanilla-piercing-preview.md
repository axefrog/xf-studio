# Female vanilla piercing preview — resource-backed slice

Game files: Cyberpunk 2077 2.31 (`GameVersion` 2310 in WolvenKit JSON), inspected 24 September 2026. The local source is the installed game's `basegame_4_gamedata.archive` and `basegame_4_appearance.archive`, not an assumed MO2 winner. WolvenKit Console 8.17.4 extracted, serialized and exported the resources. [The intake digest record](../../projects/xf-studio/authoring/evidence/vanilla-piercing-intake.json) pins the exact serialized customization, 14 appearance resources and four GLBs used for this preview.

The female `base/gameplay/gui/fullscreen/main_menu/female_cco.inkcharcustomization` has a `piercings` `gameuiSwitcherInfo` with Off (`piercings_00`) and 14 style choices (`piercings_01`…`14`). Each style names a `gameuiAppearanceInfo` in `headCustomizationOptions`, with `piercings_color` as `uiSlot`, a `.app` path and 16 indexed definitions. For example style 01's silver definition is `i0_000_pwa__earring__01_silver` in `base/characters/head/player_base_heads/appearances/head/piercings/i0_000__earring_01.app` (FNV-1a resource hash `13134131550013307257`). This `.app` has three female morph-skinned components, matching `partsValues` `.ent` resources and `partsOverrides` by component name. The overrides choose `meshAppearance = silver` and decimal unsigned 64-bit `chunkMask` values. Each component's `.morphtarget` points to the corresponding female base `.mesh`. Exported `i1_000_pwa__morphs_earring_01`…`04` GLBs together contain the geometry needed by these 14 female styles, with per-chunk names, skin weights and ear/nose/mouth/etc. morph targets. The current save has **no matching vanilla piercing appearance**; the studio therefore offers an independent viewport-only choice rather than inventing a saved choice.

## Reproduction and boundary

Extract the current female CCO from `basegame_4_gamedata.archive`; extract the 16 `i0_000__earring_XX.app`, four female `i1_000_pwa__morphs_earring_0X.morphtarget` and four corresponding base `.mesh` resources from `basegame_4_appearance.archive` with WolvenKit `unbundle`. Serialize CCO and apps with `convert s`; export the four morph targets to GLB with `export -gp <game folder> -o <existing output directory>`. Place the resources under ignored `research/consumers/vanilla-piercings/raw` and GLBs under sibling `export`, then run `bun tools/intake_piercings.ts` in the authoring project. This derives the 14×16 catalogue from the serialized CCO and `.app` contents, validates mesh parts/64-bit masks, copies GLBs to ignored `public/assets/piercings`, and emits a hash-checked local manifest. No personal path or game asset enters the portable recipe or tracked application bundle.

The exact extraction filters for this snapshot were `female_cco\.inkcharcustomization$` against the gamedata archive, then `appearances\\head\\piercings\\i0_000__earring_([0-9]{2})\.app$|i1_000_pwa__morphs_earring_0[1-4]\.morphtarget|i1_000_pwa_c__basehead_earring_0[1-4]\.mesh` against the appearance archive. Both used `unbundle <archive> -o <ignored raw directory> -r <filter>`. `convert s <ignored raw directory>` serialized those extracted resources; `export <four .morphtarget paths> -o <existing ignored export directory> -gp <game folder>` produced the GLBs. The tool records its version and the game's resource version in each JSON header; the intake rejects cross-version app/CCO mixtures.

The preview retains native female geometry, submesh masks, morph names and skin influences. It chooses one read-only style/colour pair or follows a *single exact* saved app-hash+definition match, with an independent visibility toggle; reload restores that preview state. The current MO2 profile includes PRC's replacement for vanilla `i0_000__earring_14.app`, so this intentionally vanilla catalogue should not be mistaken for Nathan's effective runtime style 12. PRC deserves its own preview adapter and source-resolution pass. Male geometry is outside this female-head slice. No game launch was needed.

## Colour correction, 24 September

Nathan observed that choices 8–16 rendered black. The female CCO's `definition.color` is literally `(0,0,0)` for all nine, while choices 1–7 have usable swatches. Thus the studio had fed a UI placeholder directly into every mesh material. Each of the 16 `.app` appearances instead names a `meshAppearance`; the four current female base meshes map those names to local material entries, whose `.mi` resources point to one of 16 `.mlsetup` files. Those setups select layer colours from 15 `.mltemplate` palettes. The chain comes from the installed game's 2.31 `basegame_1_engine`, `basegame_3_nightcity`, `basegame_4_gamedata`, and `basegame_4_appearance` archives; exact serialized input digests are in the intake evidence.

The local intake now requires this chain and rejects absent/version-mismatched palette entries. It retains CCO swatches as source UI data, but records a separate `previewColor` in the ignored manifest: choices 1–7 keep their existing visible swatch, and 8–16 use a linear-space, opacity-weighted mean of the active source layer palette values converted to display RGB. For example, style 01 blue derives `#4981be`; neon teal derives `#54f5d2`. All 14 styles × nine formerly black choices now derive nonblack tints. A changed local manifest schema rejects old intake output instead of silently showing black; rerun the intake with its third material-source argument after extracting the 48 `.mi`, 16 `.mlsetup`, and 15 `.mltemplate` resources to ignored local folders.

This is a representative browser tint, **not** REDengine multilayer rendering. The `.mlmask` and surface textures still control where blue, rainbow, wood grain, etc. appear in game; averaging their palette values flattens those patterns. The browser continues to use one metalness/roughness response and ordinary environment light. Exact coated plastic/pearl/rainbow looks, per-chunk external materials, bone physics, effective mod archive precedence and game rendering remain unresolved. No extracted resource is shipped or committed.
