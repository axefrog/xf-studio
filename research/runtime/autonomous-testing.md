# Autonomous in-game testing of XF Runtime Bridge

**Proposal with items 1 and 3 implemented offline, 24 October 2026.** Baseline: `main` at `f014a98f`; bridge 0.8.10 observed in session 17, 0.8.11 built offline for session 18. The assertion runner and pipe-sampled walk regression are implemented and fixture-tested; native recording, new taps and autonomous play remain proposed. No game launch, deployment, driver installation or capture is authorised by this document alone.

Build the assertion library first, then a bounded recorder and taps into the systems producing the effects. Use those to run increasingly capable test routines. Add pixels and sound as independent evidence, and external input only where a direct game integration cannot yet do the job. A general game-playing model is unnecessary for the first useful release.

The maintainer's governing rule, verbatim:

> Visual/audio/input external layers are always a fallback for what you can't do more precisely by directly integrating yourself into the game's systems. If something can happen in game at runtime, there *must* be a system for that, somewhere.

His framing is **“You are The Borg. Inject your nanites into the system and take control.”** Here that means finding the owner of an effect, observing its real inputs and outputs, and driving it through a small, bounded interface. When that owner or a usable observation point is unknown, the result is **“system not yet located”**, with a research task. It is not an excuse to start with OCR or blind key presses.

## Observe the producer, the consumer and the result

For each effect record this chain:

`test action → producing system → consuming controller/engine state → rendered pixels or audible samples`

Use four verdicts: **PASS**, **FAIL**, **INCONCLUSIVE** (missing, stale, dropped or ambiguous evidence), and **NOT RUN** (including unavailable fixture or consent). A refused action can be an expected PASS. An accepted command alone cannot prove its effect. Every verdict names which part of the chain it covers.

Examples of useful failures:

- A subtitle request contains the right text, but no line widget is created: a delivery or settings/eligibility problem. An intentional suppression is recorded with its reason, rather than called a rendering failure.
- The line widget has the right text and visible bounds, but OCR finds no text in an unobscured capture: a rendering, layering, capture or coordinate disagreement to investigate.
- A voiceset request reaches audio dispatch, but the game-only loopback is silent: a bank, voice, mixing, routing or output problem. Dispatch alone never proves audibility.
- The requested face is smile, but an observed animation feature changes to anger; or both say smile while the face crop stays neutral. These are different bugs.
- An input was submitted, but the action listener did not receive it; or the action was received and the selected dialogue line was never committed.

**Important sampling correction:** current [`Npc.hpp`](../../projects/xf-runtime-bridge/native/src/core/Npc.hpp) sets `kPollSeconds = 0.25`; [`Npc.cpp`](../../projects/xf-runtime-bridge/native/src/core/Npc.cpp) serialises cached positions/yaw in `npc_status`. Polling it at 10 Hz does **not** produce ten fresh samples per second. Tier 0 can catch sustained backwards walking at the existing 4 Hz; Tier 1 must sample at source and report actual cadence for a genuine 10 Hz trace. Likewise, the event probe's 512-entry ring and 20/s/kind cap cannot serve as an unlimited recording ([reference](../../projects/xf-runtime-bridge/docs/mcp-reference.md#test_events)).

For a walking sample, derive horizontal velocity from successive fresh positions. In the game's yaw convention, forward is `(-sin(yaw), cos(yaw), 0)`. Over displacement windows of at least 0.25 m and speed above 0.3 m/s, calculate the dot product of unit velocity and forward. Initial proposal: forward `dot > 0.5` for at least 90% of travelling time; backwards `dot < -0.5` for at least 0.5 s fails. Exclude a declared turn/settle interval, cap it, and report sideways travel separately. Calibrate against an observed forward fixture. Missing yaw, no displacement, stale samples or an early despawn are inconclusive. Root facing does not prove head direction, gait animation or foot contact.

## Prioritised tiers

Effort below is rough focused engineering time, including targeted tests, not elapsed calendar promises. Tiers are capability boundaries, not a requirement to finish all of one before a cheap, valuable part of the next. The first delivery is Tier 0 plus selected Tier 1 taps; then thin independent cross-checks. Combat and kernel drivers wait.

### Tier 0 — assertions over existing reads

**Producing systems:** the current bridge, game-state systems, event producers, logs and save writer. Add no sensor. Extend [`tools/session.ts`](../../projects/xf-runtime-bridge/tools/session.ts), which already plans catalogue commands, expected refusals, reports, restore steps and aborts. Put pure predicates in proposed `tools/testing/assertions.ts` and time-window evaluators in `tools/testing/windows.ts`. Use the existing `CommandApi` and advisory session lock; MCP and the runner must not compete for the main pipe.

Implemented predicates are `equals`, `range`, `eventually`, `stable_for`, `no_event`, `sequence`, `rects_disjoint`, `moves_forward`, `restored`, `no_loss`, `actor_arrived`, `actor_released` and `bridge_ready`. Assertions bind a command result or event cursor, fixture, deadline and evidence grade. Absence assertions require a complete observed interval. Validation rejects unknown fields and guessed command parameters. `xfb/session-script-2` adds explicit result bindings and assertions; schema 1 remains compatible. Its closed TypeScript assertion union and JSON schemas live in `tools/testing/assertions.ts`, observation policies in `windows.ts`, and bindings/checkpoint execution in `script.ts`. There is no expression evaluator or script execution route.

An implemented schema-2 observation and assertion (after a command bound its returned handle as `spawn`):

```json
{"do":"observe","command":"npc.release","subject":"$spawn.who","input":{"who":"$spawn.who","how":"walk_away"},"timeout_s":30,"bind":"release"}
{"do":"assert","check":"moves_forward","window":"$release","min_distance_m":0.25,"max_backwards_s":0.5}
```

Capture the event cursor **before** starting a command and pass `after` to waits. Bind returned actor handles and message IDs; never assume `a1`, `p1`, latest save or last question. Save file identity and completion matter more than an acknowledgement. Automatic report fields: row/subcheck, predicate/version, inputs, expected/actual, source time, evidence pointers, missing data and restore outcome. Keep factual/geometry PASS distinct from rendered/audio PASS.

**Tools/licences/location:** existing Bun 1.4.2 (MIT), TypeScript 7.0.2 (Apache-2.0) and XF code (MIT); no acquisition. New downloaded copies, if needed, follow `D:/Dev/tools/bun/1.4.2/` and `D:/Dev/tools/typescript/7.0.2/`; npm project dependencies stay locked in the existing project. OS/process/file reads reuse the current tooling.

**Effort:** 1–2 days for a useful assertion core and several converted rows. **Risk:** circular oracles, event races and treating no data as success. Replay captured bad sequences from sessions 15–17, including backwards-after-turn and lost-event cases. Unit tests prove predicates, not the game effects. External sensing is optional corroboration, never required to start this tier.

### Tier 1 — source taps and a rich, synchronised session recording

**Producing systems:** L/B/F/U/C/P above, followed by the native A research spike. First implement subtitle/voice/facial/UI hooks close to existing bridge code. Own recording in one native service, proposed `native/src/core/Recording.{hpp,cpp}` with game adapters in `native/src/plugin/HandlersRecording.cpp`, `redscript/XFRuntimeBridgeRecording.reds`, and a small CET draw-metrics adapter beside the existing CET window. Do not put policy or file encoding on an audio/render callback.

Proposed catalogue commands are `test.record.start`, `test.record.read`, `test.record.stop` (MCP `test_record_start/read/stop`), with explicit channels, actor IDs, rate, duration, byte cap and `since`. Declare them test-profile-only. Starting/stopping observation changes recorder state, not the world; callbacks obey the live gate before game-system access. Put catalogue definitions in proposed `tools/api/catalogueTesting.ts`, regenerate the MCP reference, and use `tools/testing/recording.ts` to stream private files.

Record V position/velocity/PSM/health/heat; actor entity/generation, position/yaw/AI motion/target/prepared state; camera transform/FOV/projection; UI visibility/rect/text identity; subtitle/voice/face requests and consumer outcomes; interactions and lifecycle events. Use 5 Hz for broad state, 10 Hz for directed actor/camera motion, 20 Hz only for a short diagnostic window. UI events are event-driven, with geometry on change/settle; expensive inventory/quest summaries are on demand, not 20 Hz. Never scan the whole world per frame.

Every sample carries schema version, process/session/world generation, monotonic source timestamp, game/simulation time where safe, tick, sample sequence, channel, validity/age and drop count. QueryPerformanceCounter is the shared host/plugin timebase; calibrate round-trip offset/uncertainty for any process that uses a different clock. Captures/audio have acquisition start/end time and uncertainty, not just file-write time. Reset entity identity on load so recycled IDs cannot attach old actions to new NPCs.

The producer writes fixed-size, bounded records to a preallocated queue; one off-thread consumer encodes them. No blocking pipe write, heap-heavy JSON or unbounded name lookup in audio/render hooks. A full queue drops with per-channel counts; critical-event reserve and a visible loss flag prevent a false silence PASS. One tools connection drains batches at 2–4 Hz under the current request budget (20/s native, client paced below it). Reuse source samples for predicates and live view; never add a second polling owner. Close callbacks on detach and unregister handles; a new world reattaches cleanly. Stop requests need the existing emergency route even while the main pipe is busy.

**Initial budgets to measure, not claimed results:** at most 32 nearby subjects, 16 MiB native buffering, 128 MiB tools buffering, 64 KiB/s average telemetry and 512 MiB telemetry/session cap. Target added game-thread p95 under 0.5 ms and no sustained p95 frame-time regression over 3% in paired routes; record hardware/settings, confidence intervals and perturbation. If sampling costs exceed budget, flag/reduce optional channels and preserve actual rates. Do not lose high-rate events silently. Three-load idle experiments disable recording and game taps between loads as the card specifies.

**All sound, before waveform analysis:** first B and script-call observations; then native A. A hook should see names before hashing when possible, and IDs, source/emitter mapping and timestamps at lower dispatch. Track event-post success/playing ID, emitter creation/removal and existing completion callbacks where observable. Preserve original calls/return values; do not inject new Wwise callback flags merely to observe. Verify separate routes for UI ping, voiceset bark, scene dialogue, gunshot, footsteps, vehicle, music and ambience. Continuous music, procedural audio, virtual voices and Audioware may need separate producers. Until coverage is measured, say “covered dispatch paths”, not “all audible sound”. Native hook addresses/ABI are version-gated and refuse unsupported builds. No proprietary Wwise SDK is automatically required or redistributed; use the game's ABI only after source/disassembly validation and a licence check if SDK material is needed.

**Proposed live 3D view:** consume this same recording for replay or a live sparse scene: V, actor capsules, headings, paths, targets, camera frustum, sight rays, pins, occluder hits and event markers. Draw stale objects distinctly; display uncertainty and omitted geometry. It is a world-state instrument, not a reconstruction of Night City and not evidence of final rendering. A simple Three-based viewer can reuse repository rendering dependencies later, with its own ownership agreement; it is not first-sprint UI work.

**Tools/licences/location:** existing C++/RED4ext/redscript/CET toolchain and Windows `QueryPerformanceCounter`/process APIs; XF additions MIT. Register any acquisition per AGENTS.md.

For conditional freeze evidence, propose `native/tools/dump/xfb_dump.exe`, an XF MIT helper using Windows DbgHelp [`MiniDumpWriteDump`](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/nf-minidumpapiset-minidumpwritedump) with the appropriate full-memory flags. ### Tier 4 — input, from the game outward

**Producing systems first:** drive the player/menu/interaction/input systems and observe received actions plus committed outcomes. Use current `player_teleport`, `player_look`, `player_action`, `player_interact_list`, `behave_look` and `behave_glide_path` where appropriate. `glide_path` uses per-tick teleports and explicitly reports `animated:false`; it cannot validate walking animations, normal locomotion, pedestrian collisions or a gunfight. Current player writes refuse combat/vehicle/scene states; retain those gates.

Implement input in this order:

1. **System requests already used by the game.** Menus, equipment, crouch, camera, save loading and NPC AI commands. These are enough for many setup steps without keyboard/focus.
2. **Retail game input lead:** [24 October's input research](../../knowledge/input-and-choices.md#5-r1-general-input-dispatch-and-native-hook-points) used session 7's `input_probe` RVAs to inspect the matching executable. Press/release/axis action wrappers read **5/1/3** arguments despite empty RTTI; key/axis helpers acquire a receiver through `gameIPlayerManager` and reach its virtual dispatch. `FakeReleaseButton` omits the dispatch, but a separate native test-command handler reaches the release helper. Finish receiver/ABI/return/lifecycle and release/neutralisation validation before any pulse; then prove receipt and effects in gameplay, menus, title/load, foreground/background and teardown separately. The player-manager route does not establish title support. Codeware's `RawInputBuffer` remains an ink observation/injection lead, not proof gameplay consumes appended records.
3. **OS fallback:** tightly bounded Win32 `SendInput`, extending [`tools/input/photo-key.ts`](../../projects/xf-runtime-bridge/tools/input/photo-key.ts). SendInput is an OS-wide stream, **not HWND-targeted**, even after checking the foreground window. Recheck executable/PID, window, focus, UI phase and session lease before each small batch; observe action receipt and outcome before the next. Foreground can change between check and send, so a residual race remains. Do not advertise safe background keyboard input. [Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) documents UIPI blocking and return-count checks. A privilege mismatch is a refusal, not a reason to auto-elevate. `PostMessage` does not supply the game's Raw Input path ([player control §6](../../knowledge/player-control.md#6-how-input-reaches-the-game-and-synthetic-input)).
4. **Driver fallback only after a documented failure of the above:** Interception for keyboard/mouse, or a virtual controller such as ViGEm for gamepad input. These are different device classes; ViGEm is not raw mouse injection. Require a separate installation decision and compatibility trial. Never silently install a kernel driver or change a real device binding.

Proposed `test.input.action`/`test.input.pointer` and `test.input.release_all` expose allowlisted actions, bounded duration and a goal/context token, not arbitrary code or unrestricted device commands. Bind dialogue input to exact world/hub generation and selected option text/hash, then confirm committed result. A focus loss, user input, bridge pause, kill, detach, deadline or lost heartbeat neutralises synthetic axes/buttons. Only release keys owned by the test; never clear the user's physical holds. A separate host watchdog handles a wedged game or dead connection. Keep existing `XFB_NO_INPUT=1` for offline tests.

### Tier 5 — autonomous behaviour scripts with awareness

**Producing systems first:** C/I/navigation/targeting/AI/perception. Extend the existing [`Behaviours.cpp`](../../projects/xf-runtime-bridge/native/src/core/Behaviours.cpp)/`.hpp` service, rather than running a frame-by-frame LLM loop. ## A credible proxy user

The proxy has a **body** (the real game input/system requests), **senses** (producer and consumer telemetry with timestamps), **independent eyes and ears** (private output captures used as cross-checks), **reflexes** (bounded in-process behaviours), and **memory** (a replayable recording and assertion report). A planner sets the card's goal, reads compact state summaries and adjusts policy between routines. It does not need to react to every frame.

Credibility comes from triangulation and negative tests. The proxy must demonstrate that it catches known bad behaviour: backwards motion after a successful turn; a requested but uncreated subtitle; a visible widget clipped by its parent; a voice event with silent output; a smile held by the bridge but replaced by the animation system; a highlight that never committed; an actor left behind after cancellation. Inject such faults in the self-test/fixture layer, then confirm representative failures against actual game instrumentation in an approved session. A simulated response is never runtime evidence.

The session output should be one readable card report with links into a time-aligned timeline: action, producer, consumer, raw state, capture/audio excerpt, verdict and cleanup. Automatically file friction candidates such as repeated retries, ambiguous state, unseen spawns, missing instrumentation, unexpected focus loss, poor progress and slow steps. These supplement the maintainer's friction log; they do not decide which experiences are annoying.

Human judgement remains essential for beauty, warmth, natural acting, readable pacing, comfort, “does it feel right?”, surprising story consequences and whether the autonomous proxy represents a real user's habits. Machines can measure clipping, spacing, cadence and repeatability and present compact before/after evidence. They cannot replace the independent UI design lead's review or turn an expression classifier score into aesthetic approval. The goal is that the maintainer spends a short review on judgement and occasional new-system commissioning, not every session on repetitive driving or transcribing numbers.

## Risks and operating limits

- **Consent and a shared machine.** Session approval covers launch/foreground/capture/actions for that run only. A foreground lease is exclusive while input or desktop capture needs it; losing focus stops those operations. Direct integration can work in the background where proven, but user input always pre-empts automation. No unattended scheduler that steals focus during the maintainer's work. Never resume input automatically after focus loss or user takeover.
- **Input containment.** In-process routing is preferable because OS input cannot be atomically bound to a game HWND. Keep bursts short, track synthetic ownership and install an out-of-process neutralisation watchdog. Driver injection increases machine-wide risk and maintenance work; it is not the default answer to foreground conflicts.
- **Anti-cheat.** No anti-cheat component is identified in the bridge sources/session evidence for this single-player 2.31 target. That is not proof about every future distribution or mod. Preflight inventories the executable, loaded modules/services and installed multiplayer/online modifications; stop on an unfamiliar protection layer and investigate. Do not add evasion, spoofing, stealth hooks or disable another application's protection. The proposal requires no anti-cheat bypass.
- **Determinism.** Pin game/framework/candidate hashes, settings, resolution/aspect/DPI, language, save/quest state, time/weather, outfit, route and test-side seed. Engine randomisers, traffic, streaming, adaptive AI and GPU scheduling still vary. Use known fixture volumes, invariants, tolerances, paired off/on trials and repeats. Refuse unavailable routes (the pre-heist save cannot freely visit Corpo Plaza); do not force quest facts to make fixtures pass.
- **Observer effect and memory.** Source sampling is cheaper than repeated full scene enumeration, but not free. Session 17's memory data separates play-heavy growth from small per-load growth; it does not establish a bridge leak. Budget and record telemetry/encoding/analysis overhead separately. Use `tools/commit-tripwire.ts` at the current 4 GB free-commit floor with the row's off switch, and the repository memory guard for heavy offline work. A floor trip means stop/retry when capacity changes; a per-job limit kill means investigate, not raise the limit blindly.
- **Capture cost.** A 3840×1600 BGRA frame is about 23.4 MiB; 20 raw frames/s is about 469 MiB/s before copies. Do not queue full-resolution raw video. Crop/downscale, encode in a bounded worker, retain a short disk-backed event ring, and cap duration/size. Initial video budget: 720p/15 fps, at most 8 Mbit/s and 1 GiB/session; reserve full-resolution stills for named events. Measure actual encoder GPU contention. Start analysis sequentially after play under a 1 GB tripwire for small OCR/CV jobs and a measured, slightly higher cap only for a model that needs it.
- **Audio cost.** Two-channel 48 kHz float audio is about 0.37 MiB/s; a mono 16 kHz PCM16 analysis copy about 0.031 MiB/s. Disk-spool short windows; don't keep a session in RAM or run transcription against the game's GPU by default. ASR/VAD false positives need dispatch/text correlation and a silence baseline.
- **Crash safety.** Respect the live-script gate, game-thread ownership and unknown-object rules. Native audio/render callbacks touch no game objects. Version/ABI mismatch disables the tap; missing observations cannot become a PASS. Add heartbeat/progress diagnostics before optional full-memory dumps: a live pipe can coexist with a hung main thread. A full dump may be tens of GB; preflight disk/commit cost and capture only under the session's explicit diagnostic allowance. No automatic relaunch loop after a crash.
- **Privacy and public-repository hygiene.** Saves, raw IDs that identify a playthrough, game-derived text/resources, images, audio, video, dumps and full logs stay private and ignored in `local/sessions/<session>/autotest/` or existing private capture locations. CPU-heavy scratch belongs on `%USERPROFILE%/xfs-scratch/<task>/`, then is cleaned after durable evidence is moved. Installed tools follow `D:/Dev/tools/<tool>/<version>/`; heavy active data stays on the fast drive, not the tool archive drive. Do not commit private payloads or copy absolute user paths into reports. Public outputs contain code, schemas, asset-free fixtures and sanitised aggregate results only.
- **Capture boundaries and network privacy.** Prefer game-process audio and game-window images. Desktop duplication and endpoint loopback can expose other apps, so they require explicit session scope and stop/discard on ownership loss. Local analysis uses no cloud upload and no microphone; block model-library telemetry. An MCP client may transmit tool results to its model service: raw captures/text/audio are not returned automatically. The maintainer chooses what evidence to share; local/private does not imply private once sent through a remote AI client.
- **Ownership and scope.** Preserve the current bridge action catalogue, permission gates, emergency pipe, save lock and one-owner architecture. The coordinator files implementation work in the existing queue and agrees shared files/resources before code changes. Prioritise repetitive checks and session friction alongside existing polish/R&D; general autonomous play follows proven test value. Knowledge pages are updated with source/offline/runtime grades when new results exist, not merely because a proposal names a hook.

The destination is the maintainer's single-session yes followed by a complete watched, hands-off run. Each step toward it should replace a particular human task with a test whose evidence can be inspected and trusted.
