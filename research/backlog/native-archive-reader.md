# Native archive and resource reader

**Status (27 September 2026): phases 1 and 2 done and hardened (NATIVE-01..34 and 40..45 fixed except NATIVE-44, [budgets](#budgets) below); the resolver and the creator catalogue's texts read natively first, with WolvenKit per resource, and WolvenKit is optional until export (`claude/native-integration`, `claude/native-catalogue`); phase 3 (textures) done (`claude/native-textures`); phase 4 planned.** A TypeScript reader for the game's `.archive` container and CR2W resources. It decompresses through the Oodle library in the user's own game folder (`bun:ffi`), so XF Studio never ships the DLL. It writes the same JSON documents the resolver reads from WolvenKit. It removes WolvenKit from the resolver's user path: a first preparation that took minutes of WolvenKit launches takes seconds. It also becomes the base for the texture and mesh exports that still need WolvenKit. The format itself is documented in [archive and resource formats](../../knowledge/archive-format.md).

**In production.** The resolver host opens one native decoder per game folder (a worker) and reads every resource natively first, falling back to WolvenKit per resource ([mod loading §6](../../knowledge/mod-loading.md#6-implementation-and-reproduction) has the rules, caches and measurements). The clothing host decodes the game's cooked appearance-name visual-tag preset (`base|ep1\entities\appearancename_visualtags.json`, a `JsonResource` WolvenKit 9.0.1 doesn't serialize) in a worker of its own, and caches a compact table per archive identity (`clothing-host.ts`; [worn clothing §4.1](../../knowledge/clothing.md#41-where-visual-tags-come-from-source-wiki)). The creator catalogue's on-screen texts (`cc-catalogue-host.ts`, also `JsonResource`s) go through the route's fetch port, natively first. The character details' textures are decoded natively too (phase 3, below); WolvenKit still exports meshes, layer masks and the textures the reader refuses.

**Licensing, non-negotiable.** XF Studio stays MIT. WolvenKit is GPL-3.0: we study its source as format documentation and run its CLI as an oracle, and we never copy or port its code. RED4ext.SDK is MIT. The game's Oodle DLL is loaded where the game installed it and never copied or redistributed. Credits are in [community credits](../../docs/community-credits.md) (WolvenKit, RED4ext SDK, Cyber Engine Tweaks, red4ext-rs, the modding wiki, psiberx's RTTI dump).

### Phase 3: textures

**Done (27 September 2026, `claude/native-textures`; PIPE-104).** The character details' textures are decoded natively, and WolvenKit exports only the ones the reader refuses. The format and evidence are in [archive formats §10](../../knowledge/archive-format.md#10-textures-xbm), the wiring in [mod loading §6](../../knowledge/mod-loading.md#6-implementation-and-reproduction).

- **Decoding.** `bcn.ts` decodes BC1, BC3, BC4, BC5 and BC7 from the Khronos Data Format Specification (BC7's partition and anchor tables checked entry for entry against the specification's); `xbm-texture.ts` reads the `rendRenderTextureBlobPC` layout (2-D, one slice; RGBA8, R8 and R8G8 besides the block formats), checks every mip against its placement and the slice without trusting the stored pitches, and picks the served mip; `texture-decode.ts` turns one texture into its PNG. Cube maps, arrays, volumes, HDR and BC6H are refused (WolvenKit exports them).
- **The mip, not mip 0.** The largest mip at or under `SERVED_TEXTURE_MAX` (4096) is decoded, so an 8192² map is served from its own 4096² mip; the host's halving (`storeScaledTexture`) now runs only for a texture WolvenKit exported larger than that.
- **The same image as before.** Rows flipped, BC5 with blue 0 (no Z), BC4 grey, colour bytes raw with the record's colour flag unchanged: the oracle found all 59 comparable textures of the default V bit-identical to WolvenKit's PNGs (BC4 needed WolvenKit's truncating arithmetic, fitted on 94,696 combinations).
- **Worker, memory and time.** Textures decode in a worker of their own per game folder (`NativeTextureDecoders`), with a 60 s budget per texture, a block row at a time straight into a streamed PNG (zlib level 3): the process peaks at 221 MiB for a 4096² BC7 map and 300 MiB for an 8192² one. TypeScript was fast enough (a 4096² BC7 map in about 0.5 s), so no native module was built; the TypeScript decoder stays the only one.
- **Wiring.** `createNativeFirstExporter` wraps the WolvenKit exporter: natively first, WolvenKit per refused texture, geometry and masks untouched; native PNGs are cached under the texture reader's identity (`xfs-native-texture:<version>`, the served size) with the depot hash and archive fingerprint. The preparation's log line counts decoded, cached and refused textures and the WolvenKit time beside them.
- **Result.** A cold preparation of the default V with the body: 64 s before (32.9 s WolvenKit export at 7.9 GB, 25.5 s halving), 23.1–23.5 s now, where WolvenKit's geometry export (17 s) is the longest stage and the 66 native decodes (14–16 s) run beside it; a warm one is unchanged at about 5 s.
- **`.mlmask`** stays with WolvenKit for now (a tiled atlas with a tile table and a low-resolution fallback; one per layered material).
- **Tests and tools.** `tests/native-texture.test.ts` (synthetic: block formats, tables, layout refusals, the served mip, the PNG stream, the worker's texture message, the exporter's fallback and cache identity, mutation fuzz); `tools/native-texture-oracle.ts` compares with WolvenKit's PNGs (run it under the memory guard; it exports only textures that fit the served size through WolvenKit).

### Phase 4: meshes

The render blob (`rendRenderMeshBlob`) holds a header with per-chunk vertex layouts (`rendChunk`: vertex factory, stream offsets, index offsets, `renderMask`) plus the vertex and index buffers, in quantised formats: positions as 16-bit normalised with per-mesh scale and offset, normals and tangents in 10:10:10:2, UVs as half floats, and eight skin weights per vertex split over two streams. A `.morphtarget` adds per-target sparse deltas and a diff/mapping block.

- **Head start:** [`eye-plate-cut.ts`](../../projects/xf-studio/authoring/src/eye-plate-cut.ts) already reads and rewrites the head mesh's render-blob vertex streams and the morph target's embedded base buffer at the byte level for the eye plate ([experiment 012](../../experiments/012-native-plate-bootstrap/README.md#built-in-production-plate)). Generalising that to every vertex factory the character meshes use is most of phase 4.
- **GLB writing:** [`glb.ts`](../../projects/xf-studio/authoring/src/glb.ts) exists. Bones come from the mesh's `boneNames`, `boneRigMatrices` and `boneVertexEpsilons`, and morph targets become glTF morph targets.
- **Materials:** the `.Material.json` WolvenKit writes is a resolved `.mi` chain. The resolver already walks those chains, so the native route can emit the same shape from resolver documents rather than re-deriving it.
- **Oracle:** compare vertex positions, normals, UVs, skin weights and morph deltas with WolvenKit's GLB (within quantisation) on the head, body, brows, lashes, hair and one piercing. This also shows whether WolvenKit applies any transform the preview has come to rely on.
- **Effort** is dominated by vertex-factory coverage and morph targets: 1.5 weeks for the character meshes the preview shows, up to 3 with garment and hair variants.

### Native modules for the hot loops

Direction (26 September 2026): performance-critical decoding may move into a small native module behind `bun:ffi` (C via `bun:ffi` `cc`, C++ or Rust, chosen per case), as the Oodle call and the bridge's window capture already do. The candidates are phase 3's BCn texture decompression and mip handling and phase 4's mesh buffer unpacking (vertex streams, morph targets, skin weights), where tight loops over megabytes dominate. The rule for choosing: first write and measure the TypeScript version against the budgets below; move a loop to native code only when the measurement shows it matters, keep a TypeScript reference implementation as the test oracle (byte-identical outputs), bound every native entry point by the same limits (`limits.ts`), and never run untrusted data through native code without the size and bounds checks happening before the call. Licence: our own code (MIT); no GPL sources consulted beyond format facts.

## Integration

Done for the resolver (27 September 2026, `claude/native-integration`). What was built, against the plan:

1. **After `claude/choice-prefetch`.** Integrated against its fetch port and lanes; the prefetch, foreground and background lanes and the prepared-file rules are unchanged.
2. **Native first, WolvenKit per resource.** The installation registry opens one decoder per game folder with `openNativeRoute` (`openNativeDecoderAsync`: a worker, 10 s per resource; the library check never blocks the event loop) before the route's first open, and shares it with every route and cache folder on that folder; a changed Oodle library opens a new one and closes the old, and `clear` closes them all. Each cache folder's port is a `ResolverFetcher` (resolver-host.ts): `NativeFirstFetcher(decoder, wolvenKitFetcher)` when the route has a decoder, else WolvenKit alone. If the decoder can't be opened, the installation's summary says `nativeReader: off` with the reason, and the diagnostics log says so in plain words (`native_reader_off`). Fallbacks are counted by kind with bounded samples (`nativeStats`), recorded in the rolling window, and the unexpected kinds logged in plain words (16 per fetcher; a reader bug through `hostFailure` with its stack). `strict` stays off in production. A fallback for a reason that may not repeat (`unavailable`, `io`) keeps the read retryable. `XFS_NATIVE_READER=0` turns the reader off for comparisons.
   - **Worker packaging.** `prepare-static.ts` bundles `native-decode-worker.ts` as `native-decode-worker.js` beside the Check worker; `main.ts` and `trial-main.ts` pass its path, and the desktop server hands it to the registry (`useNativeWorker`) and the character host. The canary check lists it among the packaged view files. The localhost server runs from source and starts the worker from its own URL. `desktop/tests/native-decode-worker.test.ts` builds the worker the same way and checks it starts (and, opt-in, decodes a real resource).
   - **What the answer adds.** `FetchedResource` carries `notes` and `defaulted`. A left-out `renderMask` is its class default, no flags, so the chunk is not drawn, as WolvenKit's `"0"` reads (NATIVE-41 reversed the earlier reading as drawn); the resource graph turns the notes and left-out masks into rule notes on the `.app`, mesh or morph model (`R11-stored-type`, `R12-property-absent`, `R13-array-past-count`); the plan carries them to the record's notes (`PlannedComponent.readerNotes`), and the rolling window records them per read (`reader_notes`).
   - **The clothing preset in its own worker.** The 13 MB preset takes far longer than any resolver read, so it is decoded in a worker opened for the read and closed after it, never in the route's queue, and a failure is remembered per archive identity (NATIVE-31, PIPE-102). Per-request root classes and time budgets (`NativeDecodeRequest.roots`, `timeoutMs`) remain for other callers.
   - **Catalogue texts (PIPE-50).** `ResolverFetcher.fetchJsonResource` reads a `JsonResource` natively when its payload class is one the documents were checked on (`NATIVE_JSON_PAYLOADS`: `localizationPersistenceOnScreenEntries`; `NativeDecodeRequest.payloads`), at `background` priority (a worker decodes it only while no other request waits), and otherwise through WolvenKit's JSON-resource mode in the resolver's own batches, whose output walk keeps a raw `.json` resource apart from its `.json.json` companion. The catalogue host keeps only the parsed entries, per depot hash, archive fingerprint and the reader that answered.
   - **Decoder lifetime.** A decoder that failed to open for a reason that may pass is tried again after `NATIVE_RETRY_MS` (NATIVE-26); a closed decoder answers `unavailable` (NATIVE-28); decoders of game folders no route uses are closed (NATIVE-33); an idle worker releases the game's library after a minute and the next request starts another (NATIVE-42; Bun's `close` doesn't unload a library on Windows, so `oodle.ts` calls `FreeLibrary` itself); a decoder that can't answer now doesn't count earlier native answers as ready (NATIVE-43).
3. **Cache keys by reader identity.** Native answers are not written to WolvenKit's JSON cache. What a later session needs, whether a prepared choice would need WolvenKit, is kept as an empty marker per resource in the cache folder's `native/`, keyed by depot hash, archive fingerprint and the reader's identity (`NativeAnswerFiles`); `ResolverFetcher.isCached` reads it beside WolvenKit's cache, so the choice manifests hold for natively read choices across restarts. Clear prepared game files removes the markers. The identity is `xfs-native:<NATIVE_READER_VERSION>:<hash of the RTTI slice and learned defaults>:<Oodle DLL hash>`, now version 3 (array records past their count; defaults learned again).
4. **Provenance unchanged.** A native answer carries the same `extractedSha256` as WolvenKit's, and documents carry `Header.XfsNativeReader`.
5. **Setup gating: WolvenKit optional until export.** A route opens without WolvenKit (`InstallationRoute.wolvenKitCli: null`, `characterRoute` in the character-detail host), so the creator catalogue needs only the game folder and resolving needs no WolvenKit. A resource only WolvenKit could read is answered null for that route and named on the part, with the hint that setting WolvenKit up may read it (`PlanReaders`). The character details still export geometry with WolvenKit (textures natively since phase 3) and ask for it in plain words when it is missing (`TOOL_MISSING`). The 3D preview card's setup flow still offers WolvenKit up front, since the preview can't draw without its geometry exports; phase 4 removes that need.
6. **Tests.** `tests/native-resolver-integration.test.ts` (synthetic archives: the integrated route, every fallback kind, the answer ledger's identity, notes, left-out masks, arrays past their count, per-request roots, the registry's decoder lifetime and plain-words reasons), `native-boundary.test.ts` (the resolver host joins the clothing host as the only importers), `clothing-host.test.ts` (the preset through the route decoder), `choice-prefetch.test.ts` (Clear removes the markers), `character-detail-plan` via the integration test (record notes). The opt-in oracle and [`tools/native-resolver-bench.ts`](../../projects/xf-studio/authoring/tools/native-resolver-bench.ts) (now on the integrated route; `--seed-wolvenkit` for a warm WolvenKit baseline) are the release check for a new game patch or WolvenKit version.

## Budgets

Every size and count in an archive or resource is chosen by the file, so the reader checks each against a cap before allocating, and counts the work a small file can cause (knowledge page §8). A resource over a cap falls back to WolvenKit (`over-budget`), so a cap that is too tight costs speed, never correctness. The defaults (`DEFAULT_LIMITS` in `src/native/limits.ts`) come from `tools/native-limits.ts` on game 2.31 and the reference mod list, 26 September 2026. The tool read 1,157 archive indexes (647,849 entries) and decoded, with no caps, the resolver cache's 1,722 distinct resources and the 406 resources of verified root classes whose body is 1 MiB or more. The string-pool, name-count and index rows come from a capped rerun the same day (1,759 cached resources, every body of 1 MiB or more read for its pool; a smaller body holds a smaller pool). No resolver-cache resource passes any default. The caps bound one decode's memory near 1 GB at worst, so the few largest world meshes (up to 33 M values) fall back to WolvenKit; the resolver reads none of them.

Rerun `bun tools/native-limits.ts --game <game> --mods <MO2 mods> --cache <resolver-cache/json>` after a game patch or when a mod falls back `over-budget`. It runs under the default caps, so no cached resource may show a `NativeBudgetError` outcome. `--uncapped` measures true maxima (the table above), but the largest meshes then take several GB, so run it only on an idle machine. The first uncapped run, beside other agents' work, preceded a machine-wide out-of-memory freeze.

## Open caveats

- `rendChunk.renderMask` absent from a file is its class default, no flags, so the chunk is not drawn, as WolvenKit's `"0"` reads (NATIVE-41; [archive formats §6.5](../../knowledge/archive-format.md#65-what-the-json-cannot-say)); the reader still reports where, as a note. No cached resource omits it.
- Learned defaults cover the classes seen in the cache. An unseen class's non-zero default becomes zero (the resolver's fields held on the hold-out). A per-class RTTI default read through the runtime bridge would close this.
- Only WolvenKit 9.0.1 served as the oracle for documents. 8.17.4 was not compared.
- The RTTI dump dates from May 2025, so newer properties come only from learned keys. A game patch that adds properties needs the harness rerun.
- The native reader decodes a value by the type the file declares, even when the RTTI disagrees (the `castShadows` case), and an array record to its end past a short count (the pack's `renderLODs`, as WolvenKit does). The engine's handling of either is unknown. Both are noted on the answer and reach the part's record notes.
- NATIVE-44 is open: a native answer's host-side copy and re-serialisation sit outside the worker's budgets, and resolver and prefetch reads share one FIFO queue without cancellation (only `background` requests wait).
- A cold WolvenKit-only resolve of the reference save now needs more than 6 GB (its launches load over a thousand archives), so it can't be repeated under the memory guard; the bench's `--seed-wolvenkit` gives a warm baseline for the equality check.
- Inside packages, a type name the RTTI dump doesn't know as a class is refused. A game patch that adds component or struct classes needs `tools/native-rtti-subset.ts --dump <dump> --hashes-only` rerun on a newer dump.
- Windows x64 only (the game's DLL). Another platform would need another decoder, and none is planned.
