# Load time and responsiveness (standing research track)

**Goal (asymptotic):** the moment the interface appears, every last thing is already loaded, visible and ready to interact with, and every click that needs other or new assets shows its result with no perceivable load time. Reality falls short; the track keeps closing the gap. Set on 27 September 2026.

## How the track works

- **Measure end to end, not per function:**
  - page shown → interactive;
  - V visible and complete, cold and warm;
  - click on a choice → pixels on screen;
  - first time and repeat.

  The host's preparation log line already times every stage ([mod loading §6](../../knowledge/mod-loading.md#6-implementation-and-reproduction)).
- **Keep budgets** (below). A regression past a budget is a bug.
- **Attack the biggest measured cost next.** Record each finding and its before/after in [mod loading §6](../../knowledge/mod-loading.md#6-implementation-and-reproduction) or the relevant knowledge page.
- **Perceived speed counts as much as raw speed:**
  - instant, optimistic feedback, and the person's actions pre-empt background work (the "respond instantly" rule in AGENTS.md);
  - progressive display: show what's ready, fill in the rest;
  - [Activity view](README.md) for what's still happening.

## Scheduling rule for background work (27 September 2026)

- Priorities: the active selection, then what's under the pointer, then the current row, then the current feature set, then everything else.
- A job that has passed a progress threshold is not cancelled when priorities change. It finishes at low priority and its result is cached for next time.
- The person's own actions always come first.
- Choice previews follow the same rule (choice-preview-service.ts): the chosen choice, then the one under the pointer, then the row in view order, then other rows of the same kind shown this session; a started job always finishes and is kept; on the host a source derivation goes before the next batch prepared ahead but never stops a running one.
- Implementation on the host: one job scheduler per host process (`src/platform/core/jobs.ts`, bound to the host in `src/host/host-jobs.ts`) owns when work runs, in three lanes: `person` (a page's V, Clear), `shown` (a choice preview's source) and `ahead` (choices prepared ahead, the V resolved after a restart, the prepared files' budget check). Its rules: one run at a time, the person lane in the order asked; the lanes below start only when no person's work waits or runs, no person's request is being answered outside a job (`hold`: the installation check, a kept answer's lookup) and the person lane has been quiet for 400 ms (a poll or a file of the V read counts, `touch`), and `ahead` waits the same for `shown`; wanting person work stops an uncommitted lower run at once and starts once that run returned, while a committed one (a preview source writing its record) finishes first and is kept; what a stopped run left settling (`afterwards`: reads already in WolvenKit) holds back the next lower job and Clear, never a person; a requester's new want replaces its previous one, the same key wanted twice is one run, and a job no want holds is stopped; a page's want of its V is held by a lease each poll renews (90 s), so a closed page stops its V; a failure is reported once and never unhandled. Lower jobs take a turn between units of work (`turn()`: a macrotask once 8 ms are used, so waiting requests are answered, and a wait while a person is being answered), and checking which choices are ready runs one manifest entry at a time. Selection and hover order the prefetch queue; a feature-set tier is not built (one row is prepared ahead at a time). All prepared files have one owner (`src/host/prepared-files.ts` `PreparedFiles`): one budget across the character's, its exports', its previews', the references' (capped, never evicting the V's), the facial cache's and the idles' partitions, checked as `ahead` work at most once a minute.
- Cooperative dependency reads use the same scheduler lanes for **CPU admission** (`cooperate`), independently of the preparation slot. Person > shown > ahead wins among eligible continuations. While shown reads are in flight, ahead CPU tickets get a fixed, non-renewable **50 ms eligibility deadline** and use **1 ms slices**, rather than filling every shown I/O gap with an 8 ms slice. They become eligible at that deadline even if shown work depends on them, or earlier when shown finishes/aborts. Reads never wait for jobs, tails, holds or another async operation to finish; they hold no permit across I/O. One shared scheduler wake timer serves the deadlines and quiet periods and is removed when no longer needed. Jobs retain slot/commit/pre-emption/quiet/tail-before-Clear policy; exclusive person jobs never trigger grace. First-frame facial setup/blink/idle reads are shown; creator/pose/control analysis is ahead. Probe deadlines exclude CPU-admission waits and failed analysis remains retryable (PREV-196, [argument and tests](../authoring/perf-restart-checkpoint.md#scheduler-bounded-protection-for-shown-io)).

## Measuring click → pixels

`tools/measure-character-page.ts` drives a headless GPU Chrome against an isolated server (its own port, `XFAS_DATA_DIR` and `XFS_SETTINGS_DIR`; never 4317) and reads the page's `xfs:character:*` marks (`src/character/character-timing.ts`): ask, answer, record, loaded, placed, first frame. It runs hairstyle, colour, makeup on, hide makeup, Reset all and a burst of three hairstyles, optionally on a save copy's V and with a row prepared ahead (`XFS_MEASURE_PREFETCH`), and can profile one change (`XFS_MEASURE_PROFILE`). Pair it with a `/health` probe loop to see whether the host answers while it works.

Two narrower tools watch the page's main thread (29 September 2026), each with a fresh Chrome profile so no compiled program is cached, and `tools/gl-probe.ts` instrumenting WebGL (each program's link and how long its first use waited, each texture upload's time and size):

- `tools/measure-finish-change.ts [port] [finish] [hairstyle]`: a finish chosen on the first layer, alone or just after a hairstyle is asked for; long tasks, the longest gap between frames, when the selection and the plate show it.
- `tools/measure-hairstyle-switch.ts [port] [indexes]`: each hairstyle, Reset all, the hairstyle again; the page's marks, long tasks, programs, uploads and files. `XFS_MEASURE_HOVER=<ms>` opens the row and rests the pointer on each choice first (the load ahead).

A restart is measured by `tools/measure-warm-restart.ts <folder> [port] [runs]` (29 September 2026): it starts an isolated server whose caches and Chrome profile are kept in one folder (as an installed app keeps them), opens the page and times, from the page's start, first paint, the head, the V's answer, record, parts and first frame, beside the host's own lines; the first run of an empty folder is the cold one. Chrome runs with `--no-proxy-server`: without it, resolving the system proxy held every page load about 0.75 s before the document was even asked for. `XFS_MEASURE_PROFILE_OUT` writes the page's CPU profile, `XFS_MEASURE_HOST_PROFILE` the host's first 20 s, and `XFS_MEASURE_WARM=off` opens the page without its warm start (`?warm=off`) for an A/B. `tools/render-smoke.ts` (`bun run smoke:render`) is the render check to run beside any of these: a full V in a GPU browser with every finish and a hairstyle switch, failing on any shader, WebGL or console error.

**The installed app** (29 September 2026, release-readiness-audit.md item 4): a UI-trial build (`XFS_DESKTOP_UI_TRIAL_SUFFIX`) unpacked from its update archive and started with `LOCALAPPDATA` pointing at a scratch folder, so its data folder, install receipts and WebView2 profile are all its own, `XFS_TRIAL_WINDOW_OFFSCREEN=1` and WebView2's debugging port (see the [desktop README](../../projects/xf-studio/authoring/desktop/README.md#driving-an-installed-trial)). Settings named the game and a scratch Mod Organizer 2 instance; WolvenKit was a copy of the app's own. A driver sent real mouse input over the port; in the page, time zero is the `pointerdown`'s `timeStamp`, then the first DOM change, the specific feedback (a tab's `aria-selected`, the working line, the install sheet), done (the result card, the plan, the sheet closing, or for panels the text settling for 1.5 s), every `longtask`, the longest gap between frames and a `/health` probe every 100 ms for the host. Four sessions: a first run with an empty data folder, then three restarts; "cold" is the first time in a session.

**Electrobun 2.0.1 → 2.0.2** (30 September 2026, `projects/xf-studio/authoring/desktop/tools/measure-installed-start.ts`): two UI-trial builds of the same commit, differing only in Electrobun, each unpacked from its update archive and started with its own scratch `LOCALAPPDATA`, settings naming the game (direct route) and WolvenKit 9.0.1, off-screen, one cold run then warm restarts, the later warm runs interleaved. Times are from the launcher process's creation. Warm, 2.0.1 (9 runs) against 2.0.2 (7 runs): the page starts at a median 0.54 s against 0.58 s, first paint 2.02 s against 2.04 s (ranges 1.35–2.29 s and 1.40–3.25 s), the whole V drawn 6.5 s against 6.6 s (5.3–10.4 s and 5.1–10.4 s). Cold (empty data folder, the 3D preview prepared from the game): first paint 12.7 s against 10.7 s, the V drawn 49.3 s against 50.0 s (a first 2.0.2 run, before the OS file cache held the game's archives, took 9.7 s and 43.9 s). No difference beyond the run-to-run spread. That is expected: the app's main process is Bun (`build.mainProcess: "bun"`), whose `bun.exe` is byte-identical in both builds, so Cottontail 0.7.1's faster start-up and SQL don't reach it; only `launcher.exe`, `ElectrobunCore.dll`, `libNativeWrapper.dll` and the bundled SDK changed. The library through the host's API (after 15 s of quiet): 200 saves took 9.1 s and 16.5 s under 2.0.1, 8.3 s and 21.1 s under 2.0.2; 20 listings 25–46 ms and reading all 200 looks 234–347 ms under both. Two findings for this track: **a library save cost 40–100 ms**, almost all of it the commit's flush to disk (WAL with SQLite's default `synchronous=FULL`); **fixed** since (row "Library saves" below), and **on a cold first start the host takes about 3 s before its loopback server answers** (launcher to "Loopback server ready": 3.5 s, against about 0.5 s warm), before the page can even be asked for.

## Known costs and candidate work (27 September 2026)

### Holotable: complete scenes during camera motion

**On main, 28 October 2026 (reviewed).** Agent preparation and painting retain a finite deadline during motion and refinement (at most 6.5 ms; 4 ms for ordinary resting work). Points, paths, zones, labels and relations retain their geometry. Above 256 eligible agent items, motion prefers the selected item, then nearest to the view target, with stable key ties; frame accounting exposes eligible, processed and omitted items, ordering and field-cell counts. Scalar and vector fields use mean aggregation into at most **8×8 cells** during motion, preserving every field item and its footprint. Immutable aggregates prepare cooperatively. At rest, all original cells return progressively; up to eight view-local raster surfaces preserve partial work across fade repaint revisions. Fields have one pick footprint rather than per-cell hit polygons. The camera, resolved colour, DPR and resolution key each surface; explicit scene clear/disposal releases it.

Coarse field paint now keeps its cursor within the current main-canvas generation, so forced deadline slices paint each cell once instead of repeatedly blending the first cells. Canvas clear, projection and LOD changes reset that cursor. Before the 256-item motion cap, unselected candidates undergo viewport culling with conservative projected bounds for paths, volumes, relations and scalar/vector fields; selected items bypass this screen cull. Cold extended bounds prepare cooperatively and cache per immutable item. Regressions cover 256 closer offscreen points competing with a visible point, behind-camera points, selected offscreen items and extended geometry crossing the viewport/near plane. The timings below are from the preceding `038a3bf7` candidate; these two follow-up fixes were verified with tests rather than a new browser timing run.

Context retains adaptive 32–900 projected-extent-ranked solids, a stable hash quarter of gathering spots and the existing 64-attempt/12-community-label limits. The **5.5 ms** adaptive target deducts measured non-solid frame cost, with separate cost models for theme, canvas size and DPR, including canvas clear/fill/stroke. Fade repaint revisions follow the opacity actually painted: crossing the deadline or enabling reduced motion forces a final opaque paint before refinement resets. New detail shares the refinement start time, avoiding a fresh fade tail for each resumed slice. The motion hold is 125 ms and fade 150 ms; playback effects retain their own clock.

**Counts are independent of level of detail.** Show and the legend report the full eligible nearest-dot set before its stable hash quarter is drawn. In the Kabuki fixture both surfaces remain at 2,000 through every motion frame and at rest, including narrow views. Actual visibility and layer switches still determine membership. Synthetic tests cover empty drawn subsets, repeated motion/rest transitions, both widths, independent theme/canvas calibration and theme repaint after cost-key resolution.

Measured by `projects/xf-holotable/tools/capture-motion.ts --dense`: isolated headless Chrome/software Canvas, Bun 1.4.4, shared Windows machine, real Kabuki W1 data, 12,000 cached W0 primitives (8,285 within 350 m of the fixture centre), twelve synthetic markers and **four 128×128 scalar fields**, all base layers on. Each case has 180 camera inputs/frames. Frame cost includes projection, Canvas/legend and SVG writes, excluding browser composition. Completion includes settling, fade and the final opaque paint; resting fields restore all 65,536 cells. Caches are read-only.
