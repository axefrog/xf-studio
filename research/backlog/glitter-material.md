## Investigation and deliverables

1. Map REDengine material resources, inheritance, channel packing, render states and shader selection. Locate actual game `.mt`, `.mi`, relevant shader/cache resources and shipped shader information using archive inventories and WolvenKit/RED4 sources. Nathan specifically suggested shipped shaders as references; establish what exists and is inspectable rather than assuming editable source is bundled.
2. Search installed mod/game materials for useful sparkling cosmetics, flake paint, fabrics, jewellery and other glitter-like responses. Trace real dependencies and parameters; distinguish glints from emission, static speckles, rough metallic surfaces or animated particles.
3. Design separate regular/shimmer/glitter responses. A glitter candidate should support sparse flake size/density/orientation, light/view-dependent glints, base pigment, roughness and coverage. Assess what the existing engine shaders permit before proposing custom shader execution. Prototypes are hypotheses until verified.
4. Build a browser approximation from the same masks/parameters and a reproducible light/camera study. Handle minification, aliasing and temporal stability. Visible sparkle should respond to lighting/view rather than unrelated random flicker. Keep browser/engine differences explicit.
5. Package a small comparison matrix of all four classes, palettes and overlap layers, then include it in one batched game-validation session. Measure loading/cache cost as well as appearance. No separate launch for each material adjustment.

Acceptance: four intentionally distinct useful classes, a convincing glitter effect in-game, documented resource/shader implementation, a useful browser preview, and captured comparison evidence. Do not mark complete from finish names, thumbnails, a metallic slider or browser-only output.

## Visual correction requested 23 September

Nathan reports that the current glitter preview does not look like glitter. His studio screenshot shows regularly spaced, similarly sized dark dots/rings with small highlights over a solid cyan base. The supplied photographs set a substantially different target: irregular fine reflective flakes, varied apparent sizes and spacing, dense and sparse areas, pigment still visible between glints, and highlights which merge toward fine sheen at distance. The peach/copper reference has a more continuous reflective appearance; preserve it as a related finish reference rather than assuming every pictured look has the same particle structure.

Preserved all five supplied images locally, originals unchanged. [Reference manifest](glitter-visual-references.json) records paths, hashes and attribution gaps; do not bundle these photos as application assets. The first two makeup photographs show closely related purple/gold looks at different scales. The large soft circles in the close-up are partly photographic defocus: do not bake circular bokeh into flakes or force all highlights to be permanently bright.

Next material pass should compare the actual flake-placement, size distribution, facet normals and base-pigment contribution against these references. Remove visible regular-grid structure and dark ring/stud appearance. Explore a stable, seeded irregular distribution with separate useful controls for flake density, fineness/size spread and base pigment, while keeping the preview and eventual engine material meaningfully related. Glints must respond to view and lighting, with stable filtering at normal editing distances and no unrelated animated flicker. Assess motion, distance and narrow FOV as well as close stills. This is a requested correction to the existing candidate, not an accepted glitter implementation or permission to pretend the game supports an unverified shader technique.

Source check at intake: `authoring/src/finish.ts::bakeFlakes` currently allocates at most one circular facet per grid cell, jitters its centre by only +/-0.15 cell, and uses glitter radii of 0.21-0.30 cell. That provides a concrete reason to investigate residual grid regularity and the narrow size range; the screenshot alone does not isolate all shading causes. `makeup-stack.ts` bakes these at 1024 pixels and uses ordinary filtered normal/roughness/metalness maps. The existing comments already flag subpixel variance filtering as unfinished. No material behavior was changed in this intake.
