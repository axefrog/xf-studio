## Creator's method and saved graph

The file is well-formed **Substance Designer XML** (`.sbs`, format `1.1.0.202501`), with one material graph, 39 computation nodes, a 2048² default parent size and six outputs: base colour, normal, roughness, metallic, height and ambient occlusion. It has no exposed material controls and retains the generic package identifier `Unsaved Package`.

island_dancer clarified the core technique directly: make **one triangle and one square**, apply a rotatable **axial (linear) gradient** to each, tile many copies with randomized seeds/positions, then turn the greyscale height into a normal map. That is the right description of what the graph is trying to achieve. The saved XML confirms the sequence: Polygon nodes with 3 and 4 sides feed separate gradient/shape blends; both feed a Tile Generator configured for 120 × 120 cells; its output feeds Height to Normal (World Units) and a 2× Transformation before the normal output. Grid settings do not prove that every possible cell contains a visible flake. The exact pre-tile blend appearance has not been rendered locally.

island_dancer also explained the **colour branch** more precisely: convert the **height-to-normal result** back to greyscale; Histogram Select defines a lighter range for uniform colour A and a darker range for uniform colour B; multiply-blend those coloured ranges for the final colour. The saved XML shows the transformed normal feeding red/green channel-to-greyscale conversions, separate Histogram Select nodes and colour blends. These are the wiring details behind the creator's explanation; the precise colour appearance has not been rendered locally. The selections are downstream of height-to-normal, **not direct selections from the original height field**. This colour construction is separate from the principal shape/normal technique and is not, by itself, a moving glint.

The XML makes those branches more specific: the transformed normal's **red** channel alone feeds Histogram Select node `1548442543` (position 0.25, range 0.45) for A, while its **green** channel alone feeds node `1548441973` (position 0.18, range 0.52) for B. The uniform bases are RGB `(0.3658, 0.4779, 0.59)` and `(0.3366, 0.31, 0.5)`, respectively; each branch also contains an HSL-adjusted copy of its base. Final blend node `1548444343` records mode 2 and opacity multiplier 0.51. island_dancer identifies the intended final operation as multiply. The saved parameter values do not establish the exact rendered colours without evaluating Substance's operators.

Tile Generator `1548411929` records a 120 × 120 field, scale 1.84, scale randomness 0.04, position randomness `(0.37, 0)`, rotation randomness 0.41, pattern-rotation randomness 1, position-offset randomness 0.93, symmetry/luminance randomness 1 and seed 274. Its tile rotation is **already randomized**. The two source axial gradients have fixed directions (one default; the other has endpoints approximately `(0.905, 0.474)` and `(0.053, 0.572)`) before this tiling stage.

After seeing our polygon preview, island_dancer pointed out that axial gradients should make **some facets appear tilted**; a field of uniformly flat-looking pieces misses their purpose. They also suggested randomizing the gradients' orientations further, for example using Perlin noise. The supplied graph does **not** wire Perlin into those source-gradient directions. The cropped node screenshot accompanying that suggestion does not uniquely identify which controls they meant, so record it as a proposed refinement rather than a claim about the saved graph. The browser study now tests broader per-facet tilt classes, but does not reproduce Substance's exact height map, histograms or noise graph.

Only **base colour and normal** carry this facet pattern in the supplied file. Roughness is a uniform 0.25; height is uniform 0.5; ambient occlusion is uniform 1. Metallic uses a grayscale Uniform node without an explicit colour override, so its actual output value should not be assumed without rendering. island_dancer says roughness and metalness could instead be derived from the greyscale nodes and adjusted with Levels/Contrast; **that is a suggested extension, not an output already wired into this file**. An unrelated Voronoi/extrude/tile-colour branch is not ancestral to the exported maps. It references `flat_normal.png`, which was not supplied and may warn in a Substance application; that missing file is not on the active output path.

## Lessons for XF Studio

- The **shape → axial gradient → randomized tile → normal** sequence is the important lesson. The gradient gives each primitive an internal height direction before many rotated/positioned copies are combined. This is more informative than simply replacing circles with polygons.
- A useful comparison must show **variation in tilt and apparent size**, not merely uniformly coloured polygon silhouettes. Coherent noise variation of source-gradient directions is a separate proposal to test against the graph's existing tile-rotation randomness.
- The light/dark Histogram Select approach provides explicit artistic control over flake colour **from the greyscale-converted normal result**. The saved base-colour variation is baked into a texture, while the normal map can still respond to lighting. Without rendering the graph, we cannot say how convincing either contribution looks; this graph is not evidence of a filtered dynamic-glint shader. Preserve the distinction between static map detail and genuinely changing sparkle.
- Optional roughness/metalness maps from the same greyscale pattern are a useful **future variation**, especially because the game's `mesh_decal.mt` shader samples separate red-channel scalar maps. Their values and material response must be calibrated instead of assuming the constant outputs in this file already implement them.
- A 120² full-atlas tile field and a 2K nominal output say little about eyelid-scale minification. Our [CPU glint oracle](../../experiments/007-irregular-glitter/glint-oracle-findings.md) shows that one averaged normal can lose subpixel directional highlights. Any polygon pilot should retain stable UV identities and test distance, animation and light sweeps rather than relying on a still map.
- No graph parameter controls are exposed. XF Studio's future density, size spread, pigment and orientation controls need an independent typed model; the supplied `.sbs` is an artistic reference, not an export schema.

The current machine has Substance 3D Painter 2025 but no detected Substance Designer, Substance Player or SBS rendering CLI.
