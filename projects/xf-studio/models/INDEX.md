## Engine gaps

What the models need that the engine doesn't offer yet, by capability: how many models record the gap, and what the capability would have to do.

| Capability | Models | What it would have to do |
|---|---:|---|
| `once-only-effects` | 4 | Outside effects with an idempotency key whose outcome is recorded before and after, so a crash or replay never runs them twice. |
| `frame-timing` | 3 | Frame-coalesced demand and input, a per-frame budget ordered by focus, state integrated over frame time for exact replay, and effects aligned to frames. |
| `live-sync` | 3 | Changes pushed between the host, the page and other windows, and nodes shared between the host's graph and the page's. |
| `uncommitted-edits` | 3 | Uncommitted edits layered over a node's value, seen by its consumers at frame rate, then collapsed into one commit or dropped without trace. |
| `undo-groups` | 3 | Undo over named sets of nodes and fields, steps spanning several commits, redo cleared by any other commit in the set, bounded depth, and undo that reaches outside systems. |
| `ordered-maps` | 2 | Ordered keyed maps whose moves keep identity, with changes reported per key. |
| `original-times` | 2 | Imported entries that keep their original time apart from when they were appended. |
| `paced-requests` | 2 | Request sources with pacing, bursts, retries after refusal and reconnection, and an age on every observation. |
| `reasons-for-work` | 2 | Requests that record who asked, why and for what goal, with consent carried as a reason and invalidated when its subject changes, and supersession scoped to the requester. |
| `separate-libraries` | 2 | Several graphs side by side on one host (the real library and the verification copy), chosen per window, with forks across them. |
| `unknown-data-kept` | 2 | Nodes, fields and entries from a newer build kept verbatim, read-only, never folded, and written back unchanged. |
| `binary-by-reference` | 1 | Large binary data carried by content reference with a residence (page, worker, GPU, host cache, host disk) and a lifetime tied to demand and references. |
| `cross-process-work` | 1 | Work that runs in another process (host, worker, game) observed here, resumed after the other side restarts, cancelled by asking; and derived values computed there without glitches here. |
| `derived-outputs` | 1 | Outputs fed by derived values (not only committed entries): debounced, writing only what changed, within a size budget, with refusals observed. |
| `environment-changes` | 1 | Environment facts (pixel ratio, colour scheme, free memory, GPU limits, context loss) as sources whose changes re-demand. |
| `host-objects-per-node` | 1 | Host objects kept per tuple of nodes, counted by demand, released whole on failure, recreated after loss, with readiness published and plain synchronous queries. |
| `scheduling-rules` | 1 | Scheduling as data: one run in flight with the newest queued, quiet periods, cooperative slicing, limits per kind of work and leases between drivers. |
| `short-lived-ui` | 1 | Cheap per-window state for menus, popovers, hover and tooltips: never stored, no history, collected with its element. |
| `stamped-files` | 1 | Validity over large sets of file stamps, checked on demand with a freshness window, and caches keyed by stamp sets. |
| `worker-pools` | 1 | Pools of workers or child processes: lanes sized from free memory, latest-wins queues per key, priority, cancellation into the worker, crash and idle policies. |
| `deadlines` | 0 | Work bound to a deadline, with its own abort reason and the remaining time carried to a retry. |
| `durable-pending` | 0 | Changes not yet acknowledged by the store kept safe across a crash of the page and of the host. |
| `fault-owners` | 0 | Failures as values that name who must act, suspend the work that depends on them, and select a declared fallback approach. |
| `keep-after-use` | 0 | Demand that lingers for a set time after its last consumer, and results kept for a later claim with an eviction rule. |
| `pause-and-resume` | 0 | Pausing running background work while the person's own work runs, and resuming it afterwards. |
| `per-key-nodes` | 0 | Nodes made per key on first demand and collected when no longer demanded, and recomputation throttled to at most once per interval. |
| `streamed-results` | 0 | Work that yields a stream of results (by reference, one at a time) beside its state. |
