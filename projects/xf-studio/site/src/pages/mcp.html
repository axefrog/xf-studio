MCP server · test builds

Let an AI client work in the game beside you

XF Runtime Bridge is XF’s own local connection into the running game. Its MCP server hands that connection to an AI client through the Model Context Protocol, so the client can see what the game is doing, set up photo mode, frame and light V, change creator options, take screenshots and check them, and ask you a question in the game, all within limits you set.

Test builds only. The bridge and its MCP server are built from source and run in a dedicated test profile for the project’s own in-game testing. They are not part of the XF Studio download. Many of the commands behind the tools have been used in the game; the MCP layer itself is proven offline, and the status below says which is which.

01What it is

One catalogue of game commands, offered as tools

Every command the bridge understands is defined once, with plain-language text, typed parameters, a permission class and an undo note. The MCP server publishes that catalogue as tools, the same list the command-line client and scripted sessions use, and the tool reference is generated from it.

  • Look

    The game’s phase, V’s state, photo mode’s menu, creator options, the world, the save list and the UI, read without changing anything.

  • Photo mode

    Open it with your own photo-mode key, frame V automatically from the game’s own camera projection, set the camera, three lights, expression and pose, and hide the menu for a clean shot.

  • The appearance screen

    Open the character creator from normal play, change an option by the label the game shows, and confirm or back out.

  • The agent’s own view

    Screenshots of the game window with named crops, bursts for flicker checks and contact sheets. A scene report says where each subject sits in the frame, whether anything blocks its face and which lights reach it, and a capture can refuse itself when those checks fail.

  • Questions in the game

    The client asks you something on screen; you answer with a key or a button without leaving the game, or type a comment, and the client picks it up.

  • Sessions

    An event log of every change and refusal, markers, handing the game to you and taking it back, and routines that run inside the game at frame rate, such as a turntable or a smooth look.

02Why it matters

Checks in the game with fewer steps

Offline work can show that a mod file is well formed, but only the running game shows how it looks. The bridge lets an AI client prepare each shot, so the person at the game only plays, watches and answers.

  • Fewer manual steps

    The client opens photo mode, frames V, places lights, switches creator options and captures, instead of reading out instructions for each click.

  • Repeatable shots

    Framing is measured, not eyeballed, and every change can be put back exactly, so a comparison can be taken again the same way.

  • The client sees for itself

    The scene report and pre-capture checks catch a blocked face or an unlit subject before anyone has to spot it in a screenshot.

  • Works with the game you have

    The bridge drives the vanilla game’s own systems through the common modding frameworks, and never installs, replaces or reorders anyone’s mods.

03Safety

Your game stays yours

The bridge is built so that a mistake, a confused model or a crash can’t harm the game, its saves or the mod setup. The full safety model, with the evidence for each rule, is in the repository.

  • Off unless switched on. The default build opens no connection. A diagnostic build can only look and show the player messages.
  • Two gates on every change. The MCP server can withhold whole classes of tools, and the bridge inside the game refuses every change its own settings don’t allow, class by class. Changes are allowed only in the dedicated test profile’s build; changing V’s clothing and cyberware stays off until it is explicitly allowed.
  • Every change can be undone. Each change answers with the exact command that puts it back, and the session log records it.
  • A kill switch. One command, a button in the game, a hotkey or a file stops the bridge at once and puts back what it left on. Nothing reaches the game again until the player reconnects from inside it.
  • Saves are protected. Nothing saves except an explicit save, which makes a new file and never overwrites one. While the bridge’s own changes are live, it refuses to save unless explicitly overridden, and loading a save must be confirmed.
  • One key, nothing else. The only input it ever sends is your own photo-mode key, only to the game window, and only while that window is already in front.
  • Local only. The connection accepts only your own Windows user on this machine, with a fresh key each game session; it is not reachable from the network or from web pages.
  • Your mod setup is never touched. A missing framework is named, with where to get it; nothing is installed, replaced, disabled or reordered.

What leaves your machine: XF itself sends nothing anywhere. Your AI client passes every tool result, screenshots included, to the model service it uses.

04An example

A portrait check, start to finish

How an AI client runs a short check, one tool at a time. Each change comes back with its undo.

  1. Ask first

    ui_message puts “Portrait check next. Ready?” on screen with two answers; session_wait returns “Ready” when the player presses its key.

  2. Open photo mode

    photo_open presses the player’s own photo-mode key in the game window.

  3. Frame and light

    photo_frame turns V to the camera and centres her face; photo_light_set places a light in front and to her left, aimed at her head.

  4. Check, then capture

    scene_report confirms the face is in frame, unblocked and lit; capture_screenshot takes the shot with those checks attached, and refuses if they fail.

  5. Hand over and finish

    session_handover gives V back so the player can judge the shot and type a comment; the session ends by loading the save it started from.

Adding it to Claude Code

From a checkout of the repository, after bun install in projects/xf-runtime-bridge. --read-only starts with looking only; the guide has the setup for other MCP clients.

claude mcp add xf-runtime-bridge -- bun PATH_TO_REPO/projects/xf-runtime-bridge/tools/mcp-server.ts --read-only

05Status

What is proven where

The in-game test sessions so far drove the bridge through its command-line client, which runs exactly the same commands as the MCP server. The test card in the repository records each command’s result.

Seen in the game

  • Photo mode: opened by the player’s key, framing, lights placed about V, the clock, exposure and expressions.
  • The creator: opened from the street, options changed by label, and backed out of.
  • Sessions: loading saves, equipping items, the finish showroom’s heads, and questions answered from inside the game.
  • The kill switch putting back what the bridge left on.

Offline or open

  • The MCP layer: tested end to end with the official MCP client against a simulated game; not yet the route of a whole in-game session.
  • Newer commands stay offline-only until their in-game check passes, and a few research tools are known not to work yet.
  • Scope: Windows and game 2.31, one AI client at a time, and the game window in front to open photo mode.

06Directions

Where it could go

Directions under discussion, not commitments, and none has a date.

  • Inside the desktop app

    The same tools hosted by XF Studio behind an off-by-default switch, with a consent screen per permission class, so you can connect your own AI client.

  • Studio tools

    The Studio’s own actions, such as editing a look or running Check and Build, offered through the same catalogue with the same undo and refusals as the interface.
