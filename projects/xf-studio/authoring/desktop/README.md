## Build and launch

From this directory, after `bun install --frozen-lockfile` in `authoring/` and here:

```powershell
bun run check
bun test tests
bun run build:dev
bun run run:dev
```

For a **private, unsigned Windows installer candidate**, run `bun run build:canary` after the same frozen installs. It creates `artifacts/canary-win-x64-XFStudio-Setup-canary.zip` with the setup executable and its required hidden payload. The command checks the actual installer ZIP, update archive and packaged `version.json` against the pinned `dev.axefrog.xf-studio` identity, version `0.1.0`, canary channel and build hash. It also checks the seven-file Studio view allowlist and refuses game assets, saved data and an unexpected update-feed URL. The archive and update JSON are local build byproducts only; nothing is uploaded or offered as an in-app update. `build:dev` remains the faster source-run trial.

`prepare-static.ts` copies the HTML/CSS, bundles `desktop-bootstrap.js` with the existing typed `LocalSetupActions` browser device, bundles `studio-main.ts` and `raster-worker.ts`, and bundles a separate Bun `check-worker.js`. Electrobun copies only those seven allowlisted files to `Resources/app/views/studio`; Bun main reads them from `PATHS.VIEWS_FOLDER`. The builder never copies `public/assets`, SQLite, credentials or game/mod files. `build/dev-win-x64/` and generated `static/` are ignored. The script fails if the shared Studio script tag changes, forcing review of this bootstrap.

Main creates an ephemeral `127.0.0.1` server. An unguessable startup token establishes an HttpOnly, SameSite cookie. Every later request needs the cookie; writes need a matching `Origin`, or WebView2's browser-controlled `Sec-Fetch-Site: same-origin` plus a same-origin referrer. The latter is needed because this WebView2 build omitted `Origin` on same-origin JSON `fetch`; the adapter adds it **only after** validating those signals so existing SQLite/settings handlers can keep their contract. No arbitrary command, SQL or filesystem action is offered to the view. `GET /api/desktop/capabilities` exposes a small typed, read-only host record: exact packaged version/channel/build hash, private user-data path, WebView2, SQLite library support, asset readiness and package Check/Build support. Build is true only when its bundled code and external dependencies pass readiness checks; install/update remain unavailable. A development-only smoke report checks UI mount, WebGL2 and module-worker construction. `/api/package` accepts a validated collection-only Check or Build request.

`Utils.paths.userData` contains `library.sqlite`, `verification.sqlite`, `settings.json` and an optional **private** `preview-assets/` directory. The desktop host owns the same versioned `LocalSettingsStore` and narrow GET/PATCH/restore contract as localhost, but roots it in this Electrobun data directory and ignores developer `XFS_PACKAGE_*` overrides. The mounted Studio opens a desktop Local setup form even when the head asset is absent; its existing Local setup panel is also available. About reports saved-path readiness and the actual user-data location. Path edits retain revision guards and previous-good recovery. These fields configure this private host only; the renderer cannot select a settings-file path or escape its host-owned directory.

The desktop host runs the same TypeScript filter and 32-pixel compiler preflight as localhost without Python, WolvenKit, a source checkout or private game inputs. Collection validation, filtering and compilation run in a fresh Bun worker with a 15-second deadline; timeout, cancellation or worker failure stops it and returns an error without a partial Check result. Only one desktop Check runs at a time. It returns the same retained preset identities, omissions and filtered SHA-256 for a shared partial-export fixture. Check runs in the UV-only editor without private preview assets; Build remains independently gated by configured host tools and plate input.

## Icon candidate and install behavior

`icon/icon.svg` is the original vector master: a graphite bevel matching the [Opus style guide](../public/style-guide.html), signal-yellow X and cyan edit knot. `python icon/make_icon.py` uses Pillow 12.3.0 to generate transparent 16/24/32/48/64/128/256 PNGs and a 16/32/48/256 multi-resolution `icon.ico`. The 256px and enlarged 16px renderings were visually inspected. `build.win.icon` points to the ICO. The final production icon still needs Windows taskbar, title bar, Start menu and light/dark desktop review; this is a reviewable candidate.

Electrobun's [Windows distribution guide](https://framework.blackboard.sh/electrobun/guides/bundling-and-distribution/) documents the setup ZIP and its adjacent hidden payload. Its [uninstall guide](https://framework.blackboard.sh/electrobun/guides/uninstalling/) places the standalone manager under `%LOCALAPPDATA%/<identifier>/<channel>/uninstall.exe`; [path documentation](https://framework.blackboard.sh/electrobun/apis/paths/) locates writable data under `%LOCALAPPDATA%/<identifier>/<channel>/`. For this canary identity, the expected root is `%LOCALAPPDATA%/dev.axefrog.xf-studio/canary/`. The documented uninstall default **App** preserves that data; **App and Data** explicitly removes the app-scoped data/cache/log root. We built and inspected the unsigned setup but have **not run the installer**. Exact installed app-bit placement, user-data durability after reinstall, uninstall choices and update replacement remain unmeasured. Keep the release identifier stable; a future stable channel has its own root, and old `-spike` development data is not silently migrated.
