# XF Studio Electrobun Windows packaging trial

24 September 2026. This is a **private desktop packaging trial**, not a public release or configured update feed. It uses the committed Opus UI entry from `cec7089`, Electrobun 2.0.1, Bun main and Windows WebView2. The independent `authoring/bun start` entry is unchanged. Follow the [desktop architecture](../../../../research/authoring/desktop-packaging.md) before expanding this host.

**Core preview intake, 25 September:** the asset-free first-run screen accepts an absolute folder path to already prepared, user-owned preview outputs. The Bun host reads only five fixed filenames (`head.glb`, `head-color.png`, `eye-color.png`, `head-normal.png`, `head-roughness.png`). It checks a bounded GLB v2 container with the three named meshes and bounded, decoded square PNGs with valid chunk CRCs and 256–4096px power-of-two dimensions. A different valid generation can open the editor. The committed [output manifest](../evidence/asset-manifest.json) supplies optional known-hash diagnostics; matching those hashes is not an eligibility condition. The host copies inputs through a temporary directory into its own `userData/preview-assets` and rechecks the copy before publishing it. Symlinked inputs are refused. An existing destination is left untouched, including optional preview resources. Missing or structurally invalid core files keep the first-run screen up, with per-file diagnostics. The renderer receives statuses, never filesystem bytes or a general read/copy API. Inspect and Import require the authenticated loopback session and same-origin write proof. Structural validity and hash agreement do **not** prove ownership, original source, rights to distribute, effective game/mod resource winners or runtime visual fidelity. The installer still includes no game/mod bytes. Optional hair/brow/lash/idle/piercing resources still require separate private preparation.

The source path is typed into the first-run form because this trial has no native folder picker. The host does not persist or log it. The path may name a local directory or Windows UNC share; it is used only for those five filenames. The fresh-destination rule prevents a new import from silently replacing or deleting a user's existing private tree. If a previous tree is incomplete, move or repair it deliberately before importing a fresh set. Readiness is cached by the five file metadata stamps, so repeated capability reads do not parse the full asset set; a changed file is checked again. The fixture tests cover a valid set with hashes different from the reference, corrupted PNG/GLB inputs, staging, refusal to overwrite and symlink rejection; host tests cover session/origin gates and narrow request shape. An asset-free Chrome first-run review confirms the diagnostic and disabled Import state at 900×650; the screenshot was visually inspected and stays in ignored evidence. Both typechecks, 15 desktop tests, dev build and canary gate pass. The private canary contains exactly seven allowlisted view files, no private assets or update feed: build `1qezm59ik31gv`, setup ZIP SHA-256 `0d775784673cea9816bd5ff43d39ce30c6f81f401318ad2ed27f62033f290980`. Installed-app intake with private assets remains untested.

**Bounded Check follow-up, 25 September:** the real partial-export fixture still matches localhost. A stalled worker times out while the host event loop continues, a second Check receives a busy error, and cancellation, malformed replies and missing workers return no partial result. ## Build and launch

From this directory, after `bun install --frozen-lockfile` in `authoring/` and here:

```powershell
bun run check
bun test tests
bun run build:dev
bun run run:dev
```

For a **private, unsigned Windows installer candidate**, run `bun run build:canary` after the same frozen installs. It creates `artifacts/canary-win-x64-XFStudio-Setup-canary.zip` with the setup executable and its required hidden payload. The command checks the actual installer ZIP, update archive and packaged `version.json` against the pinned `dev.axefrog.xf-studio` identity, version `0.1.0`, canary channel and build hash. It also checks the seven-file Studio view allowlist and refuses game assets, saved data and an unexpected update-feed URL. The archive and update JSON are local build byproducts only; nothing is uploaded or offered as an in-app update. `build:dev` remains the faster source-run trial.

`prepare-static.ts` copies the HTML/CSS, bundles `desktop-bootstrap.js` with the existing typed `LocalSetupActions` browser device, bundles `studio-main.ts` and `raster-worker.ts`, and bundles a separate Bun `check-worker.js`. Electrobun copies only those seven allowlisted files to `Resources/app/views/studio`; Bun main reads them from `PATHS.VIEWS_FOLDER`. The builder never copies `public/assets`, SQLite, credentials or game/mod files. `build/dev-win-x64/` and generated `static/` are ignored. The script fails if the shared Studio script tag changes, forcing review of this bootstrap.

Main creates an ephemeral `127.0.0.1` server. An unguessable startup token establishes an HttpOnly, SameSite cookie. Every later request needs the cookie; writes need a matching `Origin`, or WebView2's browser-controlled `Sec-Fetch-Site: same-origin` plus a same-origin referrer. The latter is needed because this WebView2 build omitted `Origin` on same-origin JSON `fetch`; the adapter adds it **only after** validating those signals so existing SQLite/settings handlers can keep their contract. No arbitrary command, SQL or filesystem action is offered to the view. `GET /api/desktop/capabilities` exposes a small typed, read-only host record: exact packaged version/channel/build hash, private user-data path, WebView2, SQLite library support, asset readiness and package Check support, while Build/install/update remain unavailable. A development-only smoke report checks UI mount, WebGL2 and module-worker construction. `/api/package` accepts a validated collection-only Check request; it rejects Build with a clear 503.

`Utils.paths.userData` contains `library.sqlite`, `verification.sqlite`, `settings.json` and an optional **private** `preview-assets/` directory. The desktop host owns the same versioned `LocalSettingsStore` and narrow GET/PATCH/restore contract as localhost, but roots it in this Electrobun data directory and ignores developer `XFS_PACKAGE_*` overrides. The first-run screen opens a small Local setup form even when the head asset is absent; the full editor uses its existing Local setup panel when assets are present. About reports saved-path readiness and the actual user-data location. Path edits retain revision guards and previous-good recovery. These fields configure this private host only; the renderer cannot select a settings-file path or escape its host-owned directory.

The desktop host runs the same TypeScript filter and 32-pixel compiler preflight as localhost without Python, WolvenKit, a source checkout or private game inputs. Collection validation, filtering and compilation run in a fresh Bun worker with a 15-second deadline; timeout, cancellation or worker failure stops it and returns an error without a partial Check result. Only one desktop Check runs at a time. It returns the same retained preset identities, omissions and filtered SHA-256 for a shared partial-export fixture. Check still requires the full editor to open, which currently needs private preview assets; the missing-assets first-run screen does not provide a collection editor. Build remains unavailable even if every external tool path exists.

The next portable Build adapter must stage a package-only snapshot in managed private data, locate version-checked external tools and the user's own plate/game inputs through host settings, run the Experiment 005 resource builder and independent verifier from a shipped, asset-free tool bundle, and promote only after the current manifest/path/hash checks. Its resource templates, Python dependencies, WolvenKit invocation, working directories and error recovery need a packaged executable trial. Do not point the desktop process at the HQ checkout, and do not enable Build merely because path-presence readiness passes. The bounded worker protects loopback responsiveness, but the desktop package path still needs an installed-app Check trial before release readiness.

## Windows evidence

`bun run check`: passed. `bun test tests`: 2 passed, 17 assertions. The full `authoring/bun test` passed 353/353 when private inputs were available locally; without those ignored assets, its five real-geometry tests fail with explicit missing-file errors. `authoring/bun run check` and `bun run build` passed. `bun run build:dev`: emitted `build/dev-win-x64/XFStudioDesktopSpike-dev`; Hutch reported `embedded Windows icon in launcher.exe` and `bun.exe`. The bundle contained only the six listed browser files plus runtime/main resources; it had no `assets/` tree. `bun run run:dev` launched a `XF Studio` WebView2 window. With a private local preview tree, the browser reached the packaged Studio bundle and `/assets/head.glb`; the smoke result was `interactive; WebGL2=true; Worker=true` at 3 and 12 seconds. SQLite databases appeared under `%LOCALAPPDATA%/dev.axefrog.xf-studio-spike/dev/`, separate from the bundle. Holding `head.glb` aside for a clean-machine-like test produced `missing-assets; WebGL2=true; Worker=true` at both checks; the private file was restored. The focused transport test rejects unauthenticated and cross-origin requests, serves the worker, verifies the missing asset 404 and stores a SQLite collection revision in a supplied data root.

These are startup and API proofs. No screenshot was captured: this task's computer-use bridge did not expose native app windows. Editing gestures, revision persistence after restart, real raster-worker messages, 4K memory/frame cadence, GPU fallback, external build tools and WebView2-missing bootstrap still need hands-on acceptance. The only worker proof here is that the packaged module worker can be constructed. The first pre-bootstrap run without a private head asset threw a GLB parsing error; the current bootstrap now prevents that path.

The pinned npm bootstrap repeatedly timed out fetching its paired Hutch artifact index. It selected the installed compatible Hutch 0.24.3 through the Electrobun 2.0.1 resolver; the global launcher itself currently selects 0.26.0 without the npm shim's paired defaults. A clean builder without the verified paired artifact or compatible global fallback would fail. The lockfiles pin Bun dependencies, but this network/cache prerequisite must be proved on a clean Windows build machine before calling the build reproducible across machines. The `dev` bundle is neither a signed installer nor an update candidate.

## Icon candidate and install behavior

`icon/icon.svg` is the original vector master: a graphite bevel matching the [Opus style guide](../public/style-guide.html), signal-yellow X and cyan edit knot. `python icon/make_icon.py` uses Pillow 12.3.0 to generate transparent 16/24/32/48/64/128/256 PNGs and a 16/32/48/256 multi-resolution `icon.ico`. The 256px and enlarged 16px renderings were visually inspected. `build.win.icon` points to the ICO. The final production icon still needs Windows taskbar, title bar, Start menu and light/dark desktop review; this is a reviewable candidate.

Electrobun's [Windows distribution guide](https://framework.blackboard.sh/electrobun/guides/bundling-and-distribution/) documents the setup ZIP and its adjacent hidden payload. Its [uninstall guide](https://framework.blackboard.sh/electrobun/guides/uninstalling/) places the standalone manager under `%LOCALAPPDATA%/<identifier>/<channel>/uninstall.exe`; [path documentation](https://framework.blackboard.sh/electrobun/apis/paths/) locates writable data under `%LOCALAPPDATA%/<identifier>/<channel>/`. For this canary identity, the expected root is `%LOCALAPPDATA%/dev.axefrog.xf-studio/canary/`. The documented uninstall default **App** preserves that data; **App and Data** explicitly removes the app-scoped data/cache/log root. We built and inspected the unsigned setup but have **not run the installer**. Exact installed app-bit placement, user-data durability after reinstall, uninstall choices and update replacement remain unmeasured. Keep the release identifier stable; a future stable channel has its own root, and old `-spike` development data is not silently migrated.
