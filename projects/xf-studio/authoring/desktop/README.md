# XF Studio desktop app (Electrobun, Windows)

The Windows desktop host for XF Studio. Alpha builds are published as **unsigned GitHub pre-releases** through a CI draft that a maintainer publishes by hand, with no update feed ([release decisions](../../../../research/authoring/desktop-release-decisions.md)). No release has been published yet. It wraps the shared Studio UI (first packaged from the committed Opus UI entry at `cec7089`) with Electrobun 2.0.1, a Bun main process and Windows WebView2. The independent localhost editor (`authoring/`, `bun start`) is unchanged and remains the primary development route. Follow the [desktop architecture](../../../../research/authoring/desktop-packaging.md) before expanding this host.

## Install the desktop app from your checkout

No GitHub download is needed. On Windows, after `bun install --frozen-lockfile` in `authoring/` and here, run from this directory (PowerShell, `cmd` or Git Bash):

```powershell
bun run build:installer
```

It prepares the Electrobun toolchain the first time (`prepare:devkit`, about 150 MB of downloads), runs the verified `build:canary` below, and ends by naming the setup program and its SHA-256. The setup lands at **`projects/xf-studio/authoring/desktop/artifacts/canary-win-x64-XFStudio-Setup-canary.exe`** (about 42 MB; `artifacts/` is ignored, so it stays on your computer). Then either double-click that file, or, in the browser Studio (`bun start`), open **Help › Get the desktop app** and choose **Install from your build**. The setup shows one **Ready to install XF Studio** page and installs for your Windows user only (no administrator rights) into `%LOCALAPPDATA%\dev.axefrog.xf-studio\canary\app`, with a Start menu shortcut and an entry in Windows' installed apps; XF Studio opens when it finishes. The desktop app keeps its own library and settings, separate from the browser Studio's.

It's an **unsigned alpha**. A setup you built yourself carries no download mark, so Windows normally runs it without a warning; if Windows does say it protected your PC (for example after the file was copied from another computer or downloaded), choose **More info**, then **Run anyway**. Smart App Control, when it's on, blocks unsigned programs outright ([signing path](../../../../research/authoring/desktop-release-decisions.md#signing-improvement-path)).

`build:installer` refuses, with the one next step, when `.hutch` is a link to another checkout (a worktree set up with a junction: remove the link itself with `cmd /c rmdir .hutch`, never recursively), and puts Windows' own `System32` first on the build's `PATH`, so Git Bash's GNU `tar` can't shadow the `tar.exe` Hutch and the gate need. On this development PC the paired Hutch download is slow, so local builds set `ELECTROBUN_HUTCH_BINARY` to the global Hutch 0.26.0 (`%USERPROFILE%\.hutch\bin\hutch.exe`; see [build environment notes](#build-environment-notes)); the shim otherwise falls back to it after 30 seconds.

**Get the desktop app (browser Studio only).** The localhost Studio offers **Get the desktop app…** in its Help panel (**More help**) and the command palette; the desktop app leaves it out. It reads `GET /api/desktop-app` (`src/desktop-app-host.ts`, read-only): whether the app is installed for this Windows user (Electrobun's entry under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall`, found by the install folder under the pinned `dev.axefrog.xf-studio` identity its values name, with the install folder itself as a fallback; trial identities such as `dev.axefrog.xf-studio-ui-trial-*` are not the app), the newest setup program in this checkout's `artifacts/` (or a staged `artifacts/release/XFStudio-<version>-win-x64-setup.exe`), and whether the site's `site.config.json` names a published release. The sheet offers one next step: **Open the desktop app** when it is installed (then the Help entry and palette open it directly), **Install from your build** with a plain consent line naming the file (the click is the consent; the host runs only the file it showed, identified by name, size and time, and refuses one that changed; it starts the setup, and the app, through File Explorer as a double-click would, so they never inherit a Microsoft Store app's private storage when the Studio's server runs inside one, and an install found only in such storage counts as not installed; see [single-file setup](#single-file-setup)), or the build command with **Copy** and, once a release exists, the GitHub releases page. Off Windows it offers only the build instructions. A verification workspace (`?verify`) and a server with its own test data (`XFAS_DATA_DIR`) show everything but start nothing, and say so. Typed actions `desktopApp.refresh`, `.install {installer}` and `.open` are in the [action catalogue](../../../../research/authoring/ui-action-catalogue.md#get-the-desktop-app-portdesktopapp); tests in `tests/desktop-app.test.ts` (a fake host: no registry, file or process is touched) and `desktop/tests/build-installer.test.ts`. The launcher path (`app\bin\launcher.exe`) follows Electrobun's bundle layout and the sandbox trials' launcher search; opening an installed app from the sheet has not been tried with a real install yet.

## Build and launch

From this directory, after `bun install --frozen-lockfile` in `authoring/` and here:

```powershell
bun run prepare:devkit  # once per clone: Hutch toolchain + SDK types the typecheck extends
bun run check        # TypeScript 5.9.3 --noEmit
bun test tests       # desktop host tests (also run by authoring `bun test`)
bun run build:dev    # prepare static view + build tools, then Electrobun dev build
bun run run:dev      # launch the dev build in a WebView2 window
bun run build:installer  # the Windows setup program, verified (see above)
```

**Last verified 28 September 2026:** 104 desktop tests pass (1 skipped); the desktop and authoring typechecks are clean; the full authoring `bun test` (which includes these tests) passes 2,657 with 21 opt-in tests skipped (peak 2.9 GB), given the ignored private detail assets in `public/assets` (without them, two brow and lash asset tests fail loudly). The opt-in real-install tests pass when `XFS_TEST_GAME_ROOT` and `XFS_TEST_WOLVENKIT` name a 2.31 install and WolvenKit CLI 8.17.4 or 9.0.1, and `XFS_TEST_WOLVENKIT_DOWNLOAD=1` downloads and verifies the real pinned WolvenKit. `tools/review-first-run.ts`, `tools/review-alpha-inventory.ts` (203 controls, none silent) and `tools/review-wolvenkit-setup.ts` (fresh data folder to 3D head and Build) passed against the prepared static view.

**Version.** `package.json` `version` (now `0.1.0-alpha.2`, prepared and not yet tagged; `0.1.0-alpha.1` was tagged and never published) is the only place the app version is set. `electrobun.config.ts` imports it, and `release.ts` derives the tag (`v0.1.0-alpha.1`), release title, asset name and changelog section from it. Change it together with the **Unreleased** section of the [changelog](../../CHANGELOG.md) when cutting a release.

**Release build.** `.github/workflows/desktop-release.yml` runs the same steps on a clean `windows-2025` runner. Pull requests build only, manual runs upload a 14-day artifact, and a matching `v*` tag creates a draft pre-release. `bun release.ts metadata|stage|notes` is the tooling it calls. Five authoring tests read ignored game-derived assets; CI skips them with `XFS_PRIVATE_ASSETS=absent` after proving the folder is absent. Never set that variable locally.

For an **unsigned Windows installer**, run `bun run build:canary` after the same frozen installs. Electrobun creates `artifacts/canary-win-x64-XFStudio-Setup-canary.zip`, a setup program that only works beside its hidden `.installer` payload folder (see [single-file setup](#single-file-setup)); `single-installer.ts` then wraps that setup and payload, unmodified, into the one self-contained `artifacts/canary-win-x64-XFStudio-Setup-canary.exe` that releases publish. `verify-canary.ts` checks the actual update archive, setup ZIP, single setup program and packaged `version.json` against the pinned `dev.axefrog.xf-studio` identity, the `package.json` version, canary channel and build hash; checks the ten-file Studio view allowlist (including `LICENSE.txt` and `THIRD_PARTY_NOTICES.md`, byte-compared with the repository's `LICENSE` and [third-party notices](../../THIRD_PARTY_NOTICES.md)) and the hashed build-tool manifest; requires the notices to name every shipped `bin/` program and the Bun, Electrobun and three.js versions actually built in (`notices.ts`); refuses game assets, saved data and any unexpected update-feed URL; and scans every packaged text file (scripts, markup, styles, JSON and Markdown, including Electrobun's host scripts) for user-profile paths (`C:\Users\<name>` in any case, slash direction, escaping or percent-encoding, WSL `/mnt/c/Users/<name>`, macOS `/Users/<name>` and Linux `/home/<name>`) and for email addresses, allowing obvious placeholders, example domains, role accounts such as an SSH remote's `git@`, versions, file names and addresses in the licence and notices (`package-content-scan.ts`, tested in `tests/package-content-scan.test.ts`). Its patterns and test vectors are the repository's own (`tools/private-data.json`), shared with `tools/check_private_paths.py` and the site's privacy guard. Its findings are redacted, because the release log is public. It also requires the ZIP's payload to be byte-identical to that checked archive, with install metadata naming the same identity and build, and the single setup program to carry the ZIP's three files byte for byte, each exactly once, plus no more than Inno Setup's own wrapper (5,255,742 bytes with Inno Setup 6.7.3 and the install-result checks; the budget, `WRAPPER_BUDGET`, leaves about 44 KB for the script's text to grow, not room for another file), and the wrapper's script to name the build it checks for. The wrapper's setup data (the compiled script, messages and wizard settings) is stored uncompressed (`InternalCompressLevel=none`), and the gate refuses a setup whose script strings aren't readable as text, so its Latin-1 and UTF-16 strings really pass the same personal-path and address scan; the loader's and Setup's program code isn't text and isn't scanned. The archive, update JSON and setup ZIP are local build byproducts only: CI never publishes them, and the packaged `baseUrl` must stay empty. `verify-canary.ts` uses Windows' own `tar.exe` (bsdtar), because a GNU `tar` earlier on `PATH` cannot read `.tar.zst` or ZIP. `build:dev` remains the faster source-run trial.

`prepare-static.ts` refuses to run without the top-level `LICENSE`, copies it and the third-party notices, copies the HTML/CSS, bundles `desktop-bootstrap.js` with the typed `LocalSetupActions` browser device, bundles the shared Studio composition root `studio-startup.ts` (the bootstrap starts it with the desktop host services) and `raster-worker.ts`, and bundles two separate Bun workers: `check-worker.js` and `native-decode-worker.js` (the native reader's decode worker, through which the resolver reads game and mod files and the clothing preset is decoded, off the host's event loop; the desktop server passes its path to the installation registry and the character host). Electrobun copies only those eleven allowlisted files to `Resources/app/views/studio`; Bun main reads them from `PATHS.VIEWS_FOLDER`. `prepare-build-tools.ts` bundles the TypeScript package builder (`tools/build_collection_package.ts`, with its compiler, resource builder and independent verifier) into one asset-free `build-tools/app/tools/build.js`, with an integrity manifest (`xfs/desktop-build-tools-2`), as a host resource outside the served view. It contains no Python. Neither step copies `public/assets`, SQLite, credentials or game/mod files. `build/dev-win-x64/`, `artifacts/` and generated `static/` are ignored. The script fails if the shared Studio script tag changes, forcing review of this bootstrap.

## Host design

**Transport.** Main creates an ephemeral `127.0.0.1` server. An unguessable startup token establishes an HttpOnly, SameSite cookie. Every later request needs the cookie; writes need a matching `Origin`, or WebView2's browser-controlled `Sec-Fetch-Site: same-origin` plus a same-origin referrer. The latter is needed because this WebView2 build omitted `Origin` on same-origin JSON `fetch`; the adapter adds it **only after** validating those signals so existing SQLite/settings handlers keep their contract. No arbitrary command, SQL or filesystem action is offered to the view. `GET /api/desktop/capabilities` exposes a small typed, read-only record: exact packaged version/channel/build hash, private user-data path, WebView2, SQLite library support, asset readiness and package Check/Build support. Install and update remain unavailable. A development-only smoke report checks UI mount, WebGL2 and module-worker construction.

**User data.** `Utils.paths.userData` contains `library.sqlite`, `verification.sqlite`, `settings.json`, the host-owned `workspace.json` (or `verification-workspace.json` for `?verify=1`), the private `preview-cache/` and `plate-cache/` derived from the player's game, the private candidate store and `tools/`, which holds XF Studio's own WolvenKit CLI (`tools/wolvenkit/<version>/` plus its install manifest) once the user agrees to download it. The desktop host owns the same versioned `LocalSettingsStore` and narrow GET/PATCH/restore contract as localhost ([local settings](../LOCAL-SETTINGS.md)), rooted in this directory, and ignores developer `XFS_PACKAGE_*` overrides. Path edits keep revision guards and previous-good recovery; the renderer cannot select a settings-file path or escape the host-owned directory. The workspace file is validated, written atomically, and an unreadable prior file is preserved rather than silently replaced; the view shows a save failure.

**About.** Desktop-only, and opened from the Studio's Help panel (**About XF Studio**) and command palette: it has no button of its own over the panels (UI-87; `StudioHost.about`, the port's `about`). Reads the installed version and build hash from `Resources/version.json` through the host capability, and states in plain words whether the 3D preview is available, where the library and settings live, whether Check and Build are ready, and the update state (UI-97: plain sentences, never phase names or build hashes; restarting to update asks inside About, not in a browser prompt). **Licences** shows the packaged `LICENSE.txt` and `THIRD_PARTY_NOTICES.md`; **Game & tools** opens the Studio's one settings form. Missing or invalid packaged metadata produces an explicit "reinstall to repair" state, never a guessed source version.

**Studio startup.** `bootstrap.js` owns the desktop-only parts (welcome, About, Licences and the host-owned workspace file), then imports `/build/studio-startup.js` and calls `startStudio` with a typed host object: the workspace storage and its larger budget, the `/api/desktop/preview` preparation service, its own `LocalSetupActions` instance with the native folder picker (`/api/desktop/pick-folder`, Electrobun `Utils.openFileDialog`), **Game & tools** as the place to set paths, `about` (opens About) and `onMounted` (hands back `openGameSetup`, which the welcome and About use), and callbacks for the close flush and the smoke report. The desktop has no settings form of its own any more: Game & tools, in the Studio's Mod package panel, is the one form (UI-03). The Studio never reads desktop page globals or data attributes.

**Adding a mod to the mod manager.** `/api/mod-install` (the shared `ModInstallHost`, `src/mod-install-host.ts`) plans and, with the person's consent to that plan, installs a verified build from `userData/package-candidates/` into the MO2 profile or game folder Game & tools names, with any extra files a product carries (overlay archives beside the main one, TweakXL files in `r6/tweaks/<archive>/`); receipts, backups and the previous mod list stay in `userData/install-receipts/`. It runs as an install transaction of the host's work activity, so an update restart waits for it. **Show in folder** uses Electrobun's `Utils.showItemInFolder`. See [the pipeline guide](../../../../research/authoring/studio-to-mod-pipeline.md#adding-a-built-mod-to-the-mod-manager).

**WebView2 and startup.** XF Studio needs the Microsoft Edge WebView2 Runtime. `webview2.ts` follows Microsoft's documented registry check; if the runtime is missing, `webview2-install.ts` asks once before any window (**Install it now** / **Not now**) and runs Microsoft's Evergreen bootstrapper, packaged unmodified with the app (`prepare-webview2.ts` fetches it from Microsoft at build time and requires a valid Microsoft Corporation signature; `verify-canary.ts` checks the packaged copy byte for byte and re-verifies the signature). Microsoft's installer shows its own progress, and the app opens when it finishes; a failure offers Microsoft's download page. `main.ts` and the server write the structured diagnostics log, `diagnostics/log.jsonl` in the data folder (version, WebView2, loopback port, page load, bootstrap, smoke state, Build failures with references; bounded, redacted, see [docs/diagnostics.md](../../../../docs/diagnostics.md)). If the WebView still never requests the page, a native message offers **Copy diagnostics**. Inside the page, `boot-watchdog.js` (a classic script ahead of the module bootstrap) replaces "Starting…" with **Try again** and **Copy diagnostics** on an uncaught error before mount or after 30 s.

**Workspace safety.** The host workspace file is the source of truth: autosave keeps one write in flight with the newest draft winning, clears its error after a later success, and never depends on browser storage succeeding. A damaged workspace, or one written by a newer version, opens a **Start fresh** screen that keeps the old file as `workspace.broken-<time>.json`; the close handshake waits only after a successful load, and a failed save on close offers **Close without saving**. The served page carries a CSP (own scripts only, no inline script), the window's navigation rules allow only the app's own loopback origin and its blob downloads, and non-JSON posts get 415. Build readiness answers from cached tool checks and runs WolvenKit/Bun probes once in the background, so capability requests never wait on external tools.

**Alpha wording.** User-facing reasons for things that are not in this alpha come from `src/alpha-availability.ts` (3D preview not prepared yet; Build needs the game folder and WolvenKit CLI) and follow its jargon policy. Build readiness is part of the `package.build` file capability, so the command palette, header and Mod package panel all show the same reason.

### Package Check and Build

The desktop host runs the same TypeScript filter and 32-pixel compiler preflight as localhost without Python, WolvenKit, a source checkout or private game inputs. Validation, filtering and compilation run in a fresh Bun worker with a 15-second deadline; timeout, cancellation, malformed replies or worker failure return an error without a partial result, and only one Check runs at a time (a second receives a busy error). It returns the same retained preset identities, omissions and filtered SHA-256 as localhost for the shared partial-export fixture, and runs in the UV-only editor.

Build uses only the saved desktop settings for game and WolvenKit and runs XF Studio's own Bun; **it does not need Python**. Python and Bun paths saved by an earlier version are ignored. Before the builder starts, the host prepares the [built-in eye plate](../../../../research/authoring/studio-to-mod-pipeline.md#where-the-eye-plate-comes-from) from the configured game into `userData/plate-cache/` within the same Build deadline and cancellation; a missing or unsupported head resource ends Build with its explanation, and readiness shows it until the game's content archives change. Readiness probes run the configured WolvenKit CLI's `--version` and `--help` (8.17.4 or 9.0.1 must expose import, export, convert, pack and extract) and a small script through XF Studio's own Bun (Electrobun's main executable), with bounded timeouts; a failed probe retries after a short cache interval. The host also checks executable/resource signatures, bundle hashes and separation of writable user-data roots (including `plate-cache/`) from game, MO2 and tool roots. Requests contain only the collection. A Build uses private snapshot/work/staging roots, a 40-minute deadline, process-tree termination on timeout/cancel/shutdown, and the same partial filter, TypeScript resource builder and independent TypeScript verifier as localhost, run by Bun from the bundled `build.js`. The host gate checks source and filtered identities, omissions, exact archive/XL members, byte counts, hashes and realpath containment before moving the pair and manifest into the private candidate store. No install or launch is performed. Probes are a dependency gate; the verifier still decides whether a specific package is valid.

### 3D preview from the player's game files, 25 September

Community users get the 3D head from their own game files. The preview setup service (`src/preview-setup.ts`, shared with localhost) reads the host's state from `GET /api/desktop/preview`, and the Studio's setup card (`src/studio-ui/preview-setup-card.ts`, driven only through the presentation port's `previewSetup`, separate from the welcome and About) offers exactly one next step:

- **Game folder not set:** runs the read-only game detection; with one confirmed install it offers **Use this folder** (saved through the revisioned `setup.update` action, which changes only that field), otherwise **Choose game folder** opens Settings › Game.
- **WolvenKit not ready:** the card becomes WolvenKit's own card ([WolvenKit on first use](#wolvenkit-on-first-use)): consent, download progress, the .NET runtime step or a retry. The UV editor keeps working.
- **Ready to prepare:** starts automatically on first contact ("Preparing the 3D preview from your Cyberpunk 2077 files…", five named steps, **Cancel**). Cancelling turns automatic start off (a workspace preference) until they start it again. **Not now** hides the card; the head pane then offers **Set up 3D preview**, which opens it again.
- **Unsupported game version or missing head:** the service's plain message stays until the game's content archives change.
- **Ready:** the card hides, and Studio attaches the head in place (no reload). Meanwhile the head pane shows a typed state: progress while checking or preparing, neutral while something is still needed, an error only for a failure, always with the next step.
- **The head won't load:** plain words and one step, never the loader's text: no WebGL 2 (update the graphics driver, or open XF Studio on the computer itself rather than over Remote Desktop) with **Try again**; damaged prepared files with **Prepare again** (the host sets the ready entry aside and prepares afresh); anything else with **Try again**.
- **Lost contact with the host mid-step:** the card keeps its last state, says it lost contact and is still trying, and polls again with backoff until the host answers.

The host (`src/preview-core-host.ts`, shared with localhost) reads the game folder and WolvenKit path from its own settings, never from the browser; `POST {"action":"prepare"|"cancel"|"rebuild", "body"?: "female"|"male"}` is the whole write surface and needs the session cookie and same-origin proof (`GET ?body=male` reads the masculine core's state). ### WolvenKit on first use

Decided in the [release decisions](../../../../research/authoring/desktop-release-decisions.md#wolvenkit-delivery): users without WolvenKit get the official **WolvenKit CLI 9.0.1** console release, downloaded only after they agree, pinned in [`src/wolvenkit-release.ts`](../src/wolvenkit-release.ts) by asset size (45,266,234 bytes) and SHA-256 (`364427384c0f4ebb6b157fa9abd01595258af1b7993c7b3a7edd2920f2016e92`, identical to the digest GitHub publishes for the asset), plus the expected file count, unpacked size and the launcher and entry-DLL hashes. XF Studio does not redistribute it.

**Flow.** When the preview needs only WolvenKit, the card says what WolvenKit is and offers **Set up WolvenKit…**, or **Use WolvenKit … from this computer** when a verified CLI is found on `PATH` (read from the file's version resource, nothing started), and **I already have WolvenKit** (Game & tools). The consent dialog lists what it is, why it's needed, size (45 MB, 94 MB unpacked), source (WolvenKit's official GitHub release, checked against its fingerprint), where it goes (XF Studio's own data folder; nothing installed in Windows or the game) and the licence (GPL-3.0), with **Read the licence** and **WolvenKit release page** links, and warns up front when .NET is missing too. **Download (45 MB)** is the consent: the request carries only that version, and the host refuses any other. The card then shows MB progress and **Cancel**, then "Setting up WolvenKit…". Once WolvenKit is ready the preview starts by itself and Build readiness follows; About names WolvenKit, its licence and its state. The card is shared with localhost (against `/api/wolvenkit`); there **I already have WolvenKit** opens the Studio's own Game & tools section, and links open in a new browser tab. The consent opens on its heading, never on **Download**, and Esc is **Not now**.

**Host.** `WolvenKitSetupHost` (`src/wolvenkit-setup-host.ts`, shared with localhost) decides the CLI in effect: a path in Settings › Tools always wins, otherwise the managed copy in `userData/tools/`. It streams the download to a private `.partial` file with a running SHA-256 and a 30-second stall limit, retries an interrupted or server-side failure twice, and keeps the file only if size and hash match. It unpacks with a strict ZIP reader (`src/zip-extract.ts`: no links, absolute or `..` names, duplicates, encryption or ZIP64; every entry's CRC checked; never overwrites) into a staging folder, checks the file count, unpacked size and pinned hashes, moves the folder into place and writes its install manifest last. It then runs the new copy's version and command check once. Later checks re-stat every listed file and re-hash the launcher and entry DLL; a damaged copy is offered for repair. Failures are typed and plain: offline, interrupted, withdrawn, fingerprint mismatch (the file is deleted), disk, cancelled. Endpoints: `GET/POST /api/desktop/wolvenkit` (`install` with the offered version, `cancel`, `recheck`) and `POST /api/desktop/open-link`, which opens only named official pages (the licence, release page and Microsoft's .NET installer and page) through Electrobun's `Utils.openExternal`; the view never supplies a URL.

**.NET.** WolvenKit 9.0.1 is framework-dependent on `Microsoft.NETCore.App` 10.0 (8.17.4 needs 8.0). `src/dotnet-runtime.ts` reads the CLI's `runtimeconfig.json` and looks where the .NET apphost looks (`DOTNET_ROOT_X64`/`DOTNET_ROOT` exclusively when set, then the registered install location, then `%ProgramFiles%\dotnet`), applying the roll-forward rule. XF Studio never installs .NET: a Microsoft system runtime needs elevation and is serviced by Microsoft Update, so the card says plainly what's missing and offers **Get .NET 10 Runtime from Microsoft**, which opens Microsoft's evergreen installer link (`https://aka.ms/dotnet/10.0/dotnet-runtime-win-x64.exe`, about 30 MB, Microsoft-signed), plus **Check again** and Microsoft's download page; returning to the window re-checks. Until then the preview does not run WolvenKit, and Build readiness names the runtime. A WolvenKit run that still fails for a missing runtime is reported as such, not as a tool failure.

**Evidence (25 September).** Unit tests cover pinning, verification, the state machine, retries, cancellation, integrity and offline failures against a local fixture server, the ZIP reader's refusals, .NET detection and roll-forward, the endpoint and the card and consent wording (`tests/wolvenkit-setup.test.ts`, `tests/zip-extract.test.ts`, `tests/dotnet-runtime.test.ts`, `desktop/tests/build.test.ts`). The opt-in `XFS_TEST_WOLVENKIT_DOWNLOAD=1 bun test tests/wolvenkit-setup.test.ts` downloaded the real release from GitHub, verified, unpacked and ran it (38 s). `tools/review-wolvenkit-setup.ts` ran the desktop host (outside Electrobun, in Chrome) against a fresh data folder on the development PC with game 2.31: welcome, **Use this folder**, consent, download, verification, "WolvenKit 9.0.1 runs", preview prepared in 11.6 s, head attached at 51 s; Build readiness green with no path typed; with `--build` a one-preset Build using the downloaded WolvenKit produced a verified candidate (128 s in total). With `--no-dotnet` (runtime hidden from the service only) it showed the .NET card and opened Microsoft's installer link. The installed app downloaded, verified and ran it on 28 September (16 s for the download on the development PC; [acceptance](#installed-acceptance-of-main-28-september)). ## Single-file setup

Electrobun 2.0.1 emits a ZIP holding `XF Studio-Setup-canary.exe` and a hidden `.installer` folder (`…metadata.json` plus the `.tar.zst` app payload, byte-identical to the update archive). Its setup program is a 1.3 MB extractor stub: it reads the payload from `.installer` beside itself and, without it, fails with "The installer package is incomplete". The stub still recognises an older payload embedded in its own file, but Hutch no longer produces that, Electrobun's source calls it legacy, and it has no configuration switch, so XF Studio does not rely on it. Hutch builds the ZIP with PowerShell's `Compress-Archive` purely to keep the stub and payload together; nothing reads the ZIP itself, and the update feed (disabled here) uses the separate update archive.

So `single-installer.ts` wraps the ZIP's three files, unmodified, in one [Inno Setup](https://jrsoftware.org/isinfo.php) 6.7.3 program built from `installer/xf-studio-setup.iss`. Inno Setup is pinned in `inno-setup.ts`, downloaded from its official GitHub release, accepted only with the pinned SHA-256 and unpacked in its own portable mode (no registry entries, no uninstaller) into `XFS_INNO_SETUP_HOME` or the ignored `installer-tools/`. The wrapper:

- shows one **Ready to install XF Studio** page ("for your Windows user only. No administrator rights are needed"); **Install** is the default button;
- unpacks Electrobun's setup and payload into Inno Setup's private temporary folder and runs Electrobun's setup, which installs to `%LOCALAPPDATA%\dev.axefrog.xf-studio\canary\app`, creates Start menu and desktop shortcuts, registers Electrobun's uninstaller and opens XF Studio (which offers WebView2 if needed, as before);
- shows **one** progress display: Electrobun's own dialog runs hidden (`SW_HIDE`) and closes itself (`ELECTROBUN_INSTALLER_UI_AUTOCLOSE=1`, Electrobun's own switch), while the wizard stays up with a moving bar and Electrobun's phases in plain words (*Unpacking XF Studio…*, *Copying XF Studio to your computer…*, *Adding XF Studio to your Start menu…*). Electrobun's dialog used to show after the wizard hid itself, and it resets its bar's mode and range on every 1% step and switches to a sweeping bar for its phases without byte counts, which is what made the bar jump about;
- decides success by **what is installed**, not by Electrobun's exit code alone (`installer/install-outcome.iss`): this build's `app\Resources\version.json` (its build hash is compiled in) and `app\bin\launcher.exe`, Electrobun's `uninstall.exe` in the channel folder and its uninstall entry `HKCU\…\Uninstall\dev.axefrog.xf-studio.canary` naming that app folder and version. Electrobun 2.0.1 returns 1 for any error, including one raised after the app's files were committed (its Start menu and uninstall integration runs last), so its exit code can say "failed" for an app that runs. Anything short of a full install gets a plain heading, one sentence and **Try again**, **Open the setup log** and **Close**: *installed, but not in your Start menu yet* (this build's files but no integration; Try again finishes it), *Close XF Studio first* (Electrobun's closing `error: AccessDenied`, `FileBusy` or `PermissionDenied`), *another XF Studio setup is running* (`InstallationAlreadyInProgress`), or *could not be installed*. Electrobun's output (its phases, its debug lines and the closing `error: <Name>`), the checks and the outcome go to `%TEMP%\XF Studio setup.log`, rewritten each run;
- refuses to install into a Microsoft Store app's private storage. A program started from inside such an app (MSIX: a development server started by one, or a download opened from one) has its writes to AppData redirected to that app's `%LOCALAPPDATA%\Packages\<app>\LocalCache\Local`, which only that app's processes see; Electrobun's setup then copies XF Studio there, finds its install folder isn't where Windows says (it compares physical paths) and reports `InvalidUninstallLocation`, leaving an app with no Start menu entry, no uninstaller and no uninstall entry that nothing else can see. Before any page, the wrapper creates and removes a probe folder in `%LOCALAPPDATA%` and compares where it really landed (`GetFinalPathNameByHandle`); if it was redirected, it says so and offers **Reopen through File Explorer**, which starts the setup again as a new process of the Windows shell, outside that app;
- installs nothing itself (`CreateAppDir=no`, `Uninstallable=no`, `PrivilegesRequired=lowest`), so there is one Apps entry and one uninstaller, both Electrobun's, and removes its temporary folder on exit. Electrobun's setup runs with `%LOCALAPPDATA%` as its working folder, so the app it opens does not hold the temporary folder open;
- stores files uncompressed (the payload is already Zstandard), which is what lets `verify-canary.ts` find the verified files byte for byte, and its own setup data uncompressed (`InternalCompressLevel=none`, about 3.2 MB more than compressed), which is what lets the content scan read the wrapper's strings; compiles from paths relative to the script, so no build-machine folder is compiled in;
- runs one copy at a time (`SetupMutex`); a second copy started meanwhile says so and stops;
- carries a Windows file version distinct for every pre-release, in release order: `0.1.0-alpha.N` is `0.1.0.(1000+N)`, `beta.N` `2000+N`, `rc.N` `3000+N`, and the release itself `0.1.0.65535` (`quadVersion` refuses a pre-release it can't number that way);
- exits with Inno Setup's own codes (0 on success, 1–8 for its own failures; 1 also after it offered to reopen itself through File Explorer, 2 when the user cancelled before installing), plus three of its own above them, used when the person closes the explanation instead of trying again: exit code 100 when Electrobun's setup couldn't be started, exit code 101 when nothing new was installed, and exit code 103 when this build's files were installed but not added to the Start menu and installed apps.

**Why the 27 September install said it failed.** The setup (build `t616yf10pay6`) was started from a development Studio whose server ran inside the Claude desktop app, a Microsoft Store (MSIX) app, so everything it wrote to AppData went to that app's `LocalCache`: the app folder, and later the desktop app's library and settings. Electrobun then refused to register an install whose folder resolved there (`InvalidUninstallLocation` in its install-folder check, before its uninstaller copy, shortcuts and uninstall entry), showed its bare **Installation failed / The application could not be installed**, and returned 1, which the old wrapper passed on silently as exit code 101. The app ran, because the Studio's **Open the desktop app** started it from inside the same app and so saw the same private copy; from File Explorer or any other process, nothing was installed. Evidence: the install existed only under `…\Packages\Claude_…\LocalCache\Local\dev.axefrog.xf-studio`, with no `uninstall.exe`, no `.electrobun-uninstall.json`, no shortcut and no uninstall entry, and the wrapper's probe answered *redirected* inside that app and *not redirected* from a process started outside it. Electrobun's source (tag v2.0.1, commit `8d09d15`, `package/src/extractor/main.zig`) confirms the order: files are committed and rollback disarmed before integration, whose first checks compare the physical paths of `%LOCALAPPDATA%`, the identity folder and the channel folder. The Studio's host now starts setups and the app through File Explorer, and treats an install found only in such private storage as not installed.

Checked offline: the outcome rules run in a compiled Inno Setup harness with fake facts (`tests/install-outcome.test.ts`, Windows and the pinned compiler only), Electrobun's real setup program showed no visible window when started hidden with the self-closing switch (its UI-preview and no-payload modes, which install nothing), its closing line reads `error: <Name>` with exit code 1, and the redirection probe gave both answers above. Inno Setup's own source (`is-6_7_3`, `Setup.InstFunc.pas` and `Shared.CommonFunc.pas`) shows `ExecAndLogOutput` waits on the process, not on its output pipe, and reads the pipe without blocking, so the app Electrobun opens (which may inherit that pipe) can't hold the wizard open. In a clean Windows Sandbox (27 September, build `laie903a1mz4`, `tools/sandbox-trial.ts`), the new setup installed in 18 s with one window (the wizard's moving bar read *Adding XF Studio to your Start menu…*; Electrobun's setup never showed a window), exited 0, left the uninstall entry *XF Studio (Canary)* 0.1.0-alpha.1 and the Start menu shortcut, wrote a setup log ending *Outcome: 0* and opened XF Studio. Opened inside the Claude desktop app on the development PC, the same setup showed **Open this setup from File Explorer** before any page (closed there; nothing installed). A full install on the development PC itself is the next manual check.

A local build (26 September 2026, Hutch 0.26.0, Inno Setup 6.7.3) passed `verify-canary.ts` with these settings: a 5,241,942-byte wrapper whose script strings read as text and scan clean, and file version 0.1.0.1001 for `0.1.0-alpha.1`. Run `build:canary` itself from PowerShell or `cmd`, not Git Bash, whose GNU `tar` Hutch can't use, and with a real `.hutch` folder in the checkout (`bun run prepare:devkit`); Hutch refuses a `.hutch` that is a junction to another checkout. `build:installer` handles both. A local `build:installer` run on 27 September 2026 (Hutch 0.26.0, Inno Setup 6.7.3, peak 1.4 GB) passed the same gate: build `t616yf10pay6`, a 43,939,123-byte setup. With the install-result checks, a `build:installer` run later that day (same tools, peak 1.4 GB) passed it too: build `laie903a1mz4`, a 44,016,851-byte setup with a 5,255,742-byte wrapper.

SmartScreen and Smart App Control judge the file the user downloaded: the unsigned Inno Setup program. A browser download carries the Mark of the Web, so SmartScreen shows **Windows protected your PC** with **More info → Run anyway** until the setup is signed and has reputation; the files Inno Setup unpacks carry no Mark of the Web, so Electrobun's setup inside does not prompt a second time. Smart App Control, when on, blocks the unsigned setup outright, as it did the ZIP's setup. Signing later means signing the single setup program as well as the payload binaries ([signing caveat](../../../../research/authoring/desktop-release-decisions.md#signing-improvement-path)).

## Build environment notes

`bunx electrobun@2.0.1` is a shim: it downloads the paired Hutch 0.24.3 from the Electrobun v2.0.1 GitHub release (SHA-256 checked against that release's index), and Hutch fetches the Electrobun core, a Cottontail runtime and a Bun toolchain into `HUTCH_HOME` (default `~/.hutch`). Set `HUTCH_HOME` to a scratch folder for a clean-machine build; CI uses a job-local one. The shim gives up on that index after 30 seconds. On a slow link it then falls back to a compatible global Hutch, and when it has to install one it **adds that Hutch's `bin` folder to the user PATH**. Remove the entry afterwards if the Hutch home was temporary. Which Hutch runs decides the bundled Cottontail: the paired 0.24.3 recorded Cottontail 0.5.0, while a build through a globally selected 0.26.0 recorded 0.6.0. `.hutch/dependencies.lock` (copied into `build-info.json` by `release.ts stage`) records what was used. A clean rehearsal (fresh shallow clone, empty Hutch home, no assets) passed on 25 September: devkit preparation took 130 s, mostly downloads, and `build:canary` took 31 s.

The dev bundle (`build/dev-win-x64/XFStudioDesktopSpike-dev`, from the package's original spike name) is neither signed nor an update candidate; it keeps its data under `%LOCALAPPDATA%/dev.axefrog.xf-studio-spike/dev/`, separate from the bundle. Its first smoke run reported `interactive; WebGL2=true; Worker=true`, and `missing-assets` with the head GLB held aside.

### Driving an installed trial

An agent runs inside the Claude desktop app, a Microsoft Store app whose private-storage redirection would catch a setup it starts ([above](#single-file-setup)), so the 28 September acceptance started everything outside it, as a process of Windows Management Instrumentation (`Win32_Process.Create`, whose processes belong to no app package). Earlier trials instead pointed `LOCALAPPDATA` at the Store app's private LocalAppData; that is not standard-user evidence.

1. Build a trial: set `XFS_DESKTOP_UI_TRIAL_SUFFIX` (8–24 lowercase letters or digits) and run `bun run build:installer`. The setup lands as `artifacts/canary-win-x64-XFStudioUITrial-Setup-canary.exe` and installs as `dev.axefrog.xf-studio-ui-trial-<suffix>`, beside and never over the real app.
2. Start a `.cmd` through WMI that sets `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<port>` and runs the setup (`/SILENT` skips the Ready page); the app it opens inherits the variable. Relaunch the same way with `app\bin\launcher.exe`.
3. Pick a port outside Windows' reserved ranges (`netsh int ipv4 show excludedportrange protocol=tcp`; Hyper-V and Windows Sandbox reserve blocks such as 9271–9370). WebView2 accepts a reserved port on its command line and then silently never listens.
4. Attach only to a trial: `tools/inspect-webview.ts` refuses a page whose data folder isn't a UI-trial identity. In the normal workspace the page exposes no presentation port, so drive it by its controls; `?verify=1` adds `window.xfStudioPresentation` on a separate verification workspace.
5. Keep the window off the shared screen: once it opens, move it off-screen without activating it (`SetWindowPos` to x = −9000 with `SWP_NOACTIVATE`); WebView2 keeps rendering and animating there, and `PrintWindow` still captures it. Take **whole-page** `Page.captureScreenshot` captures and crop afterwards: a capture with a `clip` makes Chromium re-emulate the window's surface, which then flashes white with the clipped region small in its top-left corner for as long as the captures run (29 September: seen by someone at the machine, reproduced with `PrintWindow`, absent with whole-page captures; minimising and restoring or resizing the window showed no white frames either, so it is not an app fault). Theme switches for light and dark captures (`Emulation.setEmulatedMedia`) also repaint the real window, so batch them.
6. Close with the window's own close (the close flush runs; a `WM_CLOSE` posted to the window does it without focus), and finish with the channel folder's `uninstall.exe --quiet --delete-data`.

Some disposable trial roots (`dev.axefrog.xf-studio-*-trial-*` under that redirected LocalAppData) and asset-free installer extractions (`xfs-*` folders under the Windows Temp directory) remain on the development machine because guarded recursive cleanup was refused by command policy; they contain no game assets, but the `sep25bld05` root holds a private candidate. Remove them deliberately.

### Manual checklist

Windows Sandbox gives a disposable Windows session with no Studio data, Bun, WebView2 Runtime or developer paths; it is enabled on the development machine. `bun tools/sandbox-trial.ts [setup.exe]` (default: the built single setup program) prepares an ignored `artifacts/sandbox-trial/` kit and `tools/sandbox-launch.ps1` runs it unattended as described above. Add `--network` for the app's own WebView2 prompt, or `--webview2-installer=<file>` with Microsoft's Evergreen Standalone Installer (downloaded from Microsoft beforehand; the sandbox checks its Microsoft signature) to install the runtime offline first when the sandbox's own download is slow. After a run with a WebView2 Runtime present, check by hand:

1. The welcome opens; **Start designing** reaches the Studio. With no game folder or WolvenKit, the 3D preview card names the one missing thing and the head pane shows a one-sentence status.
2. Add a layer, edit its shape, Undo and Redo; save a preset to the library.
3. Run Check; it reports the collection without needing game files.
4. Close the window, reopen from the Start menu, and confirm that the preset and selection return and setup does not reappear.
5. About shows the release version (for example `0.1.0-alpha.2`), channel `canary` and the build hash from `build-info.json`.
6. Uninstall with the default **App** choice, and note what remains under `%LOCALAPPDATA%\dev.axefrog.xf-studio`.

Mapped files carry no Mark-of-the-Web, so SmartScreen will not appear; enable networking and download from the release page inside the sandbox to see it. The sandbox account does not prove standard-user behaviour, which still needs a non-administrator account.

## Icon and install behavior

The app icon is the XF Studio mark shared with the in-app brand chip, the site header and both favicons: a signal-yellow bevelled tile with a dark **XF**. `icon/icon.svg` is the master; `icon/icon-small.svg` is the same mark with heavier, wider-spaced strokes for 16 and 24 px. `bun icon/make-icon.ts` (from `desktop/`) renders transparent 16/24/32/48/64/128/256 PNGs with resvg and writes a 16/24/32/48/256 PNG-compressed `icon.ico`, which `build.win.icon` uses. All sizes were checked on dark and light backgrounds. Taskbar, title bar and Start menu appearance are reviewed in the installed canary.

Electrobun's [Windows distribution guide](https://framework.blackboard.sh/electrobun/guides/bundling-and-distribution/) documents the setup ZIP and hidden payload (which the [single-file setup](#single-file-setup) wraps); its [uninstall guide](https://framework.blackboard.sh/electrobun/guides/uninstalling/) places the manager at `%LOCALAPPDATA%/<identifier>/<channel>/uninstall.exe`, and the [paths documentation](https://framework.blackboard.sh/electrobun/apis/paths/) locates writable data under `%LOCALAPPDATA%/<identifier>/<channel>/` (for the canary identity, `%LOCALAPPDATA%/dev.axefrog.xf-studio/canary/`). The default **App** uninstall preserves that data; **App and Data** removes it. Disposable identities have exercised quiet app-only uninstall with data retained and quiet `--delete-data` uninstall with roots removed. Interactive uninstall choices, app-only reinstall against retained data, unsigned update replacement and ordinary-user elevation remain unmeasured. Keep the release identifier stable; a future stable channel has its own root, and old `-spike` development data is not silently migrated.
