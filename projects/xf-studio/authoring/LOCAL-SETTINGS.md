# Local settings foundation

The trusted backend modules `src/local-settings.ts`, `src/local-settings-store.ts` and `src/local-settings-readiness.ts` define XF Studio's private host configuration. The localhost server exposes a narrow same-origin `/api/local-settings` endpoint and the **Mod package → Local setup** form. The desktop host exposes that same contract from its own Electrobun user-data directory, including a first-run form usable before preview assets are present (with a persistent **Continue without paths** choice). The desktop host runs package Check and a host-gated Build from these settings; no installer adapter or updater is connected.

`LocalSettings` uses `xfs/local-settings-1`, independent of recipe/collection formats, browser workspace state, immutable SQLite revisions and the `xfs/local-package-1` manifest. Defaults contain no person-specific paths. The document holds game root, direct/MO2 launch route, MO2 instance/profile, optional direct mod root, WolvenKit and Bun executable paths, source-cache directory/limit, preview cache/output directories, desired install mode and desktop update preferences. It has no credential field. Recognized migrations are an early flat `xfs/local-settings-0` draft and the retired `plateInput` field of earlier `xfs/local-settings-1` files, which is dropped without error (`load()` reports `migrated`, and the next save no longer writes it). Otherwise unknown versions and fields are rejected, so credentials cannot silently enter this file. There is no plate setting: the expanded eye plate is [built in](../../../research/authoring/studio-to-mod-pipeline.md#where-the-eye-plate-comes-from).

`LocalSettingsStore` defaults to OS user configuration storage (`%LOCALAPPDATA%/XF Studio` on Windows) and accepts an explicit absolute directory from a desktop app identity. It writes a temporary file in the same directory, flushes it, preserves the previous valid document in `settings.json.previous`, then renames into place. `load()` returns the document's source (`new`, `primary` or `backup`) and whether migration is needed. A damaged primary can be read from the backup, but editing is blocked until `restorePrevious()` is explicitly called. `save()` uses a revision guard so an old panel cannot overwrite a newer edit. Do not expose arbitrary store paths to a renderer or use `XFAS_DATA_DIR` for a packaged desktop release; that existing override remains scoped to the localhost SQLite server.

`evaluateLocalReadiness()` reports coded, path-free reasons for authoring, package Check, source discovery, cache/preview storage, package Build, installation and updates. Check needs no game or build inputs. Build needs WolvenKit and the game root; an optional Bun path is checked if supplied. Build does not use Python: a `pythonExecutable` value saved by an earlier version is dropped when the settings load (like the retired `plateInput`), and the next save no longer writes it. The host passes the last recorded eye-plate outcome for that game folder (`eyePlateReadiness`); while the game's content archives are unchanged, a missing or unsupported head is a Build issue (`plate_source_missing`, `plate_source_unsupported`) with a plain explanation, and the build limits say that the plate is derived on first Build. MO2 readiness validates instance and profile structure, while direct mode excludes MO2. An MO2 `+` indicates intended activation only; neither it nor a physical candidate proves a runtime-loaded winner. Install/update are unavailable without an explicitly provided host adapter. File presence is advisory and does not establish executable version compatibility, package validity or game rendering; operations must revalidate just before use.

`packageToolPaths()` supplies the current package server: localhost `XFS_PACKAGE_WOLVENKIT` and `XFS_PACKAGE_GAMEPATH` take precedence over saved settings. `XFS_PACKAGE_PLATE` is a hidden developer override that replaces the derived eye plate with an explicit directory; it has no setting or UI. `XFS_PACKAGE_PLATE_CACHE` relocates the localhost plate cache (default: ignored `authoring/data/eye-plate-cache/`). Unset game and WolvenKit paths do not fall back to one developer's machine. Bun, which runs the package builder, defaults to the running Bun executable if its optional path is blank. The server resolves paths at each Build request and rechecks file presence inside the package runner. Check still runs without game/build settings, even if local settings need repair. The package request remains only `{action,collection}`; the browser cannot supply tool paths to Build.

The local setup UI edits game, WolvenKit, optional Bun, and direct/MO2 source-route fields through a typed `LocalSetupActions` port. It saves with a revision guard; damaged-primary recovery is a separate action. Readiness gives path-free coded reasons and disables Build until required inputs are present, while Check stays available on localhost. The desktop shell passes `Utils.paths.userData` to `LocalSettingsStore` and disables server environment overrides. It runs Check in a bounded worker without settings, and enables Build only when the saved game and WolvenKit paths (and Bun) pass its own readiness probes (its plate cache is `userData/plate-cache/`); see the [desktop trial](desktop/README.md#package-check-and-build). Its bootstrap form uses the same authenticated GET/PATCH/recovery endpoint; the shared panel remains available once the editor can mount. The same-origin backend returns only the editable setup fields, readiness and names of active server overrides; settings contain no credentials. Source discovery already accepts the same settings type but is still a read-only research probe, not a live installed-mod catalog. Path presence does not validate WolvenKit versions or prove that the package loads in game.
