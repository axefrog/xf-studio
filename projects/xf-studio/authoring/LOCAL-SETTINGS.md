# Local settings foundation

The trusted backend modules `src/local-settings.ts`, `src/local-settings-store.ts` and `src/local-settings-readiness.ts` define XF Studio's private host configuration. This document describes the integration boundary for a future Settings UI and desktop host. No user-facing settings action, source resolver, installer or updater is connected yet.

`LocalSettings` uses `xfs/local-settings-1`, independent of recipe/collection formats, browser workspace state, immutable SQLite revisions and the `xfs/local-package-1` manifest. Defaults contain no person-specific paths. The document holds game root, direct/MO2 launch route, MO2 instance/profile, optional direct mod root, private plate input, WolvenKit/Python/Bun executable paths, source-cache directory/limit, preview cache/output directories, desired install mode and desktop update preferences. It has no credential field. The only recognized migration is an early flat `xfs/local-settings-0` draft; unknown versions and fields are rejected, so credentials cannot silently enter this file.

`LocalSettingsStore` defaults to OS user configuration storage (`%LOCALAPPDATA%/XF Studio` on Windows) and accepts an explicit absolute directory from a desktop app identity. It writes a temporary file in the same directory, flushes it, preserves the previous valid document in `settings.json.previous`, then renames into place. `load()` returns the document's source (`new`, `primary` or `backup`) and whether migration is needed. A damaged primary can be read from the backup, but editing is blocked until `restorePrevious()` is explicitly called. `save()` uses a revision guard so an old panel cannot overwrite a newer edit. Do not expose arbitrary store paths to a renderer or use `XFAS_DATA_DIR` for a packaged desktop release; that existing override remains scoped to the localhost SQLite server.

`evaluateLocalReadiness()` reports coded, path-free reasons for authoring, package Check, source discovery, cache/preview storage, package Build, installation and updates. Check needs no game or build inputs. Build needs the plate, WolvenKit and game root; optional Python/Bun paths are checked if supplied. MO2 readiness validates instance and profile structure, while direct mode excludes MO2. An MO2 `+` indicates intended activation only; neither it nor a physical candidate proves a runtime-loaded winner. Install/update are unavailable without an explicitly provided host adapter. File presence is advisory and does not establish executable version compatibility, package validity or game rendering; operations must revalidate just before use.

`packageToolPaths()` provides the migration handoff for the current package server: localhost `XFS_PACKAGE_PLATE`, `XFS_PACKAGE_WOLVENKIT`, `XFS_PACKAGE_GAMEPATH` and `XFS_PACKAGE_PYTHON` take precedence over saved settings. The current `package-server.ts` still uses its existing developer resolution, including local fallbacks, and does not read this store. Connecting it requires a trusted settings action/capability on the presentation port, host-owned discovery/validation, version probes for external tools, and revalidation inside the server's existing filtered-snapshot/manifest gate. Do not send a settings object or arbitrary executable path in the browser's package request. This checkpoint changes no package eligibility, compiler, output, installer or runtime claim; the pipeline diagrams therefore remain unchanged.
