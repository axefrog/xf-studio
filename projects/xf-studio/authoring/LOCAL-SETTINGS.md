# Local settings foundation

The trusted backend modules `src/local-settings.ts`, `src/local-settings-store.ts` and `src/local-settings-readiness.ts` define XF Studio's private host configuration. The localhost server exposes a narrow same-origin `/api/local-settings` endpoint and the **Mod package → Game & tools** form. The same settings drive the 3D preview preparation: the game folder and WolvenKit CLI saved here are what the host derives the head, eye plate and eyes from (the browser never supplies these paths). The desktop host exposes that same contract from its own Electrobun user-data directory, including a first-run form usable before the 3D preview is prepared (with a persistent **Continue without paths** choice). The desktop host runs package Check and a host-gated Build from these settings; no installer adapter or updater is connected.

`LocalSettings` uses `xfs/local-settings-1`, independent of recipe/collection formats, browser workspace state, immutable SQLite revisions and the local package manifest (`xfs/local-package-2`; readers accept `-1`). Defaults contain no person-specific paths. The document holds game root, direct/MO2 launch route, MO2 instance/profile, optional direct mod root, WolvenKit CLI path, source-cache directory/limit, preview cache/output directories, desired install mode, desktop update preferences and the eye plate head choice (`eyePlateHead`; files saved before it existed read as `installed`). It has no credential field. Recognized migrations are an early flat `xfs/local-settings-0` draft and the retired `plateInput`, `pythonExecutable` and `bunExecutable` fields of earlier `xfs/local-settings-1` files, which are dropped without error (`load()` reports `migrated`, and the next save no longer writes it). Otherwise unknown versions and fields are rejected, so credentials cannot silently enter this file. There is no plate setting: the expanded eye plate is [built in](../../../research/authoring/studio-to-mod-pipeline.md#where-the-eye-plate-comes-from).

`LocalSettingsStore` defaults to OS user configuration storage (`%LOCALAPPDATA%/XF Studio` on Windows) and accepts an explicit absolute directory. The localhost server takes it from `src/host-state.ts`: the per-user folder normally, but its own data folder when it runs with `XFAS_DATA_DIR` (as every test and acceptance server does) or an explicit `XFS_SETTINGS_DIR`, so an isolated server never reads or writes the person's settings (INSTALL-01). The desktop app passes its own user-data directory. A verification workspace (`?verify`) edits `/api/verification/local-settings`: a store of its own in `<data>/verification-settings/` that starts from the host's settings (read only, through the store's `seed`) and keeps every change to itself, so a UI test never changes where the person's next build or install goes (UI-98). It writes a temporary file in the same directory, flushes it, preserves the previous valid document in `settings.json.previous`, then renames into place. `load()` returns the document's source (`new`, `primary` or `backup`) and whether migration is needed. A damaged primary can be read from the backup, but editing is blocked until `restorePrevious()` is explicitly called. `save()` uses a revision guard so an old panel cannot overwrite a newer edit. Do not expose arbitrary store paths to a renderer. `XFAS_DATA_DIR` and `XFS_SETTINGS_DIR` are localhost overrides; a packaged desktop release never uses them.

`evaluateLocalReadiness()` reports coded, path-free reasons for authoring, package Check, source discovery, cache/preview storage, package Build, installation and updates. Check needs no game or build inputs. Build needs WolvenKit and the game root. Build does not use Python: a `pythonExecutable` value saved by an earlier version is dropped when the settings load (like the retired `plateInput`), and the next save no longer writes it. The host passes the last recorded eye-plate outcome for that game folder (`eyePlateReadiness`); while the game's content archives are unchanged, a missing or unsupported head is a Build issue (`plate_source_missing`, `plate_source_unsupported`) with a plain explanation, and the build limits say that the plate is derived on first Build. MO2 readiness validates instance and profile structure, while direct mode excludes MO2. An MO2 `+` indicates intended activation only; neither it nor a physical candidate proves a runtime-loaded winner. Both hosts provide installation ("Add to my mod manager", `src/mod-install-host.ts`), always on the route the person launches with and only with their consent to a reviewed plan; `installMode` is no longer consulted for readiness. Updates are unavailable without an explicitly provided host adapter. The reasons are written for the person (UI-83): what to choose, not which file is missing, and MO2 readiness reads the instance's own configured folders. File presence is advisory and does not establish executable version compatibility, package validity or game rendering; operations must revalidate just before use.

**WolvenKit resolution.** A WolvenKit path is optional. The CLI in effect is, in order: the localhost `XFS_PACKAGE_WOLVENKIT` override, the `wolvenKitCli` setting, then XF Studio's own copy of the pinned official release, which `WolvenKitSetupHost` (`src/wolvenkit-setup-host.ts`) downloads only after the user agrees. The managed copy lives in host-owned storage: `userData/tools/wolvenkit/<version>/` on the desktop, the ignored `authoring/data/tools/` on localhost (`XFS_TOOLS_DIR` relocates it; `bun tools/setup-wolvenkit.ts` asks and downloads there). It is never written into `settings.json`, so it stays a default rather than a user choice, and clearing the setting falls back to it. Readiness reports one plain WolvenKit issue from the setup service (`wolvenkit_unset`, `wolvenkit_installing`, `wolvenkit_runtime_missing`, `wolvenkit_missing`) instead of path checks, and the 3D preview uses a CLI only when it is present, verified and has its .NET runtime.

`packageToolPaths()` supplies the current package server: localhost `XFS_PACKAGE_WOLVENKIT` and `XFS_PACKAGE_GAMEPATH` take precedence over saved settings, and XF Studio's downloaded WolvenKit is the last WolvenKit fallback. `XFS_PACKAGE_PLATE` is a hidden developer override that replaces the derived eye plate with an explicit directory; it has no setting or UI. `XFS_PACKAGE_PLATE_CACHE` relocates the localhost plate cache (default: ignored `authoring/data/eye-plate-cache/`). Build cuts the built-in plate from the head that the saved launch route (direct, or the MO2 instance and profile) is expected to load, so an installed head mod is taken into account. If such a mod changes the head in a way the plate recipe does not support, Build stops and names it. The `eyePlateHead` setting ("Head used for the eye plate" under Game & tools: `installed`, the default, or `base-game`) then cuts from the unmodified game head instead, and the plate and package manifests record that choice; `XFS_EYE_PLATE_HEAD=base-game` in the host's environment remains a developer override. If XF Studio cannot read a mod folder or an archive index that could hide a head mod, Build stops with `plate_source_incomplete` and says what to fix. Unset game and WolvenKit paths do not fall back to one developer's machine. Bun, which runs the package builder, is the running Bun (the desktop app's own); `XFS_PACKAGE_BUN` is a localhost developer override with no setting or UI. The server resolves paths at each Build request and rechecks file presence inside the package runner. Check still runs without game/build settings, even if local settings need repair. The package request remains only `{action,collection}`; the browser cannot supply tool paths to Build.

The one setup form, Game & tools (`studio-ui/panels/game-setup.ts`; the desktop has no form of its own since UI-03), edits game, optional WolvenKit, direct/MO2 source-route fields and the eye plate head through a typed `LocalSetupActions` port, saving each choice as it is made (`setup.update` saves only the changed fields over the saved ones). Detected game folders, MO2 instances and their profiles are offered as choices, and a host with a native folder picker (the desktop) adds `setup.pickFolder`. It saves with a revision guard; damaged-primary recovery is a separate action. Readiness gives path-free coded reasons and disables Build until required inputs are present, while Check stays available on localhost. The desktop shell passes `Utils.paths.userData` to `LocalSettingsStore` and disables server environment overrides. It runs Check in a bounded worker without settings, and enables Build only when the saved game and WolvenKit paths and its own Bun pass its readiness probes (its plate cache is `userData/plate-cache/`); see the [desktop trial](desktop/README.md#package-check-and-build). Its bootstrap (welcome, About) reads the same authenticated endpoint and opens Game & tools for changes and recovery. The same-origin backend returns only the editable setup fields, readiness and names of active server overrides; settings contain no credentials. Source discovery already accepts the same settings type but is still a read-only research probe, not a live installed-mod catalog. Path presence does not validate WolvenKit versions or prove that the package loads in game.
