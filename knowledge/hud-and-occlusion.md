# HUD geometry and camera sight lines

**Maturity: Draft.** Static R4 research for **Cyberpunk 2077 2.31**, 24 October 2026. **[source/binary]** HUD controller discovery, laid-out widget bounds, the UI resolution scale, collision-query routes and hit-entity recovery are located. **[hypothesis]** These are reader candidates, not a commissioned bridge capability. Complete clipping/mask visibility, arbitrary HUD-slot composition, and the actual filter membership of vending machines and every moving occluder remain unresolved. A clear physics ray does not prove a visible subject.

Grades: **[source]** inspected decompiled scripts, framework/bridge source or an identified existing report; **[binary]** executable instructions/RTTI with RVA; **[resource]** already extracted game data; **[wiki]** pinned Modding Docs text or illustration; **[hypothesis]** inference, proposed reader or required runtime check. No new runtime evidence was collected. This supplements [ink UI](ink-ui.md), [photo mode](photo-mode.md), [world and streaming](world-and-streaming.md), [runtime access](runtime-access.md) and the [autonomous-testing survey](../research/runtime/autonomous-testing.md).

## 4. Bounds, pixel transforms and visibility limits

### The concrete native geometry route

**[source/binary]** Global native `GetScreenPosition(widget: wref<inkWidget>) -> RectF` is declared at `orphans.script:66340`. Registration **`0x1898f18`** names it and installs VM handler **`0x21b24c4`** (`0x1898f68`). The handler locks the weak handle, calls draw-area resolver **`0x2059ac`** at `0x21b258a`, then bounding helper **`0x2ecef8`** with its global flag true at `0x21b2599`. It writes **Left, Top, Left+Width, Top+Height** at `0x21b25d1–0x21b25df`. SDK `Generated/RectF.hpp:16–23` confirms those four fields: Right/Bottom are **edges, not sizes**.

**[binary]** Resolver **`0x2059ac`** obtains the parent and searches its draw-context collection (`parent+0x1d0`, helper **`0x2ef920`**), copying the matching draw area (`0x205a03–0x205a34`). **If no parent/context is found**, it builds an unpositioned area from the widget's configured size `+0x198/+0x19c` with unit scale (`0x205a50–0x205a96`). An origin-zero, nonzero-size rectangle can therefore be a **fallback**, not a live screen location. The public call supplies no `context_found` flag. A reliable native adapter must distinguish that fallback before accepting a rectangle.

**[source/binary]** SDK `inkDrawArea.hpp:13–22` holds size, scale, relative/absolute position and `UITransform`. Bounding helper **`0x2ecef8–0x2ed03c`** builds the current transform through **`0x2ed238`**, combines the positive/negative transformed size axes to bound all corners, then adds transform translation when global=true. It does **not** intersect with a clip rectangle or test ancestor opacity. Red Hot Tools independently uses the matching parent context and global bounding helper (`src/Red/InkContext.cpp:23–51`, `src/App/UI/InkInspector.cpp:51–60`). This establishes transformed geometry, not visible pixels.

**[binary] `LocalToGlobal` is not a general point transform in this build.** Registration **`0x144fa34`** installs **`0x21b55bc`**, which calls **`0x21b548c`**. That helper obtains the stored draw origin through **`0x21b53b4`** and simply **adds the supplied offset**, without multiplying it by the widget transform (`0x21b54a6–0x21b54c4`). Consequently `LocalToGlobal(widget, widget.GetSize())` cannot be assumed to return the transformed opposite corner. `GlobalToLocal` is also asymmetric: handler **`0x21b54e8`** calls **`0x21b5238`**, which uses the **parent's** draw origin and inverse draw transform (`0x21b52e5–0x21b538d`). It is not an established inverse for the widget's own arbitrary render transform. Use laid-out draw bounds, not a two-corner size shortcut.

### Resolution, UI scale, safe zones and HUD slots

**[source/binary]** `UISystem.GetCurrentWindowSize/GetInverseUIScale/GetBlackBarsSizes` are declared at `core/systems/uiSystem.script:118–122`. The first's registered handler **`0x11a77a8`** reads current width/height (`0x11a77bf–0x11a77df`). The inverse-scale handler **`0x127cbe8`** calls **`0x4faed0`**: **`inverseUIScale = 1 / min(width / 3840, height / 2160)`** (`0x4faefa–0x4faf16`; constants **`0x31eeed8 = 1/3840`**, **`0x31eeefc = 1/2160`**). This is the baseline window scale, not a proof of an entry's additional HUD-scale override.

**[source]** The perks UI compares `LocalToGlobal(widget)` with pointer screen positions, and converts configured dimensions using `1 / GetInverseUIScale` (`cyberpunk/UI/fullscreen/perks/newPerks/NewPerksCategoriesGameController.script:503–515,834–854`). Its design-coordinate path adds black bars (`:865` onwards). Notifications separately add safe-zone/black-bar offsets (`cyberpunk/UI/fullscreen/notification/ingameUINotification.script:25–33`). Codeware's `VirtualResolutionWatcher` computes per-axis ratios, and its smart scale takes their minimum (`scripts/UI/Screen/VirtualResolutionWatcher.reds:94–99`, `VirtualResolutionData.reds:43–53`). These helpers describe different inputs: **do not apply baseline scaling or black-bar offsets again to an already transformed screen-space rectangle**.

**[source/hypothesis]** Global geometry belongs to its owning window. Red Hot Tools subtracts the HUD entry's slot-image screen origin before testing the entry window (`InkWidgetCollector.cpp:364–381`), demonstrating a composition boundary beyond the widget's parent chain. The source uses translation for that inspector path; it does not establish correct arbitrary slot scale/rotation, texture resizing or HUD-scale override. For an ordinary full-screen window with validated pixel correspondence, the transformed bounds are the pixel-rect candidate. For a separate HUD window, first establish its actual **window-to-slot-to-output transform**. If that transform is unavailable, return window-local bounds with `pixel_rect: unavailable`; do not silently add a guessed margin.

**[hypothesis] Proposed returned geometry:** preserve `window_rect` and its coordinate-space identity, `context_found`, transform/layout generation, and a validated affine `window_to_output`. Transform the four rectangle corners and take their min/max for a conservative output AABB; preserve the quad when available. Intersect with the **output viewport** and only known clip regions. For a capture cropped at output-pixel origin `(ox, oy)` with size `(vw, vh)` and encoded size `(cw, ch)`, map `capture_x = (output_x - ox) * cw/vw`, likewise Y. This last formula is capture-coordinate arithmetic, not a game UI-scale formula. Reject stale resize/viewport generations, nonfinite or degenerate transforms and unvalidated supersampled/photo-mode output mapping ([photo-mode resolution](photo-mode.md#12-rendering-above-screen-resolution)). Never substitute desktop DPI or the configured 3840×2160 root size for the current output dimensions.

### Effective visibility is a separate result

**[binary/source]** `inkWidget.IsVisible` registration **`0xd95980`** → VM wrapper **`0xd68968`** → **`0x2edf08–0x2edf40`** tests flag bit `widget+0x1fd & 1`, the own visible byte `+0x1f8`, and clamped own opacity `+0x1f0 > 0.00001` (threshold **`0x31eee7c`**). The flag's full lifecycle/meaning was not established. `GetOpacity` handler **`0xca67fc–0xca6822`** returns that own opacity clamped to [0,1]. Neither body walks parents, checks layer/entry state, clips or proves painting. SDK `inkWidget.hpp:30–62` independently names the fields.

**[hypothesis]** Record the engine predicate, own visible/opacity, each ancestor's predicate/opacity, layer active state, HUD entry enabled state, current draw-context presence, viewport intersection and explicit mask/clip limitations. An ancestor eligibility conjunction and opacity product are useful conservative diagnostics, **not a complete compositor model**. Cross-window ancestors include the slot image. Do not infer hidden from non-interactive: decorative HUD elements are often not interactive. Do not treat a stale draw context as a draw-this-frame stamp.

**[source/hypothesis]** A mask can be a texture or dynamic mask, with transparency and inversion, rather than a rectangular ancestor clip (SDK `Generated/ink/MaskWidget.hpp:25–33`; Codeware `scripts/UI/Core/inkMask.reds:1–48`). No general final scissor/mask intersection reader was located in the inspected widget/draw-area/Codeware surfaces. Sibling paint order, higher layers, effects, tint alpha and cached content also prevent a structural rectangle from proving actual pixels. Return `eligible`, `ancestor_hidden`, `off_viewport`, `layout_unresolved` or `paint_visibility_unknown` separately. **Do not publish an unqualified `visible:true` or `clip_rect` equal to the bounds.** Captures remain the independent check for ink actually painted.

**[source] Existing bridge limitation:** `XFRuntimeBridgePhotoPanel.reds:557–561,859–860,875–876` measures two `LocalToGlobal` points using `GetSize`. `XFRuntimeBridgeInk.reds:349–354` measures window corners through `GlobalToLocal`. These observations need the transform qualifications above; they are not a general HUD geometry implementation. Its fixed HUD reservations remain a placement fallback (`XFRuntimeBridgeInk.reds:357` onwards), not measured live minimap/tracker occupancy. This research changes documentation only.

## 5. Collision and visibility queries

**[source/binary]** `orphans.script:27598–27648` exposes `TraceResult`, `QueryFilter.ALL/ZERO/AddGroup`, overlap and four synchronous single-ray variants. The group route's registration **`0x1321be8`** installs **`0x1117dc0`**; the explicit-filter route's registration **`0x1321ddc`** installs **`0x24c1660`**. The former resolves a named group through **`0x245eb0`** (`0x1117f46–0x1117f5b`). Both construct a query through **`0x239cb4`** and call **`0x1118008`** with separate `staticOnly`/`dynamicOnly` booleans. These names and flags are distinct filters.

**[binary/source]** Despite the method's `CollisionGroup` spelling, **`0x245eb0–0x245ee1`** searches the resource's **query-group** name array at `+0x2b0` (SDK `Generated/physics/CollisionFilterResource.hpp:33–34`), returning a bit for the matching index. An unknown name returns **zero**, not an exception (`0x245edb–0x245edd`). Validate names against the effective configuration before interpreting an empty result; a misspelled or absent group must not become a clear-space assertion **[hypothesis]**.

**[binary]** In **`0x1118008–0x111804a`**, static-only=true/dynamic-only=false selects query mode **2**; false/true selects **4**. With both false, the query constructor's mode is retained. Both true also retains it: **do not use true/true as an “all” spelling**. The ray wrappers initialise both optional booleans to false. Their Bool result is the lower query status compared with **2** (`0x1118035–0x111803c`), not a separate coverage/error report. The public signatures have **no excluded-entity argument**.

### Device, moving-object and glass coverage

**[source] Filters are data, not object-class rules.** SDK `Generated/physics/CollisionFilterResource.hpp:25–34` holds separate collision/query groups and references to preset/override/query JSON. `CollisionPresetDefinition.hpp:25–32` has CollisionType, CollisionMask and QueryDetect; `QueryPresetDefinition.hpp:23–24` has queryGroups; `physicsFilterData.hpp:30–33` adds effective masks, preset and custom data. The executable contains **`engine\physics\collision_groups.json` at `0x3011038`** **[binary]**. Its contents and effective installed overrides were not located among the inspected already-extracted resources. A `Device` script type or a moving transform does not establish physics group membership **[hypothesis]**.

**[source]** Codeware `scripts/Physics/TraceResult.reds:1–5`, `src/App/Physics/TraceResultEx.hpp:9–39` resolves up to two hit-object associations through the native result ID, returning an entity only when the object casts to `Entity`. The native result also carries proxy/actor/shape indices, distance, proxy type and simulation type (SDK `physicsTraceResult.hpp:22–33`). A static world collision may have **no entity**; keep that result rather than fabricating one. Codeware exposes `PhysicalMeshComponent.filterData`, filter source and simulation type (`scripts/Base/Addons/PhysicalMeshComponent.reds:4–17`), useful configuration diagnostics where that component exists; they do not prove a universal live-shape enumeration or all chassis/puppet shapes.

**[source/hypothesis] Vending stopping result:** inspected spatial-query and reaction helpers, device/vending scripts, SDK filter/shape/resource declarations, Codeware physics extensions, executable group/ray registration, and scoped existing consumer-resource filenames. `cyberpunk/devices/vendingMachines/vendingTerminal.script:2–21` requests UI, CanMesh and Trigger components; this supplies no cabinet collision-group assignment **[source]**. No vending collider definition, effective query-preset payload or runtime shape membership was established. Keep **device coverage unknown**; broad explicit filters, Sight Blocker and hit-entity association are the located probe routes **[hypothesis]**. The same machine may have several collision/UI components; a UI screen or targeting hit is not proof that a camera ray can hit its cabinet.

**[source/hypothesis] Moving stopping result:** source establishes the five-group `AILineTrace`, the separate Vehicle query and removal of the bridge's exclusive static-only flag as candidate routes. Actual vehicle/NPC/device collider assignments, inactive/crowd representations and updates while photo mode pauses the world remain **unlocated/uncommissioned**. Do not promise that adding only `Dynamic` fixes them all. Sample each query against current transforms with a source timestamp; even correct membership cannot account for a vehicle that moves between telemetry and capture.

**[source/wiki/hypothesis] Glass is not a binary collision question.** SDK `Generated/physics/MaterialTags.hpp:23–27` has separate AI/player visibility and projectile tags; `MaterialTagVisibility.hpp:12–18` names None, SemiTransparent, Transparent and Ignore. Their existence does **not** establish how any inspected ray applies them. The glass guide describes rendered opacity, tint, refraction and blur independently of those physics tags. A physical window can therefore require a different assessment from an opaque cabinet; exact behaviour is a session question. Retain hit material and query route, and compare intact clear glass, tinted glass and a broken/open control. Do not skip a hit solely because its material name contains “glass.” Renderer occluder nodes are another system: the wiki's occlusion diagrams/editor node explain culling, not physics-ray membership.

### Limits of the existing scene report

**[source]** `XFScene.Ray` skips distances under **0.30 m**, treats a valid hit more than **0.12 m before the endpoint** as blocked, and returns hit position/material, but no hit entity (`XFRuntimeBridgeScene.reds:84–100`). NPC face points use the Head slot or **position +1.62 m**, then **+0.045 m up / +0.08 m forward** (`:103–135`). V's occlusion is requested only in photo mode (`:178`); NPCs and showroom pieces use their respective point rays (`:193,201,243`). None estimates visible body area.

**[hypothesis]** Keep the 12 cm endpoint tolerance as an explicitly labelled existing heuristic; it can miss a real blocker near the face and cannot reliably exclude the subject's own capsule. With broader filters, use hit identity when available and controlled endpoint offsets/multi-hit continuation only after validation. A blocked centre ray can coexist with visible eyes/limbs; several clear points can miss an occluding strip. Bounds/frustum projection, streamed/rendered availability, hair/alpha surfaces, glass, masks, exposure and motion blur remain separate checks. Report **clear/blocked for the named sample and selected query**, never “subject fully visible.”

## 6. Bounded bridge reader design

**[hypothesis; proposed, not built]** Extend the existing scene/recording owner; no new input, focus takeover, hidden cursor mode or inspector UI.
