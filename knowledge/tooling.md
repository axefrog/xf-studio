# Tooling: WolvenKit CLI

**Maturity: Draft.** How the WolvenKit command-line tool behaves as XF Studio runs it: what a release contains, what it needs to start, how it reports success and failure, and what `uncook` writes. Observed with the official 8.17.4 and 9.0.1 console releases on Windows 11 with game 2.31. The WolvenKit GUI, the Blender add-on and conversion round trips are not covered yet ([WolvenKit 9 round trip](../research/authoring/wolvenkit-9-roundtrip-2026-09-24.md) holds the round-trip evidence).

## Runtime prerequisite

The console release is **framework-dependent**: its runtimeconfig names `Microsoft.NETCore.App` 10.0.0 in 9.0.1 and 8.0.0 in 8.17.4, with no `rollForward`, so the default **Minor** policy applies: any installed 10.x (respectively 8.x) release runtime satisfies it, never a pre-release and never another major. [resource] runtimeconfig files; [source] .NET host roll-forward rules (learn.microsoft.com, *.NET version selection*).

The apphost finds .NET in this order: `DOTNET_ROOT_X64`, then `DOTNET_ROOT` (used **exclusively** when set, even if empty of runtimes), then the registered location `HKLM\SOFTWARE\dotnet\Setup\InstalledVersions\x64\InstallLocation` (32-bit registry view), then `%ProgramFiles%\dotnet`, and looks for `shared/Microsoft.NETCore.App/<version>`. [source] .NET host probing design; [runtime of the tool] with `DOTNET_ROOT_X64` pointing at an empty folder, 9.0.1 printed `You must install .NET to run this application.`, `.NET location: Not found`, listed the searched locations and exited with **131** (the low byte of the host error, not the full `0x80008083`). No dialog appears for the console apphost. Implemented in [`dotnet-runtime.ts`](../projects/xf-studio/authoring/src/setup/host/dotnet-runtime.ts) and `isRuntimeMissing`.

## Success and failure

- **Exit code is not enough.** `uncook` exits 0 when some requested resources fail to export, so callers must check the files they expected. [runtime of the tool] 8.17.4/9.0.1; see PREV-01 in the [code-health ledger](../research/authoring/code-health.md).
- **`Unhandled exception`** in the output means failure even with exit 0; a bad `-r` regex, for example, raises `RegexParseException` (the pattern is a .NET regex over backslash depot paths, so every backslash must be escaped). [runtime of the tool]
- **`convert s` on a resource it can't serialise** logs `Invalid in wolven rtti` and `ConvertToText` as errors, writes an empty (0-byte) `.json` beside the file and still exits 0; readers must parse the JSON, not trust its presence. `unbundle` with `--hash` exits 0 when the hash is found, and exited 160 when the archive path did not exist. [runtime of the tool] 9.0.1, 25 September 2026, on a mod's `.app` whose `castShadows` field is a `Bool` where 9.0.1 expects `shadowsShadowCastingMode`.
- **Folder `import`** exits 3 even when every file imported; success is `Imported N/N file(s)` with N > 0. [runtime of the tool] (Build adapter rule since Experiment 005.)
- The one runner that applies these rules is [`wolvenkit-cli.ts`](../projects/xf-studio/authoring/src/host/wolvenkit-cli.ts); consumers map its typed errors. Synchronous callers (the independent package verifier, through the injected [`verifier-wolvenkit.ts`](../projects/xf-studio/authoring/src/legacy/eye-makeup/export/host/verifier-wolvenkit.ts)) use its blocking form `runWolvenKitSync`, which applies the same policy but cannot be cancelled. The character resolver's fetcher and the grading-LUT host use it too: every fetcher on one resolver cache folder runs its batches one at a time in a unique `mkdtemp` batch folder, shares in-flight resources (single-flight), and writes a lasting `.failed` marker (versioned; older markers are ignored and removed) only when `convert` finished cleanly with the extracted file intact and still produced no JSON. Cached JSON is keyed by the WolvenKit identity as well as the archive, and a marker records the identity that failed and counts only for it, so a WolvenKit update extracts again. The archive-index cache is written atomically and trusted only when it holds the entry count the archive's own index declares. The grading-LUT host keeps the opened installation between retries, retries only transient failures (time limit, missing .NET, a process that could not start, a disk error) with doubling backoff and a cap, and treats a WolvenKit exit code on the same archive, entry and WolvenKit as lasting.

## What `uncook` writes

With `-u --uext png --mesh-export-type MeshOnly -gp <game>` over `archive/pc/content` and a regex naming the resources: a `.mesh` yields the raw file, `<name>.glb` and `<name>.Material.json` (every material resolved through its `.mi` chain), plus the textures and multilayer setups those materials use; a `.morphtarget` yields the raw file and `<name>.morphtarget.glb`. The head mesh and morph target of the female player head came from `basegame_4_appearance.archive` in 2.31. [runtime of the tool] 9.0.1, 25 Sep 2026; [preview export method](../experiments/013-native-preview-core/README.md#ported-to-the-studio).

Whether a depot path exists at all is answered from the archives' RDAR indexes (FNV-1a 64 of the sanitized path), not from WolvenKit's output: reading every content index takes about 35 ms. [source] [mod loading](mod-loading.md), [`rdar-index-fs.ts`](../projects/xf-studio/authoring/src/game/host/rdar-index-fs.ts).

**The native reader replaces most launches.** XF Studio's own reader decodes archives and CR2W resources through the game's own Oodle library, in a worker. It reproduces WolvenKit's extracted bytes and the resolver's JSON, including resources that WolvenKit refuses to serialize (the mistyped `castShadows` above). The resolver reads through it first and runs WolvenKit only for what it doesn't answer: a cold resolve of the reference save needed no launches instead of 23 ([mod loading §6](mod-loading.md#6-implementation-and-reproduction)). Textures and meshes for the preview still come from WolvenKit's exports. Format and evidence: [archive and resource formats](archive-format.md).

## WolvenKit 10 beta compatibility boundary [offline]

On game 2.31, **10.0.0-beta.2-nightly.2026-10-25 reproduces beta.1's two changed members exactly**: 14/16 unpacked members match 9.0.1; the `.app` and `.morphtarget` differ only by WolvenKit's type-default/serialisation changes (21 omitted EYES fields and two explicit chunk masks). Both independent verifiers and both 120-resource extraction oracles pass. Reader v5 preserves omitted `faceRegion` instead of inferring NONE or EYES; no product behavior uses its meaning. The writer is unchanged. The 14-sample strict JSON oracle still reports only the known tool-default/shape differences: added bounding-box/texture defaults, changed omitted chunk-mask defaults and fixed-array expansion. [resource]

**Accept this beta for reading 2.5 under decoded equivalence**, with every byte difference fully explained by WolvenKit's type-default/serialisation changes and reader support for both forms; any unexplained additional difference blocks. The runner retains strict diagnostic failures (exit 1), rather than claiming byte or expanded-JSON equality. This does not change stable-download defaults or establish behavior on actual 2.5 files or in-game rendering. Exact hashes, complete sampled differences, timings and rerun procedure are in [Experiment 045](../experiments/045-game-2-5-baseline/README.md) and the reader policy in [archive formats](archive-format.md#wolvenkit-10-beta-boundary-offline). The shared probe and PATH discovery accept only the evaluated 10.x nightly when selected, retaining its full prerelease product version; a real check on a private CLI copy passes. Other 10.x builds, beta.1 included, remain unaccepted. Automatic downloads stay at 9.0.1 until WolvenKit 10 is stable, or a decision after the maintainer updates. The nightly requests .NET 10.0.0 and executed with installed 10.0.13.

## Native writer compression baseline [offline]

The [current 2.31 writer baseline](../experiments/045-game-2-5-baseline/README.md) also exposes a stable-tool compression boundary: a fresh 9.0.1 production fixture's 17 resource-table buffers reproduce at Kraken Normal, whereas the native writer uses Optimal2. Twelve resource byte comparisons fail, despite identical stored properties and decompressed buffers on all 16 resources; repacking the reference resource bytes passes except timestamps. Keep this separate from the beta's changed stored properties.

**Offline evidence handling [source and synthetic checks, 25 October 2026]:** Experiment 045's runner requires a prebuilt BCN DLL and overrides inherited configurable data-cache/tool roots with run-local paths. Captures start from empty settings and are refused in the main working tree (`git-dir` equals `git-common-dir`). Browser bundles are an exception to run-folder isolation: the server still rebuilds and prunes the linked worktree's `public/build`; it has no relocation setting. Use a separate worktree with an independent build directory and no active Studio serving it. The Git check does not detect build-directory junctions shared with another checkout or protect other servers in that same worktree.

The writer comparison honours `XFS_NATIVE_WRITER_GAME_ROOT` and records the actual loaded Oodle identity privately. Diagnostics require a previously absent directory created by the tool, with an existing parent, and all diagnostic files use exclusive `wx` creation. `lstat` refuses existing entries including dangling links; resolved containment rejects paths inside or around the oracle/game/BCN inputs. Canonical paths do not detect hard links: fresh-directory and exclusive-file creation prevent overwriting pre-existing aliases. These are path/overwrite guards, not a sandbox against concurrent replacement of directories by another process. With diagnostics enabled, compare one oracle per fresh output directory. Public baseline schema 2 permits identity hashes, equality flags and section counts/hashes only; full mappings, topology and resource differences stay ignored. Synthetic worktree, containment, exclusive-write, nested-buffer and alias tests establish these specific guards, not game compatibility or a full real-capture audit; commands and limits are in the [experiment README](../experiments/045-game-2-5-baseline/README.md).
