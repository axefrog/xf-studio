# Channels to the player: how a mod puts words, objects and markers in front of V

**Maturity: Draft.** For each way Cyberpunk 2077 can tell the player something (phone messages and contacts, holocalls, the Kiroshi scanner, crowd barks, shards, notifications, the journal and a tracker, map pins): what a script can read, what it can write, how custom content gets in (TweakXL, ArchiveXL, redscript, CET, the XF bridge), what limits apply, and whether the bridge already reaches it. Consolidated on 22 October 2026 from the game's 2.31 scripts (`final.redscripts`, SHA-256 `2119046f…ee86`, decompiled with redscript-cli 0.5.31 `decompile -f`; [manifest](../research/story-engine/quest-corpus-e-manifest.json)), the game's TweakDB source text (REDmod `tools/redmod/tweaks`) and compiled blobs read offline, the Modding Docs clone (commit `a54b08735a560bca7dd76b1e1dab1631e6aaae89`) and the scripts of seven studied mods. The framework answers in §3.3, §3.5, §3.7 and §3.9 were read on 23 October 2026 in the public source of TweakXL (`psiberx/cp2077-tweak-xl` at `b527894`, its wiki at `8349306`), ArchiveXL (`psiberx/cp2077-archive-xl` at `d56db6e`, its wiki at `b131636`), Codeware (`psiberx/cp2077-codeware` at `a652bbb`, its wiki at `0475d90`), the RED4ext SDK (`WopsS/RED4ext.SDK` at `0f5eba4`, whose generated headers come from the game's own type information) and the Modding Docs (`b2a08f5`); file paths in those citations are relative to each repository. **Nothing here has been seen in a game session**; the only [runtime] claims are the bridge's own earlier results, cited from the pages that hold them.

Grades follow the [knowledge rules](README.md): **[source]** read in the game's scripts, a mod's scripts or a framework's source (a mod's source shows it works for that mod's author; we have not run it), **[resource]** read in TweakDB or other game data, **[wiki]** documented in the Modding Docs (with the page), **[community]** stated in a framework's own wiki but not read in its code, **[runtime]** seen in the running game, **[hypothesis]** not established. "Community-claimed" in the briefs maps to **[wiki]**, **[community]** and to a mod doing it.

This page answers: *for the Story Engine's realisation layer (design seeds [DS-18](../research/story-engine/design-seeds.md) and [DS-33](../research/story-engine/design-seeds.md), requirements V3–V8 in the [runtime requirements](../research/story-engine/runtime-requirements.md)), which channels can carry our own text, which need data shipped in an archive, and which the bridge can already drive?*

## 1. The short answers

| Question | Answer | Grade |
|---|---|---|
| **Can we supply our own scanner entries?** | **Yes, by three routes, none yet seen in game.** (a) *Data:* new TweakDB records of `$type` `npc_scanning_data`, `device_scanning_data` or `FocusClue` (the type names are confirmed from the SDK's generated headers; a name and a description each, as `LocKey`s) from a TweakXL YAML file, their text in an ArchiveXL `localization: onscreens:` JSON, attached to an entity through the `ScanningComponent` in its template. (b) *Runtime events on a live entity:* `SetCustomObjectDescriptionEvent` (a description made of record ids), `OverrideScannerPreset` (which panels show), `ToggleFocusClueEvent`. (c) *Writing the scanner's own blackboard chunks* after the game fills them, which an installed mod already does to rename ordinary NPCs. Fully dynamic text needs a record created at run time (TweakXL's `TweakDBManager`) or route (c). | [source], [resource], [wiki]; see §3.3 |
| **Can we supply custom shard text through TweakXL and ArchiveXL?** | **Yes, documented end to end.** A `.journal` holding a `gameJournalOnscreen` entry (title and description keys, a category tag), a localisation JSON with the text, a TweakXL item record (`ItemType.Gen_Readable`, tag `Shard`) whose Read action names the journal entry, and an ArchiveXL `.xl` listing the journal and the text. The item record can be a few lines cloned from a vanilla shard with `$base`, provided its Read action is overridden too (§3.5). The text is static data. A journal-free popup with arbitrary text is separate: queue a `NotifyShardRead` event with a title and text. | [wiki] `modding-guides/quest/creating-custom-shards.md`; [source] for the popup; §3.5 |
| Which channels can carry text that is generated at run time? | Notifications, overhead and subtitle lines, journal-free phone threads, the popup shard, the scanner (route c) and an ink tracker. The journal, a real holocall's video and a shard's journal entry are authored data: dynamic text there means rewriting a pre-authored slot. | [source] |
| Can script create journal entries or quests? | No. The shipped scripted-quest API (`CreateScriptedQuestFromTemplate` and its siblings on `JournalManager`) is a set of stubs that return `false` in 2.31. | [source] `core/systems/journalManager.script:90-123`, `core/systems/gameplayQuestSystem.script:160-195` |
| What does the bridge reach today? | Its own status surface (`ui_message`, `ui_hud`), map pins (`world_pin`), reading named quest facts (`world_state`). The scanner and shards are not reached at all. Built offline, not yet run in game: NPC direction's barks (0.8.8) and the live-direction toolkit (0.8.12, [§5](#5-the-bridges-live-direction-toolkit-0812-what-each-command-drives-and-what-was-left-out)): a message toast, a real call from a journal contact, banners and toasts, subtitle lines, and a tracker with our own words. | [runtime] for the first three; [source] and [offline] for the rest; see the table |

## 3. Per channel

### 3.1 Phone messages and contacts

Already covered in depth by [quests and story §2.6](quests-and-story.md#26-phone-messages-and-contacts) and [terminals §3.3 and §6.1](terminals-and-arcade.md#33-messages-on-the-phone); only what the other channels need is added here.

- **Two kinds of thread.** An authored thread is journal data (`contacts/<contact>/<conversation>/<message>`), merged by ArchiveXL, with text keys supplied by `localization: onscreens:` [wiki] `modding-guides/quest/how-to-add-new-text-messages-thread-to-cyberpunk-2077.md` (Bill, April 2025; images `image1 (2).png`, `image2 (1).png` show the folder layout and the root-phase graph). A journal-free thread is a `ContactData` we inject into the messenger's lists, drawn by our own additions to `MessengerDialogViewController` [source] NightlyNow Core, Stock Market and News System ([B1 deep dive](../research/mod-ecosystem/b1-story-systems.md)), plus two more studied this time: Night City Allies (`Phone/NCAPhoneSystem.reds`) and AI NPC Cyberpunk Mod (`PhoneContacts.reds`, `PhoneChat.reds`) [source].
- **The toast.** A phone notification is `PhoneMessageNotificationViewData` (`threadHash`, `contactHash`, `title`, `SMSText`, `animation` `notification_phone_MSG`, a sound event and an action) wrapped in `gameuiGenericNotificationData` (widget `notification_message`, 6.7 s) and given to the HUD phone controller's `AddNewNotificationData`; clicking runs an action that asks `PhoneSystem` to open that contact [source] Night City Allies `Phone/NCAPhoneSystem.reds:466-520`; the data class is the game's own, `cyberpunk/UI/fullscreen/notification/journalNotification.script:41-56`.
- **What persists.** Authored message states live in the save with the journal. A journal-free thread lives wherever the mod keeps it, so for XF it must be part of the XF store, never assumed from the save ([save files](save-files.md)).
- **Read side.** `JournalManager.GetContacts(context, out)`, `GetEntryByString`, entry state and `RegisterScriptCallback(obj, fn, gameJournalListenerType.State | Tracked | Counter)` report what V has and when it changes [source] `core/systems/journalManager.script:8-75`. Stock Market also hears vanilla quest completion this way.
- **Bridge.** `phone_text` (0.8.12, built offline) shows the toast for a name and a line; it makes no thread and has no click action. Its owned view-data subclass is drawn before vanilla's journal lookups; it never supplies missing entries to native methods ([requirements](../research/story-engine/runtime-requirements.md) V4, V12).

### 3.2 Holocalls

- **The game's own call is two parts:** the phone runs the ring, the name, the picture and the panel; an ordinary scene plays the words over it. A call node's `phase` goes `IncomingCall`, `StartCall`, `EndCall` [wiki] `modding-guides/quest/custom-video-holocalls.md` (the guide's own graphs: `holocall-scene-graph.png`, `holocall-phase-1-reset-to-call.png` to `holocall-phase-5-hang-up.png`; applies to 2.31; last edited by nightcityriot, 22 September 2026, authorship unevidenced in the page).
- **State is a fact.** `phonecall_<caller>_with_<receiver>`, ids lowercase and the last part of the journal path: 0 ended, 1 ringing or opening, 2 talking, 3 declined. Reset it to 0 before each call, or a stale 2 connects the call before it rings [wiki] same page. `PhoneSystem.SetPhoneFact` writes it [source] `cyberpunk/systems/phoneSystem.script:204-212`. The bridge's `world_state` can read it.
- **The video is a stage, not a stream.** The caller stands in a hidden studio far off the map, one corner per game character (lights, camera, a workspot, a look-at marker), toggled by prefab variants; the camera renders to a texture the call panel shows. The wiki says to make our own contact rather than reuse a vanilla one, because every vanilla contact carries a built-in phone conversation that opens over ours [wiki] same page.
- **A script can start a call.** `PhoneSystem.OnTriggerCall(questTriggerCallRequest)` takes `caller`, `addressee`, `callPhase`, `callMode` (`Audio`, `Video`), `isPlayerTriggered`, `isRejectable`, `showAvatar` and `visuals`, plays the ring and writes the call blackboard and fact [source] `cyberpunk/systems/phoneSystem.script:79-120`, `orphans.script:41554-41571`. The HUD then finds the contact by comparing `GetId()` to the caller name and takes its avatar and name from it [source] `cyberpunk/UI/hud/phone/incomingCallController.script:78-110`. **So a call needs a journal contact**, vanilla or ArchiveXL-merged.
- **A mod can skip all of that.** AI NPC Cyberpunk Mod deliberately never touches the call request, the fact or the blackboard (they feed time skip, scene fast-forward and the phone itself) and instead drives only the HUD's call window through the controller methods the game's own phone code uses, so a quest call always wins. For a live picture it stages a copy of the character out of V's sight, points the game's own `holocall_camera.ent` at it and falls back to a portrait voice call if anything is not ready [source] `r6/scripts/CyberpunkConvai/Holocall.reds` (header and `ConvaiCallBegin`) and its `holocall.lua`. This is the closest installed model for a Story Engine caller without a quest phase.
- **Subtitles-only calls.** `scnDialogLineData` of type `Holocall` renders a line in the call style; whether it shows without a call in progress is open ([NPC direction](npc-direction.md), open question 6 in its design).
- **Limits.** A needed journal contact is static data. Voice needs recorded audio or a vanilla line ([NPC direction §4](npc-direction.md#4-speech)). A call is blocked by phone-disabled states, combat and some scene tiers (`PhoneSystem.IsCallingEnabled`, `IsBlockedBy…` at `phoneSystem.script:277-345`).

### 3.3 The Kiroshi scanner

**What the panel is made of.** The scanner HUD shows chunks written to the `UI_ScannerModules` blackboard by the scanned object's `CompileScannerChunks`: a name, then for people the level, rarity, health, attitude, faction, weapon, resistances, bounty and abilities as the character's **scanner preset** allows, and for devices a status, a description and skill checks [source] `cyberpunk/NPC/NPCPuppet.script:3409-3700`, `cyberpunk/devices/frame/frame.script:74-106`, `cyberpunk/UI/hud/scanner/scanner_data.script`. Beside the chunks, the quest-style entries come from the object's `ScanningComponent`: **clues** (`FocusClueDefinition`: a `FocusClue` record, extended clue records with percentages, facts to set) and an **object description** (`NPCScanningDescription` or `DeviceScanningDescription`: a gameplay description id and a list of custom description ids), each a TweakDB record id whose `localizedName` and `localizedDescription` the native layer turns into `ScanningTooltipElementData` for the panel [source] `core/components/scanningComponent.script:1-135, 571-675`, `cyberpunk/UI/hud/scanner/scanner.script:313-337`, `orphans.script:47558-47565`.

**The records.** All three families extend `ScannableData` (`friendlyName`, `localizedName`, `localizedDescription`, `iconName`, `iconRecord`) [resource] REDmod tweak source `database/scanning/schema.tweak`. The base game holds 25 `npc_scanning_data`, 299 `device_scanning_data` and 1,470 `FocusClue` records, and 5 `ScannerModuleVisibilityPreset` records (Phantom Liberty: 85, 315, 2,085 and 8) [resource] counts from the TweakDB blobs. So the vanilla scanner is mostly **clues**, with a few dozen hand-written NPC descriptions; the NPC `fullDisplayName`, `displayName`, `scannerModulePreset` and `affiliation` of the character record supply the header. The Modding Docs show the character-record route: editing Panam's `fullDisplayName`, `displayName` and faction changed what the scan tab shows [wiki] `for-mod-creators-theory/core-mods-explained/tweakxl/tweakxl-changing-game-records/changing-npcs-tweak-edit-redmod.md` (daemon2077, October 2023, game 2.01; its images `Screenshot_1.png` to `Screenshot_3.png` show the record file and the changed in-game scan).

**Route A: data.** New records of the three types in a TweakXL YAML file, their text under secondary keys in an ArchiveXL `localization: onscreens:` JSON, referenced from the `ScanningComponent` of an entity template we ship.

- **The type names are confirmed** [source]. The SDK's generated headers name the three record classes `gamedatanpc_scanning_data_Record`, `gamedatadevice_scanning_data_Record` and `gamedataFocusClue_Record`. All three derive from `gamedataScannableData_Record` and add no data of their own (RED4ext SDK `include/RED4ext/Scripting/Natives/Generated/game/data/npc_scanning_data_/Record.hpp:13-21`, `device_scanning_data_/Record.hpp:13-21`, `FocusClue_Record.hpp:15-21`, `ScannableData_Record.hpp:15-22`).
- **TweakXL accepts any of three spellings** for `$type`: it adds a missing `gamedata` prefix and `_Record` suffix, so `npc_scanning_data`, `npc_scanning_data_Record` and the full name all work (TweakXL `src/Red/TweakDB/Reflection.cpp:338-348, 559-573`) [source]; its wiki documents the same three forms (`YAML-Tweaks.md:79-85`) [community].
- **Where the fields come from.** TweakXL builds a type's field list from the record class's getter functions, read against one existing record of that type, plus a shipped list of "extra flats" that have no getter (`Reflection.cpp:63-260`, `data/ExtraFlats.yaml`). A type with no vanilla record could not be created this way; these three all have vanilla records [source].

| `$type` | Fields | Grade |
|---|---|---|
| All three, from `ScannableData` | `friendlyName`, `localizedName` and `localizedDescription` (`LocKey`s), `iconName`, `iconRecord`, and the extra flat `revealOrder` (`Int32`) | [resource] schema (`database/scanning/schema.tweak`); [source] `ExtraFlats.yaml:1181-1183`. The base class's data block is 0x40 bytes after the record header (`ScannableData_Record.hpp:20`), and TweakXL places getter-backed fields 12 bytes apart (`Reflection.cpp:22, 92-102`): room for exactly five, which matches the five schema fields |
| `npc_scanning_data` | The above, plus the extra flat `affiliation` (a record id of type `Affiliation`) | [source] `ExtraFlats.yaml:24-27` |
| `device_scanning_data` | The above (`revealOrder` is listed again for it) | [source] `ExtraFlats.yaml:36-38` |
| `FocusClue` | The above (`revealOrder` again) | [source] `ExtraFlats.yaml:1215-1217` |

A sketch of the smallest record (unverified; the key names are ours):

```yaml
XF.ScanTest01:
  $type: npc_scanning_data
  localizedName: LocKey#xf-scan-test-name
  localizedDescription: LocKey#xf-scan-test-desc
```

TweakXL fills unspecified fields with the type's defaults (`YAML-Tweaks.md:64-77`) [community].

**Route B: events on a live entity.** The component and its saved state take events: `SetCustomObjectDescriptionEvent` (holds an inline `ObjectScanningDescription`; the persistent state keeps it, so use the vanilla `NPCScanningDescription` class, whose fields are record ids, not a class of our own that a save could not load), `ClearCustomObjectDescriptionEvent`, `DisableObjectDescriptionEvent`, `DisableScannerEvent`, `ToggleFocusClueEvent`, `ToggleClueConclusionEvent` [source] `scanningComponent.script:60-135, 183-345`; and on a puppet `OverrideScannerPreset { scannerPreset: TweakDBID }` and `ResetScannerPreset` [source] `scriptedPuppetPS.script:2-17`, `NPCPuppet.script:3952-3958`. Building the description from script needs access to its protected fields, which redscript allows from added methods on the class [hypothesis: not tried].

**Route C: write the chunks.** AI NPC Cyberpunk Mod wraps `NPCPuppet.CompileScannerChunks` and, after the game has written its `ScannerName` chunk, replaces the primary text with a generated name for nameless NPCs; it never touches the other chunks [source] `r6/scripts/CyberpunkConvai/NpcNames.reds` (credited in the header to its own `npc-names.lua`). The same blackboard takes a `ScannerDescription` chunk (a default description plus a list of custom lines, plain strings passed to `SetLocalizedTextScript`), which devices fill from script [source] `scanner_data.script:397-421`, `scanner_chunks.script:986-1030`, `frame.script:101-103`. Whether an NPC's panel has a description area to show it is [hypothesis].

**Dynamic records.** Night City Allies clones a record and sets flats at run time with TweakXL's `TweakDBManager` (`CloneRecord`, `SetFlat`, `UpdateRecord`) for its equipment [source] `r6/scripts/NightCityAllies/Equipment/EquipmentRecords.reds:55-100`. The same can make a `FocusClue` or `npc_scanning_data` record at run time, but **not with generated text written into the record**. TweakXL's script `SetFlat` refuses a value whose type differs from the flat's, so a `String` sent to a `LocKey` field returns `false` and changes nothing. A `CName` of the form `LocKey#<text>` is accepted, but it is converted to a key by hashing `<text>` (TweakXL `src/App/Tweaks/Executable/Scriptable/ScriptManager.cpp:10-30`, `ScriptUtils.hpp:28-45`, `src/Red/TweakDB/Manager.cpp:444-466`) [source]. A dynamic record therefore points at a key whose text is defined elsewhere (§3.9). The game's own test clues in `scanning_clues.tweak` store plain strings in the field; how the game's own tweak compiler stores those is not shown by this source.

**Text.** A secondary key resolves from an ArchiveXL onscreens file, or from Codeware's `ModLocalizationProvider`, which several studied mods use for their texts [source] Better Fuel System Reloaded `Localization/LocalizationProvider.reds`, Photo Mode UI Improvements `Localization.reds`. A provider's text for a key is fixed once the language has loaded, as far as the game's own lookups (the scanner among them) are concerned; only Codeware's script-side table can change later ([§3.9](#39-localised-text-from-mods-what-the-frameworks-do)) [source].

**Verdict.** Writable, with three independent routes; nothing has run. **Bridge: no**; V8 stays "want". The cheapest first test is route B on a looked-at civilian (session row 1).

### 3.4 Crowd barks and voicesets

Fully covered by [NPC reactions §3–4](npc-reactions.md#3-how-an-npc-picks-and-plays-a-voice-line) and [NPC direction §4](npc-direction.md#4-speech). In the channel's terms: **read** the `UIGameData.ShowDialogLine` blackboard and an NPC's voice tag; **write** a voiceset trigger (the game picks line, audio and lip sync) or a text line (`OverHead`, `OverHeadAlwaysVisible`, `Regular`, `Holocall`, `Radio`, `Narrator`; AI NPC Cyberpunk Mod also writes `Holocall` lines through the same blackboard, `subtitles.lua`); custom audio through Audioware. A bark honours the player's chatter setting and the 150 m (20 m in tight scenes) overhead rule [source]. **No civilian line comments on V's looks** in the game's own voicesets ([NPC reactions §3.3](npc-reactions.md#33-lines-that-could-comment-on-v-resource)). **Bridge: branch** (`npc.say`, test N7 in the [NPC direction design](../research/runtime/npc-direction-design.md)).

### 3.5 Shards and readable items

**The authored route (the second named question).** The wiki's guide builds a shard from five files [wiki] `modding-guides/quest/creating-custom-shards.md` (created 17 April 2025 by Bill, text guide added by curricle in September 2025; images `shards_tutorial_01.png` to `shards_tutorial_11.png`):

| File | Holds |
|---|---|
| `…\journal\shards.journal` | A folder chain `onscreens` → `emails` → `quests` → `minor_quest` → `<mod>`, a `gameJournalOnscreenGroup` (`shards`) and one `gameJournalOnscreen` with `id`, `title`, `description` (`LocKey`s) and `tag` (one of ten: `world`, `poetry`, `notes`, `literature_fiction`, `philosophy_religion`, `others`, `technology`, `night_city_people`, `articles`, `leaflets`) |
| `…\onscreens\<mod>.json` | `localizationPersistenceOnScreenEntry` rows (`femaleVariant` text, `primaryKey`, `secondaryKey`); the guide found the primary keys unreliable and used `primaryKey 0` with matched secondary keys |
| `r6\tweaks\<mod>\<item>.yaml` | An item record: `itemType: ItemType.Gen_Readable`, tags `Readable`, `Shard`, `SkipActivityLog`, `HideInBackpackUI`, `HideAtVendor`, an `itemSecondaryAction` |
| `r6\tweaks\<mod>\<item>_inline0.yaml` | The action: `actionName: Read`, `removeAfterUse: True`, and `journalEntry: onscreens/emails/quests/minor_quest/<mod>/shards/<id>` |
| `<mod>.archive.xl` | `journal:` (the journal file) and `localization: onscreens:` (the JSON) |

The guide places the item in the world with a `shard_case_container.ent` and a `ShardCaseContainer` node whose `itemTDBID` is the record. Its screenshots show the result: the read popup with the title and description (`shards_tutorial_10.png`) and the shard under the `ARTICLES` category of the journal's shards list (`shards_tutorial_11.png`) [wiki, images inspected]. The game's side agrees: reading a `Gen_Readable` item removes it and activates the journal entry named by the action's `journalEntry` string, and `ReadAction` builds the popup from the entry's title and description [source] `cyberpunk/player/player.script:2249-2253`, `cyberpunk/items/actions/readAction.script:1-30`. The base game has 531 shard-named item records (858 with Phantom Liberty) [resource].

**A shorter record with `$base`** [source]. Hand-writing the whole item record is long; TweakXL can clone one instead. `$base` on a new record copies the source's type, so no `$type` is needed (TweakXL `src/App/Tweaks/Declarative/Yaml/YamlReader.cpp:192-208`); on a record that already exists, the source must be the same type (`:148-171`). The clone copies every field of the source *by reference*: each field of the new record points at the source's value (`src/Red/TweakDB/Manager.cpp:127-153, 507-529`). That includes `itemSecondaryAction`, which names the vanilla shard's own Read action and, through its `journalEntry`, the vanilla text. So the action must be overridden as well, or our shard opens the vanilla entry. An inline map under the field creates a new action record of ours, and an inline `$base` clones the vanilla action first (`YamlReader.cpp:451-480, 515-551`; wiki `YAML-Tweaks.md:87-145` [community]):

```yaml
Items.xf_shard_01:
  $base: Items.<a vanilla shard record>
  itemSecondaryAction:
    $base: <that shard's Read action record>
    journalEntry: onscreens/emails/quests/minor_quest/<mod>/shards/<id>
```

The vanilla shard and its action's record name come from the game's TweakDB (not read here). Everything else (tags, item type, prices) is inherited. Not yet seen working in game (session row 9).

**Giving the item without a case.** `TransactionSystem.GiveItemByTDBID(player, tdbid, 1)` exists [source] `orphans.script:18035-18037`; that it works for a shard is [hypothesis].

**The journal-free route (a popup with any text).** The popup is a plain notification, `ShardReadPopupData { title, text, isCrypted, itemID, m_imageId }` with widget `shard_notification.inkwidget`, raised when the UI system receives a `NotifyShardRead` event; the title and text pass through `GetLocalizedText` and are set as strings, and the popup pauses the game until closed [source] `cyberpunk/UI/fullscreen/notification/popupManager.script:438-470`, `shardsNotification.script:40-100`, `cyberpunk/UI/fullscreen/codex/codexUtils.script:464-477`, `orphans.script:38996-39009, 52955-52966`. The popup manager marks the entry as visited, and a script-made event has no entry, which may be an error or a no-op [hypothesis]. Nothing is added to V's shard list by this route.

**Verdict.** Authored shards: yes, wiki-documented, static. Dynamic shards: popup only. **Bridge: no.**

### 3.7 The journal and a journal-free tracker

- **Read:** entries by path or hash, state filters, the tracked entry, objective counters, the district and recommended level of a quest, and a callback on any change (§3.1). The vanilla tracker draws the tracked objective's description and counter and listens to the journal's `State`, `Tracked` and `Counter` events [source] `cyberpunk/UI/quests/quest_tracker.script:45-60`.
- **Write:** `ChangeEntryState`, `ChangeEntryStateByHash`, `TrackEntry`, `UntrackEntry`, `TrackPrevNextEntry` on entries that exist. **Create:** only from a `.journal` resource merged by ArchiveXL, hot-reloadable [source] [quests §2.3 and §7](quests-and-story.md#23-the-journal). The shipped "scripted quest" API (a quest cloned from a template, an objective description, a map pin entity per objective) belongs to `GameplayQuestSystem`, used by devices, but every function in it returns `false` or does nothing in 2.31: it is a retired or cut path, so a mod cannot rely on it [source] `core/systems/journalManager.script:90-123`, `gameplayQuestSystem.script:50-90, 160-195`.
- **A pool of pre-authored slots** (quest and objective entries shipped in our own `.journal`, driven by a generic phase and fact) is the one honest way to appear in the real journal; their text is a key, so dynamic text means substituting at draw time as Eviction Notice does for messages ([quests §2.6](quests-and-story.md#26-phone-messages-and-contacts)). ArchiveXL's journal merge accepts such a pool (below) [source]; whether the tracker redraws when only the substituted text changes needs the game.
- **What ArchiveXL's journal merge does** [source] (ArchiveXL `src/App/Extensions/Journal/Extension.cpp`, `Config.cpp`):
  - *When.* Each `.journal` listed under an `.xl` file's `journal:` key is loaded while the game builds its journal tree, and merged into the root folder with the same `id` (`Extension.cpp:58-134`). Use the list form: the single-path form reads the whole document instead of the `journal` value (`Config.cpp:35-38`), so it would queue an empty path [source; not tried].
  - *Matching.* Entries match by `id` path. Each entry in our file is looked up among the target's children by `id`, and an id may itself be a `/`-separated path. An existing entry is entered and its children merged recursively. A missing entry whose parent exists is appended whole, with its subtree. A missing parent is skipped with a "Path not fould" warning (`Extension.cpp:330-417`).
  - *Editing.* A trailing `*` on the last id segment edits an existing entry instead of adding one: every property but `id` is copied over when the classes match, and it cannot create an entry (`:353-357, 398-403, 426-448`).
  - *No class or count checks.* Nothing in this code checks entry classes or counts. A new `gameJournalQuest` whose phase holds any number of `gameJournalQuestObjective` entries is appended like any other subtree. No limit appears in ArchiveXL; any limit is the journal's or the tracker's own, which only the game shows.
  - *Two mods, one path.* When two mods add the same id path, the second's children join the first's entry. The first entry's own properties stay, unless the second marks the entry with `*`.
  - *Text and pins.* Each new entry's text fields become hashed keys (`:476-500`, see §3.9), and quest map pins in new entries are collected so their positions resolve later (`:502-540`).
  - *Hot reload.* A reload rebuilds the journal, remembering the tracked quest and tracking it again afterwards (`:48-56, 553-604`).
  - *The phase that drives the pool* is ArchiveXL's separate quest-phase feature. A `quest: phases:` entry (`path`, `parent`, input and output node paths with optional sockets, `intercept`) splices a `.questphase` node into the parent phase's graph when that parent loads (`src/App/Extensions/QuestPhase/Config.cpp:8-50`, `Extension.cpp:178-236`). When the parent is a quest resource, the new node's fact is set on game restore (`Extension.cpp:97-128, 228-231`), as [quests and story](quests-and-story.md) describes.
- **A tracker line without a journal entry.** The tracker also draws a **tracked mappin**: when `UI_System.TrackedMappin` holds a pin, it spawns an objective row whose title and text come from the pin's variant (`MappinToString`, `MappinToObjectiveString`), not from any text we supply [source] `quest_tracker.script:153-171`. So a runtime pin can give a generic "world" row; custom words need our own objective rows. The bridge's tracker (0.8.12, §5) puts them in the tracker's own container instead of a separate widget.
- **Bridge:** no journal writes; `world_state` reads named facts only (V5, V7); `quest_set` and `quest_objective` (0.8.12, built offline) draw a journal-free list. **Verdict:** real journal content is authored data; the journal-free tracker is ours to draw.

### 3.9 Localised text from mods: what the frameworks do

Every channel above that shows authored text (scanner records, shard and journal entries, item names) reads it through a localisation key. This section is what the frameworks' source says about those keys; all of it is [source] unless marked.

**A key is a number, and text written into a key field becomes a key.** A `LocKey` field holds one 64-bit number (RED4ext SDK `include/RED4ext/NativeTypes.hpp:319-327`). Text given in its place is turned into that number by FNV-1a 64 of the text, unless the text is all digits, which is taken as the number itself (`NativeTypes-inl.hpp:111-114`). TweakXL's YAML reader does this for every spelling it accepts: `LocKey#name`, `LocKey("name")`, `l"name"`, a bare name, or a number (TweakXL `src/App/Tweaks/Declarative/Yaml/YamlReader.Values.cpp:127-196`; the table in wiki `YAML-Tweaks.md:257-269` [community]). So **a literal string in a `LocKey` field is a secondary key by construction; the text itself is never stored.** In plain `String` fields that hold `LocKey#…` references, TweakXL rewrites `LocKey#name` to `LocKey#<hash>`, in YAML (`YamlReader.Values.cpp:256-280`) and in script (`src/App/Tweaks/Executable/Scriptable/ScriptUtils.hpp:46-59`). A `String` field without the prefix stores the text as written; whether the game shows it raw depends on the code that reads it.

**ArchiveXL does the same in its own files.** An onscreens entry with `primaryKey` 0 and a `secondaryKey` is registered twice: under FNV-1a 32 of the key, keeping the key, and under FNV-1a 64 of it, which is the number a TweakXL `LocKey` holds (ArchiveXL `src/App/Extensions/Localization/Extension.cpp:159-186`). This happens when the game loads a language's text resource, with the mod's fallback language merged too (`:69-139`). A primary key inside the vanilla range replaces the vanilla text (`:199-211`). That is why the wiki says to use `secondaryKey` for new text and `primaryKey` to edit vanilla text (ArchiveXL wiki `Home.md:287-326`) [community]. In merged `.journal` entries, every localisation-string field that does not start with `LocKey#` is replaced by `LocKey#<FNV-1a 64 of the text>` (`src/App/Extensions/Journal/Extension.cpp:476-500`), so a journal title written as plain text becomes a key too.

**No plain-text route is documented** in either framework's source or wiki. The documented routes are a secondary key plus an ArchiveXL onscreens file or a Codeware provider. What the game draws for a key nobody defined (blank, the key, or a marker) is engine behaviour. Codeware's own `GetText` guards for `GetLocalizedText` returning an empty string and then returns the key itself (Codeware `scripts/Localization/LocalizationSystem.reds:198-212`). That suggests an empty result but does not prove it (session row 3).

**Codeware keeps two tables, and only one can change after load.**

| Table | Filled | Read by | Can a key's text change later? |
|---|---|---|---|
| The game's own onscreens table | Once per language load. Codeware's native service hooks the game's text load, creates a **fresh instance** of every non-abstract `ModLocalizationProvider` class, and merges its packages' interface texts (not subtitles) under the same two hashes as ArchiveXL (`src/App/Localization/LocalizationService.cpp:5-71`, `scripts/Localization/Module/ModLocalizationProvider.reds:35-67`) | Every native lookup: TweakDB `LocKey` fields, `GetLocalizedText` and `GetLocalizedTextByKey`, journal and scanner text. The wiki says the same (`Home.md:904-913`) [community] | **No.** Codeware has no call to merge again, and the provider used for the merge is a throwaway instance, not the live system, so later changes in the live provider never reach this table. Only a new language load runs the merge again. Whether the game reloads texts in place when the language setting changes is engine behaviour (session row 18) |
| Codeware's script table in `LocalizationSystem` (a `ScriptableSystem`) | When the system attaches (`LocalizationSystem.reds:36-52`); when a provider registers, which each provider's `OnAttach` requests (`ModLocalizationProvider.reds:21-25`, `LocalizationSystem.reds:238-242`); when an accepted change to the interface or subtitle language reaches its settings watcher, rebuilding only if the language differs (`Watchers/LanguageSettingsWatcher.reds:18-23`, `LocalizationSystem.reds:62-65, 132-142`); and on `UpdateTranslationsRequest.Create(true)`, a forced rebuild (`:71-77, 154-157`) | Only `LocalizationSystem.GetText(key)` and `GetSubtitle(key)` called from script | **Yes.** Queue `UpdateTranslationsRequest.Create(true)` on the scriptable systems container. The rebuild asks every provider for its package again (`:159-175`). A package defines its texts once per instance and caches them (`Module/ModLocalizationPackage.reds:30-48`), so the provider must hand back a new package, or one built from current data, for new text to appear. Nothing in Codeware sends this request itself, and a widget that already drew the old text must redraw. Providers also get `OnLocaleChange` and `OnGenderChange` calls (`LocalizationSystem.reds:79-93`) |

**For the Story Engine:** text that the game itself draws (scanner, journal, shards, item names) can only come from keys defined before the language loads. Dynamic text there means a pool of pre-defined keys, or substituting at draw time. Text on our own widgets can come from Codeware's script table and change at run time.

## 4. What this means for the Story Engine

- **Words first.** Banners, overhead and subtitle lines, journal-free phone threads, the popup shard and the scanner chunk are all script-only and text-dynamic. They are the realisation channels to build first; none needs shipped data except an XF contact if a call is wanted.
- **One small authored kit.** A single ArchiveXL data pack gives the rest: one or more XF contacts in a `.journal` (callable, avatar from a `PhoneAvatars` record), a few shard slots, a pool of objective slots and scanner records. This is the "data-only pack" the [runtime requirements](../research/story-engine/runtime-requirements.md#xf-core-plugin-api-needs) describe, and it stays additive: it adds contacts and records, replaces nothing.
- **Never write the game's call path unless a quest call is wanted.** The studied mod's rule (a mod call yields to any quest call) is the safe pattern for an always-on engine.
- **Persist in our own store.** Journal-free threads, popup shards and pins vanish with the session; the XF store re-issues them after a load (requirement P2).

- `cyberpunk/UI/fullscreen/notification/journalNotification.script:544-606`: vanilla messenger data resolves both journal hashes and calls `GetAvatarID` / `GetAttachmentPathHash` without null checks. - `cyberpunk/systems/phoneSystem.script:79-120, 122-139, 186-212`: queued requests, internal timeout transitions and fact-only hang-up/rejection transitions are distinct. - `cyberpunk/UI/quests/quest_tracker.script:153-175`: mappin objectives spawn asynchronously. Redrawing immediately after the update does not prevent the completion from overwriting XF's title. Suppress the spawn while XF owns the container and handle a completion queued earlier.
- `core/components/scriptComponents/vehicleComponent.script:4055-4094`: `VehicleRadioEvent.toggle = true` advances the station when already on. An on-state request must compare `IsRadioReceiverActive` first.
- Codeware `scripts/World/DynamicEntitySystem.reds` and `src/App/World/DynamicEntitySystem.cpp:169-192`: `DeleteEntity` returns acceptance of deletion, and `IsManaged` distinguishes an already removed dynamic record from a failed request.
