# Channels to the player: how a mod puts words, objects and markers in front of V

**Maturity: Draft.** For each way Cyberpunk 2077 can tell the player something (phone messages and contacts, holocalls, the Kiroshi scanner, crowd barks, shards, notifications, the journal and a tracker, map pins): what a script can read, what it can write, how custom content gets in (TweakXL, ArchiveXL, redscript, CET, the XF bridge), what limits apply, and whether the bridge already reaches it. Consolidated on 22 October 2026 from the game's 2.31 scripts (`final.redscripts`, SHA-256 `2119046f…ee86`, decompiled with redscript-cli 0.5.31 `decompile -f`; [manifest](../research/story-engine/quest-corpus-e-manifest.json)), the game's TweakDB source text (REDmod `tools/redmod/tweaks`) and compiled blobs read offline, the Modding Docs clone (commit `a54b08735a560bca7dd76b1e1dab1631e6aaae89`) and the scripts of seven studied mods. **Nothing here has been seen in a game session**; the only [runtime] claims are the bridge's own earlier results, cited from the pages that hold them.

Grades follow the [knowledge rules](README.md): **[source]** read in the game's scripts or a mod's scripts (a mod's source shows it works for that mod's author; we have not run it), **[resource]** read in TweakDB or other game data, **[wiki]** documented in the Modding Docs (with the page), **[runtime]** seen in the running game, **[hypothesis]** not established. "Community-claimed" in the brief maps to **[wiki]** and to a mod doing it.

This page answers: *for the Story Engine's realisation layer (design seeds [DS-18](../research/story-engine/design-seeds.md) and [DS-33](../research/story-engine/design-seeds.md), requirements V3–V8 in the [runtime requirements](../research/story-engine/runtime-requirements.md)), which channels can carry our own text, which need data shipped in an archive, and which the bridge can already drive?*

## 1. The short answers

| Question | Answer | Grade |
|---|---|---|
| **Can we supply our own scanner entries?** | **Yes, by three routes, none yet seen in game.** (a) *Data:* new `npc_scanning_data`, `device_scanning_data` or `FocusClue` TweakDB records (a name and a description each, as `LocKey`s) from a TweakXL YAML file, their text in an ArchiveXL `localization: onscreens:` JSON, attached to an entity through the `ScanningComponent` in its template. (b) *Runtime events on a live entity:* `SetCustomObjectDescriptionEvent` (a description made of record ids), `OverrideScannerPreset` (which panels show), `ToggleFocusClueEvent`. (c) *Writing the scanner's own blackboard chunks* after the game fills them, which an installed mod already does to rename ordinary NPCs. Fully dynamic text needs a record created at run time (TweakXL's `TweakDBManager`) or route (c). | [source], [resource], [wiki]; see §3.3 |
| **Can we supply custom shard text through TweakXL and ArchiveXL?** | **Yes, documented end to end.** A `.journal` holding a `gameJournalOnscreen` entry (title and description keys, a category tag), a localisation JSON with the text, a TweakXL item record (`ItemType.Gen_Readable`, tag `Shard`) whose Read action names the journal entry, and an ArchiveXL `.xl` listing the journal and the text. The text is static data. A journal-free popup with arbitrary text is separate: queue a `NotifyShardRead` event with a title and text. | [wiki] `modding-guides/quest/creating-custom-shards.md`; [source] for the popup; §3.5 |
| Which channels can carry text that is generated at run time? | Notifications, overhead and subtitle lines, journal-free phone threads, the popup shard, the scanner (route c) and an ink tracker. The journal, a real holocall's video and a shard's journal entry are authored data: dynamic text there means rewriting a pre-authored slot. | [source] |
| Can script create journal entries or quests? | No. The shipped scripted-quest API (`CreateScriptedQuestFromTemplate` and its siblings on `JournalManager`) is a set of stubs that return `false` in 2.31. | [source] `core/systems/journalManager.script:90-123`, `core/systems/gameplayQuestSystem.script:160-195` |
| What does the bridge reach today? | Its own status surface (`ui_message`, `ui_hud`), map pins (`world_pin`), reading named quest facts (`world_state`). Phone, holocalls, scanner, shards, notifications, journal and the barks are not on `main`; the barks, a text and a scripted call are on the NPC-direction and DM branches. | [runtime] for the first three; see the table |

## 3. Per channel

### 3.1 Phone messages and contacts

Already covered in depth by [quests and story §2.6](quests-and-story.md#26-phone-messages-and-contacts) and [terminals §3.3 and §6.1](terminals-and-arcade.md#33-messages-on-the-phone); only what the other channels need is added here.

- **Two kinds of thread.** An authored thread is journal data (`contacts/<contact>/<conversation>/<message>`), merged by ArchiveXL, with text keys supplied by `localization: onscreens:` [wiki] `modding-guides/quest/how-to-add-new-text-messages-thread-to-cyberpunk-2077.md` (Bill, April 2025; images `image1 (2).png`, `image2 (1).png` show the folder layout and the root-phase graph). A journal-free thread is a `ContactData` we inject into the messenger's lists, drawn by our own additions to `MessengerDialogViewController` [source] NightlyNow Core, Stock Market and News System ([B1 deep dive](../research/mod-ecosystem/b1-story-systems.md)), plus two more studied this time: Night City Allies (`Phone/NCAPhoneSystem.reds`) and AI NPC Cyberpunk Mod (`PhoneContacts.reds`, `PhoneChat.reds`) [source].
- **The toast.** A phone notification is `PhoneMessageNotificationViewData` (`threadHash`, `contactHash`, `title`, `SMSText`, `animation` `notification_phone_MSG`, a sound event and an action) wrapped in `gameuiGenericNotificationData` (widget `notification_message`, 6.7 s) and given to the HUD phone controller's `AddNewNotificationData`; clicking runs an action that asks `PhoneSystem` to open that contact [source] Night City Allies `Phone/NCAPhoneSystem.reds:466-520`; the data class is the game's own, `cyberpunk/UI/fullscreen/notification/journalNotification.script:41-56`.
- **What persists.** Authored message states live in the save with the journal. A journal-free thread lives wherever the mod keeps it, so for XF it must be part of the XF store, never assumed from the save ([save files](save-files.md)).
- **Read side.** `JournalManager.GetContacts(context, out)`, `GetEntryByString`, entry state and `RegisterScriptCallback(obj, fn, gameJournalListenerType.State | Tracked | Counter)` report what V has and when it changes [source] `core/systems/journalManager.script:8-75`. Stock Market also hears vanilla quest completion this way.
- **Bridge.** No phone command is on `main`. The DM branch sends a text; the DM toolkit and the NPC-direction branch are the owners ([requirements](../research/story-engine/runtime-requirements.md) V4, V12).

### 3.2 Holocalls

- **The game's own call is two parts:** the phone runs the ring, the name, the picture and the panel; an ordinary scene plays the words over it. A call node's `phase` goes `IncomingCall`, `StartCall`, `EndCall` [wiki] `modding-guides/quest/custom-video-holocalls.md` (the guide's own graphs: `holocall-scene-graph.png`, `holocall-phase-1-reset-to-call.png` to `holocall-phase-5-hang-up.png`; applies to 2.31; last edited by nightcityriot, 22 September 2026, authorship unevidenced in the page).
- **State is a fact.** `phonecall_<caller>_with_<receiver>`, ids lowercase and the last part of the journal path: 0 ended, 1 ringing or opening, 2 talking, 3 declined. Reset it to 0 before each call, or a stale 2 connects the call before it rings [wiki] same page. `PhoneSystem.SetPhoneFact` writes it [source] `cyberpunk/systems/phoneSystem.script:204-212`. The bridge's `world_state` can read it.
- **The video is a stage, not a stream.** The caller stands in a hidden studio far off the map, one corner per game character (lights, camera, a workspot, a look-at marker), toggled by prefab variants; the camera renders to a texture the call panel shows. The wiki says to make our own contact rather than reuse a vanilla one, because every vanilla contact carries a built-in phone conversation that opens over ours [wiki] same page.
- **A script can start a call.** `PhoneSystem.OnTriggerCall(questTriggerCallRequest)` takes `caller`, `addressee`, `callPhase`, `callMode` (`Audio`, `Video`), `isPlayerTriggered`, `isRejectable`, `showAvatar` and `visuals`, plays the ring and writes the call blackboard and fact [source] `cyberpunk/systems/phoneSystem.script:79-120`, `orphans.script:41554-41571`. The HUD then finds the contact by comparing `GetId()` to the caller name and takes its avatar and name from it [source] `cyberpunk/UI/hud/phone/incomingCallController.script:78-110`. **So a call needs a journal contact**, vanilla or ArchiveXL-merged.
- **A mod can skip all of that.** AI NPC Cyberpunk Mod deliberately never touches the call request, the fact or the blackboard (they feed time skip, scene fast-forward and the phone itself) and instead drives only the HUD's call window through the controller methods the game's own phone code uses, so a quest call always wins. For a live picture it stages a copy of the character out of V's sight, points the game's own `holocall_camera.ent` at it and falls back to a portrait voice call if anything is not ready [source] `r6/scripts/CyberpunkConvai/Holocall.reds` (header and `ConvaiCallBegin`) and its `holocall.lua`. This is the closest installed model for a Story Engine caller without a quest phase.
- **Subtitles-only calls.** `scnDialogLineData` of type `Holocall` renders a line in the call style; whether it shows without a call in progress is open ([NPC direction](npc-direction.md), open question 6 in its design).
- **Limits.** A needed journal contact is static data. Voice needs recorded audio or a vanilla line ([NPC direction §4](npc-direction.md#4-speech)). A call is blocked by phone-disabled states, combat and some scene tiers (`PhoneSystem.IsCallingEnabled`, `IsBlockedBy…` at `phoneSystem.script:277-345`).

### 3.3 The Kiroshi scanner

**What the panel is made of.** The scanner HUD shows chunks written to the `UI_ScannerModules` blackboard by the scanned object's `CompileScannerChunks`: a name, then for people the level, rarity, health, attitude, faction, weapon, resistances, bounty and abilities as the character's **scanner preset** allows, and for devices a status, a description and skill checks [source] `cyberpunk/NPC/NPCPuppet.script:3409-3700`, `cyberpunk/devices/frame/frame.script:74-106`, `cyberpunk/UI/hud/scanner/scanner_data.script`. Beside the chunks, the quest-style entries come from the object's `ScanningComponent`: **clues** (`FocusClueDefinition`: a `FocusClue` record, extended clue records with percentages, facts to set) and an **object description** (`NPCScanningDescription` or `DeviceScanningDescription`: a gameplay description id and a list of custom description ids), each a TweakDB record id whose `localizedName` and `localizedDescription` the native layer turns into `ScanningTooltipElementData` for the panel [source] `core/components/scanningComponent.script:1-135, 571-675`, `cyberpunk/UI/hud/scanner/scanner.script:313-337`, `orphans.script:47558-47565`.

**The records.** All three families extend `ScannableData` (`friendlyName`, `localizedName`, `localizedDescription`, `iconName`, `iconRecord`) [resource] REDmod tweak source `database/scanning/schema.tweak`. The base game holds 25 `npc_scanning_data`, 299 `device_scanning_data` and 1,470 `FocusClue` records, and 5 `ScannerModuleVisibilityPreset` records (Phantom Liberty: 85, 315, 2,085 and 8) [resource] counts from the TweakDB blobs. So the vanilla scanner is mostly **clues**, with a few dozen hand-written NPC descriptions; the NPC `fullDisplayName`, `displayName`, `scannerModulePreset` and `affiliation` of the character record supply the header. The Modding Docs show the character-record route: editing Panam's `fullDisplayName`, `displayName` and faction changed what the scan tab shows [wiki] `for-mod-creators-theory/core-mods-explained/tweakxl/tweakxl-changing-game-records/changing-npcs-tweak-edit-redmod.md` (daemon2077, October 2023, game 2.01; its images `Screenshot_1.png` to `Screenshot_3.png` show the record file and the changed in-game scan).

**Route A: data.** New records of the three types in a TweakXL YAML file, their text under secondary keys in an ArchiveXL `localization: onscreens:` JSON, referenced from the `ScanningComponent` of an entity template we ship. TweakXL creates records by `$type`; the type names for these three (`gamedatanpc_scanning_data_Record`, `gamedatadevice_scanning_data_Record`, `gamedataFocusClue_Record`) follow the RTTI pattern the other records use but were not checked [hypothesis].

**Route B: events on a live entity.** The component and its saved state take events: `SetCustomObjectDescriptionEvent` (holds an inline `ObjectScanningDescription`; the persistent state keeps it, so use the vanilla `NPCScanningDescription` class, whose fields are record ids, not a class of our own that a save could not load), `ClearCustomObjectDescriptionEvent`, `DisableObjectDescriptionEvent`, `DisableScannerEvent`, `ToggleFocusClueEvent`, `ToggleClueConclusionEvent` [source] `scanningComponent.script:60-135, 183-345`; and on a puppet `OverrideScannerPreset { scannerPreset: TweakDBID }` and `ResetScannerPreset` [source] `scriptedPuppetPS.script:2-17`, `NPCPuppet.script:3952-3958`. Building the description from script needs access to its protected fields, which redscript allows from added methods on the class [hypothesis: not tried].

**Route C: write the chunks.** AI NPC Cyberpunk Mod wraps `NPCPuppet.CompileScannerChunks` and, after the game has written its `ScannerName` chunk, replaces the primary text with a generated name for nameless NPCs; it never touches the other chunks [source] `r6/scripts/CyberpunkConvai/NpcNames.reds` (credited in the header to its own `npc-names.lua`). The same blackboard takes a `ScannerDescription` chunk (a default description plus a list of custom lines, plain strings passed to `SetLocalizedTextScript`), which devices fill from script [source] `scanner_data.script:397-421`, `scanner_chunks.script:986-1030`, `frame.script:101-103`. Whether an NPC's panel has a description area to show it is [hypothesis].

**Dynamic records.** Night City Allies clones a record and sets flats at run time with TweakXL's `TweakDBManager` (`CloneRecord`, `SetFlat`, `UpdateRecord`) for its equipment [source] `r6/scripts/NightCityAllies/Equipment/EquipmentRecords.reds:55-100`. The same would make a `FocusClue` or `npc_scanning_data` record with generated text; what a `LocKey` flat does with a literal string is [hypothesis] (the game's own test clues in `scanning_clues.tweak` store plain strings in the field).

**Text.** A secondary key resolves from an ArchiveXL onscreens file, or from Codeware's `ModLocalizationProvider`, which several studied mods use for their texts [source] Better Fuel System Reloaded `Localization/LocalizationProvider.reds`, Photo Mode UI Improvements `Localization.reds`; whether a provider's texts can change after load is [hypothesis].

**Verdict.** Writable, with three independent routes; nothing has run. **Bridge: no**; V8 stays "want". The cheapest first test is route B on a looked-at civilian (session row 1).

### 3.4 Crowd barks and voicesets

Fully covered by [NPC reactions §3–4](npc-reactions.md#3-how-an-npc-picks-and-plays-a-voice-line) and [NPC direction §4](npc-direction.md#4-speech). In the channel's terms: **read** the `UIGameData.ShowDialogLine` blackboard and an NPC's voice tag; **write** a voiceset trigger (the game picks line, audio and lip sync) or a text line (`OverHead`, `OverHeadAlwaysVisible`, `Regular`, `Holocall`, `Radio`, `Narrator`; AI NPC Cyberpunk Mod also writes `Holocall` lines through the same blackboard, `subtitles.lua`); custom audio through Audioware. A bark honours the player's chatter setting and the 150 m (20 m in tight scenes) overhead rule [source]. **No civilian line comments on V's looks** in the game's own voicesets ([NPC reactions §3.3](npc-reactions.md#33-lines-that-could-comment-on-v-resource)). **Bridge: branch** (`npc.say`, test N7 in the [NPC direction design](../research/runtime/npc-direction-design.md)).

### 3.5 Shards and readable items

**The authored route (the second named question).** The wiki's guide builds a shard from five files [wiki] `modding-guides/quest/creating-custom-shards.md` (created 17 April 2025 by Bill, text guide added by curricle in September 2025; images `shards_tutorial_01.png` to `shards_tutorial_11.png`):

| File | Holds |
|---|---|
| `…\journal\shards.journal` | A folder chain `onscreens` → `emails` → `quests` → `minor_quest` → `<mod>`, a `gameJournalOnscreenGroup` (`shards`) and one `gameJournalOnscreen` with `id`, `title`, `description` (`LocKey`s) and `tag` (one of ten: `world`, `poetry`, `notes`, `literature_fiction`, `philosophy_religion`, `others`, `technology`, `night_city_people`, `articles`, `leaflets`) |
| `…\onscreens\<mod>.json` | `localizationPersistenceOnScreenEntry` rows (`femaleVariant` text, `primaryKey`, `secondaryKey`); the guide found the primary keys unreliable and used `primaryKey 0` with matched secondary keys |
| `r6\tweaks\<mod>\<item>.yaml` | An item record: `itemType: ItemType.Gen_Readable`, tags `Readable`, `Shard`, `SkipActivityLog`, `HideInBackpackUI`, `HideAtVendor`, an `itemSecondaryAction` |
| `r6\tweaks\<mod>\<item>_inline0.yaml` | The action: `actionName: Read`, `removeAfterUse: True`, and `journalEntry: onscreens/emails/quests/minor_quest/<mod>/shards/<id>` |
| `<mod>.archive.xl` | `journal:` (the journal file) and `localization: onscreens:` (the JSON) |

The guide places the item in the world with a `shard_case_container.ent` and a `ShardCaseContainer` node whose `itemTDBID` is the record. Its screenshots show the result: the read popup with the title and description (`shards_tutorial_10.png`) and the shard under the `ARTICLES` category of the journal's shards list (`shards_tutorial_11.png`) [wiki, images inspected]. The game's side agrees: reading a `Gen_Readable` item removes it and activates the journal entry named by the action's `journalEntry` string, and `ReadAction` builds the popup from the entry's title and description [source] `cyberpunk/player/player.script:2249-2253`, `cyberpunk/items/actions/readAction.script:1-30`. The base game has 531 shard-named item records (858 with Phantom Liberty) [resource]. Hand-writing the whole item record is long; whether a shorter `$base` inheritance works is [hypothesis].

**Giving the item without a case.** `TransactionSystem.GiveItemByTDBID(player, tdbid, 1)` exists [source] `orphans.script:18035-18037`; that it works for a shard is [hypothesis].

**The journal-free route (a popup with any text).** The popup is a plain notification, `ShardReadPopupData { title, text, isCrypted, itemID, m_imageId }` with widget `shard_notification.inkwidget`, raised when the UI system receives a `NotifyShardRead` event; the title and text pass through `GetLocalizedText` and are set as strings, and the popup pauses the game until closed [source] `cyberpunk/UI/fullscreen/notification/popupManager.script:438-470`, `shardsNotification.script:40-100`, `cyberpunk/UI/fullscreen/codex/codexUtils.script:464-477`, `orphans.script:38996-39009, 52955-52966`. The popup manager marks the entry as visited, and a script-made event has no entry, which may be an error or a no-op [hypothesis]. Nothing is added to V's shard list by this route.

**Verdict.** Authored shards: yes, wiki-documented, static. Dynamic shards: popup only. **Bridge: no.**

### 3.6 Notifications

- **Banner and subtitle.** `UI_Notifications` holds two variants. `WarningMessage` is the banner the game's own scripts use (`PlayerPuppet.SetWarningMessage`: 5 s, a type); `OnscreenMessage` is a second line, drawn with the cinematic subtitle animation. Both carry a `SimpleScreenMessage { isShown, duration, message, isInstant, type }`, and the controller upper-cases the text and passes it through `GetLocalizedText`. The type enum has 15 values: Undefined, Negative, Neutral, Vehicle, Apartment, Relic, Money, Reveal, Boss, Twintone, Police, Autodrive, TwintoneNegative, Connection, DelamainTaxi [source] `cyberpunk/UI/hud/onscreenMessage.script:33-60`, `core/blackboard/blackboardDefinitions.script:1758-1767`, `cyberpunk/player/player.script:5428-5437`, `orphans.script:7311-7330, 19457-19468`. XUtils wraps all of it in a small API (banner, subtitle, dismiss) [source] `r6/scripts/XUtils/Visual/XUtilsNotifications.reds`.
- **Toasts.** The journal notification queue takes `QuestUpdateNotificationViewData` and `PhoneMessageNotificationViewData` (see §3.1); the item log and currency toasts have their own queues, and `UIInGameNotificationEvent` shows the game's fixed warnings (Night City Allies raises `CombatRestriction` this way) [source].
- **Popups.** `GenericMessageNotification` and `inkGameNotificationData` popups (the shard popup is one) pause the game and take the screen [source] `cyberpunk/UI/common/genericMessageNotification.script`, `popupManager.script`.
- **The XF surface.** The bridge's `ui_message` and `ui_hud` draw XF's own panel in the HUD (drawn and answered by keys in session 8 [runtime], [ink UI §9](ink-ui.md#9-the-xf-runtime-bridges-ink-demos-053-temporary-test-features)); the game's own banner, toast and popup surfaces are not driven by it. For the player the XF panel is a status surface for the session, not an in-world channel.
- **Limits.** One banner at a time, replaced by the game's own; the player's HUD and subtitle settings apply; nothing persists. **Verdict:** writable now by script, **bridge: partial** (own surface only).

### 3.7 The journal and a journal-free tracker

- **Read:** entries by path or hash, state filters, the tracked entry, objective counters, the district and recommended level of a quest, and a callback on any change (§3.1). The vanilla tracker draws the tracked objective's description and counter and listens to the journal's `State`, `Tracked` and `Counter` events [source] `cyberpunk/UI/quests/quest_tracker.script:45-60`.
- **Write:** `ChangeEntryState`, `ChangeEntryStateByHash`, `TrackEntry`, `UntrackEntry`, `TrackPrevNextEntry` on entries that exist. **Create:** only from a `.journal` resource merged by ArchiveXL, hot-reloadable [source] [quests §2.3 and §7](quests-and-story.md#23-the-journal). The shipped "scripted quest" API (a quest cloned from a template, an objective description, a map pin entity per objective) belongs to `GameplayQuestSystem`, used by devices, but every function in it returns `false` or does nothing in 2.31: it is a retired or cut path, so a mod cannot rely on it [source] `core/systems/journalManager.script:90-123`, `gameplayQuestSystem.script:50-90, 160-195`.
- **A pool of pre-authored slots** (quest and objective entries shipped in our own `.journal`, driven by a generic phase and fact) is the one honest way to appear in the real journal; their text is a key, so dynamic text means substituting at draw time as Eviction Notice does for messages ([quests §2.6](quests-and-story.md#26-phone-messages-and-contacts)) [hypothesis for objectives].
- **A tracker line without a journal entry.** The tracker also draws a **tracked mappin**: when `UI_System.TrackedMappin` holds a pin, it spawns an objective row whose title and text come from the pin's variant (`MappinToString`, `MappinToObjectiveString`), not from any text we supply [source] `quest_tracker.script:153-171`. So a runtime pin can give a generic "world" row; custom words need our own ink objective list ([ink UI](ink-ui.md)), which the DM toolkit is prototyping.
- **Bridge:** no journal writes; `world_state` reads named facts only (V5, V7). **Verdict:** real journal content is authored data; the journal-free tracker is ours to draw.

### 3.8 Map pins

Covered by [quests §2.5](quests-and-story.md#25-map-pins) and [ink UI §6](ink-ui.md#6-map-pins-markers-and-the-compass). Channel summary: **read** `MappinSystem.GetMappins`, the tracked mappin and the journal's pin entries; **write** runtime pins with `MappinSystem.RegisterMappin(data, position)` and move, activate, change variant and remove them, or journal pins from an authored objective on a mod's marker; the pin's variant fixes icon, colour, label and map filter group. **Bridge: partial.** `world_pin` and `world_pin_clear` exist; session 7 [runtime] drew a head-bound pin as the game's pulsing circle, well above the head, and session 8 drew nothing because the bridge's own icon wraps hid the game's icon, so the current build keeps the icon and is [unverified]. Whether a runtime pin survives a load is [hypothesis] (the bridge clears its own on load).

## 4. What this means for the Story Engine

- **Words first.** Banners, overhead and subtitle lines, journal-free phone threads, the popup shard and the scanner chunk are all script-only and text-dynamic. They are the realisation channels to build first; none needs shipped data except an XF contact if a call is wanted.
- **One small authored kit.** A single ArchiveXL data pack gives the rest: one or more XF contacts in a `.journal` (callable, avatar from a `PhoneAvatars` record), a few shard slots, a pool of objective slots and scanner records. This is the "data-only pack" the [runtime requirements](../research/story-engine/runtime-requirements.md#xf-core-plugin-api-needs) describe, and it stays additive: it adds contacts and records, replaces nothing.
- **Never write the game's call path unless a quest call is wanted.** The studied mod's rule (a mod call yields to any quest call) is the safe pattern for an always-on engine.
- **Persist in our own store.** Journal-free threads, popup shards and pins vanish with the session; the XF store re-issues them after a load (requirement P2).
