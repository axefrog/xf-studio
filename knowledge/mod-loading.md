# Mod loading and resource precedence

**Maturity: Draft.** Consolidates MO2 2.5.2, ArchiveXL 1.27.3 (commit `5474e34d`) and WolvenKit (commit `11720772`) source reading with the XF Studio resolver's run against one reference installation (game 2.31 with Phantom Liberty, MO2 profile of about 1,000 mods, ArchiveXL 1.26.3 installed). Evidence grades follow the [knowledge rules](README.md). REDengine's own archive lookup has **not** been read or measured: every precedence rule below is a tool-source rule or a hypothesis for the native engine, and the resolver says so on each decision.

This page answers: *given an installation, which bytes does the game use for a depot path, and what do ArchiveXL declarations change about them?* The [character-customisation file chain](cc-file-chain.md) builds on it.

## 2. Archive groups and naming

- **Location decides the group, not the name.** `basegame_*.archive` inside `archive/pc/mod` (e.g. `basegame_Kala Standalone Eyes V2.archive`) is an ordinary mod archive.
- **Not mounted by this model** (listed as unmounted, never silently ignored): archives in subfolders of `archive/pc/mod`, `archive/pc/hot`, REDmod `mods/*/archives`, and archives registered by other RED4ext plugins through ArchiveXL's API. Each is a later adapter.
- **Collation.** "Alphabetical" is implemented as case-insensitive ordinal. When case-sensitive and case-insensitive order disagree for two colliding archives, the resolver records `collation-sensitive-order`.
- **Base-internal collisions.** Many resources exist in both `basegame_1_engine.archive` and `basegame_4_appearance.archive`. Their relative order is unread; the resolver picks alphabetical-first and records `base-internal-collision`. For the reference character, all **70** such collisions were byte-identical when both copies were extracted, so the choice did not matter there [resource].
- **Mod over base.** For the same character, **57** resources were supplied by a mod archive over a base copy; **55** of those payloads differ from the base bytes [resource] (skin textures, head morph rig fix, teeth app, nails, arm meshes, the lash `brown_liquorice.hp` and brow `hh_cap_grad__brown_ombre.xbm`). This is the single most consequential unproven rule; each case carries `mod-over-base-native-unread`. One anecdotal observation supports it: in a playthrough with Alliekat's hair profiles installed, many NPC hairdos showed the yellow-to-brown look that only the mod's `.hp` files produce [runtime, uncontrolled] ([yellow-hair investigation](../research/character-customization/yellow-hair-profile-override.md)).

## 3. How ArchiveXL finds `.xl` files

[source] `ExtensionLoader::Configure`: first the bundle directory (`red4ext/plugins/ArchiveXL/Bundle`, recursively), then every Mod-scope archive group's base directory recursively (the game's `archive/pc/mod`, including `X.archive.xl` beside archives), in reverse depot-group order. Every `.xl` is YAML; anchors and aliases are used by the bundle (`&AppearanceFixF` … `*AppearanceFixF`). The resolver reads the visible files in that order (bundle first, then `archive/pc/mod` by case-insensitive virtual path; the directory-iteration order under MO2's VFS is **[hypothesis]**). A YAML `!exclude` tag is dropped by the reader and reported as an issue.

| Key | Effect | Merge across files |
|---|---|---|
| `customizations: {female, male}` | Registers `.inkcharcustomization` resources, merged in declaration order | appended |
| `resource.scope` | Named alias → members; aliases expand **transitively** to leaf paths (e.g. `player_customization.app` → `player_wa_hair.app` → each hairstyle `.app`) | union |
| `resource.fix` | `paths` (CCO option `.app` remaps plus app overrides), `names` (mesh material renames), `context` (dynamic material attributes) | later keys overwrite |
| `resource.patch` | Copies properties from a patch resource into each (scope-expanded) target; see section 4 | list per target, sorted by `order` |
| `resource.copy` | `source: [targets]`: new paths holding a copy of `source` | rejected if the target exists |
| `resource.link` | `target: [aliases]`: aliases resolve to `target`. The scalar form `key: value` is filed the other way round by ArchiveXL's config reader (the key becomes the alias) | rejected if the alias exists or is a copy |

`ResourcePatch::Configure` checks patch sources through the depot, which ArchiveXL's link hooks extend to copies and links; that is why Arkhe's brows can patch from an `arkhe_copy\…` path that no archive contains. A patch source may not itself be patched. Patches for one target are sorted by `order` with `std::sort`; the resolver keeps declaration order among equal values, which holds if ArchiveXL is built with MSVC, whose `std::sort` insertion-sorts ranges of up to 32 elements **[hypothesis]**.

## 4. What a patch changes

[source] ArchiveXL `ResourcePatch/Extension.cpp`. "Overwrite" means the target already has the property: an empty `props` list then does **not** replace it; only an explicit prop does.

| Target type | Props | Behaviour |
|---|---|---|
| `.mesh` | `appearances` | Each patch appearance is added, or replaces a same-named one when the existing appearance has no chunk materials or the patch appearance has some. A patch mesh with material entries becomes the **material source** for its appearances. |
| `.mesh` | `renderResourceBlob` | Replaces geometry (with bones, LOD info) — overwrite rule applies |
| `.morphtarget` | `baseMesh`, `baseMeshAppearance`, `blob`, `boundingBox`, `targets`, `baseTexture(ParamName)` | `targets` merge by name; `blob` obeys the overwrite rule |
| `.app` | `appearances`, `partsValues`, `partsOverrides`, `components`, `visualTags`, `censorshipMapping` | New appearances appended; existing ones gain parts (only if they exist) and overrides; an unnamed patch appearance applies to all |
| `.ent` | `entity`, `components` | Merged into the compiled package (player entity patches, rule R6b) — not yet modelled |

Mesh `resource.fix names` rename chunk materials and material entries before patches apply; `context` entries join the mesh's `@context` attributes.

## 5. ArchiveXL dynamic materials (mesh side)

[source] `Mesh/Extension.cpp` and `Garment/Dynamic.cpp`, replicated in `character-resolver.ts`:

1. **Expansion.** An appearance with no chunk materials copies the chunk materials of an expansion source (a single appearance tag, else the `@context` attribute `appearance_expansion_source`, else the first appearance), replacing the part before `@` with its own name: `black_carbon@long` → `ash_brown@long`.
2. **Lookup.** A chunk material name is first looked up among the target mesh's ordinary entries, then the patch mesh's, then as a template: `name@tpl` uses the source mesh's `@tpl` entry (`@material` when there is no `@`).
3. **Instantiation.** The template instance is cloned. Same-named `@context` parameters replace its values; resource paths and `baseMaterial` starting with `*` are expanded: `{attr}` reads the material attributes (`material` = the part before `@`, `material.1`… = `+`-separated parts) and then the context attributes (the `@context` CName parameters with names converted to snake_case, e.g. `LongBaseMaterial` → `long_base_material`, plus `resource.fix context`). A trailing `?` makes a path optional. The inheritance chain is expanded the same way at each level.

4. **Patch source tag.** [source] `ResourcePatch/Extension.cpp` tags every appearance a mesh `appearances` patch adds or replaces with the patch mesh's path hash; `ProcessAppearance` then appends that tag to the (expanded) chunk material list, and `OnLoadMaterials` takes the list's **last** name to find the source mesh. The tag's material entry is an empty `CMaterialInstance` (`s_dummyMaterial`).
5. **Short chunk material lists.** A mesh may list fewer chunk materials than it has render chunks. CCXL hair does this on purpose: the High Ponytail's ponytail mesh has 10 render chunks (two real 44,893-vertex strand chunks on LOD 0, then three-vertex stubs on LOD 0 and every lower level) and its appearance lists two materials [resource: `fhair_highpony_pony.mesh`]. After a patch, the first unlisted chunk lines up with the patch source tag (so it gets the empty placeholder material); the chunks after it have no material name at all. How the engine draws a chunk with no material, or an empty one, is unread **[hypothesis: nothing visible, as the stubs are degenerate]**. The resolver reports such chunks as `route: "none"` (`unlistedChunk`, rule note `R10-short-chunk-list`); the planner neither draws them nor counts them as unsupported.

This is how one hair-colour pack colours every hairstyle without shipping per-style materials: the saved `38_ash_brown` becomes mesh appearance `ash_brown`, `ash_brown@long` instantiates the pack's `template__long.mi`, `*{long_base_material}` resolves to the hairstyle's own strand material and `*…\{material}.hp` to `ash_brown.hp`. The High Ponytail works the same way with the template inside its own mesh: the saved `15_pink_magenta` is built from the app's `01_blonde_platinum` (`FixCustomizationAppearance`), ArchiveXL's bundled `h1_base_color_patch.mesh` adds an empty `pink_magenta` appearance, which expands from `black_carbon` to `pink_magenta@long` ×2; the mesh's local `@long` template has base material `highpony_long.mi` and `HairProfile = *…\hair_profiles\{material}.hp`, so the chunks draw `hair.mt` with `pink_magenta.hp` [resource: resolver run on the reference installation, 26 September 2026]. Its cap mesh instead lists one appearance per colour, and maps some colours to another colour's cap gradient (`pink_magenta` → `black_carbon@cap`); that is the mod's own data, drawn as authored.

### Export: meshes WolvenKit won't write

Resolution can be right while the preview still can't draw a part, because the part's geometry comes from WolvenKit's GLB export. **Short `bonePositions`.** WolvenKit's mesh exporter builds the GLB skin from `renderResourceBlob.header.bonePositions` (one joint per entry, `MeshTools.GetOrphanRig`), taking each joint's transform from `boneRigMatrices` when it can invert it, while render chunks' skin indices address `boneNames` [source: WolvenKit commit `11720772`]. The High Ponytail's ponytail mesh has 141 bone names and rig matrices but 45 header positions, which also don't match the rig matrices beyond the first bone [resource]. Its vertices reach bone 140, so SharpGLTF refuses to write the file (`Accessor[7] JOINTS_0[31]: Is out of bounds`) and `uncook` writes the raw mesh and textures but no GLB [observed: WolvenKit 9.0.1]. That, not material resolution, is why the preview showed only the fringe. The mod draws in game, so the engine evidently skins by `boneNames` and `boneRigMatrices` **[hypothesis]**.

XF Studio's exporter now retries such a mesh from a repaired copy (`mesh-export-repair.ts`, `createWolvenKitMeshRepair`): serialize the raw mesh, fill the missing positions with each bone's inverted rig matrix translation (WolvenKit's own importer rule), deserialize, pack the copy alone into a private archive at its depot path and uncook it as before. Only the header positions change, and WolvenKit derives the exported joints from the rig matrices anyway, so the geometry and skin are the mod's own. The result is cached like any complete export with a `repair.txt` line, and the character record carries a note. On the reference installation the repair takes about 22 s once (five WolvenKit launches) and yields a GLB with 141 joints. Any part the preview still leaves out is named in the record's notes with its reason (`character-detail-service.ts` `build`).

## 6. Implementation and reproduction

`projects/xf-studio/authoring/src`: `depot-path.ts` (hashing), `rdar-index.ts`, `archive-precedence.ts` (mount plan, `DepotIndex`), `archivexl-config.ts` (`.xl` semantics), `resource-graph.ts` (effective resources, provenance), `cco-model.ts`, `character-resolver.ts` — all pure — and `resolver-host.ts` (source discovery, index reading, WolvenKit CLI extraction to an ignored JSON cache keyed by depot hash, archive fingerprint and WolvenKit identity). `tools/resolve-character.ts` writes a local report. The eye plate uses the same rules through `eye-plate-head-source.ts` (pure) and `eye-plate-head-resolver.ts` (adapter) to cut from the head the route loads; it applies the mesh and morph patch rules of section 4 to the extracted JSON, limited to properties that reach the plate. Tests: `tests/archive-precedence.test.ts`, `cco-merge.test.ts`, `character-resolver.test.ts`, `dynamic-hair.test.ts` (synthetic: dynamic materials, a short chunk list, a patched colour, the export repair and dropped-part notes) and the opt-in `character-resolver-integration.test.ts`.

On the reference installation the MO2 route mounts 1,079 archives (77 listed as not mounted), reads 1,000 visible `.xl` files and merges 242 female custom CCO resources. Validation: [resolver validation](../research/character-customization/resolver-validation.md).

**One opened route per process** (`installation-registry.ts`). The hosts (character details, grading LUT, the eye plate's head source for Build) share one opened installation per launch route, WolvenKit and settings instead of scanning the mod setup for every request. Opening records every path its answer depends on, with a stamp taken when it was read: every folder source discovery walked (stamped before its entries are read), every candidate archive and `.xl`, the MO2 settings file and profile `modlist.txt`, the game's ArchiveXL bundle folder and `bin/x64/Cyberpunk2077.exe`. Before reuse every stamp is read again in parallel; any difference opens the route again. This relies on a folder's modification time changing when an entry is added, removed or renamed in it and on a file edited in place changing its size or time; a tool that rewrote a candidate archive with the same size and restored its timestamp would not be noticed [source: the resolver's JSON and index caches already key archives by path, size and time]. Folder times are trusted only on NTFS and ReFS volumes, read with `GetVolumeInformationW` (`volume-info.ts`); on FAT32, exFAT, a network share or a volume that can't be identified, each scanned folder is stamped by a hash of its listing (names and entry types) instead, which a restored or coarse folder time can't hide [source: the test puts a folder's time back after adding an archive; the time stamp misses it, the listing stamp doesn't]. A change also moves the route's generation on, which the hosts' request keys include, so answers prepared from the old setup are prepared again. That holds for a route dropped to make room for another (two are kept): it keeps its watch list, and the next check or open compares it. An installation opened with read errors (an unread archive index, an unreadable folder or `.xl`) is opened again once it is a minute old, since those stamps may not change when the problem clears; its generation moves on only if the errors changed. A route whose WolvenKit changed in place can't be asked for again (the key includes WolvenKit's identity) and is dropped. A host checks the route before answering a request, and that clean check stands for the preparation's own acquire a moment later, so a request checks once. Parsed archive indexes and `.xl` documents are kept in memory by path, size and time, so reopening after a mod change reads only what changed. On the reference route (9,334 watched paths) the check takes about 50 ms, a first open about 1.4 s and a reopen about 1 s. Source discovery dominates the open; it now takes entry types from the folder listing and inspects only folders and candidate files (0.8–0.9 s instead of 1.6–2.2 s, with identical output).

**Fewer WolvenKit launches.** A resolver batch extracts every resource that has a depot path with one `uncook -u -s` launch, whose JSON equals `unbundle` followed by `convert s` once the converter's `Header.ArchiveFileName` (the temporary file it read, a private path) and the export time are set aside; the cache stores neither route's `ArchiveFileName`. An opt-in oracle (`tests/wolvenkit-uncook-oracle.test.ts`) compares both routes on a material instance, a mesh, an `.app`, an `.ent`, a morph target, a layer setup and a texture from the installed game, and passed with WolvenKit 9.0.1 and 8.17.4 on 26 September 2026. Resources it does not write (hash-only references, archives without path names, or a resource written without JSON) fall back to `unbundle --hash` and `convert`. A launch's selection pattern and archive list are split so its whole command line, escaping included, stays within Windows' 32,767 characters. Each WolvenKit launch costs about 2.6 s before doing any work, and 4.0–5.1 s with `-gp` (measured with a launch that selects nothing, WolvenKit 9.0.1). A resource the archive lists but WolvenKit writes nothing for, in launches that finished cleanly, is marked `not-written` for that archive and WolvenKit; from the second such batch the marker is lasting, so it is not extracted again until the archive or WolvenKit changes. The resource graph reads a resource's ArchiveXL patch sources together with it (only once the target itself is provided), reads a requested appearance's part `.ent`s together, and prefetches from a freshly extracted resource the kinds that consumers otherwise read one at a time: the `.mt`, `.hp`, `.sp`, `.gradient` and `.mlsetup` a mesh or material names (a fresh `.mlsetup` brings its `.mltemplate`s). An `.app`'s parts are no longer prefetched: an `.app` names every appearance's parts (a framework's piercing `.app` names 31, one appearance needs one to three). A morph component's mesh is read with its morph target rather than after it (`ResourceGraph.prefetchRef`; the component usually names the morph target's own base mesh). A cached resource is never expanded, so a cached V starts no extraction. What remains is the chain's real depth (`.app` → `.ent` → morph target → mesh → material instances → layer setup → layer templates → textures), one batch per level. Precedence ambiguities are recorded for the resources a V's resolution reads (a prefetched resource nobody asked for adds none), so a V reports the same ambiguities from a cold or a warm cache.

Timings on the reference MO2 route in one process, WolvenKit 9.0.1, 26 September 2026 (offline measurements, not game evidence): a cached preparation took 3.9–5.4 s per V before (every preparation opened the route and resolved from scratch) and now takes 0.3–1.2 s once the route is open (about 3 s for the first V in a process, which also opens the route). Through the localhost server: 2.9 s for the first V, then 0.6–1.1 s. With new resources, trying piercing style 05 on the default V took 85.7 s and 24 launches before, 29.6 s and 8 now; a save's first preparation took 180.6 s and 36 launches before, 100.9 s and 14 now (reference save), and 133.7 s and 40 before, 58.6 s and 16 now (a second save). The graph each cache folder keeps holds a mesh, morph target or `.app` as the shape its models read rather than the whole document (a morph target's document is mostly per-target data nothing reads: 10 MB for the player head's), about 44 MiB of JSON after three Vs and three piercing styles; the heap after that sequence fell from 318 to 136 MB, with the same or shorter times (the reference save 1.07 → 0.85 s, a second save 0.45 → 0.38 s, a cached try 0.08–0.37 s). The graphs of every route and cache folder keep at most 256 MiB of JSON together (the least recently used start afresh first), and a graph is replaced after a consumer's read failed in a way that may not repeat.

**A first-time choice: what is left.** After the resolution, everything the plan implies is asked for at once, so it shares one extraction batch: hair and skin profiles, colour ramps, layer setups (their templates follow in the next batch) and each texture's colour flag, and the templates read for their names. The export of the change's parts runs beside those reads. All of a change's exports (every archive, geometry, textures and masks) go into one `uncook` launch (`GameAssetExporter.exportAll`) when the archives' requested resources don't collide (outputs are written by depot path; the index says which archives hold what), otherwise into as few as don't; a shared launch that fails is retried per archive, so one archive can't fail the others. The character details export geometry **without the game folder** (`-gp`): WolvenKit then neither resolves the materials nor decodes every texture they name (73 files for one CCXL hair mesh, which the character details never read, since they resolve materials themselves), and the GLB is the same, byte for byte [resource: a CCXL hair mesh and a vanilla morph target, WolvenKit 9.0.1]; that cuts one hair export from 7.6–8.8 s to 4.2 s. A resource that gives no GLB that way is exported again with the game folder. The core preview still exports its head and eyes with materials. What remains of a first-time click is the chain's depth, one batch per level, and one export beside the last reads: a CCXL hairstyle is `.app` → mesh → material instance → (profiles and textures, export), 5 launches instead of 6–7; a vanilla `.app` whose name WolvenKit's hash list lacks (e.g. `hh_011_pwa__hairs_063.app`) costs `unbundle` and `convert` besides. About three quarters of what is left is WolvenKit start-up (5 launches × 2.6 s of a CCXL hairstyle's 16–20 s).

**Settled exports.** An export is cached per resource, archive identity and WolvenKit identity (`game-asset-export.ts`). A mesh exported without the materials file it was asked for (the core preview's) is kept as a partial entry and served from the cache from its second clean run (`PARTIAL_RUNS`); a resource clean launches export nothing for is recorded (`<entry>.none.json`) and, from its second, not asked for again. Both follow the resolver's `not-written` rule: another WolvenKit or a changed archive has another key. [resource] WolvenKit 9.0.1 writes nothing for one CCXL hairstyle's `fhair_highpony_pony.mesh`, with or without the game folder, by path or by hash; before this rule every preparation of that hairstyle launched WolvenKit twice for it.

**Preparing choices ahead** (`choice-prefetch.ts`, `CharacterDetailHost.prefetchRow`, `warmCharacters`). When a Character panel row is open, the host prepares its choices in the background, the ones in view first: each choice's request is the V with that choice set, and a batch of up to 8 of them resolves side by side on the shared graph, so each level of all their chains is one extraction batch, and their parts are exported in one launch. Nothing is written to the preview's store; the shared preparation cache keeps what was resolved and exported, so the click only plans and writes. On the reference route, 16 CCXL hairstyles took 11 launches and 44 s (65% of it WolvenKit start-up) and added 185 MB (11.5 MB per hairstyle); the 16 hair colours of one of them took 6 launches and added 0.8 MB. A click on a prepared choice then took 0.08–0.23 s (0.4–1.3 s while other work loaded the machine), against 3–25 s the first time. Rules:

- **A person's own change comes first.** Preparations run as foreground work on the resolver's cache folder (`foregroundExtraction`): their batches go on their own chain, never waiting behind a background batch already in WolvenKit, at normal priority. Background batches (`backgroundExtraction`) and prefetch exports run below normal process priority; when a preparation starts, WolvenKit processes still running below normal are raised to normal (`raiseBackgroundWolvenKit`), since the preparation may be waiting for a resource one of them is extracting. When a preparation starts, the batch being prepared ahead is also stopped (its export launch is ended; reads already in WolvenKit finish and are cached) and its choices are queued again; the queue waits until the preparation ends. A hover or focus moves a choice to the front.
- **Single flight holds across both.** A resource one chain is extracting is awaited by the other (the lane's in-flight map), batch folders are unique, and an export published twice keeps the first.
- **Bounded.** A row's job stops after 10 minutes and preparing ahead stops for the session once it has added 2 GB of prepared files; the remaining choices show "not prepared", and a click still prepares them. Closing the row stops its job.
- **Only one row at a time**, the one opened or pointed at last, and only while it shows all its choices (not a search) and the 3D view draws the option. Its job is keyed by the V without the row's own choice, so choosing in the row keeps the job and its states; the chosen choice shows as being prepared, then ready.
- **Background reads don't check the installation.** A readiness check or a batch uses the route's opened installation as it is (`InstallationRegistry.peek`): a check reads every watched stamp (9,334 on the reference route), and an acquire would spend the vouch a person's request relies on (PIPE-62). What they derive is checked again before it is used, and a person's request still checks.
- **Batches grow.** The first batch is 8 choices (the ones in view come back soonest); each later one doubles, up to 32, since every batch costs its chains' depth in launches whatever its size: the reference route's 51 vanilla hairstyles took 70 launches and 302 s in batches of 8, and 39 launches and 133 s growing (1 MB per hairstyle, mostly JSON; those hairstyles don't draw in the preview on that route yet).

**Prepared files: what persists, and when it is prepared again.** A choice is shown ready when a later preparation of it would need no WolvenKit. Everything prefetch writes is keyed so that a changed source is never served:

| What | Where | Keyed by | Invalidated when |
|---|---|---|---|
| Extracted JSON | resolver cache `json/` | depot hash, archive path + size + modification time, WolvenKit identity | the archive changes (another key), another WolvenKit |
| Exports (GLB, PNG, mask layers), partial and settled markers | preview cache `exports/resources/` | depot hash, archive path + size + modification time, exporter version, WolvenKit identity | the same |
| What a prepared request depended on (`xfs/choice-manifest-1`) | preview cache `choices/` | the route (settings, WolvenKit path and identity) and the request | checked, not trusted: see below |
| The preparation cache (resolved appearances, templates, exports, built parts) | memory | installation fingerprint (route, stamps, WolvenKit, registry generation) | a new installation or process: rebuilt from the files above without WolvenKit |
| Served files and records | preview cache `characters/` | content (SHA-256) | never stale; removed only by Clear |

A manifest (`choice-manifest.ts`) lists every resource the preparation read (the depot hash, the archive entry after ArchiveXL copies and links, and that archive), every export it served, the WolvenKit identity and the identity of the route's `.xl` files. It **holds** when, on the installation opened now, WolvenKit and every `.xl` file are the same, each read still resolves to the same entry in the same archive and is in the resolver's cache for that archive's current identity, and each export's archive still wins its path and is in the export cache. So a mod updated in place (its archive's size or time changes), a mod installed or reordered so another archive wins, a changed `.xl` or an evicted file makes the choice "not prepared" again, and preparing it reads only what changed. A choice's manifest carries its batch's reads together, which can only make it checked again more often. Loose files are not read by the character details (the resolver reads archives and `.xl` files only; `.xl` files are fingerprinted by the route's watch list). [test] `tests/choice-prefetch.test.ts`: a restart keeps a prepared choice ready; another archive time or size, another `.xl` or an evicted export does not.

**Budget and Clear** (`prepared-files.ts`). Exports and extracted JSON are kept within 8 GB together, the least recently used first (a cache hit or write stamps its entry's time; eviction runs at most once a minute after a preparation or a prefetch batch); nothing this process used is evicted, so a V on screen and its tried choices keep their files even over the budget. Failure markers, archive indexes and creator texts are small and kept. The Character panel shows the prepared files' size on this computer and **Clear prepared game files** (`character.clearPreparedFiles`), which stops preparing ahead, removes exports, extracted JSON, the served store and the manifests, and forgets what was derived from them, so the next preparation reads the game files again. On the reference machine before this work the caches held about 1.35 GB (0.48 GB exports, 0.55 GB JSON, 0.32 GB store).

## 7. Store editions: where the game is, and which copies can be modded

Everything above starts from a game folder. Which store installed it changes only how that folder is found, not how files load.

| Store | Where the install is recorded | XF Studio | Evidence |
|---|---|---|---|
| GOG | `HKLM\SOFTWARE\(WOW6432Node\)GOG.com\Games\<product>` `path` | Detected | [observed] on the development machine, plus fixtures |
| Steam | `SteamPath`/`InstallPath`, then `libraryfolders.vdf`, then `appmanifest_1091500.acf` `installdir` in any library | Detected | Fixtures only; formats observed without the game |
| Epic Games Store | `.item` manifests (`InstallLocation`, `bIsIncompleteInstall`) and `LauncherInstalled.dat` | Detected | Fixtures only; formats observed with other apps |
| Xbox app / Microsoft Store | `.GamingRoot` library folders (`<drive>\XboxGames\<title>\Content` by default), Gaming Services package list | Recognised, never offered | Fixtures only |

- **Frameworks install the same way on Steam, GOG and Epic.** RED4ext and ArchiveXL are extracted into the game folder, and RED4ext recognises the game by the executable's `ProductName` and the game's own `cyberpunk2077_addresses.json`, not by store. **[source]** RED4ext `src/dll/Image.cpp`, `src/dll/Addresses.cpp`.
- **No framework mentions an Xbox app edition, and there isn't one for Windows.** Microsoft's store lists Cyberpunk 2077 for Xbox consoles and cloud only, and CD PROJEKT RED's REDmod and support pages name only Steam, GOG and Epic. **[source]** Citations, clone commits and the message XF Studio shows are in [store coverage](../research/authoring/source-discovery-foundation.md#store-coverage).
- **Framework versions and launch routes do not depend on the store.** The version check reads files under the chosen folder (and the MO2 profile), whichever store installed it.
