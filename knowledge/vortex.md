# Vortex: how it deploys Cyberpunk 2077 mods

**Maturity: Draft.** Source read at Vortex 2.7.1 (tag `v2.7.1`, commit `c8ea03d0`) for deployment and state, and at Vortex 2.9.0 (tag `v2.9.0`, commit `e0409300`, the current stable) for the command line, start-up, registration, updater and discovery behaviour that [§8](#8-running-vortex-as-a-test-bed) relies on, plus the Cyberpunk 2077 Vortex extension (`E1337Kat/cyberpunk2077_ext_redux` commit `565deef1`, package 0.13.0; newest published extension 0.12.1) and the `vortex-games` stub (commit `18bbee9b`). One Windows Sandbox run of the released Vortex 2.7.1 with extension 0.12.1 ([experiment 023](../experiments/023-vortex-sandbox/README.md), 26 September 2026) checked the central claims. It used a synthetic game folder and local test archives. Evidence grades follow the [knowledge rules](README.md); **[observed]** marks what that run showed of Vortex's own behaviour. No Vortex-managed game has been launched: nothing here is runtime evidence about the game.

This page answers: *when Vortex manages Cyberpunk 2077, which files does the game see, which mod put each one there, and how should XF Studio add its own mod?* It complements [mod loading](mod-loading.md), whose archive and ArchiveXL rules apply unchanged once the files are in the game folder.

## 1. The short answer

| Question | Answer | Grade |
|---|---|---|
| Where do mods live? | Each installed mod is a folder in the game's **staging folder**, default `%APPDATA%\Vortex\cyberpunk2077\mods\<mod id>`. The mod id is the installed archive's name without its extension. | [source]; [observed] |
| What does the game see? | Vortex **deploys** the enabled mods of the active profile into the game folder itself, as hard links. Unlike MO2 there is no virtual file system: the game folder holds the winners, whoever launches the game. | [source]; [observed] |
| Which mod wins a file? | The mod Vortex deploys last, by its dependency rules ("load after"). The loser's copy is not deployed at all. Different archive **names** with the same resources are ordered by the game (alphabetically), not by Vortex. | [source]; loser not deployed [observed] |
| Who put a file there? | `vortex.deployment.json` in the game folder lists every deployed file and the mod it came from. | [source]; [observed] |
| Nexus ids, versions, enabled state? | Only in Vortex's state database (`%APPDATA%\Vortex\state.v2`, LevelDB) or its JSON backups, and readable only while Vortex is closed. A mod installed from a local archive has no Nexus ids or version at all. | [source]; [observed] |
| How should XF Studio add its mod? | Build an archive Vortex can install and hand it to the user's Vortex (`Vortex.exe --install-archive <file>`), with consent. Vortex installs, enables and deploys it without a prompt. | [observed]; recommendation |

## 2. Deployment

### 2.1 Staging and deployment methods

- **Staging folder.** `settings.mods.installPath[gameId]`, a path or a pattern with `{USERDATA}`, `{GAME}` and `{USERNAME}` (case-insensitive); the default is `{USERDATA}\{GAME}\mods`, and a relative result is taken from Vortex's user data folder. The folder holds a marker, `__vortex_staging_folder`, containing `{"instance": <Vortex instance id>, "game": <game id>}`, written by the manage-game flow (`ensureStagingDirectory`). A mod is extracted into `<mod id>.installing` and renamed when done. **[source]** `mod_management/util/getInstallPath.ts`, `stagingDirectory.ts`, `InstallManager.ts`, `modIdManager.ts`.
  - **[observed]** The default folder and one subfolder per mod, named after its archive, both matched the source.
  - **[observed]** The sandbox's state was seeded with `--set`, which skipped the manage-game flow, and no marker was written. The marker's presence in a normal setup is therefore source-only, and XF Studio treats it as optional.
- **Methods**, tried in priority order until one works for every mod type: hard links (5), symbolic links (10), symbolic links through an elevated helper (20), move (50, experimental). The choice is stored in `settings.mods.activator[gameId]`. **[source]** `extensions/*_activator/index.ts`, `mod_management/util/deploymentMethods.ts`.
- **Cyberpunk forbids symbolic links**: the extension registers the game with `compatible: { symlinks: false }`, so a Cyberpunk setup uses **hard links**, which need the staging folder on the game's volume (Vortex suggests `<game volume>\Vortex Mods\cyberpunk2077` when it isn't), or the experimental move method. **[source]** extension `cyberpunk2077_ext_redux/src/index.ts`. This matters for XF Studio: its source scan skips symbolic links, but hard links are ordinary files to it.
- **What a deployment leaves in the game folder:** the files (hard links share the staging file's identity and modification time), `__folder_managed_by_vortex` in every folder Vortex had to create, `<file>.vortex_backup` for a file that was already there and that a mod replaced (restored on purge), and the manifest. **[source]** `LinkingDeployment.ts`.
  - **[observed]** Deployed files had two hard links, and their modification time was the staged file's, equal to the manifest's `time`.
  - **[observed]** A hand-placed `Preexisting.archive` that a mod also shipped was renamed `Preexisting.archive.vortex_backup` with its content intact.
  - Not exercised: the folder marker (every folder already existed) and the restore on purge.
  - The sandbox chose hard links explicitly. Vortex's automatic choice for Cyberpunk remains **[source]**.

### 2.2 The deployment manifest

One manifest per mod type, in that type's target folder: `vortex.deployment.json` for the default type, `vortex.deployment.<type>.json` otherwise. The Cyberpunk extension registers **no** mod types (its `registerModType` is commented out because it stopped Vortex deploying), so a Cyberpunk setup has exactly one manifest, in the game folder, listing everything. **[source]** `activationStore.ts` `saveActivation`; extension `cyberpunk2077_ext_redux/src/index.ts`. **[observed]** One `vortex.deployment.json`, in the game folder, with exactly these fields in this order. Vortex's generic `dinput` and `enb` types were deployed with zero files and left no manifest. A real manifest is committed as a test fixture ([§7](#7-implementation)).

| Field | Meaning |
|---|---|
| `version` | Format version, 1 |
| `instance` | The Vortex installation's id (`app.instanceId`, a UUID made on first start). A per-user and a shared (multi-user) Vortex have different ids. |
| `deploymentMethod` | e.g. `hardlink_activator` |
| `gameId`, `deploymentTime` (ms), `stagingPath`, `targetPath` | Private paths: never copy them into a portable document |
| `files[]` | `relPath` (relative to the target folder, backslashes, original case), `source` (the mod id, i.e. staging folder name; `__merged` for merged files), `target` (empty for Cyberpunk, whose extension sets `mergeMods: true`), `time` (the staged file's modification time in ms), optional `merged` |

- It is written atomically (`<name>.XXXXXX.tmp`, then renamed) after every deployment, with a binary copy, `vortex.deployment.msgpack`, in the staging folder (both **[observed]**: rewritten after each of three deployments). **A purge deletes both**; an empty deployment never leaves an empty list. Vortex treats the manifest as a fallback and works if it's deleted, so its absence doesn't prove Vortex isn't in use. **[source]** `activationStore.ts`.
- **Only winners are listed.** Mods are deployed lowest priority first and each file key is overwritten by later mods, so a file two mods ship is listed once, for the mod that won. **[source]** `LinkingDeployment.ts` `addModFiles`. **[observed]** Two mods shipped `XF Test Shared.archive` with no rule between them. The one deployed second won: it was listed once, for that mod, and the other copy stayed in staging. Vortex showed "There are unresolved file conflicts" but still deployed.

### 2.3 Conflicts and order

- **File conflicts** (two mods ship the same path) are settled by a topological sort of each mod's `before`/`after` rules; mods without a rule between them fall in whatever order the sort gives. `conflicts` rules block deployment; unresolved file conflicts only block **launching** from Vortex. `fileOverrides` hide a mod's copy of a file. **[source]** `mod_management/util/sort.ts`, `modActivation.ts`, `mod-dependency-manager`.
- **Archive order is the game's.** The extension never writes `archive/pc/mod/modlist.txt`, and its own help says archive mods load "in the usual alphabetical order", before REDmods. Two differently named archives that contain the same resource are therefore ordered exactly as in a direct install ([mod loading §1](mod-loading.md#1-the-stages-in-order), stage 3). **[source]** extension `cyberpunk2077_ext_redux/src/load_order.ts`.
- **REDmod** has its own load order: stored in Vortex state (`persistent.loadOrder[profile]`), written to `<game>\V2077\Load Order\V2077-load-order-<profile>.json` and `<game>\V2077\modlist.txt`, and applied by running `tools\redmod\bin\redMod.exe deploy … -modlist=V2077\modlist.txt` after a deployment in which the order changed. REDmods deploy to `mods\<name>`. **[source]** extension `cyberpunk2077_ext_redux/src/load_order.ts`, `cyberpunk2077_ext_redux/src/installer.redmod.ts`.

### 2.4 How the extension installs mods

- **One installer for everything.** Priority 30, accepting every archive, it recognises the frameworks (CET, redscript, RED4ext, TweakXL, ArchiveXL, …), REDmods, multi-type mods, and archive mods, unwrapping a single top-level folder. **[source]** extension `cyberpunk2077_ext_redux/src/installers.ts`.
- **Archive mods keep their paths:** `archive\pc\mod\x.archive` and `x.archive.xl` land at the same path in the game folder (**[observed]**). Archives found elsewhere in the download are placed under `archive\pc\mod\<their folder>`, which the game doesn't read, with a warning. **[source]** extension `cyberpunk2077_ext_redux/src/installer.archive.ts`.
- A loose `.archive` dropped on Vortex (not inside an archive) skips the installers and would deploy to the **game folder root**, where the game ignores it. **[source]** Vortex `mod_management/index.ts`, extension `queryModPath: () => ""`.

## 3. Metadata: Vortex's state

- **Where.** `<selected data folder>\state.v2`, a LevelDB database: an explicit `--user-data` (or `startup.json`'s `userData`), else shared mode's `%ProgramData%\vortex`, else `%APPDATA%\Vortex`. The base per-user database holds `user.multiUser`; the shared database can veto a stale true flag. See [§8.7](#87-data-folder-selection-and-outside-discovery). Vortex 2.x opens it through DuckDB's `level_pivot` extension, but the files are ordinary LevelDB. **[source]** Vortex `Application.ts`, `store/LevelPersist.ts`, `store/DuckDBSingleton.ts`.
- **Keys and values.** A key is the Redux state path joined with `###` (`persistent###mods###cyberpunk2077###<mod id>###attributes###modId`); a value is the leaf's JSON. Arrays and other non-plain objects are stored whole. **[source]** `LevelPersist.ts`, `store/stateDiff.ts`. **[observed]** in the real database. An empty object can sit beside deeper keys under the same path, as in `persistent###profiles###xfstest###modState = {}` next to `…###modState###<mod>###enabled`. Tables are Snappy-compressed.
- **What XF Studio reads:**

| State path | Meaning |
|---|---|
| `app.instanceId` | Matches the manifest's `instance`: this is the Vortex that deployed |
| `settings.profiles.activeProfileId`, `settings.profiles.lastActiveProfile.<game>` | The profile in use |
| `persistent.profiles.<id>` `{gameId, name, modState.<mod>.enabled}` | Profiles and what each enables |
| `persistent.mods.<game>.<mod id>` `{installationPath, attributes}` | Installed mods. `attributes`: `name`, `logicalFileName`, `customFileName`, `version`, `source` (`nexus`), `modId`, `fileId`, `downloadGame`, `installTime`. **[observed]** A mod installed from a local archive records only `name` (the archive name), `fileName` and `logicalFileName` (the file name, which the Mods page shows), `fileMD5`, `fileSize`, `modSize`, `installTime` and `downloadGame`. It has no `version`, `modId`, `fileId` or `source`, even when the file name follows Nexus's download naming. A mod downloaded from Nexus also carries `author` (the mod page's author) and `uploader` (who uploaded it) from Nexus's mod info **[source]** Vortex v2.7.1 `nexus_integration/index.tsx`, `mod_management/types/IMod.ts`; XF Studio groups creator choices by `author`, else `uploader` (`src/character/host/mod-makers.ts`). |
| `settings.mods.installPath.<game>`, `settings.mods.activator.<game>`, `settings.gameMode.discovered.<game>.path` | Staging folder, deployment method, managed game folder |

- **Reading it safely.** Vortex holds LevelDB's `LOCK` while it runs; a second Vortex waits and then reports the database as locked. XF Studio never opens the database: it reads the files beside `LOCK` and interprets them itself. **[source]**
  - **[observed] While Vortex runs, its current MANIFEST and write-ahead log can't be opened by another program** (sharing violation); older tables and `CURRENT` can.
  - Vortex keeps the database open for its whole session, so everything written since it started is invisible until it closes: installs, enabled states, even the instance id made at first start. The readable tables hold only earlier sessions' state, each start having flushed the previous log into a table.
  - On closing, Vortex compacts the database, and XF Studio's reader then reads it completely through the MANIFEST.
  - So state read while Vortex runs is **stale, not merely partial**. XF Studio marks it not current and never concludes from it that a deployed mod is uninstalled.
- **Fallbacks.** Vortex's own full-state JSON backup is `%APPDATA%\Vortex\temp\state_backups_full\hourly.json` (written every hour Vortex runs, from an hour after it starts; none appeared in the sandbox's five-minute session **[observed]**) or `manual.json`, and may be up to an hour old. `Vortex.exe --get <path>` prints `path = value` lines while Vortex is closed (**[observed]**), but it starts Vortex's executable, so XF Studio doesn't use it. **[source]** `recovery/index.ts`, `store/store.ts`, `main.ts`.

## 4. Detecting a Vortex setup

| Signal | What it proves | Grade |
|---|---|---|
| `vortex.deployment.json` in the game folder | Vortex has files deployed there now; names the installation (`instance`), method, staging folder | [source] |
| `__vortex_staging_folder` in the staging folder | That folder is a Vortex staging folder for the named game and installation. Absent in the sandbox's seeded setup, so optional. | [source] |
| `%APPDATA%\Vortex\state.v2` (or `%ProgramData%\vortex\state.v2`) | Vortex has run for this Windows user (or in shared mode); its state names the managed game folder and the active profile | [source] |
| `HKCU\Software\Classes\nxm\shell\open\command` naming `Vortex.exe` | Vortex was the last program to claim Nexus links. Vortex claims them **on first start and again on every start** unless its "handle Nexus links" setting (`settings.nexus.associateNXM`) is off, so this only says Vortex ran most recently, not that it manages the game. | [source]. **[observed]** With the setting off before the first start, the key was never written; Vortex registered `nxm` in-app only. |
| Uninstall entry `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\57979c68-f490-55b8-8fed-8b017a5af2fe` (`DisplayName` "Vortex", `Publisher` "Black Tree Gaming Ltd.", `DisplayVersion`, no `InstallLocation`) | Vortex is installed, per machine, at `%ProgramFiles%\Vortex\Vortex.exe` | [observed] (quiet install of 2.7.1) |

**Active profile:** `settings.profiles.activeProfileId` when that profile's `gameId` is `cyberpunk2077`; otherwise the game's `lastActiveProfile` (Vortex is managing another game right now, and the game folder holds whatever was last deployed for Cyberpunk).

## 5. What XF Studio sees

**The direct route is already right about the files.** Because Vortex deploys hard links into the game folder, the direct route scans exactly the files the game will read, whatever Vortex's state says. What it lacked was *who* put each file there.

| Situation | Game folder (what the game loads) | Direct route before | With Vortex attribution |
|---|---|---|---|
| Normal deployment | Winners of enabled mods | Correct files, all "Installed game" | Each deployed file names its Vortex mod (and Nexus ids when the state is readable) |
| A mod disabled or uninstalled but **not yet deployed** (auto-deploy off, or deployment failed) | The old files | Correct: the game loads them too | Reported as a stale deployment: "deploy in Vortex" |
| Purged | Nothing from Vortex | Correct | No manifest; nothing to attribute |
| Profile switched to another game | Last Cyberpunk deployment | Correct | Profile shown as not active |
| A file replaced or deleted outside Vortex | The new file / nothing | Correct | Reported as changed / missing; Vortex shows the same in its External Changes dialog. A replaced file keeps the game folder as its provider and is never credited with the Vortex mod's Nexus ids: its modification time no longer matches the manifest's |
| A file placed by hand (or by another tool) | It | Correct | Reported as not deployed by Vortex |
| REDmod mods | `mods\<name>` + `r6\cache\modded` | Not mounted (REDmod unmodelled on every route) | Same gap |

- **Symbolic links** would have been a problem (the scan skips links), but Cyberpunk forbids them in Vortex. A symlinked file from another manager still shows as a skipped link.
- **The move method** leaves real files in the game folder; attribution works the same.

## 6. Placing XF Eye Artistry in a Vortex setup

| Option | Vortex's reaction | Fits "don't touch users' setups"? |
|---|---|---|
| Copy `XF Eye Artistry.archive` + `.xl` into `archive\pc\mod` | Ignored: Vortex's external-change check walks only files in its manifest, and purges remove only its own links. If a Vortex mod later ships the same file name, Vortex renames ours to `.vortex_backup` and restores it on purge. The mod is invisible in Vortex and can't be toggled there. **[source]** `LinkingDeployment.ts`. **[observed]** A dropped-in `XF Eye Artistry.archive` survived a later deployment untouched, with no external-change prompt, and a replaced file became `.vortex_backup`. | Adds only our files, but leaves the user an unmanaged mod in a managed setup |
| **Hand an installable archive to Vortex** (`Vortex.exe --install-archive <zip>`; the running Vortex receives it) | Installed through the Cyberpunk installer like a download, then enabled and deployed by Vortex's defaults (`settings.automation.install`, `enable` and `deploy` all default to on). **[source]** `cli.ts`, `settings_interface/reducers/automation.ts`. **[observed]** Three archives, each installed, enabled and deployed within seconds, with no prompt. | Yes: Vortex adds one mod the user can see, disable, update and uninstall |
| Write into the staging folder or state | — | No: never |

**Recommendation.** For a Vortex-managed game, Build writes `XF Eye Artistry.zip` holding `archive\pc\mod\…` exactly as the game needs, and offers **"Add to Vortex"**, which (with consent) runs the user's own `Vortex.exe --install-archive`, or tells them to drag the file onto Vortex's Mods page. The archive's file name becomes the mod's id and, extension included, the name on Vortex's Mods page (**[observed]**: `XF Eye Artistry.zip`), so keep it the plain mod name. Open questions: what Vortex does when a same-named archive is installed again (it offers replace or variant), and whether a `.zip` built by XF Studio needs a `fomod` or Nexus metadata (it shouldn't).

## 7. Implementation

`projects/xf-studio/authoring/src`:

- `vortex-deployment.ts` (pure): manifest names and parsing, attribution of a game-folder file (`deployed` while its modification time matches the manifest's within 2 s, else `changed`), and the comparison of a scan with the deployment (unmanaged, missing, changed, stale).
- `vortex-state.ts` (pure): Vortex's `###` keys into the state tree, then the game's profile, mods and Nexus ids; the staging-folder pattern. The tree is built from null-prototype objects, a key segment `__proto__`, `prototype` or `constructor` is skipped (and reported), and reads take own properties only, so a mod named after one, or a damaged database, can't reach `Object.prototype`.
- `installation/vortex-data.ts` (pure): typed launch/settings/marker/log/environment facts into ordered, deduplicated data-folder candidates, with their source and reason. CLI overrides startup settings; shared mode honours the shared database's false veto. It interprets Windows argument quoting, rejects relative data paths and ignores Electron children and command-line state-editor processes.
- `installation/host/vortex-process-host.ts` (adapter): a native Toolhelp snapshot, query-only process handles, `NtQueryInformationProcess` command-line metadata and `QueryFullProcessImageNameW`. It starts no helper and reads no remote process memory. Unsupported/denied metadata contributes no process lead. The 64-bit Windows implementation caps process enumeration and command-line allocation; other hosts retain settings/log/default discovery.
- `installation/host/vortex-data-host.ts` (adapter): the base `startup.json` (64 KB maximum), only the final 256 KB of the base `vortex.log`, and native process facts for a cheap first answer. `VortexShortcutDiscovery` owns the session cache, revision and requester-scoped wants; first paint never waits for a sweep. Shortcut roots include Windows' redirected known folders. The native `installation/host/vortex-directory-host.ts` adapter uses Win32 search handles to materialise at most 4,096 results across at most 512 directories, counting ignored and dot entries; reparse points are skipped. Bun 1.4.4's `opendir().read()` materialises the whole directory internally, so `bufferSize: 1` does **not** enforce this bound and is no longer used. The traversal yields every 64 results to service cancellation. Only the resulting `.lnk` paths go to a query-only COM helper. Each helper has a four-second timeout and 1 MB output cap; the sweep has an eight-second cancellation deadline. Earlier shortcut snapshots survive helper timeout. Nothing saves a shortcut, executes its target, starts Vortex or writes to its data.
- `leveldb-read.ts` (pure): a read-only LevelDB reader (log records, write batches, tables with Snappy blocks, MANIFEST live-file set). When the MANIFEST can't be read it reads every file and keeps each key's newest sequence number, and says so. The files are another program's, so decoding is bounded: a Snappy block's claimed length is checked against what its bytes can hold (22 times) and a 64 MB limit before anything is allocated, a block the index lists more than once is decoded once, and everything a read allocates (blocks and expanded keys) counts against one budget, 16 times the input and between 64 MB and 1 GB; a file past it is a gap.
- `vortex-host.ts` (adapter): `readVortexManifests` (synchronous and small, used by source discovery on every route: a game-folder file still as deployed gets `deployedBy` and names its Vortex mod as provider, a changed one keeps the game folder's name; the manifest is watched, so a redeploy reopens the installation) and `inspectVortexSetup` (the installation that deployed, matched by instance id, else by managed game folder; state from the database or a backup; staging marker). State is read asynchronously, at most 256 MB a file and 512 MB together, and never past the caller's deadline (a problem report's time budget); a complete read is kept for the same files, so preparing a report again doesn't read them again. The newest backup replaces the database when the database couldn't be read completely and either lists no mods or is older than the backup. The staging marker is read only from a folder on a local drive (on Windows, a drive-letter path once its separators are normalised, so `/\host\share` and `\??\UNC\…` are refused; on POSIX, an absolute path that does not start with `//`): a `stagingPath` in a manifest anyone can write never makes the host open a network share or a device. State is `current` only when the whole database was read. Otherwise its gaps say why (Vortex appears to be running, too large, or out of time), and the stale-deployment check (`compareWithDeployment`) is skipped.
- `tools/vortex-check.ts`: a read-only report for one game folder, with no paths and no profile name in its output (testers paste it).
- `diagnostics/mod-identity.ts`: a problem report's involved mods. An archive goes with a Vortex mod only while the game folder holds the file Vortex deployed (time as in the manifest), and on the Mod Organizer 2 route an MO2 mod whose folder holds the archive stays an MO2 mod even when a leftover manifest names a Vortex mod of the same name. A Vortex mod gets its Nexus mod and file IDs and version from Vortex's state (re-downloadable); without readable state, the staging folder name's mod ID is used only when the name follows Nexus's `<name>-<mod id>-<version>-<upload time>` download naming, a convention rather than a Vortex record **[hypothesis]**.

Tests: `tests/vortex-deployment.test.ts`, `vortex-setup.test.ts` (prototype keys, changed files, bounded and kept state reads, newer backups, network staging folders, the check tool's output), `vortex-data.test.ts` (launch precedence/quoting, shared-mode veto, cancellation, bounded log tails, custom-folder state reads and selection evidence), `leveldb-read.test.ts` (hostile Snappy lengths, repeated blocks, a decoding budget) and the Vortex cases in `diagnostics.test.ts` and `diagnostics-report.test.ts`; fixtures in `tests/fixtures/vortex/`. `sandbox-023/` holds what Vortex really wrote in experiment 023: the final manifest, the game-folder listing, the closed database (one Snappy table) and the tables readable while Vortex ran. The older `cyberpunk-hardlink` manifest was built from the source-documented format; `data-discovery.json` contains synthetic launch facts and placeholder paths.

**[offline]** The staging-path guard follows the host platform: Windows drive paths are relative filenames on POSIX, while a mixed-separator Windows UNC spelling starting with `/` is an ordinary absolute POSIX path. VORTEX-06 tests use a refused share spelling for each host and exercise both module defaults and the inspection warning in isolated processes with Windows and Linux platform values (26 October 2026, `tests/vortex-setup.test.ts`); this is platform simulation on Windows, not an Ubuntu runtime run.

## 8. Running Vortex as a test bed

Facts for running Vortex 2.9.0 on a developer machine without letting it touch the real game, another manager's `nxm://` association or the user's setup. All **[source]** (Vortex tag `v2.9.0`) unless marked, and **[observed]** only where a run says so; §8.6 holds the runtime evidence from the test bed. Paths below are relative to the Vortex source tree (`src/main/src`, `src/renderer/src`).

### 8.1 The installer, and running without it

- **The installer is per machine and needs administrator rights.** `electron-builder.config.json` sets NSIS `perMachine: true`, `oneClick: false`, `allowToChangeInstallationDirectory: true`, `runAfterFinish: true`. It writes the uninstall entry under `HKLM`, installs to `%ProgramFiles%` by default and elevates through UAC even with `/S` (a UAC prompt on the user's screen; the earlier sandbox run saw none because the account was already an administrator). NSIS accepts `/S` (silent) and `/D=<dir>` (last argument, unquoted); the installer's own `customInstall` macro also installs the Visual C++ redistributable and the .NET 9 desktop runtime quietly, **adds a Windows Defender exclusion for the install folder** (`Add-MpPreference`, hidden PowerShell) and removes it on uninstall. **[source]** `src/main/electron-builder.config.json`, `src/main/nsis/installer.nsh`.
- **Nothing needs the installer to run the program.** The installer's payload is a 7z archive, `$PLUGINSDIR\app-64.7z` (292 MB, 908 files, 937 MB unpacked: `Vortex.exe`, `resources\app.asar` and friends), which 7-Zip opens directly; extracting it gives a runnable copy with no registry entry, no elevation, no Defender change and no runtime installers. **[observed]** the installer's listing and the archive's contents (`7z l`, `7z e`, nothing run).
- An extracted copy has no `Uninstall Vortex.exe` beside it, so Vortex classes it `managed`, and **the self-updater stays off** for a `managed` install (`isUpdaterActive` is `installType === "regular"`). **[source]** `Application.ts` `identifyInstallType`, `extensions/updater.ts`.
- The installer's SHA-256 matches the one published with the release (`eff11541c40c7143b9a35f789b86a22c49d9a2bc2ef75d8031664f2781f5b714`). **[observed]**

### 8.2 Command line and its start-up side effects

Parsed with `commander` in `cli.ts`; merged over `startup.json` (`%APPDATA%\Vortex\startup.json`, which Vortex rewrites on each start with the running version).

| Flag | Meaning |
|---|---|
| `--user-data <dir>` | Use `<dir>` for Vortex's data (`<dir>\state.v2`, `plugins`, `temp`, the default staging folder, log). Also used by `--get`, `--set` and `--del`. |
| `--set <path>=<json>`, `--get <path>`, `--del <path>` | Change, print or remove a state value and **exit without a window**; repeatable. The value is split at the first `=` only, so a value containing `=` is cut. |
| `--install-archive <abs path>` | Install a local archive (absolute path only): at start-up through the import-downloads path, or in a running instance through the single-instance hand-off (`second-instance` → `applyArguments`). |
| `--profile <id>` | Activate that existing profile. Does nothing if the profile is missing. |
| `--game <id>` | **Runs discovery for that game and manages whatever it finds.** Dangerous next to a real install; use `--profile` instead. |
| `--start-minimized` | Skip the splash; the window is shown then hidden. Listed in `ARG_COUNTS` as taking an argument (a bug that only matters for a second-instance command line: keep it off those). |
| `-d <url>` / `-i <url>` | Download / install an `nxm:`, `https:` link. |

- **`--user-data` is not complete isolation.** The `Application` constructor still creates Electron's default data folder (`%APPDATA%\Vortex`: `temp\dumps`, a startup log, `startup.json`), and start-up first opens a base state database there (`state.v2`) before opening `<dir>\state.v2`. A run with `--user-data` therefore leaves an `%APPDATA%\Vortex` behind (a full Electron profile, §8.6). Passing Electron's own `--user-data-dir` as well would make Vortex open one LevelDB twice. **[source]** `Application.ts` (constructor, `setupPersistence`), `cli.ts`.
- **Hidden running.** `VORTEX_E2E_HEADLESS=1` in the environment stops Vortex ever showing its main window, splash or tray toggle (the window object still exists, so `--install-archive` works). It is read at run time in the shipped bundle. **[source]** and the bundled `main.cjs` contains the same checks (**[observed]**, string match). `VORTEX_E2E=1` also redirects `userData`/`appData` from `ELECTRON_USERDATA`/`ELECTRON_APPDATA` and turns off start-up discovery, but it **disables the single-instance lock** (so `--install-archive` could not reach a running instance) and is not used. A saved window position that is mostly off-screen is moved back on-screen, so off-screen placement isn't an option.
- **Extensions** load from `<user data>\plugins\<name>` and the bundled folder. The 2.9.0 bundle holds a *stub* for Cyberpunk 2077 (`game-cyberpunk2077`, `registerGameStub`: "downloaded the first time it's managed"); the real extension (0.12.1) is dropped into `plugins\` as in experiment 023. Its `info.json` must sit at the folder's top level. **[source]** `ExtensionManager.ts`, the stub's `index.js`.

### 8.3 `nxm://`

- **When Vortex registers.** Once per start, in the Nexus integration's `once()` hook: `registerFunc(settings.nexus.associateNXM)`. If the setting is **unset** (a first start) it dispatches `associateNXM = true` and registers; `true` registers; **`false` registers nothing** (`setAsDefault = def !== false`). Registering calls Electron's `app.setAsDefaultProtocolClient("nxm", Vortex.exe, ["-d"])` on every start, which writes `HKCU\Software\Classes\nxm` (command `"…\Vortex.exe" -d "%1"`; `--user-data` is **not** part of it in 2.9.0, so a clicked Nexus link would start Vortex on its default data). Turning the setting from on to off later calls `removeAsDefaultProtocolClient`. **[source]** `extensions/nexus_integration/index.tsx` (`once`), `util/protocolRegistration/`, `ipcHandlers.ts` `selfCL`, `nexus_integration/eventHandlers.ts` `onChangeNXMAssociation`.
- **Also in-process:** `protocol.registerHttpProtocol("nxm")` and `registerProtocol("nxm" | "http" | "https")` set Vortex's own handlers inside its process; `http`/`https` register with `setAsDefault: false`, so no registry write. **[source]**
- **How to keep it off:** seed `settings.nexus.associateNXM=false` with `--set` before the first start. **[observed]** (experiment 023, 2.7.1): the key was never written. For 2.9.0 the same code path is **[source]**; the test bed's phase B must prove it by comparing the registry value before and after. The installer itself writes no protocol key (`installer.nsh` has none and the builder config declares no `protocols`). **[source]**
- **Start at login is separate:** `settings.automation.start` (default `false`) is only changed by the Settings toggle, which also calls Electron's `setLoginItemSettings` (a value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`). Seeding the state value writes no login item. **[source]** `settings_interface/SettingsInterface.tsx`, `reducers/automation.ts`.

### 8.4 Discovery and which game Vortex manages

- **What discovery does.** On every start (`startQuickDiscovery`) the Cyberpunk extension asks the game-store helper for the Steam (`1091500`), GOG (`1423049311`) and Epic (`Ginger`) app ids, so on a GOG machine it finds the real install and records it as the game's discovered path. It only *records* it; Vortex manages a game when a profile for that game is activated (by `--game`, by `--profile`, or the Manage button). **[source]** extension `findGame`, `GameModeManager.ts`, `gamemode_management/index.ts`.
- **Pre-seeding protects the path.** `discovery.ts` skips a game whose discovered entry has `pathSetManually: true` (it only refreshes tool settings), and the reducer drops a discovered `path` that would overwrite a manual one. So `settings.gameMode.discovered.cyberpunk2077.path=<test copy>` plus `…pathSetManually=true` before the first start makes the test copy the only path Vortex has for the game. `removeDisappearedGames` clears an entry whose folder is missing, so the folder must exist. **[source]** `util/discovery.ts`, `reducers/settings/settings.ts`.
- **The seeded setup** (what experiment 023 used, unchanged for 2.9.0 **[source]**): `settings.nexus.associateNXM=false`, the discovered path and `pathSetManually`, a profile (`persistent.profiles.<id>.{id,gameId,name,modState={},lastActivated}`), `settings.profiles.activeProfileId` and `lastActiveProfile.cyberpunk2077`, `settings.mods.activator.cyberpunk2077="hardlink_activator"`, and for a test bed also `settings.mods.installPath.cyberpunk2077=<staging folder>`, `settings.update.channel="none"`, `settings.automation.start=false`, `settings.analytics.enabled=false`. Start with `--profile <id>`, never `--game`.
- **Updater.** `settings.update.channel` (default `stable`; `none` disables) is read five seconds after start and every four hours; patch releases auto-download for a `regular` install and are installed when Vortex quits. `IGNORE_UPDATES=yes` also stops the start-up check. **[source]** `renderer/extensions/updater/index.ts`, `main/extensions/autoupdater/index.ts`.
- **Extension catalogue.** Vortex fetches the online extension catalogue at start and may offer to link a local extension to its Nexus page and update it; the offer is a dialog (never auto-accepted), so a hidden Vortex leaves the dropped-in extension unchanged. **[source]** `extension_manager/index.ts`.
- **Cyberpunk requirements.** The extension requires only `bin/x64/Cyberpunk2077.exe` in the game folder, forbids symbolic links (so hard links, with staging on the game's volume) and sets `requiresLauncher` for GOG: *launching* from Vortex would start GOG Galaxy, which a test bed never does. **[source]** extension `index.js` (`requiredFiles`, `compatible`, `requiresLauncher`).

### 8.5 The isolated test copy

A copy of a game snapshot that Vortex may deploy into without risk: hard-link the base-game archives (`archive\pc\content`, huge and never rewritten), set them **read-only** (the attribute belongs to the file, so it protects both names: a tool that later writes a linked archive in place fails loudly instead of changing the snapshot) and **copy** everything else, because the game, redscript and the frameworks rewrite files in `r6`, `red4ext`, `bin` and `engine`. Staging sits on the same volume so hard-link deployment works.

**[observed]** Built from the 2.31 GOG snapshot (7,403 files, 86.5 GiB) on one NTFS volume: 33 files (60.45 GiB) hard-linked, 7,370 files (26.03 GiB) copied with `robocopy /E /COPY:DAT /DCOPY:DAT /MT:4 /XD <content>` in about 13 minutes on a mechanical drive (the 23 GiB `archive\pc\ep1` is the bulk; hard-linking it too would save that space and time). Checked file by file with Python's `os.stat`: counts equal, nothing missing or extra; every `content` file has the snapshot's file index and two links; none of the 7,370 copies shares an index (one link each); sizes and modification times equal and the SHA-256 of every copied file under 300 MB (7,365 of 7,370) equal; a write-open through the test copy's name raised `PermissionError`, and the snapshot's own name carries the read-only attribute too (intended). The snapshot had no read-only files before. Deleting the linked files later needs the attribute cleared, which clears it for the snapshot's name as well, restoring its original state.

### 8.6 Observed: Vortex 2.9.0 on the test copy

**[observed]** 26 October 2026: Vortex 2.9.0 extracted from the installer (no installation), the Cyberpunk extension 0.12.1 in its `plugins` folder, state seeded with `--set`, started hidden (`VORTEX_E2E_HEADLESS=1`, `--profile`, `--start-minimized`) through WMI, 11 mods borrowed from a Mod Organizer 2 collection installed with `--install-archive`. Mixed types: archives, ArchiveXL, a TweakXL yaml, redscript, CET, and two conflict pairs.

- **`--set`:** one `--set` per process worked (each printed `changed`); a single process given sixteen `--set` options printed nothing and wrote nothing. `--get` needs the same `--user-data`.
- **Seeded state held.** `--get` before the first start showed only the test copy's path, the staging path, `associateNXM = false`, `update.channel = "none"`, `automation.start = false`. After the run the path was unchanged. Discovery logged no `discovering game "cyberpunk2077"`; it logged only `updating previously discovered game {store: "gog"}`, a store identified from the GOG marker files inside the test copy (`goggame-*.info`), and left the path alone.
- **Hidden start.** No visible top-level window for any Vortex process at any poll; log: `installType: "managed"`, `updaterActive: false`, `updater initialized {active: false}`, the extension registering the game, and `register protocol {"protocol":"nxm"}` as an in-app handler only. The extension loaded with no catalogue dialog. Vortex logged 78 `[ERRO]` lines, all other games' discovery (`Game entry not found`, registry look-ups failing for games that aren't installed).
- **`nxm://` and start at login: unchanged.** A sorted snapshot of `HKCU` and `HKLM` `nxm` (all three views), `UrlAssociations`, every `Run` and `RunOnce` key and the uninstall entries stayed identical to the baseline before the seed, after the seed, after the first start, between every install and after closing. The extracted copy wrote no registry entry at all.
- **Footprint outside the data folder.** `%APPDATA%\Vortex` appeared on the first `--set`: a full Electron profile (caches, `Local Storage`, `Preferences`, `temp`, a log) plus a base `state.v2` and `startup.json`. It is not removable by Vortex and holds nothing about the managed game.
- **Installs.** `--install-archive` reached the hidden running instance every time (a second instance via WMI exits at once); each of the 11 archives was installed, enabled and deployed in 16 to 25 s with no prompt. Mod id and staging folder are the archive's name without `.zip`; `persistent.mods` records `name`, `fileName`, `logicalFileName` (with `.zip`), `fileMD5`, `fileSize`, `modSize`, `installTime`, `downloadGame` and **no `version`, `modId`, `fileId` or `source`**, even for Nexus-style file names (as in 2.7.1).
- **Deployment.** `vortex.deployment.json` (the same eight fields, `deploymentMethod: hardlink_activator`) listed 34 files; every deployed file had two links; 13 `__folder_managed_by_vortex` markers (the marker, unseen in experiment 023, appears when Vortex creates a folder, e.g. `r6\scripts`); no `.vortex_backup`; the msgpack copy sits in the staging folder as `vortex.deployment.msgpack`; **no `__vortex_staging_folder` marker** (state was seeded). Nothing else in the game folder changed (48 new files, 0 changed or removed), the 33 linked base archives stayed two-link and read-only, and neither the snapshot nor the real install changed.
- **Conflicts.** With no rules, the mod installed later won each shared path: the 9 files shared by two CET-and-archive mods went to the second (11 files to it, 2 left to the first), and the shared archive of two ArchiveXL suits is listed once, for the second. Vortex deployed regardless.
- **Closing a hidden Vortex.** `taskkill /PID` without `/F` did not close it (no window to receive `WM_CLOSE`); a forced kill of the process tree was needed. The state database was still complete (all 11 mods, enabled states and instance id read back with `--get`), so a forced stop lost nothing here; the log simply ends without `Vortex closing`.
- **XF Studio's original check** (`tools/vortex-check.ts`, read-only) against the closed test copy found the manifest (34 files, hard links) and attributed the 8 archive-bearing mods by staging name, but `state` was `null`: its fixed-folder discovery missed `--user-data`. With a copy of the closed state database placed where it looked, it matched `--get` exactly: instance id matches, manages this folder, profile found and active, 11 installed mods all enabled, method hardlink, state current with no gaps, no unmanaged, missing, changed or stale files, names equal to `logicalFileName`, no versions or Nexus ids. The replacement discovers candidate folders from Vortex's own launch/settings/mode/log evidence (§8.7), without copying state.

### 8.7 Data-folder selection and outside discovery

**[source]** Vortex 2.9.0 chooses the folder in two stages:

1. `cli.ts` declares `--user-data <path>` at [lines 232–236](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/cli.ts#L232-L236). It reads `%APPDATA%\Vortex\startup.json` ([154–178](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/cli.ts#L154-L178)) and merges command-line options over those settings ([273–276](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/cli.ts#L273-L276)). Thus a saved `userData` is effective, but an explicit CLI value wins.
2. `Application.setupPersistence` opens the base per-user `state.v2` and reads `user.multiUser` ([936–953](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L936-L953)). If true, it checks the shared database's `user.multiUser`: an explicitly false value returns it to per-user mode; a missing key leaves shared mode enabled ([969–1001](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L969-L1001)). Then explicit `userData` wins, otherwise shared mode, otherwise Electron's default user-data folder ([1004–1012](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L1004-L1012)). The shared folder is `%ProgramData%\vortex` on Windows; without `ProgramData`, or outside Windows, it falls back to per-user storage ([889–910](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L889-L910)). `--shared` is a separate option for `--get`/`--set`/`--del`, not the UI's shared-mode marker ([cli.ts:247–251](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/cli.ts#L247-L251), [Application.ts:283–295](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L283-L295)).

**[source] Outside records.** A running main process's command line and a shortcut's arguments can carry `--user-data`; a shortcut need not be named Vortex, so discovery checks its target. Startup settings can contain `userData`, but Vortex does **not automatically save the CLI value there**: the startup write changes only `storeVersion` ([Application.ts:917–921](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L917-L921)). No structured last-CLI-folder pointer is written by this selection path. It does log `using <path> as the storage directory` to the **base** `vortex.log`, immediately before switching logging to the selected directory ([1028–1035](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/Application.ts#L1028-L1035)); the actual format is `[INFO] [MAIN] …` with optional trailing whitespace ([logging.ts:24–37](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/logging.ts#L24-L37)). This is a durable lead for a closed script-launched copy. Rotation or clearing the base log loses that lead; Studio reads only its final 256 KB, not rotated logs. The `nxm` registration does not preserve `--user-data` (§8.3).

**[source] Absolute paths.** Vortex passes `userData` to Electron's `app.setPath` ([getVortexPath.ts:126–129](https://github.com/Nexus-Mods/Vortex/blob/v2.9.0/src/main/src/getVortexPath.ts#L126-L129)); [Electron's implementation](https://github.com/electron/electron/blob/v37.6.0/shell/browser/api/electron_api_app.cc) rejects relative paths (`App::SetPath`, `Path must be absolute`). Studio therefore does not invent a working directory or drive: Windows `\Data`, `/Data` and `C:Data` are rejected before normalisation, even though Node classifies the first two as absolute. Windows candidates must carry their own drive root or UNC root; the host subsequently refuses UNC/device paths under the local-drive contract.

**[offline] Studio policy, 26 October 2026.** Available leads are ordered: running main-process command lines, cached shortcut arguments, startup `userData`, enabled shared mode (with the shared false veto), the last run's base log, default per-user folder. Each launch itself applies Vortex's CLI/settings/shared/default rules. This is an outside-reader evidence order, not a Vortex-defined ordering between separate launches. Paths are normalised and deduplicated; remote/device paths are refused. **Every source requires readable `state.v2` files**: a backup-only folder is never accepted, including one named by a process, shortcut, startup setting, shared marker or default location. Once a readable database establishes the folder, the existing reader retains its database/backup preference and stale/incomplete reporting. A newer backup may still enrich an incomplete database.

Cheap facts get at most 100 ms of an inspection's budget, reserving 250 ms for validation under the Character panel's normal three-second deadline. Explicit custom candidates are validated immediately, before base/shared markers. A readable matching instance at the highest available precedence ends lower-priority work. Otherwise the instance id wins across readable candidates, then the first matching managed-game path. Ties follow discovery order. One-shot inspections only read the shortcut cache and start no background work. A ready Character catalogue with Vortex providers says `pending` while shortcut evidence is unresolved. After rendering that usable panel, the browser holds one cancellable `follow=1` question on the existing state endpoint. The session owner acquires a want for that question and releases it in `finally`; the last release aborts scheduled/running work. The browser shares that question while retaining each context's own interest, and disposal aborts its interest. A sweep completed for the session is cached once; a cancelled unfinished attempt can be retried by a later consumer. Completion changes the catalogue key and returns the normal state through that same question. The browser avoids caching a pending panel as final, invalidates on the returned state and follows the ordinary rebuild to its new identity and maker labels. An empty completed sweep settles the usable panel without rebuilding. `stateSelection` reports the candidate path, source, reason and match criterion; the public check tool reports source/reason/criterion without paths. Mode flags use the same bounded reader, so while Vortex is running they may be stale just like other state (§3).

**[source; offline] Native process lead.** Toolhelp and `QueryFullProcessImageNameW` provide the image and executable path. The query-only command-line route follows Chromium's [GetCommandLineUsingProcessInformation](https://chromium.googlesource.com/chromium/src/+/0ed6d7ba52656400c3f3604e9fd62cbf2c1623f9/chrome/chrome_cleaner/engines/broker/scanner_sandbox_interface.cc#112): information class 60 returns a `UNICODE_STRING` in the caller's buffer. Studio validates the size, pointer offset and UTF-16 length, caps allocation at 128 KB and closes every handle. It deliberately has no PEB/remote-memory or WMI fallback. The Windows test reads only its own test process and confirms the executable and command line; the Vortex test bed was not started for this check.

**[source; offline] Bounded native enumeration.** Microsoft's [FindFirstFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfilew) returns the first result and its search handle; [FindNextFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findnextfilew) returns the next result into the same fixed-size structure. Studio calls neither again after its cap and always calls `FindClose`. The real Windows adapter test creates **4,100 files**, counts materialisation at those native calls, and proves exactly **4,096 results**, one opened search and one closed search. This replaces the earlier injected-reader test, which did not expose Bun's internal whole-directory read. Actual loopback HTTP tests drive the production host endpoint, browser device, shared catalogue and Character contexts: late completion reaches an already ready panel after preparation polling stops, and disposing the last context aborts the request and sweep. Owner tests also cover the sole requester aborting before scheduling and a surviving second requester. Backup-only rejection covers all six discovery sources.

**[offline] Cold-inspection regression measurements, 26 October 2026.** Three fresh Bun processes per implementation, the same asset-free three-mod database and manifest, and the same supplied custom-process lead after the real host metadata query. Before the original latency fix: **1,147.5 / 1,075.3 / 1,013.8 ms**; after it: **86.9 / 54.5 / 42.5 ms** (medians 1,075.3 and 54.5 ms). The later native-enumeration/consumer-lifetime/browser-delivery re-review measured **62.6 / 33.6 / 30.4 ms before**, **36.6 / 32.9 / 39.4 ms after** (medians **33.6 and 36.6 ms**; no material first-answer change). All reads were current, with three mods and an instance match. These are fresh-process host-inspection timings with the machine's filesystem cache, not full Character rendering or in-game measurements. The cold-timeout fixture separately keeps the shortcut sweep unresolved while both cold and repeated inspections return current custom state.

**[observed] Read-only test-bed probe, 26 October 2026.** The saved launch script explicitly passes `--user-data` and `--profile`, using a scripted launch rather than a shortcut. A direct read of its original data folder (no copy) returned `database`, MANIFEST mode, current, zero gaps, 11 installed mods, all 11 enabled, active profile. Inspection with that script's command line supplied as a launch fact selected the custom folder (`process`), matched the deployment's instance and managed-game path, and read its 34-file manifest. No Vortex process was started/stopped and nothing in its folders was written. The earlier CIM enumeration was denied in the implementation sandbox; it has since been replaced by native metadata reads verified against the test process. Live Vortex discovery and the real base-log lead still need the dispatching chat's host probe. The saved script confirms the launch arguments, not the absence of every possible shortcut.

## Open questions

1. What does Vortex do with a second `--install-archive` of the same archive name: replace, variant, or a prompt that blocks an unattended install?
2. Does anything in the game or a framework behave differently for hard-linked files (for example a tool that rewrites an archive in place, which would change the staged copy too)?
3. How do Vortex collections and "load order" entries for REDmods interact with archives shipped inside REDmods, once the resolver mounts REDmod archives?
4. Vortex looks installs up on Nexus by MD5 (`<md5>:<size>:<game>`; attempted, and failed offline, in the sandbox). Does that lookup record Nexus ids and a version for a real Nexus file installed from disk?
5. With "handle Nexus links" on, what exactly does Vortex write under `HKCU\Software\Classes\nxm`, and does it overwrite another manager's handler on every start? Source (2.9.0): it calls Electron's `setAsDefaultProtocolClient` on every start with `["-d"]`, which replaces the key; not yet observed, and a test bed must never turn the setting on while another manager owns the association.
6. Answered for 2.9.0 with extension 0.12.1 and a hidden run (§8.6): it runs, installs and deploys with no dialog. **The `--user-data` discovery part is answered [source; offline; observed read-only state probe] in §8.7:** launch arguments, startup settings, the base/shared state markers and the base log supply generic discovery evidence. A closed script-launched copy without a surviving log or saved launch arguments has no recoverable data-folder pointer in this path. Still open: whether installs keep working once the extension catalogue is reachable and accepted, and commissioning the new Windows discovery adapter outside the sandbox.
