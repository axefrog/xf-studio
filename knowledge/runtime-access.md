# Runtime access: RED4ext, redscript, CET and the XF bridge

**Maturity: Draft.** This page covers how each Cyberpunk 2077 mod type gets code into the running game, where each one logs, and how XF Studio's local bridge reaches the game. It is consolidated from source reading of RED4ext 1.30.0, RED4ext.SDK 1.0.0, redscript 0.5.31, CET 1.37.1, TweakXL 1.11.4 and psiberx's plugins, plus the decompiled 2.31 scripts and the offline build, self-test and tests of [`projects/xf-runtime-bridge`](../projects/xf-runtime-bridge/README.md). Claims seen in the game (the bridge's first in-game run, 26 September 2026) are marked [runtime]; their evidence is the test card's [script-call check](../research/runtime/runtime-bridge-test-card.md#script-call-check-first) and [first-session results](../research/runtime/runtime-bridge-test-card.md#first-session-bridge-checks), and later sessions' experiment pages ([session 4](../experiments/029-session-4/README.md), [sessions 5 and 6](../experiments/032-sessions-5-6/README.md)). The rest wait for the [test card](../research/runtime/runtime-bridge-test-card.md). Crash fingerprints are on [game crashes](game-crashes.md). The full citations, capability matrix and phase-2 plan are in the [runtime bridge design](../research/runtime/runtime-bridge-design.md).

**0.8.15 Round 3 supervisor [source/offline]:** autonomous builds add supervisor.set/state/clear, one game-tick owner and a bounded worker through the existing dispatcher. A trusted C++ execution guard is copied into every queued game step; it cannot be supplied by request data. It rechecks actor/world/connection/entry/input on every step; violation checks apply before state changes, while settlement reads can retain a successful result/undo after resolution. Arming requires policy-specific frontend capabilities, sent as authenticated envelope metadata; the native owner snapshots the caller mask and the dispatcher checks it on every intervention as well as config. Missing arming claims fail closed; restore scopes remain unconditional cleanup. Clear invalidates an already-admitted set; kill, bridge pause, handover, accepted load/detach and owner loss cancel. The normal package omits the supervisor module and input seam. No new global native: counts stay **27 normal / 32 autonomous**. The self-test pipe host explicitly refuses arming because it has no retail actor/input adapter; core state/race fixtures test the policy owner. See [design](../research/runtime/runtime-bridge-supervisor-design.md) and [runtime commissioning](../research/runtime/runtime-bridge-test-card.md#supervisor-0815-round-3).

## Source recording [source]

**Holotable live observer [source/offline, 27 October 2026]:** the [M6 candidate](../research/live-world-view/live-checkpoint.md) uses a dedicated `CommandApi({readOnly:true})` observer, never the writer or an emergency command. Discovery targets the confirmed 0.8.23 bridge-thread `recorder.status` contract: `{active, run, session, world, channels, start:{s,at}, latest, stop_reason, requested_hz, duration_s, byte_cap, ack}`. Before the first run it answers `active:false`, `channels:[]`, the current `session`, and null for every other field. The maintainer reports this built as `fdb214bc` on `claude/bridge-0823`, pending main for 0.8.23; that report is contract evidence, not runtime proof. It has no game-thread call, lease or ack. The adapter maps `start.s` and `stop_reason` in one place: `start.s` is QPC seconds on the manifest/sample timeline; `start.at` is derived ISO wall time for display only. An older bridge's unknown-command answer hides the live action. This contract has not passed in-game row RS1. Holotable never starts the recorder. Detailed catch-up uses the exact opaque returned cursor with `now:false`; cursor paging/backlog is not loss. The observer drains its current stopped run through `more:false` before waiting, and delivers every known gap before any samples it splits. Discovery combines requester/source cancellation; late cancelled results cannot update the cache. Epoch resets put paused/scrubbed time at the new start and following time at the latest sample, clearing absent selections. Failing-before/passing-after regressions cover these client policies. Its fake-backed tests establish client/source policy, budgets, cancellation and replay parity only, not native discovery, cadence, frame cost or runtime teardown. Session events carry `source_s` but no universal top-level world id ([native event log](../projects/xf-runtime-bridge/native/src/core/Events.cpp)); the adapter scopes them from the active run's source start and respects `data.world_generation` where a receipt has it. Load/run identity changes end that timeline before a new epoch is admitted.

**Unattended runner evidence and teardown [source/offline, 26 October 2026]:** each row's prelude compares the running bridge's build and loaded settings to the staged manifest/config, and compares again after startup. A failed replacement close, missing build evidence or a mismatching replacement blocks the row. Teardown has its own execution mode: handover refusals are recorded without reinstating the batch stop gate, so later releases and host close are still attempted. Descendant cleanup failures remain visible, and a row with failed cleanup cannot remain PASS or CAPTURED. Blocks pass their absolute deadline to guards, branches and fallbacks. Recorder readiness (including runs without a report) is indexed by bridge session id plus run; the persisted attempt summary includes unknown readiness, so a clean later attempt cannot erase it. After saving a stopped run's tail, rollover sends a final `test.record.read` with `since` equal to the saved cursor's `record`; failure retains the old run for retry. These contracts are exercised by [runner regressions](../projects/xf-runtime-bridge/tools/test/runner-review.test.ts), with corrected rollover acknowledgement in [earlier review fakes](../projects/xf-runtime-bridge/tools/test/review-34eb.test.ts). This is offline evidence, not game validation or a cadence measurement.

**Runner launch job [source/offline]:** preflight and launch inspect the current Bun process through `IsProcessInJob` and `QueryInformationJobObject(NULL, JobObjectExtendedLimitInformation)`. A job without `JOB_OBJECT_LIMIT_BREAKAWAY_OK` (`0x800` in `LimitFlags`) blocks launch and asks for a PowerShell runner; failed inspection also blocks it. MO2's run command rechecks for an existing game after waiting for its window. The Win32 contracts are [current-job queries](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject) and [job limit flags](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information); implementation and fake coverage are [host.ts](../projects/xf-runtime-bridge/tools/testing/host.ts) and the runner regressions above. No game or MO2 launch was used to verify this change.

**Save delta evidence [source/offline]:** A save-list net increase is likewise distinct from proof of exactly one addition and no removal: truncated windows cannot establish changes outside their overlap, so the `save_delta` oracle reports INCONCLUSIVE unless complete lists establish the claim (`tools/test/input-evidence.test.ts`).

**Cancellation and ownership [source/offline]:** native recorder starts carry the cancellation generation captured before game-thread enqueue; an emergency stop invalidates earlier pending starts without preventing a later explicit start. The tools apply the same rule to queued starts and late start responses. Recorder heartbeats use a bounded, paced transport ping independently of the outer local-command queue, so a long local capture cannot starve ownership. Disconnect cancels both pending and installed capture arms and aborts their delays/queued work. Arming reserves its slot before initial reads, and an inactive source cancels before retained events are matched. Execution-frame spawn conditions use the dedicated `XFDmSense.Presence` reader, which neither changes watcher subscriptions nor drains events. Regression coverage: `tools/test/review0814.test.ts`, `native/src/selftest/UnitTestsRecording.cpp` and `UnitTestsDm.cpp` under the runtime-bridge project. These offline checks do not establish in-game cadence or latency.

Bridge 0.8.14's test-only `core/Recording.*`, `plugin/HandlersRecording.cpp` and `redscript/XFRuntimeBridgeRecording.reds` own fresh V, selected-actor and camera snapshots on 100 ms game-update deadlines. This is independent of `npc.status`'s 250 ms cache. The read adapter deliberately avoids `XFNpc.Poll`, which also refreshes the hub. Every individual script call checks the live guard; detach/load invalidate the run, and reconnect cannot continue an old run. QPC timestamps bracket each source acquisition; unavailable simulation time is null. Actual/valid rates, age, misses and drops are exposed rather than assuming 10 achieved samples per second.

The 512-slot/8192-byte-payload ring is bounded. One off-thread native writer drains private 1 MiB JSONL chunks and a final manifest even after kill closes the pipe; errors/loss/invalid samples make it incomplete. `test.record.stop` uses the existing control route without game access. Package gating omits the adapter and commands from normal builds; only explicit autonomous `-writes` builds with `allow_test_hooks` enable them. These are source properties, not measured game performance or rendered/aural proof. [Recorder API](../projects/xf-runtime-bridge/docs/mcp.md#source-recorder-0814).

**Timeline ownership and readers [source/offline]:** the 0.8.14 tools retain the recorder's exclusive writer connection for its bounded duration, with one bounded queued heartbeat, so three-second idle-close/local waits do not silently end observations while the coordinator thinks. `game.catchup` uses the ring plus the existing native private chunks (bounded 8 MiB/1024 returned rows, explicit `more` cursor), source channel summaries, session events and the existing digest; it owns no second history. Bridge 0.8.15 adds a default `contacts` channel: V car-hit entry and bounded landing/wall controller reports, gated to autonomous packages. Catch-up reports contact alerts and cursor-carried run latches; its covered-path summary always says `no_contact_proof:false`. Reports may include supporting ground and lack other-body identity; continuous physical-contact coverage is uncommissioned. Full details and offline evidence are in [R6](navigation-and-safety.md#bridge-0815-round-1-implementation-offline-24-october-2026). Test-gated action conditions are re-read on the game frame before each changing step; unavailable/mismatched state refuses, and restoration remains allowed. Process-owned event capture uses the same API/queue, exact future event matches, source-clock latency bounds, count/expiry and cancellation. Native session receipts now expose the same QPC seconds as recorder rows. These changes are exercised offline; cadence, sampling cost, UI output and event-to-exposure timing still need the [Borg recorder card](../research/runtime/runtime-bridge-test-card.md#recorder-and-taps-borg-mode-session). [R8](game-lifecycle-control.md) covers lifecycle consumers; `game.continue` is still uncommissioned. In 0.8.15 Round 2 the autonomous UI observer reads bounded active loading trees on the original ink callback thread, separately from the gameplay gate: fresh initial readiness/subscription/panel/consumption signals and engagement-menu presence reach game.status/game.load. Start GSM acceptance stays null. game.lifecycle.probe records a read-only candidate consumer, never an executing-frame invocation; shutdown/save-flush ordering keeps game.quit out. See [R8 candidate](game-lifecycle-control.md#bridge-0815-round-2-offline-observer-and-read-only-plan).

**Borg 2 recorder fixes [source/offline, bridge 0.8.17]:** the second autonomous session (25 October 2026, 0.8.16) ran the recorder for real and found five faults, now fixed offline and listed as [B217 rows](../research/runtime/runtime-bridge-test-card.md#borg-2-regressions-0817) for runtime confirmation. (1) The `ui` channel recorded the CET line and window every 100 ms even when nothing changed (445 rows in 20 s), which put `game.catchup` minutes behind real time; U rows are now written on change plus a 2 s heartbeat per surface (`reason: change|heartbeat`), both for the CET adapter and for the native polled UI snapshot. The CET adapter learns who is recording from a new autonomous-only native, `XFBridge_RecordIdentity(channel)` (`r<run>.w<world>.c<connection>`, empty when nothing records; 33 autonomous natives, 27 normal), and starts every surface from a fresh baseline whenever it changes, so a stop and fast restart between two looks cannot leave the new run without its first CET state. (2) A catch-up page that is behind (`more:true`) now always carries `v.current` (the newest V: the digest sample, `stale:false`; with the digest off, only a recorder sample marked `historical` and `stale` with its source time and age, remembered in the cursor so an empty page still reports it), a `backlog` object (records, events and seconds behind) and a `summary` line; a recorder page is "caught up" only when its cursor reached the latest sequence the final read showed (a live recorder keeps writing while the tools page); `v.latest`, `v.path` and the counts still describe only the page read, flagged by `v.latest_stale`. (3) Coverage gaps are scoped to the interval since the cursor: the cursor carries the run's loss counters at its position (`source_counters`), advanced only when the cursor has reached the head the final read showed, so early invalid samples no longer flag every later call. A cursor is the caller's data: a baseline above the recorder's totals, or nonzero at the start of the run, is refused as `invalid_cursor` instead of being clamped into apparent coverage. An armed capture takes its baseline at the arm, looks again at the interval after the page just before each source-timed capture (the delay is time the recorder can stop or lose data in), and cancels only on loss, or invalid rows on a channel that can carry the event, after it; invalid polled-state samples (`v`, `actors`, `camera`) cannot hide a named event and do not cancel it. (4) `supervisor.set` accepts the V reference as `v` or `V` (normalised to `V` in the entry, state and receipts alike; NPC handles accept upper case too). Other commands name V as lower-case `v` in their schemas and still refuse `V`. (5) A cursor without a `heat` (or other) baseline now means unknown: no change alert, only the baseline is established.

**Tap readiness at a run's start [source/offline, bridge 0.8.22]:** the subtitle and voice taps find the HUD's two subtitle controllers (Subtitles and Chatters) a moment after the world starts, so the first coverage heartbeats of a run started right after a load can report `controller_count: 0`. Such a sample is recorded as `reason: not_ready`: a valid row, counted under the run's `not_ready` and `channel_stats.<channel>.not_ready`, not as an invalid sample. Three conditions apply. It must come in the run's first 2 s (`kTapNotReadyS`). The channel must not yet have been ready in that run. The rest of the tap must be healthy: all three source listeners and no registry overflow. Otherwise it is invalid, as is a tap that loses its controllers after once being ready, even inside those 2 s. A selected tap channel that never becomes ready is listed in `tap_not_ready` and has `channel_stats.<channel>.ready: false`. The run's `complete_coverage` and the manifest's `complete` are then false, so a run made only of not-ready samples never reads as complete. Whether 2 s covers the controllers' arrival in the game is for a session to confirm (B318-1).

## 2. Rules learned the hard way (from source)

- **Declare natives outside a module.** `tools/lint-redscript.ts --natives-only` now rejects module-scoped native globals and cross-checks exact names against `Natives.cpp` under each package's build flags. `stageVariant` repeats the check on every staged `.reds`, including probes; unknown build conditions fail closed. The regression test recreates the missing `XFRuntimeBridge.XFBridge_TestUiTake` launch error. Redscript prefixes the module onto global natives (`XFRuntimeBridge.XFBridge_Ping`), but the plugin registers the plain name. Declare them in a module-less file, as Codeware does [source] redscript `unit.rs:1023`, `symbol.rs:222-246`.
- **Ship `.reds` that declare natives through the plugin (`scripts->Add`), not `r6/scripts`.** A redscript compile error blocks every mod's scripts behind a message box, and a declared native without its DLL is such an error [source] `scc/lib/src/lib.rs:86-94`.
- **Call game and script functions from a plugin the way script code does: with a context and a caller frame.** Script calls some natives as statics that the engine registers as member functions (every `TweakDBInterface` function, `TDBID.ToStringDEBUG`); the VM hands them the calling script's context, and with none the game dereferences null in `rtti::Function::InternalCallNative` and crashes (`exe+0x1e28769` on 2.31; [game crashes §2](game-crashes.md#2-known-crashes)). `RED4ext::ExecuteFunction(nullptr, …)` starts a script with no context. Use Cyber Engine Tweaks' and RedLib's recipe instead: the engine's internal execute (SDK hash `CBaseFunction_InternalExecute`) with a caller frame passing the arguments as `ExternalVar` instructions, a dummy caller function, and a dummy `entEntity` context for statics [runtime] crash and probe, first in-game run; [source] CET `RTTIHelper.cpp:765-812`, Codeware `lib/Red/TypeInfo/Invocation.hpp:9-107`, SDK `Functions-inl.hpp` `ExecuteNative`; the fix itself [offline] ([design §3.5](../research/runtime/runtime-bridge-design.md#35-calling-game-and-script-functions-from-native-code)).
- **A redscript class's static functions are global functions,** named `<Class>::<Name>;<ParamTypes>`; `CClass::GetFunction` on the class finds nothing, so look them up among `CRTTISystem::GetGlobalFunctions` [runtime].
- **Return `false` from a Running `OnUpdate`.** RED4ext removes a state callback that returns `true`, even though the SDK comment says the Running result does not matter [source] `StateSystem.cpp:128-160`.
- **Include `RED4ext/RED4ext.hpp` before any `RED4ext/Api` header.** The SDK becomes header-only only when `Common.hpp` is included first; otherwise `CreateSemVer`/`CreateFileVer` fail to link [offline].
- **CET cannot open network connections.** Its sandbox exposes no sockets, HTTP, `ffi` or process spawning, and file access is confined to the mod folder [source] CET `LuaSandbox.cpp:10-79, 152-161, 695-719`. Any external link must be native.
- **CET API details:** CET has `spdlog.warning`, not `spdlog.warn`; its Lua is LuaJIT (5.1), so use `unpack`; `onDraw` runs every frame even with the overlay closed [source] CET `LuaSandbox.cpp:641-666`, `LuaVM.cpp:50-56`.
- **Retail `Log`/`LogChannel` print nowhere** unless CET (`gamelog.log`, `scripting.log`) or Red Hot Tools hooks them. Route script logs through a plugin native instead [source] CET `LuaVM_Hooks.cpp:192-250`.
- **Bound JSON nesting before handing it to nlohmann/json, and serialise with `error_handler_t::replace`.**
  - Parsing and destruction are iterative in 3.12, but copying, comparing and `dump()` recurse. A 10 KB value nested 5,000 deep overflowed a 1 MB stack, and the game thread's 2 MB would take only about twice that [offline].
  - `dump()` throws `type_error.316` on invalid UTF-8 unless given a replace or ignore handler [source] json 3.12.0 `serializer::dump_escaped`.
- **Don't `FlushFileBuffers` a named pipe before disconnecting.** It waits until the client reads, which a client can simply not do [offline: held a stop 12 s]. `DisconnectNamedPipe` discards unread data, so give a client a short, bounded window to read a final reply instead [doc] Microsoft `DisconnectNamedPipe`.
- **`node:net` can't choose a pipe client's impersonation level or query the server PID.** Use `CreateFileW` with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` and `GetNamedPipeServerProcessId` (through `bun:ffi` in Bun), or .NET's `NamedPipeClientStream` with `TokenImpersonationLevel.Identification` [offline].
- **`redscript-cli lint` exits 0 even on errors,** so parse its output for them. It also doesn't check `@wrapMethod` parameter lists on `cb` methods [offline].
- **Check a pre-2.3 RTTI dump against the 2.31 script bundle before relying on a signature.** `TimeSystem.SetPausedState` has no parameters in 2.31, although the dump lists two [source].
- **`PhotoModeMenuListItem.ForceValue` silently selects the first option for an option value it doesn't know.** Validate against the option data the menu set up (`OnSetupOptionSelector`) before calling it [source] 2.31 photo-mode scripts.
- **A photo-mode expression is selected by its option data (the `faceId`), not its position in the menu** [source]; the next session's expression checks R2 tell option data and menu position apart in game ([test card](../research/runtime/runtime-bridge-test-card.md#expression-checks-r1-and-r2)).
- **Game scripts can't read the engine's render options** (`GameOptions` such as `Editor/Characters/Hair/GlobalLight/R`): no script type exposes them. Cyber Engine Tweaks can, because it hooks the options' initialiser at start-up and keeps the list (`GameOptions.Get(category, name)`, returning text, empty when unknown) [source] CET `src/patches/OptionsPatch.cpp`, `src/scripting/GameOptions.cpp`. The player's *user* settings (graphics, display) are script-readable through `inkISystemRequestsHandler.GetUserSettings()` → `UserSettings.GetGroup(path).GetVars(false)` and the `ConfigVar…` types; their groups and names are the game's `r6/config/settings/platform/pc/options.json` [source] 2.31.
- **A mod can add its own event to a game menu scenario** with `@addMethod(<scenario>) protected cb func On…() -> Bool`; menu instance events are dispatched to the current scenario by name, as Mod Settings' pause-menu entry shows [source] Mod Settings `Extensions/MenuScenario_PauseMenu.reds`. From anywhere in script, `MenuEventBlackboard.MenuEventToTrigger` becomes such an event through the in-game menu controller, which is how the game's devices open menus (`GameObject.TriggerMenuEvent`, set to `None` first so the same event fires again) [source] 2.31 `gameObject.script:2480-2490`, `inGameMenuGameController.script:76, 294`.
- **`PrintWindow` with `PW_RENDERFULLCONTENT` returns black for a window that is entirely off-screen,** while legacy `WM_PRINT` works there but not for DirectX content; capture the game on-screen [offline].
- **RED4ext loads DLLs only from `red4ext/plugins/<dir>/` and that folder's direct files.** It skips anything deeper and silently ignores a folder with no DLL. `sdk->scripts->Add` takes an absolute path or one relative to the calling plugin, so one plugin can add another folder's `.reds` to compilation. The proposed XF Core relies on both to gate its plugins' scripts [source] RED4ext v1.30.0 `PluginSystem.cpp`, `ScriptCompilationSystem.cpp:101-134` ([XF Core architecture §1](../research/runtime/xf-core-architecture.md#1-sources-and-findings)).
- **A redscript compile error switches off every mod's scripts for that session.** The game still starts, with none of them in effect [source] redscript v0.5.31 `scc/lib/src/lib.rs`.
- **CET runs each mod in its own context and keeps hotkey bindings per mod folder.**
  - A mod reaches another mod's exported table with `GetMod(name)`.

## 4. The XF bridge

- **Transport:** a Windows named pipe owned by the RED4ext plugin, off unless `[bridge] enabled = true`. It is local only (`PIPE_REJECT_REMOTE_CLIENTS`, user-only DACL, first-instance flag, random name), and uses newline-delimited JSON, protocol 1.
- **Security boundary:** the Windows user at medium integrity. Other users, remote machines, browsers and low-integrity or AppContainer processes can't reach the pipe. Same-user processes can, but they could already read or change the game's memory ([design §4](../research/runtime/runtime-bridge-design.md#4-safety-model)).
- **Security measures:**
  - A 256-bit token per session, published in `%LOCALAPPDATA%\XFStudio\runtime-bridge\session.json`. The plugin has no override for this folder.
  - Only allowlisted methods exist, and writes are gated by `allow_writes`. `bridge.kill` is a *control* method, which only changes the bridge.
  - Input is bounded: 64 KiB per line and 32 levels of nesting, and only scalar `id` values are echoed. Deep nesting would otherwise overflow the stack when a value is copied or serialised [offline: a 5,000-deep request crashed the host before the fix].
  - A rate limit covers unauthenticated requests too. Five malformed or unauthenticated requests drop the connection. Every refusal is logged.
  - A kill switch covers the CET hotkey, `bridge.kill` and a `KILL` file. Stopping is bounded and never waits for a client to read.
  - A pipe serves one request at a time, so the emergency controls have a second pipe of their own (0.8.1): `<pipe>-control`, served on its own thread with the same token and checks, answering only the kill switch, the stops and a handover's steps. A stop is then read at once while the main pipe still serves a long request such as a five-second smooth look [offline].
  - Accepted ordinary requests are logged with a correlation ID. Reader refusal floods and repeated reader emergency details are sampled before the shared log sink. No C++ exception can unwind into the game.
  - A named pipe was chosen over loopback HTTP because browsers and other network clients cannot reach it ([design §3.1](../research/runtime/runtime-bridge-design.md#31-choosing-the-external-transport)).
- **Concurrent observers (0.8.15 candidate; source/offline):** the original endpoint remains an exclusive writer; discovery adds fixed `read_only_pipes` (default 3; `[bridge] max_read_only_connections` 0-8). Each preserves existing security and bounded single-worker transport. CLI/MCP `--read-only` and `CommandApi({readOnly:true})` select native reader endpoints and never fall back to the writer. One dispatcher owns aggregate pacing, reserving half its two-second burst for the writer. One 16-slot queue reserves a slot for non-readers and drains writer/control steps before readers within the unchanged four-task frame budget. Authenticated emergency cancellation/ownership commands bypass ordinary pacing. These are scheduling bounds, not measured end-to-end latency guarantees.
  - Event cursors remain caller-owned request data; session events have no destructive global ack. Reader recorder replay does not advance the owner's acknowledgement. Reader endpoints never affect `HasClient()` / `ConnectionsAccepted()`, which continue to identify the writer for recorder, supervisor and input leases. Reader disconnect has no global cleanup callback; its transport buffers are discarded, while endpoint abuse strikes and cooldowns survive reconnects.
  - **Safe subset:** `npc.pick` (allocates shared NPC ownership), recorder start, singleton save-list/CET exchanges (`game.saves`, `game.options.read`), and `test.events` with `stims` require the writer, refusing `read_only_connection` on readers. Notify/write requests also refuse; emergency cancellation/ownership controls remain available. Shared recorder acquisition and concurrent singleton query exchanges are deferred pending requester-scoped ownership. Source: `core/Bridge`, `Dispatcher`, `GameThreadQueue`, `Recording` and `tools/bridge-lib.ts`. [In-game commissioning](../research/runtime/runtime-bridge-test-card.md#concurrent-readers-0815) remains required.
  - **Reader abuse containment (review follow-up to 83237ddf; source/offline):** authenticated reader `rate_limited` replies count as rejections and abuse strikes. Each fixed reader endpoint retains a 50 ms exponential backoff capped at 1 s (strikes reset after 5 s quiet), plus a 100 ms reconnect cooldown. Penalties are applied before writing the reply, so disconnecting without reading cannot escape them. Every reader refusal has a spacing floor, including invalid-version or unavailable emergency envelopes. Blank reader lines are paced and count towards disconnect, so neither path bypasses containment. Five rejected/throttled replies drop that connection using the existing linger/rejection penalty. Reader refusal logs are sampled globally at most once per second before entering the shared log sink; emergency detail logs likewise share a one-second sample. Reader connect/disconnect log pairs are sampled once per endpoint per second. **an abusive reader endpoint's emergency requests wait for its backoff; use the control pipe or kill key**. These waits observe stop/drop signals and never delay the control pipe or game thread.
  - **Repeated reader cancellation:** identical normalized parameters for one of six fixed emergency methods share a one-second admission receipt across reader endpoints; a coalesced reply says `coalesced:true` and explicitly requires a state read to prove completion. It is not another execution. Completed failures remain retryable; an intervening writer change/control or rearm invalidates prior receipts. Every reader emergency also has a 100 ms transport spacing floor, so changing parameters cannot remove reader backpressure. The independent writer/control route always executes cancellation without reader cooldown or coalescing. Cache count is fixed at six and each key is bounded by the existing request limit.
  - **Offline verification, 25 October 2026 (review follow-up to 83237ddf):** guarded Release build passed (1.8 GB peak under 4 GB). The final guarded native `--unit` passed **1,301 checks**, including 38 multi-client/flood checks and 63 recorder checks. The final full guarded `bun test tools` passed **717**, with **4 opt-in screen tests skipped**, zero failures (721 total, 48 files; 0.8 GB peak under 6 GB). The targeted multi-client run passed all five tests; TypeScript and diff whitespace checks passed. Added regressions prove `npc.pick` is refused before the read-only API opens a transport and by native admission, readers cannot reserve picks across disconnect, and writer picks plus reader list/status still work. Eight concurrent native readers exercise authenticated pacing strikes, global refusal-log sampling and writer reserve; deterministic backoff tests cover reconnect history, escalation/cap and quiet reset. Real-pipe tests cover retained reconnect cooldown, writer/control availability and repeated cancellation coalescing. Native tests also cover independent control execution, receipt invalidation on control/rearm, retry after failed cancellation, backoff on malformed/unavailable emergency envelopes, and paced disconnect for blank-line floods without releasing the writer. This confirms offline ownership/admission/teardown, not achieved game latency or runtime commissioning. No game/MO2/Studio process was launched or altered.
- **Threading:** the pipe thread never touches the game. Game work is queued and drained from the plugin's Running `OnUpdate` (at most four tasks per tick), which runs on the game's main thread, in the same state tick as CET's Lua `onUpdate` [runtime; source CET `GameHooks.cpp:93-104`].
  - A task not started before its timeout is cancelled and never runs.
  - A task already running at the timeout gets a 1 s grace. If it still hasn't finished, the client gets `timeout_after_start` and the late completion is logged.
- **Game access:** by RTTI name at run time, plus a check of the static flag, parameter types and return type before each call. A missing function fails with `rtti_missing` and a changed signature with `rtti_signature`. A function whose signature is unchanged but whose behaviour changed is not caught; the runtime pin is the main guard. Two routes are in use:
  - `GetPlayer;GameInstance` → `entEntity.GetWorldPosition`;
  - `ScriptGameInstance.GetPhotoModeSystem` → `gamePhotoModeSystem.IsPhotoModeActive`.

  Both worked in the game [runtime]. Phase-2 game access goes through our redscript actions layer instead (plugin → redscript statics by name), which lints against the installed 2.31 bundle. Every call, native or script, goes through one routine (`plugin/ScriptCall.cpp`) that calls with a caller frame and a context (rule above).
- **Clients:** Bun (`bun:ffi` calls kernel32, [offline] Bun 1.4.2) and PowerShell 7 (`NamedPipeClientStream`). Both open the pipe at the Identification impersonation level. Both check the server PID against `session.json` before sending the token. `node:net` can do neither, which is why the Bun client doesn't use it.

- **A write class for scene direction.** `dm` (`write-dm`) holds 26 commands: props, vehicles and lights brought in, doors and vehicles changed, sounds, a radio, a message toast, a real call from a journal contact, a tracker with our words, banners and toasts, watchers with micro-actions, and a one-call digest. Off unless `allow_write_classes` lists it; only the -writes package lists it and carries its script (`XFRuntimeBridgeDm.reds`). What each command drives is in [channels to the player §5](player-channels.md#5-the-bridges-live-direction-toolkit-0812-what-each-command-drives-and-what-was-left-out).
- **One release for everything.** The kill switch, the pause, a handover and a load share one step: doors, vehicles and radios are put back to the state the first change saw (a change undone by hand holds nothing), spawned things are removed, the call ended, lines and the tracker taken down. A load forgets without a game call, since the world took the entities. The game thread's tick also releases when the gate closes, so a handover's own request may find it already done; both report it.
- **Watchers run inside the game, not through the agent.** A fired watcher hands its micro-actions to a runner that sends them through the dispatcher's own gates on a worker thread; each answer, with its undo, becomes a `dm.micro` event. A watcher may run only commands of the read, notify, world, dm, player, photo and showroom classes (so never inventory, save or NPC commands), never `game.save`, `game.load`, `bridge.kill`, a handover, the creator commands or the live-pose apply, and a `watch.arm` inside a watcher cannot carry actions of its own.
- **A Codeware dependency is a refusal, not a crash.** Spawning, subtitle lines and light components need Codeware; without it those commands refuse `codeware_missing`, and the script layer lints in both variants.

## 6. What agents can and cannot do yet

- **Seen working in game:** reads, the photo-mode camera, placement, light values, fade and expression, `cc.apply`, the clock, the freeze and the kill switch's restore, through the CLI and a session script (the MCP server shares the same catalogue and code path but was first registered with a client on 30 September 2026; its own layer is tested offline) [runtime]. Sessions 4–6 (28–29 September) added [runtime] ([experiment 029](../experiments/029-session-4/README.md), [experiment 032](../experiments/032-sessions-5-6/README.md)): `photo.open` (only with the game window in front: keys posted to a background window don't reach it), `photo.frame` without drift, lights placed about V, photo mode's own clock and exposure, expressions by label and by table index, `cc.open` and `cc.back` from the street, `cc.apply` by label and through a row's slot, `game.load` and `game.wait` through a load, and spawning, lighting, turning and clearing XF Finish Showroom heads. Every other command works with the game in the background.
- **Found not to work in game:** placing photo mode's camera directly (`photo.camera.place`: photo mode puts its camera back, `held: false`), and the vanilla-wardrobe writes while an outfit hides every area ([worn clothing](clothing.md#in-game-results-sessions-5-and-6)) [runtime].
- **Built, not yet confirmed in game:** light type and shadow, the cursor hidden with the menu, the clock with the creator open, `game.options.read`, the full-body camera preset, and the refusal paths that need a missing engine address (`script_calls_unavailable`); the session-7 ink demos (bridge 0.5.3) ([design](../research/runtime/runtime-bridge-design.md), [test card](../research/runtime/runtime-bridge-test-card.md#ink-demo-rows-bridge-053)).
- **Verified to exist (still untested in game):**
  - reading photo-mode state, camera transform and FOV;
  - time of day, pause and dilation, teleport;
  - weather (with Codeware);
  - listing and loading saves by ID;
  - the character-customisation system calls;
  - quitting through `ExitGame`.
- **No API found:**
  - taking a game screenshot to a chosen file;
  - opening the full photo mode without input (Codeware's quest-node route opens a restricted one; [photo mode](photo-mode.md));
  - saving to a chosen slot.
- **Driving V (design only):** teleport with facing, the camera turned by the game's own look-at, navmesh paths, crouch, weapons, consumables, menus and the HUD's interaction choices all have script routes; walking with the game's locomotion, jumping, sprinting and choosing dialogue lines need input, and the retail build carries CD PROJEKT RED's functional-test input natives (`FunctionalTestsGameSystem.FakeInput*`, parameters stripped) as the lead for input without window focus ([player control](player-control.md), [design](../research/runtime/player-control-design.md)).
- **Directing NPCs (built offline, bridge 0.8.8):** XF actors spawned and walked, lines, gaze, faces and dialogue choices in the game's own widget, stand-ins that can be shot, spawns out of V's sight and a release once she can't see them, all through script routes; none of it has run in game yet ([NPC direction](npc-direction.md)).
- **Capture paths:** capture is external for now (window capture after post-processing). The lossless, before-effects route is an optional ReShade add-on (6.7.x headers, full add-on build only), which must never change the user's preset.

Details and citations: [design §7](../research/runtime/runtime-bridge-design.md#7-autonomy-capability-matrix).
