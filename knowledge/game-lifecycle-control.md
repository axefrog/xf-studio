# Game lifecycle control: start, load, quit and window focus

**Maturity: Draft.** Static R8 research for **Cyberpunk 2077 2.31**, 24 October 2026. **[source/binary]** The launch screen's native `Start` consumer, the initial-load screen's `UI_Skip` consumer and readiness gates, both menus' exit route, and MO2's argument override are located. **[hypothesis]** The native continue consumers still need instance, ABI, thread and lifetime commissioning. They are not enabled bridge commands. A script attach interval is **not** proof that a continue prompt exists. No game, MO2 or game tool was launched for this research.

Grades: **[source]** inspected decompiled game scripts, public framework/application source or an identified session report; **[binary]** executable instructions/RTTI with RVA; **[resource]** inspected extracted game data; **[wiki]** documentation; **[hypothesis]** inference, proposed adapter or runtime question. Existing session reports are identified as reports, not new observations. This supplements [input and choices](input-and-choices.md), [ink UI](ink-ui.md), [runtime access](runtime-access.md), [game events](game-events.md), [save identity](save-identity.md) and the [autonomous-testing survey](../research/runtime/autonomous-testing.md).

## 3. The launch screen: engagement and the native Start action

**[source]** `cyberpunk/UI/fullscreen/pregame/preGameScenarios.script:81–101,141–144` handles `ShowEngagementScreen`, switches to **`MenuScenario_EngagementScreen`** and opens **`engagement_screen`**. A hide request switches back to `MenuScenario_SingleplayerMenu` and opens `singleplayer_menu`. `ShowInitializeUserScreen` is a separate transition (`:103–139`); closing it updates the launch counter, checks patch notes/one-time messages and may display GOG UI. Calling a scenario's hide callback alone would change UI without proving that user initialisation happened.

**[binary]** The controlling engine path is **GSM**, not `PlayerPuppet.OnAction`. Type registration **`0x1551514`** names **`gsmState_SessionActive`**, size `0x110`, descriptor slot **`0x3438408`**; its type getter **`0x1902f30`** and vtable **`0x2ac67f8`** establish the consumer's owner. SDK `Scripting/Natives/Generated/gsm/State_SessionActive.hpp:17–26` independently identifies this class, leaving `+0xc0..+0x10f` opaque.

**[binary]** Static initialiser **`0xf2980–0xf29bb`** registers logical **`Start`**, CName **`0xae1c7f13b7c0c47f`**, in global slot **`0x34845f0`**. Binding setup **`0x124dd5c–0x124df0a`** maps three native key codes (`0x8c`, `0xff`, `0x20`) to this action. These are native binding codes; do not reinterpret all three as Win32 virtual keys. Helper **`0x124dc54`** arms session fields **`+0x84=1`, `+0xdc=1`**. Consumer **`0x62b000`** accepts the matching Start action at event `+8` only while **`+0xdc==1`**, plays `ui_jingle_press_to_continue`, stores the event's first qword at **`+0xc0`**, and advances **`+0xdc=2`** (`0x62b014–0x62b097`). This is the concrete native acceptance boundary, not a guessed Space injection.

**[binary]** Follow-up **`0x7f4ce0`** runs only in phase 2, checks its supplied service object's virtual `+0x70`, calls **`0x7f4d34`** and advances to phase **3**. The latter enters the user/add-on initialisation path. Response handler **`0xbffa44`**, with cold blocks **`0x1f81524–0x1f8157a`**, moves success to **4** and cancellation/failure in phase 3 back to **1**, clearing the stored event identity. Thus bypassing the phase field skips real work. There is no validated parameter-free “set main menu ready” helper here.

**[binary] Detector connection:** **`0x30b974`** maps GSM `+0x84` values to ink states: **1 → `inkEngagementScreenState`** (`0x30ba9e`, name getter `0x1862b64`), **2 → initialise-user state**, **3 → pregame menu state**. The script scenario above names the engagement menu. A versioned observer can report `start_accepting` only for the **current active** GSM instance with `+0x84==1 && +0xdc==1`, correlated with the current engagement ink state/menu. Phase 2 means Start was accepted and services are progressing; it is not another prompt to press.

**[hypothesis] Bridge boundary:** instrument original GSM entry/input/leave calls, publish copied scalars plus a lifecycle generation, and corroborate with engagement scenario/menu presence and a capture. This is a real state signal; it is not final proof that pixels painted, for the [ink visibility reasons](hud-and-occlusion.md#4-bounds-pixel-transforms-and-visibility-limits). No public script Start method, safe owned native action-record constructor, complete event ABI or title-safe standalone dispatcher was located in the inspected scripts/SDK/Codeware surfaces. Do not manufacture the record or write `+0xdc`. The next native adapter should call the existing Start consumer through a validated owner/event route, scoped to this one phase. Meanwhile §5's launch argument is the located way to request startup bypass without a key.

## 4. Post-load continue: observe the real initial loading controller

**[source]** `cyberpunk/UI/fullscreen/loading_screen/initialLoadingScreenLogicController.script:2–28` declares **`InitialLoadingScreenLogicController`**, with script progress callbacks and **native `OnAnimReadyForLoadingSkip`**. Its script callback `OnAnimReadyForLoadingSkipEvent` invokes that native. This contradicts the earlier summary that the controller has no script-callable native at all. **Animation-ready does not mean continue**.

**[source]** SDK `Scripting/Natives/Generated/ink/InitialLoadingScreenLogicController.hpp:20–32` identifies **`afterSkipAnimation +0x190`**, **`skipButtonPanel +0x1c0`**, `loadingPartsContainer +0x1d8`, total size `0x2c8`. The loading layer definition independently has **splash, initial, fast-travel and fallback** resource slots (`ink/LoadingLayerDefinition.hpp:24–27`). A splash controller is a different native class with its own skip panel and `afterSkipAnimation +0x250` (`ink/SplashScreenLoadingScreenLogicController.hpp:24–42`). Classify the controller, not any widget labelled “skip”.

No safe public “continue initial load” method was located. A controller-specific native event adapter is now a concrete research target; fabricating `inkPointerEvent`, setting `+0x2bf` or merely playing an animation is not an established substitute.

**[source/runtime report] The false detector and current boundary:** `projects/xf-runtime-bridge/native/src/core/ScriptLayer.cpp` in bridge 0.8.13 computed `waiting_for_input` from `State::Attached && m_puppet`. The offline regression covers attachment without a prompt, not rendered UI readiness. `ScriptLayer::Describe` implements this conservative report; the Round 2 observer below is built offline but remains uncommissioned, and `game.continue` still refuses `no_safe_route`.

**[hypothesis] Detector contract:** discover the active loading-layer tree/controllers, require the exact initial-controller type, current layer/controller lifetime, resolved skip panel with eligible ancestors, both readiness flags, current subscription and **not consumed**. Preserve `prompt=unknown` for an unresolved tree/ABI, `loading` before readiness, `initial_continue` when offered, and `continuing` after consumption until player attach. Do not infer the prompt from load origin alone; mods, automatic paths and cancelled loads can alter it. Codeware's layer/controller traversal is a useful discovery model (`scripts/UI/inkSystem.reds:4–5`, `src/App/UI/inkLayerWrapper.hpp:36–78`), but scripting remains closed during detach. The loading observer/adapter must have its own native UI-thread lifecycle, not call gameplay scripts through the [load-detach gate](game-crashes.md#23-calling-scripts-while-a-save-loads).

## Bridge 0.8.15 Round 2: offline observer and read-only plan

**[source/offline, not runtime commissioned]** The autonomous DLL now installs a **read-only** observer on the original `inkSystem::ProcessInputEvents` callback (Codeware address hash **673454961**, typed argument forwarding from `src/Red/InkSystem.hpp` and `RawInputHook.hpp`). Installation requires `allow_test_hooks`, the exact §1 executable SHA-256, and a resolved entry point inside that executable. There is no raw-RVA invocation. Normal DLLs install no lifecycle hook. A change from the first observed callback thread disables observation rather than sharing unowned UI state across threads. The original system/value/input-buffer arguments are forwarded unchanged; no action is constructed, modified or consumed by the bridge.

On that owning native callback thread, every 100 ms at most, `plugin/Lifecycle.cpp` reads Codeware's current layer-manager relationship and scoped SDK handles: up to **8 managers / 64 layers per manager / 512 loading widgets / depth 32 / 32 secondary controllers per widget**. Only active loading-layer trees qualify. Exact initial-controller RTTI/size, the §4 native flags `+0x2bd/+0x2be/+0x2bf/+0x1a1`, subscription `+0x240`, and the actual resolved skip panel plus visible/opacity ancestors supply the detector. Duplicate controllers, unresolved or truncated trees, missing imports, stale samples over **500 ms**, or a future clock value yield **unknown**. No opaque input/event bytes are read, no controller is retained across callbacks, and no gameplay script call crosses the load-detach gate. These bounded layout reads compile; their thread/lifetime, winning tree and cost still require the session rows.

Script-bodied engagement/menu callbacks pass the actual `engagement_screen` root as a weak observation reference through the autonomous-only `XFBridge_LifecycleMenu` native. Current visible ancestry must also connect that root to an active native layer in the new snapshot. Menu transitions invalidate the old generation immediately; a main-menu entry seeds the negative engagement scope on `-skipStartScreen`, while a missed seed stays unknown. This supports **`prompt_state:start_screen` as observed menu presence only**. **The active GSM owner and `+0x84/+0xdc` acceptance reader are still unavailable:** `gsm_phase`, `start_phase` and `start_accepting` stay null. It cannot certify Start acceptance. Widget presence/visibility is not final pixel proof.

Copied scalar snapshots, generation, age, source thread and readiness evidence reach `game.status` and `game.load` without dereferencing UI objects from the pipe thread. `initial_continue` requires both readiness flags, a live subscription, a resolved visible panel and no consumption/automatic flag; `loading`, `continuing`, `none` and `unknown` remain distinct. `none` is scoped to a complete observed UI snapshot and a seeded engagement scope, not to load origin or player attach. Detach invalidates the old snapshot. The tools' load wait requires a fresh complete observed **initial** offer, preserves its detector state and never promotes a bare `waiting_for_input` boolean or an engagement screen into a post-load prompt.

**[source/offline]** `game.lifecycle.probe` is an autonomous/test-gated, read-only command. It records a candidate **Start → `0x62b000`** or **UI_Skip → `0xff2bdc`** plan and the source snapshot in `session.events`, optionally rejecting a changed detector generation. `called:false`, `admissible:false`, `route_available:false` and **`execution_frame:false`** are explicit. Comparing a copied observation is **not** an execution-frame compare-and-act contract. The native event constructor/ABI, current GSM/initial-controller ownership, targeted thread/lifetime and one-shot consumption remain RB-234. **`game.continue` still refuses `no_safe_route`**; it calls neither consumer, `OnAnimReadyForLoadingSkip`, nor a synthetic input path. Native global counts are **27 normal / 32 autonomous** (the one additional observation native). The [Round 2 card](../research/runtime/runtime-bridge-test-card.md#lifecycle-detection-and-continue-plan-0815-round-2) commissions these observations before any adapter can be enabled.

## 5. Exit and launch arguments

### What the menus call

**[source]** Main menu inherits `gameuiMenuItemListGameController`: `cyberpunk/UI/menus/menuItemListGameController.script:10–14,30–47,74–80` defines `CanExitGame`, `ExitGame`, `GotoMainMenu`, and routes `PauseMenuAction.ExitGame` to `this.ExitGame()`. `singleplayerMenu.script:1131–1136` also uses it for held `system_quit_game`. Pause `pauseMenu.script:174–182` calls the same `ExitGame`; its **Exit to Main Menu** branch calls **`GotoMainMenu`** instead. Neither script branch requests a save.

**[binary]** Menu `ExitGame` registration **`0x10bd714`** installs VM thunk **`0x286a434`**, which tail-calls **`0x286a0e0`**. That body locks the live ink system's request-handler weak reference, permits a direct platform branch via virtual `+0x178`, otherwise creates a confirmation and retains it at controller **`+0x160`**. Confirm closure **`0x2869c04 → 0x2869fec`** calls handler virtual **`+0x108`** and clears the retained notification. The public **`inkISystemRequestsHandler.ExitGame`**, declared `orphans.script:45222`, is registered at **`0x10bd660`** with VM wrapper **`0x21db5f0`**, which directly dispatches that same virtual slot.

**[binary/source]** Concrete **`gsmBaseRequestsHandler`** vtable **`0x3139348`** (`GetNativeType 0x268060`, descriptor `0x3438460`) has **`+0x108 = 0x2999494`**. That native constructs request **type 5** and submits it via **`0x7e536c`**, which appends to the handler's **`+0x6f8`** request queue and releases the temporary request strings. Codeware `src/Red/InkSystem.hpp:25–33` independently identifies the live request-handler weak reference at ink system **`+0x370`**. Thus the typed public request is the bridge candidate; no raw `ExitProcess`, `TerminateProcess` or window close is required.

**[binary]** `CanExitGame`'s VM handler **`0xb2dac4`** returns **true**, without checking saving. It is not a save barrier. Neither the inspected menu confirmation path nor native request submitter requests a save or waits for one. This does not prove what every later engine/platform teardown step does: full save-flush, cloud synchronisation, plugin/D3D shutdown order and their completion signals were **not located** in this bounded trace. Exit submission must not be reported as saved or cleanly terminated.

**[hypothesis] Bounded quit design:** prepare an explicit `game.quit` operation through a **live menu controller's** `GetSystemRequestsHandler().ExitGame()` on the existing game-thread script-call boundary. This deliberately submits the request after the bridge has supplied its own explicit quit/discard policy; calling the menu's `ExitGame()` instead preserves the game's confirmation and requires separately handling it. Refuse during loading, save-in-flight, unresolved save state, creator transition or outstanding bridge cleanup. Stop/cancel owned work and wait for reversals before quitting; if a save was requested, require the correlated successful completion and settled slot first ([save/load events](game-events.md#9-save-and-load), [save identity](save-identity.md)). Do not auto-save a test world or lift its save lock. Submit once, invalidate the bridge session for further work, and let an external supervisor observe the **same process incarnation** exit and capture framework logs. A lost pipe is not proof of exit; uncertain submission is not retried. Native teardown completion and crash-after-exit remain commissioning questions.

The list also names `noBinksOnLoadingScreens`; that is a different scope and is not proof of either continue prompt being dismissed. Do not advertise `-skipIntro`, or a guarantee that `-skipStartScreen` removes every cinematic, on this evidence.

## 6. Focus the existing window, with an honest failure result

**[wiki]** Microsoft documents [`EnumWindows`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows) and [`GetWindowThreadProcessId`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid) for enumerating top-level desktop windows and identifying their owning process/thread. [`ShowWindowAsync`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync) posts a show-state request without waiting for the target to respond; success means the operation was started.

**[hypothesis]** A focus-only local helper should take the bridge/launcher-verified **PID and process creation identity**, verify its executable is `PATH_TO_GAME/bin/x64/Cyberpunk2077.exe`, select its live main window by HWND/PID (never display name alone), restore it if minimised, request foreground, then re-check `GetForegroundWindow` and its PID. Return `focused`, `foreground_denied`, `window_missing` or `ambiguous`; no launch fallback. A PID or HWND can be reused, so repeat identity checks. Do not select GOG Galaxy, MO2, a RED4ext error dialog or a second process merely because its title mentions Cyberpunk.

**[wiki]** [`SetForegroundWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) is restricted by foreground ownership/last input, foreground-lock timeout, active menus and foreground locking, among other conditions, and may still be refused. [`AllowSetForegroundWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow) is a **cooperative grant** from a process already allowed to set foreground; an arbitrary background tool cannot grant itself permission. A grant can expire on later user input or another grant. A cooperating authorised launcher/foreground application can grant the exact helper/game PID; do not use `ASFW_ANY` as a default.

**[wiki]** [`AttachThreadInput`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-attachthreadinput) shares input state/focus between threads, requires message queues and the same desktop, fails for some hook/queue conditions, and resets key state. Its documentation does **not** promise an unconditional bypass of foreground restrictions. **[hypothesis]** Keep it an optional bounded diagnostic fallback with matching detach in `finally`, rather than an always-on focus strategy. Avoid coupling the automation thread to an unresponsive game/foreground thread. If the documented request fails, flash/notify or await a cooperative foreground grant. Never simulate Alt/key input or launch another copy as a focus workaround. Even after successful focus, any external capture/input must re-check it because another application can take focus immediately afterwards.

**[hypothesis]** Use a versioned diagnostic candidate with read-only native lifecycle taps first, one disposable save/profile, executable/hash and MO2 commit recorded in the manifest. Keep private captures/logs outside published evidence; record each friction point. Observe original callers before enabling a native continue adapter. Each mutating attempt is one-shot, tied to the controller/session generation; unknown or changed state refuses.
