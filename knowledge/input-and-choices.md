# Input and choices: driving the game's own consumers

**Maturity: Draft.** Research and candidate source for XF Runtime Bridge **0.8.13** on **Cyberpunk 2077 2.31**, 24 October 2026. [source] The autonomous candidate implements the XF hub action-handler route, queued photo exit event and comparison callback, rendered CET Save anyway activation, and a bounded native-choice owner behind a refusing engine-dispatch boundary. Cleanup failures retain owned controls and prevent re-arming/resuming cancelled work. [source] No native receiver-lifecycle recorder is shipped and no native press/axis is enabled; concrete ownership, virtual implementations, load-safe release and physical overlap remain blocked (RB-227). Retail choice eligibility/action semantics and universal hub identity remain blocked (RB-228). [hypothesis] Delivery of these new candidate routes awaits the [Borg-mode session](../research/runtime/runtime-bridge-test-card.md#input-and-choices-borg-mode-session). Offline checks do not establish engine effects. `LastAttemptedChoice` has no hub ID. The existing `game.save.override_lock` policy is unchanged and pending the maintainer's decision (RB-226).

Grades: **[source]** means inspected game/framework/bridge source or executable instructions; **[community]** means a mod's implementation, not proof of engine behaviour; **[hypothesis]** means a proposed route or an inference needing a session check. **[offline]** means a compiler/tool check only. Existing runtime observations are identified separately. This page supplements [player control](player-control.md), [photo mode](photo-mode.md), [ink UI](ink-ui.md), [game events](game-events.md), [NPC direction](npc-direction.md) and [runtime access](runtime-access.md). ## 2. Dialogue and interaction choices

### The producer and the display are different owners

**[source]** `UIInteractionsDef`, `core/blackboard/blackboardDefinitions.script:805–838`, contains two different offers:

| Offer | Shape and meaning |
|---|---|
| `DialogChoiceHubs` | `DialogChoiceHubs.choiceHubs[]` → `ListChoiceHubData { id, activityState, flags, isPhoneLockActive, title, choices, timeProvider }`; each `ListChoiceData` has `localizedName`, `type`, `inputActionName`, `captionParts`, `timeProvider` (`orphans.script:42023–42026, 54489–54517`). |
| `InteractionChoiceHub` | `InteractionChoiceHubData { id, flags, active, title, choices }`; each `InteractionChoiceData` has `inputAction`, `rawInputKey`, `isHoldAction`, text, type, data variants and caption parts (`orphans.script:42008–42021, 54537–54552`). A device prompt is not automatically a dialogue hub. |

**[source]** `InteractionUIBase.OnInitialize` registers **delayed** listeners for hub data, `ActiveChoiceHubID` and `SelectedIndex`; `OnDialogsData`, `OnDialogsActivateHub` and `OnDialogsSelectIndex` redraw (`cyberpunk/UI/interactions/interactionUIBase.script:32–107`). `dialogWidgetGameController` stores those values and passes them to `DialogHubLogicController.SetData` (`dialogUI.script:56–117`). These controllers do not commit a quest choice. Writing their fields or the blackboard can change a highlight without changing the native interaction owner's selection.

**[source]** The selected-line **action** is `ChoiceApply`, whose **mapping** is `DialogConfirm`; `ChoiceScrollUp/Down` use `UI_MoveUp/Down` (`inputContexts.xml:866–868`, also vehicle/device contexts at 128–130 and 154–156). `DialogConfirm` is not the action name to send to `OnAction`. Its default mapping includes F/Enter (`inputUserMappings.xml:1195` onwards). Honour an offered line's dedicated action where present, and a device choice's hold semantics; do not translate every offer into a tap of F.

### Bridge-owned hubs: a contained route already has an owner

**[source]** `redscript/XFRuntimeBridgeNpc.reds:403–465` implements `XFNpcHub.Build` and **`OnChoiceAction(name, actionType)`**. Its `ChoiceScrollUp/Down` branches move the registry index and refresh the widget; its `ChoiceApply` branch sets `HubAnswer(index)`, hides the hub and refreshes. The `PlayerPuppet.OnAction` wrap at `:525–534` calls this function and consumes handled input. This is the bridge's actual button-action consumer, not the game's scene dispatcher. Its display hub is appended by a UI wrap, rather than installed as an engine scene choice.

**[hypothesis: build next]** A test-gated redscript entry point can call that same function with `BUTTON_PRESSED`, one scroll per update until the requested index is observed, then `ChoiceApply` on a later update. Require the expected hub ID and generation at every step. **Do not send scroll and apply in the same frame:** the existing `LastInputAt` guard accepts only one action per engine timestamp. Keep device-focus withdrawal and all existing ownership checks. This tests the shared action handler; it does not test engine delivery of `ListenerAction`.

**Read-back [source]:** the registry owns `HubAnswer`, independently of `SelectedIndex`; `XFNpc.Poll` reports hub ID/answer/shown/withdrawn (`XFRuntimeBridgeNpc.reds:1501`). `core/Npc.cpp:3172–3245` validates the hub and index and emits `npc.choice` with `hub`, `index`, `label` on an answer, or a distinct timeout/withdrawal/walk-away result. Wait for that event, including matching ID; hiding alone is not success. These are authoritative for **our** hub only.

### Real quest/vendor hubs: drive input, observe the attempt

| Operation | XF hub | Real quest/vendor dialogue hub |
|---|---|---|
| Move selection | Existing `XFNpcHub.OnChoiceAction(ChoiceScrollUp/Down, BUTTON_PRESSED)` [source]; test caller proposed. | Native interaction input consumer, `ChoiceScrollUp/Down` [source mapping]; engine submission adapter still [hypothesis]. |
| Commit requested index | Observe the registry index, then send `ChoiceApply` to the same handler on a later update [source consumer]. There is no direct choose-index call to add. | Observe `ActiveChoiceHubID`/`SelectedIndex` and the offered choices, then submit `ChoiceApply` or the validated offered action [hypothesis route]. Writing the board is insufficient. |
| Authoritative result | Matching `npc.choice` with `index`/`label`, excluding timeout/withdrawal [source]. | Fresh `LastAttemptedChoice` with `isSuccess`, `Dialog` and `choiceIdx` is native acceptance [source]; **which hub/scene accepted it** is unresolved when attribution is ambiguous. Assert the known quest/vendor response independently. |

**[source]** `InteractionManager` exposes only `IsInteractionLookAtTarget`, `SetBlockAllInteractions`, `AreSceneInteractionsBlocked` (`orphans.script:33671–33678`); `SceneSystemInterface` has no script-callable select/commit API (`:32204–32252`). No general commit function was found in the 2.31 dialogue controllers or those interfaces. This is an API limit, not evidence that the native system cannot do it.

**[source] Candidate owner, still refusing retail dispatch:** `core/InputChoices.cpp` wires `player.choice.select` to bounded 30 ms owned button pulses, one scroll followed by observed index read-back and a separate update before the next action. It rechecks active hub, offer generation/content, context/world/connection, deadline and physical overlap, caps steps, submits commit once and waits for a fresh native attempt paired with that observed offer. A failed or ambiguous attempt cannot pass as a correlated success. A select-only highlight is never committed. Both build gates and explicit `act` permission apply. **No retail offer publishes `input_eligible`**, and `plugin/InputDispatch.cpp` is unavailable: this code path is exercised only with injected simulated operations. It does not make real quests selectable. [hypothesis] After source-backed eligibility/dedicated-action resolution and R1 commissioning, it can drive the actual offered protocol; timed/phone-locked/inactive/disabled/skill-check/hold offers remain refused until understood. A vendor scene and its shop UI are separate consumers. No blackboard or quest-fact mutation is a substitute.

**[source] `LastAttemptedChoice` is stronger than the highlight.** `InteractionAttemptedChoice` has `visualizerType`, `choice: InteractionChoice`, `choiceIdx`, `isSuccess` (`orphans.script:33653–33662`). Crucially, **`PreventionSystem.OnPlayerChoice` checks `isSuccess && visualizerType == EVisualizerType.Dialog`** before treating it as a player choice (`core/systems/preventionSystem.script:3045–3049`; registration at `:1148–1159`). The device widget uses the same record's success/failure for feedback (`interactionsUI.script:73, 92–106`). This supplies a source-supported native **successful attempt** signal for dialogue, not just devices.

**[hypothesis: correlation, not a universal identity proof]** Register a **non-delayed** `LastAttemptedChoice` listener on the bridge's live observer. Record every notification with a monotonic sequence, session/world generation, visualizer, success, `choiceIdx`, caption and available `choiceMetaData`, plus the cached **pre-attempt** hub snapshot and current board values. Keep identical consecutive notifications; do not deduplicate by caption. Emit failed attempts separately. `InteractionChoiceMetaData` has tweak name/ID and type, not a hub ID (SDK `game/interactions/ChoiceMetaData.hpp`). The attempt itself contains **no hub ID, scene node or output socket**. Duplicate text, multiple hubs, expiry and native write ordering can make the association ambiguous; report `hub_attribution: ambiguous`/INCONCLUSIVE instead of inventing a committed hub. A fresh successful attempt plus a unique matching pre-attempt offer is the first practical oracle; a universal authoritative scene/hub identity still needs the native producer tap.

**Notification limit [source/hypothesis]:** the scripts locate readers, not the native writer of `LastAttemptedChoice`; no writer was found in this bundle. An immediate listener avoids the UI's delayed coalescing, but does not prove the writer signals every repeated identical attempt. Do not poll the retained last value and call it a new commit. If notification ordering or repeated delivery fails the session counterexample, instrument the native publisher before promoting this to an every-choice feed.

**[source] `gameinteractionsChoiceEvent` is `InteractionChoiceEvent`, not a choose-by-index request.** It extends `InteractionBaseEvent` (`hotspot`, `activator`, `layerData.tag`) and carries `InteractionChoice` plus `gameinputActionType` (`orphans.script:18261–18278, 22133–22146, 35785–35790`; SDK `game/interactions/ChoiceEvent.hpp`, size `0x110`, `choice` at `0x68`, `actionType` at `0x108`). `InteractionChoice` includes caption, caption parts, opaque `data[]`, metadata and the prevention flag. `InteractiveDevice.OnInteractionUsed` dispatches `ExecuteAction(evt.choice, evt.activator, evt.layerData.tag)` (`cyberpunk/devices/core/interactiveDevice.script:276–278`).

**[hypothesis; do not implement as general selection]** Fabricating or replaying that event skips the native choice's eligibility, current layer, hold completion and scene progression. `ListChoiceData` does not contain its full executable `InteractionChoice`. A device handler accepting an event would prove that handler ran, not that the game's quest choice was committed. The native-only `gameinteractionsPublisherChoiceEvent` is another research lead; the inspected SDK header exposes only an opaque payload and no callable dispatch method.

**Risks:** real choices can irreversibly advance quests, buy items or start combat. Require the action permission and a disposable fixture, one input owner, deadline, releases and cancellation on world/hub change. A successful native attempt does not prove the intended quest branch completed; assert a fixture-specific downstream effect too. These limits apply even if the widget disappears.

|---|---|
| Choose index 1 of a two-line XF hub; then, from a pinned save, move the highlight without confirming on a real two-line quest/vendor hub, commit the other line, and separately let a timed/cancelled hub disappear. | XF: exactly one matching `npc.choice` answer. Real: scrolling alone produces no successful attempt; commit produces a fresh Dialog success with the expected index/caption and a known downstream response. ## 3. Photo-mode Esc: exercise the exit attempt

**Producer [source]:** `PhotoModeUI` maps **`ExitPhotoMode` → `ExitPhotoModeButton`** (`inputContexts.xml:176–183`), whose defaults are **Esc, N, pad B/Circle** (`inputUserMappings.xml:2076–2080`). The native photo input handler at executable RVA **`0x1326908`** tests action type **1** at `0x1326a2d` (`BUTTON_RELEASED` in SDK `game/input/ActionType.hpp`), compares the action name with `ExitPhotoMode`'s FNV-1a CName **`0x86d0dad094b1ce4c`** at `0x1326a7b`, and calls **`0x1d32280`** at `0x1326a92`. That helper, when its native photo-state guard passes, constructs an event via `0x1d2d5c0` and dispatches it via `0x62d4ec`. This is a **release**, not a press-only path. `UI_Exit`/`back` are other menu routes.

**The event-to-callback link [source]:** the event is **`gameuiTryExitPhotomodeEvent`**, alias **`TryExitPhotomodeEvent`**, an empty `red::Event` of size `0x40` (SDK `game/ui/TryExitPhotomodeEvent.hpp`). Native type registration at `0x1d21880` names it and sets its descriptor at RVA `0x3436f48`; its constructor's vtable (`0x3111c60`) resolves that same descriptor through `0x1d21c20`. The callback registration at `0x1d20f10` uses that descriptor and thunk **`0x1d220b0`**; the thunk dispatches **`OnTryExitPhotomode`**, CName **`0x2b295f261342ed10`**, via `0x32b7ec`. Those links locate the producer and receiver without assuming a script handles the action. The event is absent from the decompiled script declarations, despite being present in the executable/SDK RTTI.

**Consumer [source]:** `gameuiPhotoModeMenuController.OnTryExitPhotomode` (`cyberpunk/UI/fullscreen/photoMode/photoModeMenuController.script:213–230`) asks for confirmation when `m_anyOptionChanged`, otherwise calls native `OnExitConfirmed(true)`. `OnExitConfirm` accepts Confirm and clears the token. `OnPMButtonRelease` (`:791–800`) forwards to page/top-bar/option controls; it contains no exit-action branch. Merely passing an invented `inkPointerEvent` to it is not an established Esc route.

**Contained route [source + offline feasibility; runtime unproven]:** **Codeware already imports this event** in `scripts/Base/Imports/TryExitPhotomodeEvent.reds:1` at the pinned commit: `public native class TryExitPhotomodeEvent extends Event {}`. With Codeware, queue **`new TryExitPhotomodeEvent()`** through **`GameInstance.GetUISystem(game).QueueEvent(...)`** (`core/systems/uiSystem.script:2–6`); do not add a duplicate declaration. That exact call compiled successfully against the installed bundle with redscript-cli 0.5.31 and Codeware's import. A standalone declaration using the full RTTI name `gameuiTryExitPhotomodeEvent` also compiled, but is unnecessary for the existing Codeware-dependent panel. Verify the actual runtime class exists, derives from Event and has the expected layout before enabling the command; a compiler accepting a declaration does not establish runtime binding. Submit only while the existing photo-panel owner reports the current shown controller/generation and the game is in the appropriate photo state. The event should enter the native registration above and then the compiled wrap chain, including the bridge's `XFRuntimeBridgePhotoPanel.reds:946–952` hold [hypothesis: runtime delivery]. Never call `OnExitConfirmed` or `photo.exit` as this test's stimulus.

**Lower-level control [source + offline]:** a small public `@addMethod(gameuiPhotoModeMenuController)` calling `this.OnTryExitPhotomode()` also compiles. Keep it as a comparison/control if event delivery fails; record `coverage: consumer_callback` explicitly. It exercises the same hold wrapper but omits the event dispatch now located above. Do not call a retained `wrappedMethod` pointer, which would bypass that wrapper.

**Coverage [hypothesis]:** `coverage: native_exit_event` should cover the real event-to-controller-to-hold path; it skips the physical mapping, action dispatch and native photo-state check before event creation. Recheck equivalent eligibility at the bridge boundary. A later test submits a complete `ExitPhotoMode` press/release through the validated engine adapter and compares the observation chain; that covers the upstream input integration. Neither direct route should be described as an injected Esc key.

**Read-back [source/offline]:** `XFPhotoMenuPanel.HoldExit` logs `ink_input.exit_held` and increments its holds; it holds only with modal enabled and a fresh unanswered question. The test candidate's `XFBridgeInputPhotoObserve` records `input.photo.entry`, `held`, `return`, `show`, `hide` and `hidden`, with controller generation and changed-option/confirmation state. The existing `OnUpdate` wrap observes confirmation-token creation/clearing, including cancellation through the game's normal callback; it does not mutate the token. `test.photo.exit_attempt {route: "event"}` queues the native event (`native_exit_event`); `{route: "callback"}` calls the public shim into `this.OnTryExitPhotomode()` (`consumer_callback`), preserving the wrap chain. A receipt from an immediate unchanged-option exit survives the context transition. Missing or stale-generation callbacks stay inconclusive, with no retry. The event has no request payload, so attribution is the next matching controller callback, not a universal producer identity proof. An unchanged photo-mode-active flag cannot distinguish a veto from an open exit prompt.

**Risks [source/hypothesis]:** with no changed option the unheld callback exits immediately; prepare an actual changed option and assert `m_anyOptionChanged` before the prompt test. The event has no per-request/controller payload: keep one attempt in flight, correlate the next callback with the current controller generation, and mark a generation change or missing receipt inconclusive without retrying. A stale/destroyed controller, hidden menu or another mod's wrap can change behaviour. Do not set `m_anyOptionChanged` artificially to make a test pass. Advanced Pose Mod also wraps this callback to protect edited characters [community], `35013-advancedposemod`, `r6/scripts/AdvancedPoseMod/PoseEditor.reds:4539` onwards; that demonstrates an interoperability consideration, not native input delivery.

## 4. Save anyway: keep the CET button path

**Producer and consumer [source]:** `cet/xf_runtime_bridge/panel.lua:150–153` calls `ImGui.Button`, suppressing clicks while the layout settles. In the `lock.save_anyway` branch at `:696–709`, a press queues `saveanyway`. `init.lua:421–445` drains actions during `onUpdate`; its `saveanyway` branch (`:399–413`) calls `XFBridge_SaveAnyway("cet-panel")` and shows Saving/refusal. `redscript/Natives.reds:57` declares that native; `plugin/Natives.cpp:698–760` validates `SaveAnywayOffered`, serialises attempts and starts the save worker. `PlayerSaveAnyway` (`plugin/GameHandlers.cpp:2027–2035`) shares `SaveWith` but retains the player's own saving policy. Final `save` events have `via: save_anyway`; `bridge_info.save_lock` reports running/refusals/last outcome (`Plugin.cpp:161–180`).

**Save policy, decided 24 October 2026 [source]:** `game.save { override_lock }` stays as a deliberate coordinator tool. It is test-build only already, because `game.save` needs the `save` write class, which only the -writes package lists. The no-bypass guarantee therefore means that no route exists in normal builds. Background: the current supported API allows `game.save { override_lock }`: `tools/api/catalogue.ts` exposes it, `core/Params.cpp::ParseGameSave` accepts it, and the save owner honours it. Thus “an agent cannot bypass the save lock” is **not currently guaranteed by this API**. The maintainer has been asked to decide whether that policy should change. The round-2 instruction is explicit: **“Don't change `game.save`'s `override_lock`.”** The catalogue, parser and save behaviour remain unchanged; the separate, test-only CET activation route does not settle this policy. Tracked as RB-226 in the [code-health ledger](../research/authoring/code-health.md). Do not claim a no-agent-bypass guarantee before that decision.

## 5. R1: general input dispatch and native hook points

### What scripts can hear is not a general injector

**[source]** `GameObject.RegisterInputListener(listener, opt name)` and `RegisterInputListenerWithOwner` (`core/entity/gameObject.script:152–156`) receive mapped actions. `PlayerPuppet.OnAction` (`cyberpunk/player/player.script:1202` onwards) and other registered listeners get `ListenerAction` plus `ListenerActionConsumer`. `ListenerAction` has getters for name/type/value/key and button/axis/relative tests; the consumer can consume, suppress release or wait for axis zero (`orphans.script:31981–32027`). There is no script constructor/setter for an arbitrary mapped action. SDK `game/input/ScriptListenerAction.hpp` describes only an opaque eight-byte struct. Do not fabricate it or invoke `PlayerPuppet.OnAction` as though that would update the native PSM, interaction manager and menus.

**R1 answer:** native code contains real press/release/axis dispatch operations [source], so external input is not the only engine route. No safe universal bridge injector is established yet [hypothesis]. Registered gameplay listeners and ink callbacks receive their respective delivered actions; the native interaction/PSM/photo consumers do not require a call to `PlayerPuppet.OnAction`. Photo mode's native release-to-exit-event path (§3) is a concrete example. Title input remains native/unlocated here; the existence of a player-listener hook cannot establish title support.

**Receiver acquisition now traced [source]:** the key helpers read `FunctionalTestsGameSystem + 0x40` (the inherited `IGameSystem.gameInstance`), then call helper **`0x4d7fb4`**. **Contained boundary implemented [source], native calls blocked:** `plugin/InputDispatch.{hpp,cpp}` exposes `InputDispatchStatus`, `DispatchInput` and fail-closed physical-overlap detection.
