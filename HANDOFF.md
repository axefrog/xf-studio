## The crash at load (0.8.1, 3 of 3 launches)

- **Cause:** a stale object file. 0.8.1's DLL linked a `Main.obj` compiled before `Bridge` gained its control-pipe `PipeServer`: `StartBridge` asks `operator new` for 0x2F8 bytes (`mov ecx,2F8h` in the shipped object) while `Bridge::Bridge`, compiled fresh, writes up to offset 0x424 (sizeof 0x428). Every launch overran a heap block by 0x130 bytes. The two crash reports fault in the heap allocator (`ntdll+0x88f9`, one on the main thread, one on a game worker; the bridge's threads idle). `Main.obj` was older than `Bridge.hpp` (17:32 against 18:04; the DLL 18:14), and the plugin's MSBuild include record had no entry for `Main.cpp`. The control pipe's own code was sound: 200 rounds of both pipes started and stopped with clients racing them, kills during the start and two threads stopping at once, all clean under AddressSanitizer (`xfb_selftest --pipe-stress 200`).
- **Proof:** under AddressSanitizer, constructing the current `Bridge` in a 0x2F8-byte block stops with a heap-buffer-overflow in the constructor, at the control pipe's `PipeServer` (`xfb_selftest --layout-repro`); and linking a `Main.obj` from before a header change now fails with LNK2038.
- **Fix (three guards):** a header stamp in every translation unit (`native/cmake/HeaderStamp.cmake`, `core/LayoutGuard.hpp`, `#pragma detect_mismatch`), so the linker refuses objects compiled against different headers; `Bridge::Create`, so the plugin's allocation and the constructor share a translation unit; and `tools/package.ts` refuses any build with an object file older than a native source file (`packaging.ts staleObject`), so packaging needs `cmake --build build --config Release --clean-first`. [Game crashes §2.5](knowledge/game-crashes.md#25-a-stale-object-file-in-the-plugin-bridge-081) has the fingerprint and the rule.
