## What's on the branch

- **0.8.1, the wave-4 review (RB-119..128)**, each with a unit check or a tools test ([design §3.9](research/runtime/runtime-bridge-design.md#39-bridge-081-the-wave-4-reviews-safety-fixes)):
  - RB-119: `game.save` with `override_lock` owns the relock before `SavePrepare` releases the lock; `XFGame.Retake` acts only on the relock flag. Unit checks in `InventoryAndSaveTests`.
  - RB-120: the screen capture route reads only while the game is the front window, re-checked before and after every grab and every burst frame (`capture_not_foreground`, in `REFUSALS`). `tools/test/capture.test.ts` (fake windows through `CAPTURE_PORT`); the opt-in on-screen test now expects the refusal for its non-activating window.
  - RB-121: `bridge.kill`, `behave.stop`, `player.stop` and `session.handover` skip the command API's queue and go on a second pipe, `<pipe>-control` (session.json's `control_pipe`), which the plugin serves on its own thread and which answers only those and a handover's steps (`not_on_control_route` otherwise); kill and handover supersede earlier work (`superseded`, keeping its `detail` and `cause`; the `AbortSignal` reaches every forward bridge call and wait of the local commands, cleanup still runs) and are barriers for the commands sent after them. batch15: a serialising fake transport with a five-second look, the self-test host's control pipe beside `selftest.hold`, handover-then-resume ordering, a handover during a sweep's settle through `CommandApi`.
  - RB-122: every game-thread step that changes the game goes through `Dispatcher::RunWrite` (the kill switch, the pause and a handover checked on the game thread right before it runs); reads use `RunGameTask`; steps that put something back run inside a `RestoreScope`. The plugin's handlers and the self-test's simulations bind their changing steps that way; `photo.open` re-checks the gate before the key. Unit checks `Bridge081Tests`, including the real `photo.pose.set` (paused during its settle) and `photo.light.set` (paused after its selection) handlers; batch15 for `photo.open`.
  - RB-123: `scene.read` refuses a null point (`core/Scene.cpp`). `Bridge081Tests`, batch15.
  - RB-124: the session lock is a Windows named mutex per runtime folder (`tools/session-lock.ts`), chosen over a sturdier file protocol because the kernel frees it when the runner dies, so no stale-lock judgement or takeover exists to get wrong; the lock file stays as the description the MCP server reads, and a process that has ended counts as gone even while a handle to it is open. batch15 (six runners racing, a holder killed); the old RB-33 putback test is gone with the code.
  - RB-125: inventory undos carry the exact copy (`id`); `inventory.equip` takes `id`, answers `exact`, and its wait reads the slot for the copy it equipped (`XFInventory.Equip` and `Slot` gained a `hash` parameter). The self-test host keeps distinct copies of one record (`selftest.give`). `Bridge081Tests`; batch15, including two copies of one jacket.
  - RB-126: `cc.back` skips the busy check and clears a stuck busy flag (`busy_cleared`); Confirm still waits. batch15 checks the script's structure (no game offline); `busy` left `cc.back`'s refusals.
  - RB-127: a teleport's undo carries `far: true` beyond 50 m (`player::TeleportUndo`). `Bridge081Tests`, batch15.
  - RB-128: a sweep whose heads can't be turned back answers `returned: false`, `return_failed` and a warning with the exact undo; a failed sweep's error carries it in `detail`. batch15.
