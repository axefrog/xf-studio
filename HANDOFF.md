## What's on the branch (0.8.3)

- **The ink panel's mapping.** Root cause: 0.8 assumed the HUD's 3840 × 2160 canvas covered the screen centred and cut 280 units at the top and the bottom at 21:9 (the log's `visible=3840x1600 at 0,280`); in fact the root's top-left corner is the screen's and its width the screen's, so every anchor sat about 280 units too low. The overlay now measures the visible part from the game's own layout (`WidgetUtils.GlobalToLocal` of the window's corners, accepted only when plausible) and uses the corrected model until then; the `panel geometry` line says `from=measured` (with the model beside it) or `from=model`. `tools/overlay/ink-place.ts` mirrors the arithmetic; `batch17` checks all nine anchors at 16:9, 21:9 and 32:9.
- **Readability.** A nearly opaque plate (an opaque underlay under the game's panel colour) and each anchor's floor from its edges, in HUD design units, measured on session 10's capture: top_right, center_right and bottom_right left of the minimap, quest tracker and weapon block; top_left under the status bars (the default 40, 360 stays); bottom_left above the status and cyberware icons; the bottom centre above subtitles.
- **The world pin's XF mark** in a fixed-size canvas, every part placed by a margin (0.8.2 reused the map badge: a 0 × 0 canvas with centred parts, placed 280 units low); `ui_state.pins[].xf_mark` says where it is on screen.
- **The staged showroom found by itself.** `showroom.staged` (plugin, read): the showroom archives the game itself sees in `archive/pc/mod` (MO2's virtual folder), with SHA-256 and the manifest a build ships beside the archive (each sidecar read within the request's nesting limit and type-checked, a bad one failing its own entry; the listing bounded and stopped when the bridge stops). The tools resolve each to that shipped manifest when its record matches the staged bytes, else to this machine's build with the same bytes (this checkout's dist, the primary checkout's, `XFS_SHOWROOM_DIST`), and use every resolved build. Showroom builder 2 (`projects/xf-studio/authoring/src/showroom/build.ts`) writes `xfs_showroom_<key>.showroom.json` beside the archive; the pipeline guide records it, with its diagram re-rendered and inspected.
- **A smooth `player_look`** steers along the eased great-circle arc in 0.1 s steps (`player::LookArc`, shared with `behave.look`), so `duration_s` 5 takes 5 s; the player's input (the glide's input watch, checked before every step) or a drift past the closest angle ends it (`took_over`); the answer has `took_s`.
- **Emergency calls from any process.** Root cause of session 10's L2c: the command API decided the route by the name as typed, so `session_handover`, `player_stop` and `bridge_kill` typed with underscores on the command line went through the ordinary queue onto the main pipe, which the other process's `game_wait` held. Now the canonical name decides; `session.resume` is an emergency control too (its steps are on the control route); emergency controls other than the kill keep their order; a handover and a resume each run whole under a cross-process handover lock (named mutex per runtime folder), and a cancelled resume sends nothing; the kill never waits. The plugin log names the pipe of each connection (`pipe=control|main`).
- **No XF surface on a loading screen** (`ChooseStatusSurface` answers `none` while the script layer isn't ready).
- **The bridge's own kill key**, `[ui] kill_key` (default End: free in the game's 2.31 bindings), read by the plugin from the keyboard on the game thread while the bridge runs, the game's window is in front and CET's overlay is closed (a key held elsewhere never fires on returning: it must be released first); in normal play, photo mode, menus and loading screens; shown in the XF Runtime Bridge window beside Stop. The CET hotkey stays a second route.
- **The press-any-key screen (research):** no contained route inside the game: its controller (`inkInitialLoadingScreenLogicController`) is native with nothing script-callable, and the key is the UI action `UI_Skip`; ending it from the game thread would be a synthetic input in another form. `game.continue` keeps refusing ([runtime access](knowledge/runtime-access.md)).
- **Names by appearance:** the **CET line** (was the status label), the **XF box** (was the overlay panel), the **ink panel**, the **XF Runtime Bridge window**; `status_surface` and the frame say `ink_panel`, `xf_box`, `cet_line` or `none`.
- **`inventory.list`** (read): the clothing V owns, one entry per copy with record, slot, id, name and whether worn.
- **Card fixes** in session 11: L1 reaches the save's prepare path through a clock change (the save lock covers it, it isn't a blocking effect), L4 names a jacket from `inventory_list`, L5 teleports to an absolute point 60 m along an open street found with `world_probe`.
- **Queue unit tests** no longer depend on a thread starting within 50 ms.
