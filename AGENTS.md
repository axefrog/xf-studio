# XF Studio repository working rules

These are the standing rules for any agent working in this repository. They record the maintainer's decisions. Current state and priorities live in [docs/status.md](docs/status.md) and the [ranked backlog](research/backlog/README.md), not here. Rewritten 25 September 2026 when Claude took over coordination; the earlier wording is in git history. Technical invariants that used to be dated checkpoint paragraphs here now live in the contract docs linked below.

## What this is

XF Studio (`projects/xf-studio`) is a specialised, all-in-one Cyberpunk 2077 modding toolkit. The first suite is V customisation, starting with eye makeup. Next come tools for designing piercings and hair and other facial/head details, then full body customisation, and later world integration such as quest and area design. That breadth is why the Studio's architecture must stay strict. Photo Mode Tools (`projects/xf-photo-mode-tools`) is an independent second project, not a child of an all-in-one toolbox.

**Read first:** [README.md](README.md), [docs/status.md](docs/status.md), the [backlog](research/backlog/README.md), the [knowledge base](knowledge/README.md), [docs/developer-orientation.md](docs/developer-orientation.md), then the relevant project README and linked research. Keep these current whenever work changes a project's state. Write them as *current truth*: update or replace stale statements instead of prepending dated paragraphs above them.

## R&D lab

R&D is a permanent, first-class mandate, run like a research lab beside the product work rather than as an occasional detour. CP2077 modding knowledge is thin in model training data, so our own understanding of the engine is the foundation for every advanced feature to come.

- **Always run R&D.** Keep at least one R&D track active alongside feature work. The standing tracks are the game's material and shader system, the character-customisation file chain, and **load time and responsiveness**.
- **Load time is a standing research target.** The asymptotic goal: the moment the interface appears, everything is already loaded, visible and interactive, and every change that needs new assets shows with no perceivable wait. Measure end to end, keep budgets, find the next biggest cost, and treat any slow load as a research task, not an accepted cost. See the [performance track](research/backlog/performance.md).
- **Distil findings into the [knowledge base](knowledge/README.md).** It holds current, cited, evidence-graded answers to "how does X work?". Task logs alone are not enough.
- **The meta-coordinator owns the [research queue](research/backlog/research-queue.md).** A chat that needs something researched, beyond a quick lookup inside its own scope, sends the meta-coordinator the full brief it would have given its own research agent. The meta-coordinator acts as the go-between. It points at material we already have, trims covered parts and merges overlaps between chats' requests, then runs the brief and delivers the result into the knowledge base. R&D build tracks stay with their own chats.
- **Read before you work.** Agents and subagents read the relevant knowledge pages before starting and update them when they learn something.
  - Every agent brief names the knowledge pages to read first.
  - Every agent report ends with a "Knowledge used" line: the pages it relied on, and any it found wrong or incomplete.
- **Observed results update the knowledge page in the same commit.** When a test, a compile or a game session confirms or contradicts a knowledge page, update that page (with the evidence and its grade), not only your own notes. The meta-coordinator checks this when agreeing merges.
- **Offline understanding serves the tests.** Its purpose is to make the maintainer's in-game tests succeed first time, not to replace them.

## Working with the maintainer

- **Report at each milestone** what was achieved and what, if anything, the maintainer needs to test. Keep it short and concrete.
- **The maintainer runs the game; agents never do.** Offline programmatic understanding of the game exists so that those tests succeed with minimal attempts. It is not a reason to avoid asking for a test. Batch runtime questions into one prepared session with a checklist, the exact candidate and profile, and versioned evidence capture. Later work will add live programmatic game access (RED4ext, CET, redscript, Lua) under the maintainer's supervision.
- **Volunteer design insights.** The maintainer welcomes useful unsolicited insights; explain meaningful design implications as they arise.
- **Finish before widening.** Completing what is already on the list, and bringing half-finished or preview features to a 1.0 state, comes before any new feature beyond those already in the pipeline (set 28 September 2026). A new feature request is banked in the [backlog](research/backlog/README.md) with a plain note that it waits for the current product to be finished and polished; bugs and polish on existing features are not new features.
- **The 1.0 bar is "ready to publish on Nexus for the first time".** It feels ready when:
  - UI/UX is consistent down to minor details;
  - nothing behaves glitchily;
  - nothing is annoying;
  - everything is straightforward and easy to discover;
  - what fills the UI is mainly things that export and work in game, and the UI isn't cluttered with preview or early features;
  - everything is fast: no multi-second wait for anything, optimised as far as possible, snappy.
  The first public release is a **beta**, to verify with other people's setups that things "just work" about 99 % of the time. The checklist is [1.0 readiness](docs/release-readiness.md) (set 29 September 2026).
- **Discuss before building each later feature.** The order is piercings/earrings, eyebrows, cheek makeup, hair, facial expressions (static/animated, plus varied idles), tattoos (full body by then). Early approved exception: playing the real default character-creator idle with an on/off toggle. Never label synthetic motion as the game idle.
- **Keep a friction log in every in-game session.** Record every point of friction met in passing, not only what blocks the goal: anything that could be streamlined, automated, expanded or improved in the integration, and anything that would give the maintainer more control. Session write-ups turn it into queued work (set 29 September 2026).
- **Make the game integration self-contained.** Whatever the integration relies on (another mod's route, a key binding, a UI screen, a manual step), take the reins and build a better, more streamlined version into our own bridge where that's feasible, driving the underlying game systems directly rather than their screens. The more self-contained the integration, the further it can reach into the game's systems. This concerns our own integration only: users' own mod setups are still never touched (set 29 September 2026).
- **Give agents their own view of the game.** For everything the integration drives, build machine-readable introspection an agent can read and filter: what the camera sees, where subjects sit in frame and whether they are blocked, which lights are on and reach them, exposure and frame statistics, world and UI state. Add pre-capture checks that refuse or warn automatically, so problems don't depend on someone noticing them in a screenshot (set 29 September 2026).
- **Ask when a decision is genuinely his.** Otherwise pick a sensible default and say so.
- **Test UI changes in an isolated `?verify=1` workspace,** never in the maintainer's active draft.
- **Keep the maintainer's local Studio running.** The Studio chat starts the localhost dev server (port 4317) whenever it isn't running, and restarts it after merges that need it. A chat whose merge needs a restart tells it.

## Coordination and parallel work

- **The work queue is the anchor.** The coordinator keeps the [work queue](research/backlog/README.md#work-queue) current and decides from it what to start, delegate or report. It has six lanes: in flight, beta blockers, polish, next tracks, R&D and after 1.0. Every request is filed in a lane the day it arrives. One agent slot always works the polish lane. R&D runs only while polish is moving. Milestone reports give each lane's progress and name any blocker or polish item older than two weeks (set 21 October 2026).
- **Parallelise independent tracks** with subagents. The maintainer expects queued independent features to proceed concurrently.
- **Worktrees for code-changing subagents.** Create a separate worktree at `%USERPROFILE%/xfs-worktrees/<slug>` (the fast system drive, reachable by both Claude and Codex agents; not `%TEMP%`, which Storage Sense may clean) on a `claude/<slug>` branch and give the agent that absolute path and a bounded ownership scope. It edits, tests and commits there, never in the shared checkout. Never use `git stash` in a worktree: the stash stack is shared by every worktree, so another agent's pop can take yours. Use a WIP commit on the branch or a patch file instead. Read-only research agents may use the primary checkout.
- **Guard heavy work.** The machine is shared with other projects and the game. Run full test suites, fuzzing, benches, real-data oracles, WolvenKit batches and any reproduction of a memory or CPU blow-up under `python tools/memory_guard.py --limit <GB> -- <command>`, with the smallest limit that fits (a full authoring `bun test` fits in 6). Scale blow-up reproductions down so they stay under 1 GB. **Use memory as the work needs it, and let the tripwire guard the maximum.** There's no reserve to keep free and no need to hold work while the game runs. The guard trips when the machine's free memory falls below its `--floor` (default 4 GB, set near the machine's maximum), so a job is stopped before the machine or the game runs out. Near the maximum, be mindful: stagger big jobs rather than starting them together. The guard's `--limit` is a per-job tripwire against runaway use, sized a little above the job's normal peak. Run targeted tests while developing and the full suite at the end. A limit kill (exit 99) means a job blew past its normal size, so investigate it rather than raising the limit. A floor kill means the machine was nearly full: wait and retry. Start the guard with the full interpreter path (`%LOCALAPPDATA%\Python\pythoncore-3.14-64\python.exe`), not the `python` alias: the alias is a packaged app whose redirected AppData hides the Studio's saved settings from the processes it starts.
- **Keep heavy disk work off drive D.** D is the machine's slowest drive (mechanical), and it holds the main checkout. Anything disk-heavy runs on C, which is NVMe: worktrees, installs, builds, typechecks, test suites, caches, extraction and scratch output. Use `%USERPROFILE%/xfs-worktrees/<slug>` for worktrees and `%USERPROFILE%/xfs-scratch/<slug>` for temporary files (not `%TEMP%`, which Storage Sense may clean mid-run). Never put work under `%LOCALAPPDATA%` or `%APPDATA%` from a chat: the Claude app is a packaged app, so those writes are redirected into its own package folder, where anything started outside the app (detached Codex runs, the desktop Studio) can't see them. Scope searches instead of sweeping D, and run at most one heavy disk job per chat at a time. **Clean up after yourself:** C's space is limited, so delete your scratch folder when the task ends and move anything worth keeping to its canonical location first.
- **Keep what's needed, delete what isn't.** Collecting plenty of evidence is fine; files left behind after they stop being needed are the problem.
  - Build outputs and runs: when a newer one supersedes them, delete the old ones. Regenerable outputs don't need keeping once their result is recorded.
  - Captures and screenshots: keep the ones a write-up, review or knowledge page references. Delete the rest once that write-up lands.
  - Worktrees: remove a worktree when its branch merges or is abandoned (unlink junctions first, as under "Clean up after integration").
  - Temporary folders: tests and tools remove their own on exit (the `tempDir` helper; see [developer orientation](docs/developer-orientation.md)).
  - Codex and Claude agents do the same with what they write. The dispatching chat checks it when the agent finishes.
- **Watch your footprint.** Run `python tools/disk_footprint.py` at each checkpoint and at wrap-up, and note anything over about 5 GB that you're keeping, and why, on your board row. Heavy jobs run under the memory guard, whose `--disk-floor` (default 20 GB free on C and on the working drive) stops a job that's filling the disk. The meta-coordinator runs the report regularly and asks the owner about anything stale.
- **No nested agents without approval.** Subagents do not start their own subagents (helpers, parallel researchers, workflows) unless the coordinator approves it for that task. Usage quota is limited and shared, and nested agents are invisible to the coordinator's budgeting and clean-up.
- **Integrate centrally.** The repository holds several subprojects, so `main` belongs to none of them: it belongs to the meta-coordinator (see [Cross-chat coordination](#cross-chat-coordination)). A chat lands its own verified work once the meta-coordinator agrees, or under a standing route recorded on the board. Before agreeing, the meta-coordinator checks the change against the other chats' registry rows and the shared hot files, and tells any chat it affects. The landing chat merges, pushes and updates shared status and provenance.
- **Clean up after integration.** Check for uncommitted work, then move any ignored private outputs (e.g. `experiments/*/generated/`) into the main checkout's canonical ignored locations. Old worktrees may contain directory junctions into the main checkout (e.g. `node_modules`, `.hutch`, private assets). Unlink each junction non-recursively (`cmd /c rmdir <link>`) before deleting a worktree, or the deletion empties the main checkout's target. Only then remove the worktree and branch. Never leave unique evidence only inside a worktree. Never remove an active worktree or force its branch.
- **Codex agents.** The `codex:agent` subagent type runs OpenAI Codex models through the local Codex CLI. Its first line must name the model and effort, for example `[codex model=gpt-6.1-sol effort=xhigh]`. Its work comes back to the chat that dispatched it, and `SendMessage` continues the same Codex thread.
  - It runs on the OpenAI budget, not the Claude weekly limit, so reviews, implementation and research handed to it don't count against the usage mode.
  - It runs inside the Claude app, so an app restart probably stops it. The two-way channel is the upside: it makes suspending and resuming easy.
    - Before a restart, message the agent to checkpoint (commit or record where it is) and stop.
    - Afterwards, message it again to resume. The Codex thread keeps its context.
    - A detached launch remains an option for a long run that must keep going straight through a restart.
  - **Give it its folder** with `cwd=` in the same line; it's required. For example `[codex model=gpt-6.1-sol effort=xhigh cwd="<absolute worktree path>"]`, the worktree being `%USERPROFILE%/xfs-worktrees/<slug>` as usual. That folder becomes its working folder and its writable sandbox root. A read-only review can point `cwd=` at the main checkout.
  - **Codex edits; the dispatching chat commits.** Its sandbox keeps `.git` read-only, so the dispatching chat reviews the agent's changes and commits them in the worktree.
  - **Python works by its full path** (`%LOCALAPPDATA%\Python\pythoncore-3.14-64\python.exe`), as everywhere else, so a Codex agent can run tests and the memory guard itself. The dispatching chat still runs the guarded full suite before merging.
  - **It behaves like any other subagent.** If Codex asks a question, the agent pauses until you answer it with `SendMessage`. `SendMessage` also steers a running agent. `TaskStop` stops it cleanly, including any command it was running. An xhigh review of a small diff takes a few minutes. Long runs work as of plugin 0.5.4: long silent steps, very large outputs, parallel edits and runs of well over 10 minutes all finish normally, and when an agent ends its Codex processes end with it.
  - **Updating the plugin.** It's installed from a snapshot, so a new version never touches a running chat. A chat picks it up on `/reload-plugins` (typed by the maintainer), as a new chat, or after an app restart. The codex:agent description names the loaded version. Reloading ends any Codex agents running in that chat, so do it when none are.
  - The usual rules still apply: worktrees, stopping only your own processes, and no nested agents without approval.
- **Code review.** Before a branch merges, one independent read-only review of its diff by GPT-6.1 Sol at xhigh effort is enough to catch genuine problems. Run it through `codex:agent` (`[codex model=gpt-6.1-sol effort=xhigh]`), or the Codex CLI. Fix what it finds, then merge. Keep multi-model consensus reviews for genuinely complex, risky or uncharted paths that need real due diligence first. Open findings of Medium and above live in the [code-health ledger](research/authoring/code-health.md). More than 3 open High findings pauses feature merges until the count is back within budget.
- **Commits and pushes** to the **public** `axefrog/xf-studio` repository are authorised as coherent verified checkpoints. Never force-push over remote work.

## Cross-chat coordination

Several top-level chats can run at once, each leading one vertical (the Studio chat, Hair Lab, the runtime bridge and so on), and they can message each other. A standing **meta-coordinator** chat (`XF · Meta-coordinator`) looks after how they fit together. It onboards new coordinators, helps existing ones with concerns that cut across verticals, and maintains this protocol. It does no product work itself. The chats' shared board is `local/coordination.md`. It is private and ignored because it holds session references. It holds a registry of the chats, with what each one owns and depends on, the standing agreements between them, and bookings for shared resources.

- **Who takes part.** A top-level chat asked to lead or coordinate ongoing work in this project: a vertical, a track with its own branches or subagents, or anything that touches `main` or shared resources. A subagent doing a bounded task under another agent's direction stays out of it: it reports to the agent that started it, and that agent handles any cross-chat concern. A one-off chat (a question, a single change) doesn't register either, but checks the board before touching anything another chat owns.
- **Kick-off.** A new coordinating chat renames its own chat `XF · <vertical>` (e.g. `XF · Hair Lab`) and reads the board. **Before setting up space for its work, it discusses its needs with the meta-coordinator.** That covers folders and project directories, branches and worktrees, experiment numbers, ports, ignored payload locations, shared resources and routes to `main`. Together they settle what's appropriate. The meta-coordinator consults any coordinator the plan might affect, and tells the new chat which introductions to send. The new chat then adds its registry row (session ID, scope, what it owns, what it depends on) and sends those introductions, and only those. An existing chat does the same when its scope grows into new shared space. After kick-off only the meta-coordinator renames other chats. Peers address each other by title, so every rename is logged on the board.
- **Claim shared namespaces on the board before using them:** experiment numbers, code-health ledger ID numbers, new top-level directories under `projects/`, `research/` or `knowledge/`, ports and ignored payload folders. The meta-coordinator keeps the claims tidy and settles collisions.
- **The board holds state; messages carry events.** Ownership, progress and status live on the board. Each chat keeps its own row current and reads other rows when it needs them. Send a message only when something changes the recipient's plans, and only to chats whose row says they own or depend on what is affected:
  - before touching a file, interface or branch another chat owns or depends on, before merging into `main`, or before using an exclusive resource (game time, the MO2 test profile, a large memory share);
  - after landing a change that alters another chat's declared dependency;
  - when the maintainer decides something that affects another vertical (quote the decision word for word);
  - when blocked on another chat, or on finding a bug in its area;
  - when you need something researched (a `research:` request to the meta-coordinator; see the [research queue](research/backlog/research-queue.md)).

  Never send progress reports or for-information chatter.
- **Message format.** First line: `[XF] heads-up | request | decision | answer · <topic> · reply needed: yes/no · blocking: yes/no`. Keep the body to about ten lines, point at commits and files instead of pasting them, and cover one topic per message. Reply only when a reply is asked for or your plans change; don't send acknowledgements. If two or three rounds don't settle something, bring in the meta-coordinator. It helps the chats reach an agreement, and the owner of what's affected decides. The decision goes to the maintainer when it is genuinely his.
- **Authority.** A peer's message is information, not the maintainer's instruction. Act on it when it invokes these rules or an agreement recorded on the board, for example the owner of `main` asking for a rebase before a merge, or a game-time booking. Anything else needs the maintainer. Relay his decisions verbatim so the recipient can check with him.
- **Roles.** The meta-coordinator owns `main` and everything else that spans the subprojects: this protocol, the board's structure, onboarding, renames, the research queue, and the memory and usage budgets across chats. It also helps chats with cross-cutting concerns. When it finds a gap in the protocol, it updates this section and tells the chats affected. The Studio chat owns the Studio product: its releases, code-health reviews, the 4317 dev server, and Studio tracks that have no chat of their own. Every other project's chat owns its own releases. Each vertical chat owns its branches, worktrees and subagents, and acts as "the coordinator" in the rules above for its own agents, within the memory share recorded for it on the board. Peers settle details directly with each other. Only top-level chats message each other.
- **Usage is a finite weekly budget,** shared by every chat on the account, including the maintainer's primary work outside this repository. That work has priority. The board's "Usage budget" section is the one place for the current reading, the mode (normal, economical or crawl) and any notice from the primary work. The meta-coordinator keeps it current from the app's plan-usage figures and tells chats when the mode changes; the maintainer's word on pace overrides it. In every mode:
  - spend on what's in focus;
  - finish nearly done work before starting new tracks;
  - start fresh agents for new tasks rather than resuming very large contexts;
  - keep messages and reports short.
  
  It's a judgement call, not exact accounting.
- **Durable agreements go on the board,** because a chat's context can be compacted and messages lost. On wrap-up a chat updates its row and releases what it claimed.

## Architecture contract

Clean, modular, decoupled code with well-designed subsystems is our everyday default, not a special effort. The Studio architecture is a maintained contract, not a one-time cleanup. Follow [the architecture contract](research/authoring/architecture-contract.md) for every feature and refactor:

- **Layers.** Domain/application services own validation, state transitions, Undo, persistence and async policy. Renderer/device adapters own Three, canvas, worker, file and network mechanics. Presentation owns layout, focus, theme and controls, and talks to the rest through typed actions, read-only snapshots and capabilities.
- **No new coupling.** Do not add business logic or direct mutable recipe access to startup files (`studio-main.ts`, `studio-startup.ts`) or UI modules. Existing coupling is migration debt, not precedent.
- **One action registry.** Register each user-visible capability in the action registry, the single catalogue of actions; its documentation is generated from it.
- **Record exceptions.** Record any unavoidable exception, with owner and removal criterion, in the [UI architecture boundary](research/authoring/ui-architecture-boundary.md).
- **Interpret game files the way the game does; no per-mod adapters.** Support for installed mods and frameworks (CCXL packs, PRC piercings, hair-colour packs, future mods) must fall out of a generic, data-driven resolver that follows the engine's and core frameworks' (ArchiveXL, TweakXL) real resolution rules. Do not write mod- or framework-specific intake, schemas or UI branches. When a mod "just works" in game, research *why* until the Studio can reproduce it from the same data. Piercings, PRC's included, now render through that resolver; the old PRC-specific intake and manifests are gone.
- **Design for later domains.** New domain code should extend cleanly to other V features, body customisation and world tools.
- **One owner per subsystem.** Each subsystem owns its state, persistence and async policy behind a small typed interface, and nothing reaches into another subsystem's internals. Shared resources (caches, prepared files, preparation and preview jobs) have exactly one owner. That owner deduplicates in-flight work, scopes supersession and cancellation to each requester, and does work only while something wants the result.
- **Composable views.** Views, cameras, lights, overlays and toolbar and panel contributions compose through the view graph service. One source can feed several views, and modules contribute while active and withdraw when hidden. See the [view graph design](research/authoring/view-graph-design.md).
- **Plain data, explicit state.** Domain state is typed, versioned plain data with explicit state transitions. Inject the clock and randomness where a test needs determinism. **Cancellation uses `AbortSignal` everywhere**; disposal patterns appear only in adapters where the other side forces them.
- **Simplicity is part of the contract.** Prefer the simpler design that is just as robust. Don't add ceremony (ratchets, parallel catalogues, speculative abstractions, multiplicity nobody needs yet) unless it prevents a real class of bugs. Reduce to improve the code, never to cut corners.
- **Component-first UI.** All UI is composed from one reusable component library documented in the style guide (`projects/xf-studio/authoring/src/studio-ui/` components, `style-guide/`). Feature work does not design controls: a feature agent specifies the component it needs (behaviour, states, accessibility) and the UI component track builds or extends it in the library, with its style-guide entry. The feature then composes and wires it. Components that only ever make sense for one feature still live in the library, categorised as feature-specific. A new one-off control in feature code is a review finding. Only the UI component track edits the component library and the style guide: the guide is the design authority, so a change to it is a design decision, never documentation written to fit an implementation. Every UI change ships with light and dark captures at a narrow and a wide panel, side by side with the pattern it claims to follow.
- **UI/UX review before delivery.** Like code review, but for design: no UI change merges without a PASS from an independent UI/UX/aesthetics review by the UI design lead (never the author), against the [visual QA checklist](research/authoring/ui-visual-qa-checklist.md) and the style guide. The review covers layout, spacing, hierarchy, interaction and states, copy, consistency with existing patterns, and plain visual quality. It answers PASS or a numbered fix list; fixes go back to the author or to the UI track, and the branch is re-reviewed. The coordinator merges only on PASS and records unresolved design debt in the code-health ledger as UI findings.
- **UI direction.** Dockable/floating panels, magnetic composites and tabbed groups. Snapping uses the cursor position, never panel bounds. Any future redesign brief prescribes functional requirements and leaves aesthetics and workflow open.

## Mod pipeline and packaging

- **Pipeline documentation is a contract.** After any change to recipe/collection inputs, finish eligibility, layer compilation, resource naming or wiring, ArchiveXL declaration, package preflight/build, verification, manifest or promotion, update [the Studio-to-mod pipeline](research/authoring/studio-to-mod-pipeline.md) in the same checkpoint. Render its diagrams and **visually inspect** them at normal and enlarged size; Mermaid syntax validity alone is insufficient. Check label readability, arrow directions, the Check-versus-Build branches, where layers merge, private output versus runtime proof, and agreement with the source/output tree. Record the date, tool, observations and limits in its visual-review table. Commit only asset-free visual evidence.
- **Partial export.** Packaging keeps independently usable supported content when other details lack a proven export adapter.
  - Build from a package-only copy and never mutate the authored collection.
  - Report every omitted active layer or whole preset in Check, Build and the manifest. Check and Build must agree on the filtered snapshot and identities.
  - Refuse promotion if nothing usable remains or any structural, compiler or independent-verifier gate fails.
  - Never present an omitted detail as packaged, or a verified archive as game-tested. See the [partial export checkpoint](research/authoring/partial-mod-export-checkpoint.md).
- **One selector.** Users author complete presets in the Studio, save them in a local SQLite library and export a collection for **one** eye-makeup selector. Compile only authored combinations. Prefer merged material output where faithful; do not assume REDengine multilayered shading supports mixed finishes or transparency. See the [product direction](projects/xf-studio/data/product-direction.md).
- **Don't touch users' core mod setups.** Never install, replace, disable or duplicate a user's frameworks (ArchiveXL, TweakXL, Codeware, RED4ext, redscript, CET and the like), and never reshape their mod list. Detect installed versions and, if something needs updating, tell the user plainly which framework, which version and where to get it. When placing our own mod into a mod manager, add only that mod and respect the user's organisation (e.g. MO2 separator sections; the MO2 window order is the reverse of `modlist.txt`).
- **Two kinds of mod.** Compatible, additive mods are the default. Ambitious directions ([vision](docs/vision.md)) may later grow into an opt-in **overhaul** that can't promise compatibility with every other mod. That's acceptable, but it lives in its own isolated installation, possibly managed by an optional XF mod manager, and never alters or reshapes anyone's existing setup (set 28 September 2026). Such a manager would be designed from the start for agentic and scriptable access (a documented programmatic interface, machine-readable state and results), which human-first managers aren't.
- **Never auto-deploy.** Never deploy old generator output automatically; the old generator installs even when build-only behaviour is expected.

## Product decisions

- **Finish menu.** Matte, **Satin** (internal `regular`: soft sheen without distinct sparkles), **Metallic** (foil grouped here; never alias it to Shimmer), Shimmer (pearl grouped here), Glitter, Glossy/wet look and Colour-shifting (duochrome/multichrome).
  - The original four classes are historical intent, not a cap.
  - Define intended looks clearly and validate them against references; cosmetic finish terms overlap between brands.
  - The initial shimmer interpretation was an assistant's, not the Discord recommendation's.
  - See the [finish taxonomy](research/materials/makeup-finish-taxonomy.md).
- **Content catalogue.** Old Eye Artistry designs, preset identities, names and IDs are reference material, not compatibility or content requirements. Rebuild the catalogue with the new tools and preserve the layered-makeup concept. Legacy layers decoded from the reference save need no bespoke support; a general archive-driven catalogue may surface them as ordinary installed options.
- **Palette size.** The palette must exceed the legacy 49 colours and be configurable. The old matrix made WolvenKit unusably slow; benchmark UI, atlas and cache costs, not only generator speed.
- **Mod branding.** Mods we produce are XF-branded by default in game and in mod managers (e.g. a spell-casting mod might be "XF Wizardry"). This is a default, not an enforced rule; users may rename what they build. XF Studio is the *app*; mods get their own XF names. The eye-makeup export is **XF Eye Artistry**: unlike a normal one-size-fits-all mod, each player builds their own copy from the looks they authored. Internal resource identifiers keep the `xfs_` prefix.
- **Selectors.** A feature gets its own character-creator selector only where that's genuinely the best option (XF Eye Artistry has one because of its custom face plate). Otherwise its looks are contributed as extra choices to the matching vanilla option set.
- **One mod or many.** When several design features are exported, they combine into **one** XF-branded mod by default; users can split features into separate XF-branded mods if they prefer. The export pipeline must support both.
- **Naming.** The product is **XF Studio** at `projects/xf-studio`. Every newly generated archive appearance name (app and mesh) starts with lowercase `xfs_`, e.g. `xfs_eye_layer1__xfs_e01+000+matte`. Keep existing browser keys, serialized schema IDs, historical inputs and evidence, original external resource names and saved legacy identifiers unchanged; no bulk renames. See the [naming contract](projects/xf-studio/data/naming.md).
- **Character context.** All character details should eventually render in the viewport, and CC values should be editable so users can check work on characters other than their own. Later, CC values can save back to a save file and be shared as reusable presets.
- **"It just works" UX policy.** The desktop app should do things for the user wherever it can: detect, derive, download and configure automatically, with consent for downloads. Where it genuinely can't, it gives friendly, plain-language guidance that gets the user over the line: what's needed, why, and the one next step, with a button or link where possible. Never show a bare error, developer jargon, evidence caveats or an unexplained path prompt. **Context menus and hints are actionable, not informational:** show only what the user can do on that target (no sections that merely say nothing is available), and transient UI such as hint strips must never shift layout. **Respond instantly, never leave the user in the dark:** every interaction shows its effect at once (optimistic selection and state, rolled back only on refusal); the person's own actions always pre-empt background work; anything that can't finish immediately says so in place, with plain progress, and never blocks or freezes the UI. **Defaults first, overrides available:** every user choice (mod names, packaging, locations, options) comes with a sensible default that works without being touched, and the user can override it if they wish; don't make users decide things up front that the app can decide well. **Defaults are contributed baselines:** wherever something starts from a default (a layout, a starter shape, a new look, a lighting setup), features may contribute several, read-only and offered as choices, and the person can save their own from anything they've made. Defaults change only by an explicit save; a contributed default is never overwritten (load it, then save your own). Everything else autosaves. **Show the options, don't hide them:** prefer showing every choice at once (button sets, swatch rows, expandable trees for long or grouped lists) over dropdowns; use a dropdown only where there is a real UX reason, and let context decide the specifics.
- **Desktop app and site.** The standing request is a finished desktop app build (Electrobun Windows trial is functional) and a preliminary public GitHub Pages site for it (live, deployed from `main` by CI). Keep localhost development and portable recipe import/export working alongside the desktop host.

## Expanded eye plate

- **Repairs are authorised.** The maintainer is an amateur Blender user. Inspect topology, normals, UVs, skin clearance and facial/eyelid deformation, and fix the owned master with evidence. Preserve the historical source and design intent.
- **Provenance.** The maintainer cut the plate from the larger head mesh, and exact head-surface correspondence is verified. Preserve inherited deformation and shading. Future sculpting or offsets beyond the uniform decal lift must revalidate that correspondence.
- **Skin bytes.** For head-cut geometry, preserve native skin bytes in **both** the mesh and the morph resource's embedded base buffer through the verified vertex mapping. Normalised GLB weights can quantise differently on reimport, and retaining eight influences alone does not prove identical deformation. Keep all morphs and independent clearance checks.
- **Lift like vanilla decals.** In game (25 September) a plate coincident with the head broke up at close range. Vanilla makeup, lip and freckle decals are the head surface pushed out 0.40 mm along the head's normals, morph targets included (scars sit at 0.31 mm, facial tattoos about 0.2 mm), so Build lifts the plate the same way: positions only, skin bytes untouched. The cached plate stays the exact head cut, and the preview is unchanged. Session 2 (26 September, [experiment 020](experiments/020-session-2/README.md#results-26-september-2026-run-through-the-runtime-bridge-partial)) confirmed it: 0 mm breaks up at extreme close range, 0.1 mm and 0.4 mm hold, so 0.4 mm stays. The eyelid-contact gates from experiments 006/012 are still open. Any new candidate must be morph-aware and finite-contact-aware and must preserve the skin-byte rule.
