# Recipe-driven Glitter material boundary — offline only

24 September 2026. This follow-up uses a valid generated `xfs/recipe-10`
`uv-cell-direct-3` layer, then calls XF Studio's **actual** `parseRecipe` and
`raster` functions at 1024². The mask bytes and authored pigment colour thus
come from recipe semantics. The facet maps deliberately do **not** claim to
reproduce the browser optical model. The original [synthetic fixture](README.md),
[2.31 shader trace](shader-and-minification-audit.md), and
[authoring bridge](authoring-export-bridge.md) define the stock channel contract.

## Reproduction and provenance

From the repository root, with Bun, Python/Pillow and WolvenKit 8.17.4:

```powershell
python experiments/009-glitter-game-fixture/recipe_adapter.py --check
python experiments/009-glitter-game-fixture/recipe_adapter.py --check --serialize --pbr-template C:/local/mesh_decal.mt --emissive-template C:/local/mesh_decal_emissive_subsurface.mt
```

The two binary templates must be extracted unchanged from installed Cyberpunk
2077 2.31, with adjacent WolvenKit JSON. Their SHA-256 digests are pinned in
the [original fixture](README.md). `--check` compares against the tracked
[map report](recipe-adapter-result.json) and
[binary report](recipe-adapter-serialization.json). Use `--recipe PATH --layer
ID --size 512|1024|2048` without `--check` for a different local study; its
generated report will reflect that recipe. Do **not** commit personal recipes,
generated pixels, XBM/MI binaries or extracted templates. All outputs are
ignored in `generated/recipe-adapter/`. The tracked sample is constructed
in [recipe-mask.ts](recipe-mask.ts) from `initialRecipe`, with an opt-in
recipe-10 direct-3 layer; `--recipe` accepts an existing portable recipe.

The `xfs_` pixels, polygons and placement are newly generated by this study.
The independent profile uses 2,400 candidate triangular/quadrilateral facets,
0.6–1.7 source pixels in radius at 1024, seed 20260924 and a sparse emissive
subset; 953 candidates land in the authored mask. The polygon/tilt question
was informed by island_dancer's explained axial-gradient Substance approach,
but this fixed-normal comparison does not copy the graph, map pixels or full
height-to-normal sequence. The community-learning record must link this study
when integrated; no reuse permission for the `.sbs` is assumed. The generated
2.31 templates are CDPR game resources inspected locally with WolvenKit, not
redistributed artifacts.

## Exact coverage versus lossy optics

The source recipe's Glitter layer has 5,754 nonzero atlas texels, of which
3,771 are at least half covered; its exact alpha hash is
`03ba8012d01de4d342cafcdd1651c335606ba35a39016bcb43525e1a015705ab`.
The adapter writes its RGB pigment from the layer colour and square-root
encodes alpha for the inspected `mesh_decal` squared-coverage equation. It
passes that same coverage as `NormalAlphaTex`; roughness and metalness each
occupy a separate red scalar map. Independently seeded resolved polygons set
tilted R/G normals and scalar contrast. A separate sparse red emission mask
uses `mesh_decal_emissive_subsurface` and would need a second plate component.
It remains light-independent glow, never reflected glitter. These are the
stock material channels identified in the installed 2.31 shader cache.

**No direct-3 optical setting controls the generated facets.** The browser's
`density`, `fineShare`, `strength`, `seed` and facet colour are retained in the
report for provenance, while the candidate has its own named profile and seed.
Silently reusing those browser fields for a different distribution would
change authored meaning and still fail to preserve per-fragment light/view
evaluation. The generated MI/texture files are a decision fixture only; there
is no recipe-to-game adapter in the production compiler and its Glitter guard
must remain. This sample proves a recipe mask can feed the checked stock
resource chain, not that it produces the intended cosmetic finish.

In the current browser source, direct-3 evaluates a 2304-cell fine population
and a separate sparse 768-cell population with 3×3 neighbourhood searches,
UV-derived screen footprint, deformed tangent frame and a light/view half
vector. The inspected game `mesh_decal` pass samples *one* filtered R/G normal
at the pixel; the emissive pass samples a mask and material constants without
a light/view vector. Map serialization cannot transfer the browser's
per-fragment selection or its statistical footprint attenuation into those
programs. The 953 accepted polygon candidates here are placements inside
the mask, **not** a count of visible glints.

The imported six XBM resources have the expected current-game gamma,
compression and mipchain flags. Two MIs round-trip with identical parameter
values and all their local texture references resolve. The decoded base-mip
pigment alpha, squared, differs from partial authored coverage by a mean
`0.00580`; the decoded emissive map has no byte>8 texels outside zero-coverage
shape pixels. These are serialization/channel checks, not a render.

## Scale loss and decision

BOX reduction of the **source maps**, measured inside pixels whose reduced
recipe coverage remains at least half, gives:

| Atlas tier | Covered pixels | Strong tilted-normal fraction | High-contrast emission atlas fraction |
| ---: | ---: | ---: | ---: |
| 1024 | 3,771 | 67.1% | 0.0417% |
| 512 | 949 | 43.7% | 0.0301% |
| 256 | 238 | 15.1% | 0.0122% |
| 128 | 60 | 0% | 0% |
| 64 | 15 | 0% | 0% |

Thus this actual recipe-shaped test loses the resolved PBR tilt and bright
emissive accents rapidly under simple minification. It does not establish
the exact game transition distance: the CLI exposes the compressed base mip,
not decoded lower mips, and screen footprint, lighting, sampler selection and
TAA also matter. The browser evaluates UV-stable facets against current light
and view per fragment; neither tested stock decal program consumes a facet
distribution at the screen pixel footprint. A larger baked atlas can shift
the loss threshold but cannot reconstruct reflections of several filtered
facets from one averaged normal. This is a decisive **rejection of parity and
automatic Glitter export**, while retaining the candidate as a bounded
stylized comparison for the eventual single batched game session.

Before any game claim: place the two material states on a native-weight,
morph-correct plate, validate all references/components and clearance, then
compare close and face-framed views under independent light and camera sweeps,
dim light, blink and repeated Off switching. No game was launched here.
