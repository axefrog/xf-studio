# Brown-eye compiled shader and gaze-source trace

25 September 2026. This is a second, offline checkpoint after the [source-input probe](README.md). It inspects the installed Cyberpunk 2077 2.31 **compiled** `eye_gradient` programs and the native eye mesh/facial rig. It changes no Studio, game or MO2 files. This describes a candidate template variant, not proof of the exact live runtime pass, final eye appearance or permission to distribute source assets.

## Exact source and selection

The fixed `brown_eye_gradient.mi` SHA-256 `3dab26626dece44d46811c00504d75a65971bbdfcf2d72871324906cb896c676` inherits `base/materials/eye_gradient.mt` SHA-256 `348ec8d2b88288dec4fea5dca69f4d15bcc0c2c3c0b89111bf4f922fdb0f36f5`. Its inspected `usedParameters` map `Albedo`→register 0, `Normal`→1, `Roughness`→2, `NormalBubble`→4, `IrisMask`→5, `IrisColorGradient`→6, `Specularity`→22 and `RoughnessScale`→23. The template also maps the other optical scalars reported by the first probe. These register identities come from the serialized template, not guesses from resource names.

The installed `engine/shader_final.cache` is 161,804,693 bytes, SHA-256 `339145371a3b5aaa08eb4ef82d558f445b632e28603ee0f3b4860270dfc3ccfa`, RDHS version 10. A bounded parser finds 100 `eye_gradient` compilation records, 10 with `VF: MeshSkinned`, including `renderstage_gbuffer_regular` pass 0 with vertex GUID `1226803013347725086` and pixel GUID **`10020572278408962832`**. That pixel DXBC is 7,177 bytes, SHA-256 `cf4b1423c4c1241ff81434e58e65a0b7ac1b9eb75353c13613b05e13fff533c7`. Pass 1's different pixel GUID `14382710511169564885` is a 3,105-byte selection/debug path, not the colour arithmetic below. The template compilation material GUID is `15633238436580003019`. Runtime pass selection remains unobserved.

Windows SDK 10.0.22621 `dxc.exe -dumpbin` exposes the selected pass 0 DXIL. Numbered values here refer to the ignored local disassembly produced by the reproduction commands below:

| Compiled operation | Direct observation and implication |
|---|---|
| Gradient lookup | The shader samples `IrisMask` (template register 5) at its computed eye UV `%216,%217`. It takes sample **R** `%359` as the X coordinate to sample texture `t55` with sampler `s10` (`%365`). The Y coordinate is `(material register 6 + 0.5) / 512` (`%361`–`%365`), linking the template's `IrisColorGradient` parameter to a row of the runtime gradient texture. This establishes the lookup coordinate in this pixel variant. |
| Colour composition | The sample's RGB `%366`–`%368` is blended with `Albedo` RGB using `IrisMask` **A** `%360`: `albedo + (gradient − albedo) × maskAlpha` (`%369`–`%377`). The result is square-rooted before the G-buffer RGB writes (`%461`–`%463`, output 0). Thus the profile does not simply replace the full eye diffuse. |
| Roughness | The shader samples `Roughness` (template register 2) at the original interpolated UV `%19,%20`, takes **R** `%386`, multiplies it by `RoughnessScale` register 23 `%388`, then writes the product `%389` to G-buffer target 2, G. This independently agrees with the earlier compiled `eye` variant's R-channel finding; it does not justify experiment 013's provisional G-copy as game parity. |
| Other optics | `Normal` uses packed R/G and reconstructs Z (`%218`–`%232`), while `NormalBubble` is another packed R/G sample (`%247`–`%265`). Both sample computed coordinates, and the bubble uses `BubbleNormalTile` register 14. The code reads the horizontal eye angles (10/11), radius (12), refraction index/amount (7/8), parallax (13), iris size (9), egg/iris coordinate controls (15–20), `Specularity` (22) and the fields above. `Blick` (3), `BlickScale` (21), `SubsurfaceFactor` (24) and anti-lightbleed registers 25/26 do not appear in this selected G-buffer pixel program; other passes or later lighting may use them. |

The compiled pixel shader performs one hardware `sample` from `t55`; it does **not** contain the three serialized `CGradient` stops or a visible stop-interpolation loop. [Microsoft's DXIL reference](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst) confirms that this operation takes a texture handle, sampler handle and coordinates; the shader call alone does not state the sampler's filtering. The cache and material template do not expose the generated gradient texture's pixel values, format, colour-space conversion, row assignment or sampler filter/address state. Therefore the exact interpolation between the three stops remains **unresolved**, despite the known mask-red lookup coordinate and alpha blend. A discriminating offline next test is to locate the game/WolvenKit gradient-atlas construction and capture the exact generated row and sampler metadata; if the engine builds this at runtime, a controlled in-game two-stop sentinel profile plus frame capture or GPU texture inspection would distinguish linear/sRGB interpolation and filtering. Do not bake a brown iris from raw stop bytes yet.

## Native eye and gaze references

The installed female `he_000_pwa_c__basehead.mesh` SHA-256 `4d5dfa91efdf54485c5637ad34d64c32ae2f02cad7c52915062f3a0ec0f7aa19` has 57 `boneNames` and 57 `boneRigMatrices`. Both `l_J_eye_JNT` and `r_J_eye_JNT` occur (mesh indices 53 and 55). Every one of its 57 names occurs in the installed sibling facial skeleton `h0_000_pwa_c__basehead_skeleton.rig` (SHA-256 `61a72dc075968394b14063a3236669ee6b1f81ed6c52f53363ee5b0cc4597777`); in that rig the eye joints are indices 9 and 10, both parented to `Head` at index 6. The sibling eye mesh and skeleton were extracted from the same `basegame_4_appearance.archive` whose SHA-256 is recorded in the input probe. Mesh bind matrices are **not** treated as gaze pivot coordinates or proof of a linked runtime rig.

The existing [female idle investigation](../../research/animation/cc-idle.md) identifies the installed facial skeleton, facial setup and `ui_female_face.anims` as offline sources for eye movement. Its [facial-bake evidence](../../projects/xf-studio/authoring/evidence/idle-face-bake.json) reports changing `l_J_eye_JNT` and `r_J_eye_JNT` tracks in a project-authored solved preview clip. This establishes compatible **named source references** without launching the game; it does not validate the new native GLB's joint transforms against the baked clip, the game UI animation graph, or the actual gaze/blink result. A next offline gate is to assemble the native eye skin with the same pinned facial rig, compare both eye-joint bind/world transforms and eye vertices across the 663 sampled idle frames, and check eyelid/plate contacts. A private isolated viewport and eventual matched runtime capture remain separate gates.

## Reproduce and limits

From this worktree with Bun and Windows SDK `dxc`, run:

```powershell
bun experiments/014-native-eye-gradient/inspect-cache.ts 'PATH_TO_GAME/engine/shader_final.cache' 'PATH_TO_WORKTREE/experiments/014-native-eye-gradient/generated/shader'
& 'C:/Program Files (x86)/Windows Kits/10/bin/10.0.22621.0/x64/dxc.exe' -dumpbin experiments/014-native-eye-gradient/generated/shader/10020572278408962832.dxbc > experiments/014-native-eye-gradient/generated/shader/gbuffer-full.ll
```

The cache reader verifies the full source hash, footer, region boundaries, stages and compilation names before extracting pixel programs. Two independent runs produced byte-identical `index.json`, SHA-256 `a936df40da909f4dd8cb70cf8e88e0161e2c7856c40a808b624f9e12c480b5f8`; the selected pixel bytes also matched on repeat. The installed `dxc.exe` SHA-256 is `e51ba98aee7656b05ecea156107398d2b62224eb185d90d0fea9d45d62733ad5`. The eye mesh/rig were separately unbundled and serialized with the hash-pinned WolvenKit CLI 8.17.4, which produced exact source hashes and the 57/57 name check above. All DXBC, disassembly, game resources and serialized JSON remain beneath ignored `generated/`; only the parser and written findings are tracked.

This study does not establish the final colour or lighting, generated gradient-row bytes, full renderer interpolation, native gaze assembly, effective archive winners, safe eye plate or game-tested appearance. It made no game launch and did not touch a saved character or active draft. [Community credits](../../docs/community-credits.md) cover game source, WolvenKit and Windows SDK tool use.
