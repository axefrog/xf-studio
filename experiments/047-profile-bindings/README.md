## 1. Outcome and scope

In one tab, three Presets panels can follow or pin to three different scenes, choose and edit their looks independently, and retain their own identity through docking, Undo, tab switches and restart. Every panel explains what it edits; missing targets never cause a silent replacement. Panels is a dockable picker, with the same commands available through the palette and action registry.

Phase 3 also owns the deferrals explicitly named by the design's **Built in** notes: recorded panel addition/removal and binding changes; several controllers per type; look documents needed by those controllers; History's other recent scopes; captures for shell menus beyond the context menus already captured. Phase 2's three Choose routes are extended, not rebuilt. The full header subject slot/profile flyout remains phase 5 (044 D9), Duplicate tab UI remains phase 6, and simultaneously drawn 3D views remain phase 4b. The existing 3D pane subject choice stays and gains recovery states; no replacement profile header is introduced here.

The architecture and [visual QA checklist](../../research/authoring/ui-visual-qa-checklist.md) apply. This document specifies behaviour and access; the UI component track writes the style-guide entries before implementing controls, and the UI design lead owns their appearance and independent PASS. No feature author edits the component library or guide to fit a one-off implementation.

## 3. Service and identity contract

### 3.1 Session operations and dock policy

Extend `ProfileSessions`, not a parallel panel store. Proposed registered action names are `panels.add`, `panels.show`, `panels.remove`, `panels.setBinding`, `panels.reveal` and `panels.openPicker`; reuse an existing equivalent if implementation finds one. The action descriptor records explicit `profile`, `tab`, `instance` or `type` and captured structural version as appropriate, capability/reason, Undo policy and persistence effect. `add` allocates a fresh ID; `show` reopens a retained instance; `remove` parks it; `reveal` only activates/expands an already open instance. The picker and dock are clients of these operations. A type-level Hide operation parks its open instances as one atomic structural step; one instance's Remove parks only that instance.

“Remove panel” retains its binding, serializable instance state and remembered place, so reopening is lossless. It is not hard deletion of the saved record or of the underlying subject, look or view. Unmounted controllers release their subscriptions and handles. If the last controller goes while writes are pending, existing outbox ownership retains them until acknowledged. Undo reactivates the same instance; Redo parks it again. Only a **new** instance gets a new ID. Closing a 3D **pane** parks its instance and keeps its view; the existing Close view operation removes the graph view. Preserve this distinction in commands and wording.

Membership changes apply coherently to both size classes: adding/restoring places an instance at its remembered place in each, else its contribution's factory slot; Add another goes beside its type's sibling, else factory. Neither action resets a tab to its contributed default. Counts/checkmarks refer to the displayed size class; after the person's subsequent independent arrangement in either size, the mixed state can describe that accurately. Collapsed/floating/background-tab instances count as open. A retained or withdrawn instance does not activate a module. There is no count cap, apart from existing validated storage/resource constraints with plain reasons.

Record field/instance-level structural changes and the placement needed to reverse them, rather than checkpointing every tab's whole arrangement. Reuse the session's held-content/replay mechanism, but separate recorded membership/binding fields from unrecorded placement. Undo of a binding change must never move a panel. Undo of an add removes only that instance; Undo of a remove restores its last remembered home without moving surviving neighbours back to an old layout. Close-tab/reopen/reset snapshots still contain the whole tab and all retained instances. Operations, their history step, focus cleanup and notifications settle atomically; replay validates the whole result before publishing. Seeded interleavings must cover this boundary before UI wiring.

Dock IDs become instance IDs end to end; the catalogue stays keyed by **type**. Use a typed projection from instance to type/meta/default slot. Eliminate first-match type lookups in normal operation. The historical `head`/`view.<id>` aliases stay only at named compatibility/evidence boundaries, with a deterministic mapping to a view's instance. Preserve existing stored IDs and parked/last-place records; this is not a new profile migration or a legacy-preference rewrite.

**3D view row.** Its instance list names the existing graph views. Show/Remove operate on their panes; Add another must create a new graph view and its pinned pane atomically through the session's existing view operation, not create an unbound `view` instance or a second pane identity for the same view. Reuse the captured scene/subject choices: visibly default to sharing the named eligible scene (044 M2), with New scene beside it; when there is none, reuse Open a 3D view's default-V/empty choices. Cameras and other unshared nodes get fresh IDs. This still draws one view at a time. A view pane's graph identity is fixed, so U1's general binding selector is for bindable inspectors; the pane keeps its scene subject choice rather than allowing its identity pin to be rebound.

### 3.2 Bound editing contexts

Extend the existing keyed `LookSessions` ownership with an on-demand map of editable look contexts (document, geometry, feature action handlers, selection and look history). Each `LookRef` has exactly one such context while wanted. Several panels on the same look share it; panels on different looks never share mutable editor state. Do not make a second full Studio/preview core, renderer or outbox per controller. Keep composition as wiring; the map and routing belong to application/library services.

Give every factory an instance identity and a scoped read/action facade. Frames, collection summaries, feature facades, context queries, continuous controls, imports/file completions, presets and capabilities read the same resolved context they dispatch to. `preset` edits use the named collection/look. A scene-bound Presets choice calls `scene.setLook`; a directly look-pinned Presets choice records `panels.setBinding` to the chosen look. A scene without a look lists that profile's collection choices. A look without a scene remains editable and visibly named; no hidden scene is created. Character panels similarly acquire their target's existing keyed character context, not the drawn V's facade.

The single drawn 3D view continues to drive the renderer/editor attachment. Binding an inspector must not call `heads.show`, switch tabs, steal the canvas or allocate a hidden head. Multiple UV panels need independent canvas/input adapters bound to their instance and look; share immutable geometry/resources where appropriate, not a single DOM canvas between simultaneous panels. Reuse the preview job owner: requesting an off-screen edit does not create another raster scheduler, eager full-look rasters or thumbnails for every picker candidate. Raster demand is cancellable and budgeted, the person's latest edit pre-empts background work, and only current complete results publish. Several looks rastering in parallel remains phase 5; data editing and target labels must respond immediately in phase 3 while a demanded image updates in place.

Controller lifetime and data lifetime differ. Mount wanted instances of the shown tab; release them on removal, tab withdrawal, experiment withdrawal or page abort, keeping serializable state in the session. Retain one shared edit context while any panel, drawn editor or in-flight captured action wants it. Abort stale work through requester `AbortSignal`s; one panel closing cannot cancel another's shared load. Release pending writes through `LookSessions`, never discard them. Instance-scope DOM IDs, anchors, scroll/folds, search, pending status and control-run IDs; shared same-look selection remains the existing look memory. Guidance's type-level entry resolves to a matching visible instance deterministically, without aliasing its actual DOM ID.

### 3.3 Resolution, capture and recovery

Keep pure binding resolution and separate target-status descriptions. Offer only target kinds the panel's declared context can use: view controls require a view, scene controls a scene or view, subject panels accepted subject kinds or a suitable scene/view, look panels a look or a suitable scene/view. Evaluate constraints at listing and again at dispatch. Use the subject registry/owner labels, not a character-only branch in the selector. Follow-focus stays within the instance's own tab. Explicit pins may name compatible session targets outside that tab, and the header must say so.

A capture has two parts: the existing frozen semantic target/revisions and a structural destination (profile, tab, instance, binding version/identity). Validate the origin still exists and has not been reset, replaced, rebound or withdrawn, as well as the chosen candidate and relevant document revisions. A focus move alone does not invalidate an open menu or retarget its command. A scene generation change, removed target, external revision, or old callback after release refuses `missing_target`, changes nothing and records no history. Unrelated acknowledgement/progress must not invalidate a capture. A binding selector changing its own target validates the old structural destination plus the chosen new candidate, rather than requiring the old dangling entity to exist.

| Resolver/owner state | Presentation and permitted route |
|---|---|
| No eligible view in this tab | Existing Open a 3D view choices at the feature's primary owner; other instances point to that owner. Selector also offers a compatible direct pin. No fallback into another tab. |
| Scene has an unassigned subject/look | Existing Show which V?/Show which look? choices, preserving the captured scene and incrementing its generation through the scene owner. Other panels on the same missing target point to the matching chooser. |
| Direct pin to missing view/scene | Preserve the pin. Name what is missing; Follow focus and Choose… are available. Reopening/Undo of the actual view can make it resolve again. No fabricated Restore for an absent graph entity. |
| Direct subject/look pin deleted or removed | Preserve identity. Follow focus, Choose… and owner-backed Restore while retained. After purge, omit Restore and offer the remaining recovery actions. |
| Existing view/scene references removed subject/look | Keep the reference and identify it as removed/deleted, rather than presenting it as an unassigned slot. Restore acts on that document; Choose replaces the captured scene target. The original returns automatically after restoration if no replacement was chosen. |
| Subject removed from profile membership only | Existing scenes and pins keep showing it (design §1.4); it leaves the profile's new-choice list. Do not call it deleted. |
| Wrong kind/constraint or contribution unavailable | Plain explanation from the rule/registration; usable alternatives shown. Preserve the pin and saved unknown state. Never invoke the last valid controller behind an unavailable pane. |
| Recovery pending, conflict, locked/newer data or missing decoded save | Preserve the existing owner-specific recovery/readonly/conflict controls and reasons; a missing-target wrapper must not hide them. No Restore that bypasses outbox conflict/recovery checks. |

Chooser ownership is keyed by the missing entity/scene and route, not the word “Presets”. Prefer a matching open owner in this tab, then a matching retained owner; otherwise add a correctly bound owner through the recorded action. Follow the chosen owner's instance when revealing it. A panel without any compatible contribution can use its selector directly. Recovery controls and owner pointers have non-mutating reads and no hidden instance creation during paint.

## 8. Risks, ranked

1. **Wrong-target edits through a global facade (High).** A correct resolver is insufficient if snapshot, capability, preset/file handler or frame still reads the drawn look. Mitigation: P3-ii before visible multiplicity; G1 uses real controller actions across multiple collections, not test-side named service calls only. Maintain one context/history owner per look.
2. **Undo clobbers later arrangements or revives a removed controller (High).** Current held-content replay deliberately carries unrecorded state; recording all of `@content` naively makes add/remove/bind undo unrelated drags, or replay preservation erases the recorded mutation. Mitigation: explicit membership/binding fields and minimal placement deltas; independent seeded model and close/reset/flag/restart interleavings in i, before picker UI.
3. **Late menus/controls/files edit a replacement (High).** Existing semantic captures do not alone fence the panel's binding/lifetime. Mitigation: structural destination generation plus semantic/revision checks, released on AbortSignal; G2 includes remove/reopen under the same ID and rebind away/back. Candidate refresh must not silently choose another entity.
4. **Context/controller multiplication hurts memory or responsiveness (High).** Documents, histories, DOM trees, per-panel searches and UV adapters can grow while GPU residency looks unchanged. Mitigation: demand ownership, shared contexts for equal look/subject, requester cancellation, no head per pin, no duplicate raster scheduler; G5 measures CPU acquisition/paint, resource counts and lifetime rather than only GL objects. Keep outbox pending ownership visible and bounded by its existing budget.
5. **Experiment withdrawal destroys authored state or leaves stale capabilities (Medium–High).** The incoming live-defaults API and instance-aware dock touch common registration assumptions. Mitigation: §6 agreement, availability separate from removal, registration-generation checks, unavailable saved-default/panel tests and flag-off/restart/on proof. Do not guess the incoming API's names or duplicate its owner.
6. **Recovery looks like an empty slot and replaces restorable work (Medium–High).** Boolean `exists` loses removal/tombstone distinctions; wrappers can hide Restore/conflicts; a type-based owner pointer can open another scene's Presets. Mitigation: status matrix and exact owner-instance key, owner-backed restore commands, retention/revision checks, real last-preset and membership-detach regressions.
7. **Defaults carry repeated panels but lose external/empty pins (Medium).** Existing `fragmentBinding()` (`app/profiles/layout-fragment.ts:236`) drops pins to external views/scenes; unfilled subject/look slots omit their pin (`:313`). Keep this existing default-fragment behaviour explicit and tested: defaults are substitutable baselines, not a byte-exact backup of cross-tab bindings. Live authored sessions must retain their pins unchanged. U8 discloses the affected panels before Save and the Leave-empty effect before substitution; never present the default as an exact binding copy. Preserving external pin identity would need a separate design change, not a hidden phase-3 rewrite.
8. **Visual crowding and ambiguous duplicate names (Medium).** Header target/policy, stage tags and count/actions compete at 300 px; several identical empty cards are annoying. Mitigation: component-first U1–U6, target-specific ownership, readable parent disambiguators, four-way app/guide captures, keyboard/overflow/focus cases and independent PASS. Correct the affected generic Undo/empty guide wording before composition.
9. **Inherited GPU timing/memory variability misreported as a regression or a pass (Medium).** G4 passes are real, as are the later cold-warmup outliers and T-h's bimodal OS readings. Keep raw trials and baseline comparisons, preserve GL/identity/cancellation gates, and report unresolved variance. New UI measurements cannot prove game rendering or erase the cold-different-V cost.

It also found one High and two further Medium lifecycle defects: a queued tab switch could save B into A, rapid off/on reused stale specs for replacement controllers, and withdrawal during a drag could reinsert an unavailable panel. The follow-up replaces those mechanisms with two rules.

**One owner and one safe point.** The shell queues registration snapshots; `ViewPanels` owns the reconciliation with tab navigation. It captures the destination tab and arrangement, cancels pending/active dock gestures, transfers ownership to that explicit tab, and holds saves while contributions, bindings, view panes and the whole dock load settle. A registration-only change on the same tab uses the live arrangement after gesture cancellation, preserving read-only local resizing; a tab switch or external restore uses the captured destination arrangement. The final save names the captured destination. Instance reads/factory contexts follow the explicit owner tab, including when controllers survive a later tab switch. `DockView.load` replaces specs for retained IDs as well as new IDs, withdraws old elements and visibility, then renders the complete replacement set; old controllers are disposed afterwards. Pending drag initiation, active drags, splitter/window resize previews and keyboard window movement all have a cancellation route, and a late drag release cannot replay a canceled session. Recovery remains local in read-only windows; only the save relay checks the lease.

**A place is a path.** New withdrawal records keep a root-to-leaf ancestor chain: split identity, axis, selected child, and sibling node/group identities and shares. Returning into a surviving group keeps its live location; otherwise the nearest surviving ancestor or sibling subtree reconstructs the missing branch. Inserting a returning child scales the survivors together, preserving their current relative shares and order instead of restoring historical sizes. Floating composites grow proportionally from their current rectangle, retaining user resizing/movement; unchanged minimum-size clamps can still recover the original rectangle. Path reads validate depth, fan-out, identities, continuity and shares. Legacy neighbour records remain readable and semantic Close/Remove replay retains its existing format.
