**Status:** P2-i through P2-v are built on `claude/profiles-p2`: session operations (§8), fragments and defaults (§9), per-view editing (§10), view panes (§11) U1–U5 (§12), and feature focus with U8/U9 (§13). ## 1. Where main stands

Phase 1 built the session as data and the resolver over it, but the window still shows one tab. Phase 4a built the renderer device and scene runtimes, with `heads.show(view)` ready for a tab switch, but nothing calls it with another view.

- **One tab.** `ProfileSessionState` (`app/profiles/profile-session-state.ts:31`) holds the session and shows its first tab only (`:43–44`). Every view opened in the window joins that tab (`:63`). It has no operations beyond `setLook`, `setSubject` and the instance lookup (`:81–121`).
- **The dock is still a preference.** Tab 1's arrangement is copied into `UIPreferences.layout` at start (`compose/studio-startup.ts:199–201`). The dock saves through `layout.set` (`studio-ui/app.ts:138–141`), and the session reads it back when the workspace is written (`compose/studio-startup.ts:294–297`).
- **One 3D view panel.** The shell contributes one `head` panel (`studio-ui/views/shell.ts:20`), and its controller is a singleton that hosts the device (`studio-ui/panels/viewports.ts:112–129`). The view graph requires the main view (`platform/core/view-graph.ts:119`, `:459`), refuses to close it (`:373`) and caps views at 16 (`:22`, `:356`).
- **One edited look.** The authoring core edits one document (`app/trusted-authoring-core.ts`), and `LookEditor` (`library/look-editor.ts:84`) shows the drawn scene's look (`compose/studio-startup.ts:279–281`, `:474–475`). The heads owner draws `MAIN_VIEW` (`:397`). `show(view)` of a view whose scene shows another look is refused (`preview/browser/browser-scene-heads.ts:274–277`, with `ANOTHER_LOOK` and `refusal(view)` from `preview/browser/scene-editors.ts:61`, `:121–125`).
- **Saved layouts and modules are still live.** The Layouts button (`studio-ui/app.ts:518`) drives `layoutController` (`studio-ui/layouts.ts`) over the preference library (`app/layout-library.ts`). The Modules button (`studio-ui/app.ts:485`), its menu (`:708`), the Panels menu's module switches (`:736`) and the palette's module commands (`:894`) drive `modules.set` (`app/ui-preferences.ts:61`). Phase 1's migration already copied every saved layout into an own default (`app/profiles/host/profiles-migrate.ts:320–327`), so the library is input only.

## 5. G4: the tab-switch gate on real data

Run by the coordinator at the end of P2-vi, with 043's environment: an isolated server per build (its own port, data folder and caches; never 4317 or 4331), `measure.ts` gaining tab rows, warm cache then a fresh Chrome profile. Memory as G3: server `--limit 5`, Chrome `--limit 5` (head only); the whole-body part needs Chrome 6.

| Row | Setup | Gate (S2's budget) |
|---|---|---|
| T-a | Two tabs whose views share one scene | Click to first presented frame ≤ 100 ms |
| T-b | Two tabs, two scenes of one V, the other warm and prepared | ≤ 100 ms; 0 links and 0 programs in the first shown frame |
| T-c | Two tabs, two Vs of different bodies, the other warm | ≤ 100 ms; 0 links |
| T-d | T-b with the two scenes showing different looks | ≤ 100 ms; no raster; 0 links |
| T-e | A third tab, cold (beyond the warm budget) | Progress in place within 150 ms, never a blank pane; no task ≥ 50 ms; the result shown once ready (no gate on duration) |
| T-f | Rapid switching: A, B, C, A within 300 ms | Only A shown; nothing superseded drawn; no late result |
| T-g | The switch's main-thread part (dock load, rebind, paint) | No task ≥ 50 ms from the click to 1 s after |
| T-h | Close a tab whose scene nothing else shows | Its runtime disposed; GL objects and memory back at the baseline |

## 7. Risks, ranked

1. **Switching looks costs a raster.** Without the kept resources (D3), a tab switch between two looks re-rasters the whole look: about 1 s at 2K for a complex layer, far over 100 ms. Keeping them costs memory per warm look (preview-size canvases per layer). P2-iii measures it in T2 and G4 measures it on real data (T-d). If the memory is too high, the warm look keeps its masks at a smaller tier and is brought up after the takeover.
2. **Fresh scenes multiply runtimes** (M2). Each tab on its own scene is a runtime. With one warm, the third tab is cold on every visit. G4's T-b and T-e measure it; the levers are the warm budget and the substitution default, not the model.
3. **The switch's main-thread work.** A dock load, rebinding every panel and its first paint could pass 50 ms in one task, or push the first frame past 100 ms. P2-iv probes it early on synthetic panels; G4 T-g measures it on the real Studio. Rebinding (D2) rather than rebuilding is the first mitigation; painting off-screen panels lazily is the second.
4. **One history over session and graph.** Coalesced camera and lighting steps, CORE-94's whole-result check and structural session steps share one scope. A step restoring views into a tab another step removed must be impossible by construction. The model-based T1 test in P2-i, with seeded random operations, is the guard.
5. **Removing the main view's special status** touches the graph's parser and history check, capture tools and the viewport attachment. The `head` alias (D6) limits the change; the parity test and the workspace fixtures catch drift.
6. **Workspace size.** Tabs, closed fragments (with value copies of lighting setups) and no `MAX_VIEWS` grow the session. The workspace budget already refuses with a reason; P2-i adds a size row to the multi-subject test.
7. **Phase 3 inheriting phase 2's shortcuts** (one controller per type, one document). New code addresses instances and looks by ID (D2, D3), so phase 3 replaces the controller map and the document, not the callers.

## 8. P2-i as built

On `claude/profiles-p2` (from `dac8d54d`). Source paths as in §1.

**`ProfileSessions`** (`app/profiles/profile-sessions.ts`) replaces `ProfileSessionState` as the one owner of a profile session's tabs, view graph and focus.

- **One history.** It opens the `view:<profile>` scope over a target that is the graph's plus its own: `@tabs` (order, closed fragments, shown tab), `@tab:<id>` (name, origin, other fields) and `@content:<id>` (arrangement and instances). The graph records through it (`ViewGraphOwner` in `platform/core/view-graph.ts`): the graph's own edits are steps as before, and the graph edits inside an operation are collected into that operation's one step. An Undo or Redo is checked whole before anything changes: the order names each tab once, every tab in it exists and no other does, and every view is in one of them. An operation run outside the history (restore-time) clears the steps rather than leave any that name what no longer exists (CORE-94's rule). A recorded operation makes `view:<profile>` the editing context (§3.7), so global Undo reaches it after a look edit; showing and arranging a tab are navigation and leave it.
- **Settled before anyone hears.** The graph's, focus's and the session's notifications are held (`ViewGraph.hold`, `FocusService.hold`) until an operation, or an Undo or Redo, has settled whole: tabs, views, fragments, the shown tab and the step. Then each listener hears, isolated from the others (`notifyAll`, `platform/core/listeners.ts`, also used by the history service), so one that throws can't leave the session half changed; the history service settles its target even when a listener throws. The session's own change is marked pending before its step is published, so a history listener that throws can't keep a committed operation from the session's listeners. The history service runs one move at a time per scope: an Undo, Redo or jump asked for while a move settles (a listener undoing again) waits and runs after it, so each move applies and publishes its own graph change whole.
- **The drawn view stays** until P2-iii makes it follow the shown tab. The window passes the session the view it draws (`drawn`); closing or resetting the tab that holds it, closing it, and an Undo or Redo that would remove it are refused with a plain reason. A history move its target refuses for now (`HistoryTarget.refusal`, read through `HistoryScope.blocked` from the values the move would show, without moving) changes nothing and keeps every step; the View and lighting Undo and Redo report the reason.
- **Operations:** `newTab(content)` (the content P2-ii instantiates, with IDs from `freshId`; views may name existing nodes, which is Share the scene of), `close`, `reopen`, `reset(tab, content)`, `rename`, `move`, `duplicate`, `show`, `addView` and `closeView`, plus the unrecorded `arrange` and `instance`. Each validates before it changes anything (the graph's own checks inside an operation run before its commit), so a refusal changes nothing, records nothing and notifies no one. A tab holding a view a newer build made can't be closed or reset, and a duplicate leaves such views out.
- **Closed-tab fragments** (`ClosedTab` in `profile-session.ts`, typed): the tab with its arrangement and instances, its place, its views and a value copy of every node they name, each with its place, scenes with what they showed, and the views' focus numbers (D13). Reading validates each one whole; one whose views or instances collide with the session's is dropped. A step holds what is outside Undo (a tab's arrangement and instances, what its scenes show, its views' focus numbers) as it was when recorded, so an Undo or Redo that brings in a tab or a fragment takes that state from what it takes away instead: the same content, known by its identity. Each tab holds one in memory (`@content`), carried in its `@content:<id>` history value and with it into a fragment, given anew to a new, duplicated or reset tab; it is never stored or read out, and a session gets fresh ones when it opens. So an empty tab, with no instance to recognise it by, keeps its arrangement too. Close, Undo, arrange, Redo, Reopen therefore brings the tab back as last arranged, and a look shown meanwhile keeps its generation. Reopen keeps what the session knows a scene shows; the fragment's copy counts only after a restart.
- **IDs** are fresh and random (`t-`, `v-`, `s-`, `c-`, `l-`, `d-`, `x-` or `<type>--`, then base 36), from the platform's cryptographic source. A tab's, view's or node's has 25 characters (over 128 bits) and an instance's 12 (over 60 bits, the most the stored format and the builds reading it allow), so none recurs in practice and no record of retired IDs is needed across a restart. Within a run the session also never gives out one it holds, keeps in a fragment or gave out before.
- **Scenes:** what each shows (`subject`, `look`, `gen`) stays outside the history, as before.

**The view graph** (`platform/core/view-graph.ts`) has no required main view and no `MAX_VIEWS`: a graph may hold no view, and the main view closes like any other. Views carry their `tab`. New IDs come from the owner. `restructure` removes and adds views and nodes as one commit, each in its place, and a structure step records the nodes' order, so Undo brings nodes back where they stood. `adoptViews` puts tab-less views (the default stand-in for a graph that couldn't be read) in the shown tab.

**Focus** (`platform/core/focus.ts`) holds the shown tab (D1) and restores views' focus numbers on reopen (`placeViews`).

**Actions.** `tabs.show`, `tabs.rename`, `tabs.move`, `tabs.close`, `tabs.reopen`, `tabs.duplicate` and `tabs.arrange` are the Layout tabs family in the action registry, each naming its tab. Duplicate is built at the data level, as the chunk's brief asked; the tab menu still leaves it out until phase 6 (§2.10).

**Wiring.** The window opens the session with the Studio's graph factory, and the core takes the session's graph (`createTrustedAuthoringCore`'s `views` port, which replaces `viewScope`). The workspace stores every tab, its fragments and the shown tab. The dock still saves through `layout.set` in memory, because the Layouts button reads it until P2-iv. `relayDockSaves` (`app/profiles/profile-window.ts`) passes each save on to the shown tab as `tabs.arrange`, so the tab, not the preference, is what is stored. Only a change of the preference's arrangement itself is a save, compared by value, and an arrangement the session makes for the shown tab (`tabs.arrange` from elsewhere, another tab shown) becomes the preference's, so the relay never passes a stale one on. Bringing P2-iv's direct save forward was not needed: the relay is correct with those two rules, and switching the dock now would break the Layouts button, which reads the preference until P2-iv removes it. With one tab, behaviour is unchanged.

## 9. P2-ii as built

On `claude/profiles-p2`, after P2-i. Source paths as in §1. No UI: everything here is data and actions that P2-iv's strip, tab menu, New tab ▸ and substitution step present.
